# Glossary

This page defines the terms used across the documentation, in alphabetical
order. [Concepts](../getting-started/concepts) explains the main terms in more
depth, and each entry below links to the page that covers its term.

- **Artifact**: a packaged authoring unit: a skill, agent, context, command, rule, hook, MCP server registration, or extension type. The term is distinct from a build artifact or an ML artifact. See [Artifact](../getting-started/concepts#artifact).
- **Bootstrap admin**: an identity listed in `PODIUM_BOOTSTRAP_ADMINS`. The registry grants each listed identity the tenant `admin` role on the `default` tenant at boot, so a new deployment has an admin before anyone runs `podium admin grant`. The grant is distinct from the instance-operator role. See [Bootstrap admin](../deployment/identity/tenants#bootstrap-admin).
- **Canonical artifact ID**: the directory path under the registry root, such as `finance/ap/pay-invoice`. All references use this ID, optionally suffixed with `@<semver>` or `@sha256:<hash>`.
- **Catalog**: the set of artifacts a registry holds. Podium is the registry, and the catalog is its content. A caller sees the part of the catalog its effective view includes.
- **Completion record**: the record a registry stores in its metadata store when a release-time rewrite of stored content hashes, such as the 0.5.0 rewrite, has finished. A start that finds the record skips the rewrite. A store that holds manifest rows and no completion record makes the registry either run the rewrite at start or refuse to start until `sign-stored-rows` runs it, depending on where the store lives. See [Upgrade notes](../deployment/operations/upgrade-notes).
- **Delivery record, delivery hash, and delivery signature**: the delivery record is the part of a `load_artifact` response that a consumer verifies: the artifact's identity, type, version, content hash, sensitivity, and ingest time, the served manifest documents, and each bundled resource's path and content hash. The delivery hash is the SHA-256 digest of that record, computed per response. The delivery signature is the signature the registry's managed key makes over the delivery hash, served as `delivery_signature`. The MCP server, server-source `podium sync`, and the SDKs recompute the hash and verify the signature before they write anything. See [Verifying deliveries](../consuming/verifying-deliveries).
- **Deployment mode**: one of the ways to run a registry: local (a directory read by the CLI), single node (one server binary), or clustered (registry replicas with Postgres and object storage). See [Deployment modes](../deployment/modes/).
- **Domain**: a node in the catalog hierarchy, defined by a directory. The term is distinct from a DNS domain or a DDD domain. See [Domains](../authoring/domains).
- **Effective view**: the composition of every layer visible to the caller's identity, in precedence order. It includes admin-defined layers, user-defined layers, and the workspace local overlay.
- **Effort hint**: advisory metadata (`effort_hint: low | medium | high | max`) that records the author's intent about reasoning budget.
- **Filesystem source**: a catalog directory on disk that the `podium` CLI reads directly, with no server. It is the catalog source of the local deployment mode. See [Local](../deployment/modes/local).
- **Freeze window**: a period, declared in the `freeze_windows:` list of `registry.yaml`, during which the registry rejects ingest with `ingest.frozen`. A `podium layer reingest --break-glass` run with a justification and two distinct approvers overrides an active window. See [Freeze windows](../deployment/modes/clustered#freeze-windows).
- **Harness**: the AI runtime hosting an agent, such as Claude Code, Claude Desktop, Claude Cowork, Cursor, Codex, Gemini CLI, OpenCode, Pi, or Hermes. The term is used interchangeably with "host" when the runtime context matters. [Configure your harness](../consuming/configure-your-harness#supported-harnesses) has the full roster with documentation links.
- **Harness adapter**: the component that translates a canonical artifact into the native file layout of one harness at materialization time.
- **Host**: the MCP-speaking system that runs the Podium MCP server alongside its own runtime.
- **Instance operator**: an identity that holds the instance-operator role, seeded at boot from `PODIUM_OPERATOR_ADMINS`. The role authorizes tenant management through the `/v1/admin/tenants` API and the `podium admin tenant` CLI on a multi-tenant registry. It confers no tenant `admin` rights, and a tenant `admin` grant confers no operator rights. See [Instance operator](../deployment/identity/tenants#instance-operator).
- **Layer**: a unit of composition with a single source and a visibility declaration. The source is a Git repository, a local filesystem path, or a custom source through `LayerSourceProvider`. A layer is admin-defined, user-defined, or the workspace local overlay. See [Layered composition](../deployment/content/layers).
- **Manifest**: the `ARTIFACT.md` file specifically. A skill also has a `SKILL.md` that carries the agentskills.io frontmatter and the agent-facing prose body. For a skill, "manifest" without qualification refers to `ARTIFACT.md`, and "skill manifest" refers to `SKILL.md`. A skill's `ARTIFACT.md` is optional. A skill without one has no manifest on disk, and its stored manifest is empty.
- **Marketplace**: a Git repository a harness imports to install plugins. It holds a vendor manifest at a fixed location and per-plugin content. The extension, package, and tap formats are the analogous repository distributions for Gemini, Pi, and Hermes.
- **Marketplace output**: a `podium sync` target of `kind: marketplace`, made of a Git repository, a harness set, a plugin list, and a workflow. See [Publishing marketplace repositories](../deployment/content/publishing).
- **Materialization**: the atomic write of a loaded artifact's content onto the host's filesystem. The content is the manifest and the bundled resources, after harness adapter translation.
- **MCP server (Podium MCP server)**: the in-process bridge binary the host runs.
- **Model class hint**: advisory metadata (`model_class_hint: nano | small | medium | large | frontier`) that records the author's intent about model capability tier.
- **Package**: the on-disk directory containing an artifact's manifest files (an `ARTIFACT.md`, a `SKILL.md`, or both) and its bundled resources.
- **Plugin (publishing)**: a named bundle of selected artifacts, defined by a scope filter and rendered into each harness's distribution layout. The term "plugin" for an in-process SPI extension keeps its separate meaning, and this entry names the publishing sense.
- **`podium serve` and `podium-server`**: the commands that start a registry server. Both run the same server code. `podium serve` is a subcommand of the `podium` CLI that accepts flags such as `--standalone`, `--config`, and `--layer-path`, each of which sets the matching `PODIUM_*` variable for the process. `podium-server` is a separate binary, configured through environment variables and `registry.yaml` alone, and it is the only binary in the container image. See [`podium serve`](cli#podium-serve).
- **Profile**: a named scope stored in `sync.yaml`. Its include globs, exclude globs, and artifact types select the subset of the catalog that `podium sync` writes to a target. See [Selective materialization](../consuming/selective-materialization).
- **Progressive discovery**: the consumer path in which an agent finds artifacts at runtime through the meta-tools and loads only the ones it selects. It requires a server source. See [Browsing the catalog](../consuming/browsing-the-catalog).
- **Public mode**: a registry setting, enabled with `--public-mode` or `PODIUM_PUBLIC_MODE`, that skips authentication and visibility so every caller sees every layer. It cannot be combined with an identity provider or with multi-tenant mode, it rejects ingest of `sensitivity: medium` and `sensitivity: high` artifacts, and the audit log records each caller as `system:public`. See [Public mode](../deployment/modes/single-node#public-mode).
- **Registry**: the service that ingests artifacts from layer sources and serves the catalog. Podium is a registry. In the local deployment mode a folder on disk backs it, and in the single-node and clustered modes a Podium server runs it.
- **Rule mode**: the `rule_mode` field on a `rule` artifact (`always`, `glob`, `auto`, or `explicit`). It controls when the harness loads the rule. See [Rule modes](../authoring/rule-modes).
- **Server source**: a Podium registry server that consumers reach over HTTP. It is the catalog source of the single-node and clustered deployment modes, and the MCP server and the SDKs require one.
- **Session ID**: an optional UUID the host generates per agent session. The registry uses it for `latest`-resolution consistency and learn-from-usage reranking.
- **SPI (service provider interface)**: a Go interface that a plugin implements to replace or extend one part of the registry's behavior, such as a layer source, an identity provider, or a harness adapter. See [Extending](../deployment/services/extending).
- **Standalone**: the registry server configuration with embedded SQLite, `sqlite-vec`, and filesystem object storage, bound to `127.0.0.1:8080` with no identity provider by default. `podium serve --standalone` selects it, and `podium serve` with no configuration enters it automatically. The single-node deployment mode runs it. See [Single node](../deployment/modes/single-node).
- **Standard stack**: the registry server configuration with Postgres, S3-compatible object storage, and an OIDC identity provider, run as registry replicas behind a load balancer. The clustered deployment mode runs it, and `podium admin migrate-to-standard` moves a standalone deployment's state into it. Standalone and the standard stack are configurations of the same binary. See [Clustered](../deployment/modes/clustered).
- **Tenant**: an organization (org) that a registry server serves, with its own layer list, admins, audit stream, and quotas. A single-tenant registry serves only the `default` tenant. A multi-tenant registry, started with `PODIUM_MULTI_TENANT=true`, resolves each request to the tenant its caller's organization names. See [Tenants and admins](../deployment/identity/tenants).
- **Tenant admin**: an identity that holds the per-tenant `admin` role. A tenant admin registers, removes, and reorders admin-defined layers, triggers reingests across the tenant's layers and catalog re-embeds, and can view any layer for diagnosis, which the audit log records. `podium admin grant` and `podium admin revoke` manage the role. See [Tenant admin](../deployment/identity/tenants#tenant-admin).
- **Up-front sync**: the consumer path in which `podium sync` writes the effective view, or the subset a profile selects, to disk before a session starts, and the harness discovers the files natively. It works against a filesystem source or a server source. See [Configure your harness](../consuming/configure-your-harness).
- **Verification key set**: the Ed25519 public keys under which a verifier accepts a registry-managed signature: the signing key's public key and every key on a `verify:` line of the key file. A consumer takes the set from `PODIUM_SIGNATURE_VERIFY_KEY`, a comma-separated list, or otherwise from the `public:` and `verify:` lines of the key file at `PODIUM_SIGN_KEY_PATH`. An SDK client can also be given the list directly. During a key rotation the set holds both the new and the retired key. See [Signing keys](../deployment/operations/signing-keys) and [Verifying deliveries](../consuming/verifying-deliveries).
- **Visibility**: the per-layer access declaration in the registry config: `public`, `organization`, OIDC `groups`, or explicit `users`. A user-defined layer is the exception. Its visibility is the implicit `users: [<registrant>]`, set from the authenticated identity at registration, and it cannot be widened. See [Access control](../deployment/content/access-control).
- **Workspace local overlay**: the workspace-scoped layer that the `LocalOverlayProvider` reads from `${PODIUM_OVERLAY_PATH}`, or from `<workspace>/.podium/overlay/` when that directory exists. The consumer merges it client-side: the MCP server, `podium sync`, and the SDKs each apply it. It has the highest precedence in the caller's effective view.

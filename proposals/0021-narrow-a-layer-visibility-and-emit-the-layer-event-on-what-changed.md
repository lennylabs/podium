# Proposal 0021: Narrow a layer's visibility on update, and emit the layer event on what changed

- Issue: (to be filed)
- Status: Implemented (2026-09-05). Signed off by the maintainer for implementation, whole, with every step in the checklist in scope. Converged after 17 adversarial review rounds (44 findings fixed). OQ-1 is resolved in favor of the staged position: `owner` stays on its value reading and is not clearable, because on an admin-defined layer it names no authorized subject, so clearing it withdraws nothing and symmetry alone does not justify a capability with no effect. OQ-2 is resolved in favor of the staged narrow wake, whose staleness risk is answered by construction: the test tables every field of `store.LayerConfig`, so a field added later fails the table until it is classified. OQ-3 is resolved in favor of an explicit `--clear-groups` and `--clear-users` pair. `--group=""` appends an empty string under the current `stringSliceFlag` and reads as a value rather than a withdrawal, and a sentinel value hides the operation inside a magic string; a named flag is unambiguous, self-describing in `--help`, and is the form an operator reaches for. DOC-2's synopsis takes the pair. OQ-4 is resolved in favor of including `reorder`: SPEC-3's sentence binds it, so leaving it unfixed would land a spec rule the registry contradicts at the one call site §8.1's row names literally. OQ-5 is resolved in favor of staging SPEC-5c, because without it §4.6's bypass list is incomplete for the deployment §13.1.1 uses, and an incomplete list in the spec is a defect a later reader inherits. OQ-6 is resolved in favor of adding the `none` cell to the §4.6 axis with its `// Matrix:` annotated test, landing together in S2 or later since `matrix audit` exits non-zero on an uncovered cell. This proposal makes the no-axis state reachable through `update` for the first time, so the matrix that enumerates visibility unions carries it and the rule cannot lose its test.

## Summary

**What changes.**

- §7.3.1 gains a paragraph fixing the patch semantics of `POST|PUT /v1/layers/update` on the visibility members: a member the body carries is applied and a member it omits keeps its stored value, so `"public": false` withdraws the axis and `"groups": []` empties the list. Today the handler grants on every axis and withdraws on none, so an admin-defined layer's visibility is widened and never narrowed while the endpoint answers `200` with a record reporting the visibility the patch tried to replace.
- §8.1's `layer.config_changed` and `layer.user_registered` rows are both replaced, because §7.3.1 binds a patch, a restore, and an erase to each of them by class, and §7.3.1 gains a paragraph tying the layer event to what the write changed. Today `update` emits unconditionally, so a patch that stored nothing writes an audit record reporting a change that did not occur and, on an admin-defined layer, publishes a §7.5.4 wake that re-resolves and re-materializes every `podium sync --watch` in the tenant.
- §4.6 states in one place what a stored record setting no visibility field means to the visibility evaluator, which a full withdrawal through the update endpoint reaches and which registration already reaches whenever the deployment default resolves to neither `public` nor `organization`. Its visibility-table intro is corrected so it admits a layer declaring no field, and it gains a bypass paragraph for a registry started with no request-time identity verifier, so the arms on which the evaluator admits a caller without reading the record are listed together. `pkg/layer/composer_test.go` gains the case pinning the evaluator half, which has no test today.
- The §7.5.4 wake narrows to a change that can alter what a profile resolves. A webhook-secret rotation, a `force_push_policy` change, and a `git_provider` change record their §8.1 audit event and wake no watcher.
- `reorder` takes the same rule, keyed on the tenant's precedence sequence rather than on the stored `Order` integers, which the handler renumbers to `(i + 1) * 10` on every call. It guards only on `len(req.Order) > 0` today, so a reorder naming layers in the order they already hold emits and wakes every watcher.
- `cmd/podium/layer.go`'s `layerUpdate` builds its body from the flags the operator set rather than from the flags carrying a non-zero value, reusing the `setFlags` helper the §7.3.3 tenant PATCH already uses, so `--public=false` becomes expressible.
- `web/ui/src/surfaces/UpdateLayerForm.tsx` gains withdrawal controls on the axes it renders as fixed state, and the copy telling the reader a grant is permanent is replaced. `web/bundle` is rebuilt in that same commit.
- The comments citing §7.6 for the watch-mode contract are corrected to §7.5.4.
- `docs/reference/http-api.md`, `docs/reference/cli.md`, `docs/deployment/layers.md`, `web/design/README.md`, `web/DESIGN.md`, `test/manual-validation.md`, and `CHANGELOG.md` follow.

**Fixed decisions.**

- **The mechanism is a presence-aware decode confined to `update`, following the pattern this repository already runs for the §7.3.3 tenant PATCH.** `handleTenantUpdate` decodes into `map[string]json.RawMessage`, `tenantQuotaIn` carries `*int64` and `*int` sub-fields, and its `applyTo` "overlays the present sub-fields, preserving every omitted" (`pkg/registry/server/tenants.go:58-85`). The update path is where that preservation carries weight: `handleTenantUpdate` decodes the presence map at `:195` and overlays it onto the stored record at `:207`. The CLI half is `setFlags`, which walks `fs.Visit` and is documented as serving "the §7.3.3 partial PATCH" (`cmd/podium/admin_tenant.go:54-58`). The same problem has the same solution here, and the solution is already reviewed, shipped, and spec-backed.
- **`LayerRegisterRequest` is untouched, so the register path is untouched.** The presence map is read inside `update` alone. `register`, `adminOnlyRegistrationFields`, §7.3.1's register-path value-assertion sentence that proposal 0017 landed, and the wire format the CLI and the web UI send are all unchanged. This is what rules out pointer members on the shared struct, which would put the register path into the same edit.
- **The wire format does not change, so §7.2.1 is not touched.** A nested `visibility` object was considered and rejected: it would name a value one way in the request and another in the response, which §7.2.1 forbids in the sentence proposal 0019 landed, and it would move the CLI, both web forms, and every test that builds a body.
- **Presence decides application; a difference from the stored value decides assertion and emission.** These are two predicates over one body and they are not the same. Presence answers "did the client ask for this member to be set", which is what makes `false` and `[]` reachable. Difference-from-stored answers "would this write change the record", which is what §7.3.1's immutable-visibility refusal and §8.1's event both key on. Collapsing them into presence alone would break proposal 0020's guarantee that a client reading a layer object and returning it unchanged is admitted, because the layer object carries all four members on every layer and `store.LayerConfig` marshals `groups` and `users` without `omitempty`, so a user-defined layer reads back as `"public": false, "organization": false, "groups": null, "users": ["alice"]` and every member is present in the echo.
- **JSON `null` on a visibility member is that member's empty value.** `"groups": null` withdraws on the same terms as `"groups": []`, because the read side emits `null` for an empty list and the echo above depends on it.
- **The meaning of a stored record that sets no visibility field is stated once, in §4.6, and referenced everywhere else.** `layer.VisibleWith` has one arm that admits a caller without reading the record, `Identity.IsPublic` (`pkg/layer/composer.go:65-66`), and public mode and a registry the boot path wires no identity resolver onto both set that one field on the composed-view caller (`pkg/registry/server/server.go:1386-1388`, `:281-286`, reached because `bootstrapOptions` adds no `WithIdentityResolver`, `internal/serverboot/serverboot.go:2380-2394`). SPEC-5c adds the second of those to §4.6's bypass list beside the two already there, so the overrides are listed in one place. SPEC-1, SPEC-2, and the edge-case table state the outcome and defer, and none of them enumerates a deployment or a route by which the record is reached.
- **Emptying a user-defined layer's `users` becomes a refusal.** It differs from the stored `[<owner>]`, so it asserts under the reading above and proposal 0020's rule refuses it. This is the one shipped case that flips, and 0020's own sentence already covers it once the member is applicable.
- **`owner` keeps its value reading.** A non-empty value replaces and an empty one leaves the stored value. On an admin-defined layer it names no authorized subject, so clearing it withdraws nothing; on a user-defined layer 0020 already refuses a differing value.
- **A patch that stores nothing writes no record and emits no event.** The handler compares the merged configuration against the one it read and returns `200` with the unchanged layer object, calling neither `PutLayerConfig` nor `emitLayerEvent`. The response is unchanged, so no client branches differently.
- **The comparator treats a nil slice and an empty one as equal.** `reflect.DeepEqual` separates them, so a layer stored with `nil` groups and patched with `[]` would report a change that did not occur, which is exactly the echo case. The comparison uses `slices.Equal` on `Groups` and `Users` and `==` on the rest.
- **The audit event's type keeps its class-derived resolution on the per-layer operations, and `reorder` keeps its single tenant-level event.** §8.1 distinguishes `layer.user_registered` from `layer.config_changed` by class on `register`, `unregister`, `update`, `restore`, and `erase`, and the retention path reads that split. `reorder` writes one `layer.config_changed` on the comma-joined identifier list and resolves no class, which stays as it is; the spec text and the §8.1 cell are written to match it. What is wrong is the two rows' wording, neither of which names a patch, and the unconditional emission.
- No §6.10 code is added and no matrix cell changes. Podium is pre-1.0; no flag, environment variable, or `registry.yaml` key restores the grant-only application or the unconditional emission.

**Watch out for.**

- **Two wrong implementations, one of which the suite catches and one of which it does not.** Making the *value* clear (treating `len(patch.Users) == 0` as "clear") breaks `TestLayerUpdate_PartialPatch` (`pkg/registry/server/layer_update_test.go:20`), which asserts a stored `Users` survives a patch carrying no `users`. Making *presence* assert breaks nothing in the suite and silently converts proposal 0020's verbatim-echo guarantee into a refusal on every user-defined layer.

The first three keep their `nil` expectation, and `empty users` at `:51` moves to asserting `["users"]` against a stored `["alice"]`. `empty owner` at `:52` stays on the same terms as the first three, and the helper's signature changes.

Clearing a repeatable slice flag has no in-repo precedent and is OQ-3.
- **The web UI is built around the defect and its copy states it as fact.** `UpdateLayerForm.tsx:52-63` explains that granted members and axes are displayed rather than edited "because the endpoint grants on each axis and withdraws on none: a field holding them would accept a deletion the registry discards while still answering success". `GrantedAxes` renders "An axis already granted stays granted. All go false in the same commit as the server change, and the shipped vitest cases TEST-5 names assert that rendering and that copy.
- **The shipped bundle stays functionally correct under a server-only commit.** `UpdateLayerForm.tsx:100-113` sends all four members on every admin-defined patch, seeded from the stored record and merged through `merge(grantedGroups, …)`, so it re-asserts what the layer holds rather than narrowing it. That is what admits splitting the server and client steps, and it is the difference from proposal 0019, whose spanning test forced one commit.

## Current state and the gap

### The update handler grants and never withdraws

`LayerEndpoint.update` decodes into `LayerRegisterRequest`, authorizes the write, evaluates the git-provider rule, the local-source gate, and proposal 0020's immutable-visibility refusal, applies the source fields, performs a requested rotation, and reaches the application block (`pkg/registry/server/layers.go:875-889`):

```go
	if patch.Owner != "" {
		cfg.Owner = patch.Owner
	}
	if patch.Public {
		cfg.Public = true
	}
	if patch.Organization {
		cfg.Organization = true
	}
	if len(patch.Groups) > 0 {
		cfg.Groups = patch.Groups
	}
	if len(patch.Users) > 0 {
		cfg.Users = patch.Users
	}
```

Every arm sets and none clears. `cfg.Public` is assigned the literal `true` rather than `patch.Public`, so `{"public": false}` cannot reach the field even by accident.

The handler's own doc comment states the intent: "Body fields that are non-zero replace the corresponding LayerConfig field; zero fields keep the prior value. This shape avoids having to send the whole config and accidentally clear visibility filters." The stated hazard exists and the guard over-fires: it prevents an accidental clear by preventing every clear.

The defect has already deformed the client tier and is documented there as behaviour. `UpdateLayerForm.tsx` withholds a checkbox for a granted axis and displays granted members as static tokens, and its comment names the endpoint as the reason. A checkbox was offered once and removed, because it "was operable in appearance and inert in fact". `.claude/rules/code-best-practices.md` requires a security-relevant path to fail closed; a visibility narrowing the API cannot express, and a client built to withhold rather than send it, fails open.

The recourse is unregistering and re-registering, which resets `created_at`, recomputes `order` at the tail, clears the ingest history, and mints a new inbound webhook secret that must be installed at the Git host. Proposal 0020 accepts that cost for an exceptional act on one user's personal layer. Charging it for a routine revocation on a shared layer is a different trade.

### The presence problem, and the pattern that already solves it

`LayerRegisterRequest` declares `Public bool`, `Organization bool`, `Groups []string`, and `Users []string`, and it is the decode target for both `register` and `update`. §7.3.1 fixes for the register path that "A field is asserted by its value rather than by its presence", which proposal 0017 landed and 0020 extended to the update path.

The repository solves this exact problem once already, on the §7.3.3 tenant PATCH, where §4.7.8 gives a zero quota a meaning. `handleTenantUpdate` decodes into `map[string]json.RawMessage` and unmarshals each present key individually; `tenantQuotaIn` carries `*int64` and `*int` sub-fields; and its `applyTo` "overlays the present sub-fields, preserving every omitted" (`pkg/registry/server/tenants.go:58-85`), which the update path calls on the record it just read (`:195` for the presence-map decode, `:207` for the overlay). The CLI half is `setFlags` (`cmd/podium/admin_tenant.go:54-58`), which walks `fs.Visit` to record the flags the operator passed. That pattern is reviewed, shipped, spec-backed, and confined to one endpoint. This proposal applies it to `update`.

### The event fires on a patch that changed nothing

`update` calls `e.emitLayerEvent(r, cfg, "update")` unconditionally. `emitLayerEvent` resolves the type from the layer's class and, on the `config_changed` arm, calls `publishConfigChanged`, which reaches `(*Server).PublishEvent` and fans out to the §7.3.2 outbound receivers and onto the NDJSON `/v1/events` stream. `pkg/sync/watch_server.go:83` subscribes that stream on three types including `layer.config_changed` and signals a full re-resolve on every non-heartbeat line.

A rotation on an admin-defined layer, which changes one credential and nothing a profile resolves, re-materializes every watched working tree in the tenant. A `force_push_policy` change, a `git_provider` change, and a patch whose every field restates what the layer stores have the same effect.

§8.1's row reads "Admin added, removed, or reordered admin-defined layers". It names three operations and the code emits on four, so an update's event has no spec basis under the current wording in either direction. `reorder` has the same defect at its own call site, guarded only on `len(req.Order) > 0`, so a reorder naming layers in the order they already hold emits and wakes.

### A stored record that sets no visibility field

`store.LayerConfig` carries `Public`, `Organization`, `Groups`, and `Users` (`pkg/store/store.go:283-287`), and a record setting none of them is a state the registry already stores. `core.VisibilityOf` is the one projection from that record to the §4.6 evaluator (`pkg/registry/core/core.go:427-434`), read by the composition path (`:438-440`) and by the layer list (`pkg/registry/server/layers.go:265`). `layer.VisibleWith` reads the four members and no role (`pkg/layer/composer.go:64-99`): it returns true immediately on `id.IsPublic` (`:65-66`), and on a record setting no field every other arm falls through to `return false` (`:98`).

Only an admin-defined layer holds the record. `register` stores `users: [<owner>]` on the user-defined arm and refuses a registration whose owner does not resolve (`pkg/registry/server/layers.go:1035-1057`), and SPEC-2 refuses a patch emptying that list. The register path stores the record whenever the deployment default resolves to neither `public` nor `organization`, which covers `private`, an unrecognized value, and `users` against a caller the registry does not authenticate (`pkg/registry/server/layers.go:1099-1121`). The boot path stores it on the same default for declared layers and for `--layer-path` layers (`internal/serverboot/serverboot.go:549-578`, `:686-688`, `:898`). SPEC-1 adds the update endpoint as a further route.

## Spec amendment: §7.3.1 patch semantics on the update body

**SPEC-1.** Anchor: `spec/07-external-integration.md`, §7.3.1. One paragraph lands after the paragraph beginning `**Layer read visibility.**` and before the paragraph beginning `**Local-source authorization.**`.

> **Patch semantics on the update body.** `POST|PUT /v1/layers/update` applies a partial patch. On the visibility members `public`, `organization`, `groups`, and `users`, a member the body carries is applied and a member it omits keeps the layer's stored value, so `"public": false` withdraws the public axis, `"organization": false` withdraws the organization axis, and `"groups": []` and `"users": []` empty those lists. A member carrying JSON `null` is the empty value for that member and withdraws on the same terms, because the layer object reports an empty list as `null` and a client returning a layer object it read carries that value. This is what makes a visibility grant reversible: a grant applied through this endpoint or through a registration is withdrawn through this endpoint, without unregistering the layer and losing its order, its registration time, its ingest history, and its inbound webhook secret. Withdrawing every member leaves the layer's stored record setting no visibility field, and §4.6 states what that record means to the visibility evaluator and where a bypass overrides it. On the remaining members the patch semantics are unchanged: a non-empty `ref`, `root`, `local_path`, `owner`, `git_provider`, or `force_push_policy` replaces the stored value and an empty one leaves it, and `id` and `source_type` are immutable. A layer declared in the registry configuration is re-seeded from that declaration at each start, visibility included, so a withdrawal applied to a declared layer over this endpoint reverts at the registry's next start; the declaration is the place to withdraw it durably.

**SPEC-2.** Anchor: the paragraph beginning `**Immutable visibility on a user-defined layer.**`. ## Proposed solution

### CODE-1: the presence decode, confined to `update`

`update` reads the body once into a byte slice and unmarshals it twice: into `LayerRegisterRequest` for every member whose semantics are unchanged, and into `map[string]json.RawMessage` for the presence of the four visibility members. `LayerRegisterRequest` is untouched, so `register` and its rule are untouched.

```go
// visibilityPatch is the §7.3.1 visibility half of an update body, resolved
// against the members the body actually carried. LayerRegisterRequest decodes
// into plain bool and []string members, so an absent key and a zero value are
// one thing after decode, and the update path needs them apart: a present
// member is applied, so "public": false withdraws the axis and an absent
// "public" keeps the stored one. The register path needs no such distinction
// and keeps the flat struct, which is why the presence map is read here.
//
// This mirrors the §7.3.3 tenant PATCH, where tenantQuotaIn carries pointer
// sub-fields and applyTo overlays the present ones.
//
// A member carrying JSON null resolves to the member's zero value, which
// §7.3.1 fixes: the layer object reports an empty list as null, so a client
// returning a layer object it read carries that value on every layer.
//
// Spec: §7.3.1, §4.6
type visibilityPatch struct {
	public       *bool
	organization *bool
	groups       *[]string
	users        *[]string
}

// applyTo overlays the members the body carried onto cfg and leaves the rest.
// A carried list that decodes empty is stored as nil rather than as an empty
// slice: json.Unmarshal of [] yields a non-nil empty slice, store.LayerConfig
// marshals Groups and Users without omitempty, and §7.3.1 fixes the read side
// as reporting an empty list as null. Storing nil is what keeps the emptied
// list and the never-populated list one stored value, so the layer object a
// client echoes back is the value the endpoint just stored.
func (p visibilityPatch) applyTo(cfg store.LayerConfig) store.LayerConfig
```

The normalization is the reason `pkg/registry/server/layer_visibility_test.go`'s `empty groups` subtest keeps passing. That subtest seeds a layer whose `Groups` is nil (`:77-80`), merges `{"groups": []}` with `{"ref": "release"}` so the write happens, and compares the stored `Groups` before and after with `reflect.DeepEqual` (`:443-445`), which separates nil from an empty slice. Storing the decoded empty slice would fail that comparison on a case this proposal admits unchanged.

`assertedImmutableVisibilityFields` is re-expressed over the merged value rather than the raw patch, which is what preserves 0020's guarantee under presence:

```go
// assertedImmutableVisibilityFields reports the §4.6 fields the patch would
// change on a stored user-defined layer, in sorted order, and nothing against
// an admin-defined one. A field asserts when the value the patch would store
// differs from the stored one, which is the reading §7.3.1 fixes and the same
// predicate the §8.1 emission reads. Presence alone would refuse a client that
// reads a layer object and returns it unchanged, because that object carries
// all four members on every layer and a user-defined layer reads back as
// public:false, organization:false, groups:null, users:[<owner>].
//
// Emptying users asserts where every other zero value does not, because the
// class stores users:[<owner>] and every other axis at its zero value: on the
// three zero-valued axes a difference from the stored value is exactly a
// non-zero value, and on users it is any list that is not the stored one.
//
// Spec: §4.6, §7.3.1
func assertedImmutableVisibilityFields(patch LayerRegisterRequest, vis visibilityPatch, cfg store.LayerConfig) []string
```

The refusal's position above the rotation, its message, and its `details.constraint` are unchanged.

### CODE-3: the write and the event follow what changed

Between the application block and `PutLayerConfig`:

```go

	// no §8.1 event, so a body restating what the layer holds is answered 200
	// with the unchanged layer object and leaves the audit stream reporting
```

`before` is the value `GetLayerConfig` returned, captured before any member is applied.

```go
// layerConfigEqual reports whether two stored layer records are equal for the
// purpose of §7.3.1's unchanged-write rule. It uses slices.Equal on Groups and
// Users rather than reflect.DeepEqual, which separates a nil slice from an
// empty one: a layer stored with nil groups and patched with [] would then
// report a change that did not occur, and that is exactly the echo case.
func layerConfigEqual(a, b store.LayerConfig) bool

// wakesWatchers reports whether the difference between two stored layer
// configurations can alter what a §7.5.4 watcher's re-resolve produces. The
// visibility members decide which layers a caller resolves, the order decides
// precedence among them, and the source location decides what the layer
// serves. A webhook secret, a force-push policy, and a git provider decide how
// the registry ingests, which no materialized tree observes.
//
// Spec: §7.3.1, §7.5.4
func wakesWatchers(before, after store.LayerConfig) bool
```

`emitLayerEvent` gains the wake predicate, calling `publishConfigChanged` on the conjunction of the existing class test and this one. The register, unregister, restore, and erase call sites pass a zero `before`, which every predicate reads as a change, so their behaviour is unchanged.

`reorder` takes the same rule, stated over the tenant's precedence sequence rather than over the stored `Order` integers. The handler renumbers every layer it names to `(i + 1) * 10` (`pkg/registry/server/layers.go:1332-1334`), while `bootstrapDeclaredLayers` seeds declared layers with `1..N` (`internal/serverboot/serverboot.go:593`, `:605`) and `register` assigns the tail plus ten (`layers.go:1126-1128`), so a comparison over the `Order` integers reports a change on a registry whose orders are not already `(i + 1) * 10`, which is the outcome this fix removes.

**IMPLEMENTOR'S CHOICE:** how the two sequences are read and compared — the comparison is over the tenant's layer identifiers in ascending `Order` with ties broken by identifier, read before the write and, after it, from the records the handler already re-lists; a reorder naming a proper subset renumbers only the layers it names and is judged on the sequence that renumbering produces; an empty order needs no arm of its own, because it writes nothing and leaves the sequence identical.

`reorder` keeps its single `layer.config_changed` on the comma-joined target and resolves no type from any layer's class, which is what SPEC-3's reorder sentence and SPEC-4's amended cell state. That matters because `authorizeLayerWrite` admits a user-defined layer's stored owner (`layers.go:1327`, §7.3.1's layer write authorization rule), so a reorder can name a layer of that class.

The comments at `pkg/registry/server/layers.go:80` and `:420-431` cite §7.6 for the watch-mode contract. §7.6 is Language SDKs; watch mode is §7.5.4. They are corrected in this edit, along with the same miscitation in the test files that carry it.

## Open questions

**OQ-1. Does `owner` become clearable on an admin-defined layer?** The staged position leaves it on its value reading, so `{"owner": ""}` is a no-op on both classes. The argument for clearing is symmetry with the visibility members beside it. The argument against is that on an admin-defined layer the field names no authorized subject, so clearing withdraws nothing.

**OQ-2. Does the §7.5.4 wake follow any stored change, or a composition-affecting one?** The staged position is the narrow one. The argument for the broad one is that it needs no predicate and cannot go stale as the record gains fields: a field added later would silently fall outside `wakesWatchers`. The narrow position accepts that risk and pays for it with a test that tables every field of `store.LayerConfig`, so a new field fails the table until it is classified.

**OQ-3. How does the CLI clear a repeatable slice flag?** `--group=""` appends an empty string under the current `stringSliceFlag`, and there is no in-repo precedent. The candidates are a `--clear-groups` and `--clear-users` pair, a sentinel value, and treating the flag given once with an empty value as a clear. The choice fixes the CLI reference's synopsis. S60 leaves the route its withdrawal takes to the implementor, so that scenario runs whichever candidate is chosen and does not wait on this question.

**OQ-4. Should `reorder` land here or separately?** The staged position includes it, because SPEC-3's sentence binds it and leaving it unfixed would land a spec rule the registry contradicts at a call site the §8.1 row names literally. It adds the precedence-sequence comparison at that call site and the reorder arms of TEST-3.

**OQ-5. Does §4.6 gain the no-identity bypass paragraph?** The staged position is SPEC-5c. §4.6's bypass list then covers every arm on which the evaluator admits a caller without reading the record, and SPEC-5's deferral to "the bypass paragraphs below" is true. The cost is one paragraph of §4.6 outside this proposal's original scope, which a later §13.2.2 posture change would touch again. The alternative is to add no paragraph and close SPEC-5 with a sentence naming the anonymous-public resolution on the terms §13.10 states, dropping SPEC-5c from S1 and from the edge-case row; that leaves §4.6's list incomplete for the deployment §13.1.1 uses and for one naming an identity-provider label the registry resolves to no configured provider.

## Non-goals

- **The register path's value reading.** §7.3.1's admin-only registration fields rule and `adminOnlyRegistrationFields` keep the reading proposal 0017 landed, and `LayerRegisterRequest` keeps its flat members.
- **A nested `visibility` object.** It would name a value one way in the request and another in the response, which §7.2.1 forbids, and it would move the CLI, both web forms, and every test that builds a body.
- **Pointer members on `LayerRegisterRequest`.** They would put the register path into the same edit.
- **Making `owner` clearable.** OQ-1.
- **Changing the event type resolution.** The class-derived split is what §8.1 distinguishes and what the retention path reads.
- **Recording refused layer writes.** No layer write refusal is audited today under any rule.
- **Waking a personal layer's owner's watcher, or a declared-layer change at boot.** Both are cases where the trigger set is too narrow and a watcher serves a stale profile until an unrelated event fires. Closing the first needs a per-caller filtered subscription so one user's layer is not named to every subscriber; the second needs the declared-layer path to route through an emission path it currently bypasses.
- **A compatibility shim, dual code path, or configuration key restoring either behaviour.**

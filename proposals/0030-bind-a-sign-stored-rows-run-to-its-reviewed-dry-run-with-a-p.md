# Proposal 0030: Bind a sign-stored-rows run to its reviewed dry run with a plan digest, and drop the chart's reviewed-dry-run gate

- Issue: (to be filed)
- Status: Verified (2026-09-26). Converged after 8 adversarial review rounds (13 findings fixed); awaiting sign-off.
- Date: 2026-09-26

This document stages the proposed spec, code, test, and documentation changes. It does not modify any spec, code, or doc file. Apply the changes in the staged sections after sign-off.

## Summary

**What changes.**

- §13.4 defines a **plan digest** that `sign-stored-rows --dry-run` reports, and a `--plan-digest` flag that binds a run to the plan the operator reviewed. A run whose own plan has a different digest writes nothing and exits with a status of its own. Outside `--dry-run`, `--include-unsigned` requires `--plan-digest`, so the §13.4 attestation covers the rows the reviewed dry run listed (SPEC-1).
- `internal/serverboot` computes the digest over a domain-tagged, §4.7.6-framed stream built from the plan header and every row the run writes, signs, or refuses, in a canonical row order. The dry run prints its rows in that order, with the stored content hash, a plan header line, and a final digest line. `pkg/version` exports the framing writer the digest reuses (CODE-1, CODE-2).
- `serverboot.RunSignStoredRows` parses `--plan-digest`, applies the new usage rules, and maps a changed plan to exit status 3 in both `podium-server sign-stored-rows` and `podium admin sign-stored-rows` (CODE-3).
- The Helm chart drops `migration.reviewedDryRun`, the reviewed-dry-run gate, and the Job's reviewed-dry-run annotation. A new value, `migration.planDigest`, is passed to the run Job as `--plan-digest`, and the migrated-store gate's refusal and the NOTES name the dry-run-then-digest procedure. The serving preflight, its pod-config digest, and the Secret lookup it reads are unchanged (CHART-1).
- The upgrade procedure, the CLI reference, the operator guide, the progressive-adoption page, the runbook, `CHANGELOG.md`, the unit, end-to-end, chart, and kind tests, and manual scenarios S66 and S76 follow (DOC-1, TEST-1 through TEST-4).

**Fixed decisions.**

- The binding lives in the binary. No plan file is persisted, and the operator carries the digest from the dry-run log to the run (Decisions).
- The digest is `sha256:` followed by 64 lowercase hex digits, over §4.7.6 length framing, led by the framed domain tag `podium/sign-stored-rows-plan/1` (CODE-2).
- The digest covers a header of the completion-record mode, the `--include-unsigned` setting, the signing `key_id`, and the verification-only `key_id`s in ascending byte order, then each covered row in ascending byte order of (tenant ID, artifact ID, version) (CODE-2).
- The digest excludes exactly the rows of class `migrated`. The spec states the same set in behavioral terms (SPEC-1 (c), CODE-2).
- The digest excludes per-row notes, stored signature bytes, and resource bodies. It covers the signature state (the verifying `key_id`, `unsigned`, or `unverified`) (CODE-2).
- `--plan-digest` with `--dry-run` is a usage error. A malformed digest is a usage error. `--include-unsigned` without `--dry-run` and without `--plan-digest` is a usage error. All three are checked inside `parseSignStoredRowsArgs`, before the store opens, and exit 2. In every other invocation `--plan-digest` is optional and compared when given, so a rotation run without `--include-unsigned` needs no digest (CODE-3).
- A changed plan returns `ErrSignStoredRowsPlanChanged`, declared in `internal/serverboot/signpass.go`, and exits 3. No §6.10 code is added (CODE-3).
- The comparison runs in `rehashStoredHashes` after `planRehash` and before `refuseStrandedSignature` and `applyRehash`. The boot leaves `rehashDeps.ReviewedPlan` empty and is unchanged (CODE-2).
- A transient object-store failure between the dry run and the run refuses the run, and no override flag is added. A completion-record mode change also refuses (Decisions).
- The compare-and-swap in `applyRehash` stays the only guard between the run's plan and its writes (Decisions, Non-goals).
- The chart keeps `podium.podConfigDigest` with each referenced Secret's `uid` and `resourceVersion`, the serving preflight's pod-config condition, and the `get` on Secrets permission. The migrated-store gate, the stop gate, and the image gate stay, and GitOps renderers stay unsupported for the upgrade from v0.4.0. Removing the Secret lookup is out of scope (CHART-1, Non-goals).
- The chart requires `migration.planDigest` for `migration.mode=run` whatever `migration.includeUnsigned` is (CHART-1).

**Watch out for.**

- **Every bare `sign-stored-rows --include-unsigned` run breaks.** Callers exist in `internal/serverboot/signpass_test.go`, `test/e2e/boot_rehash_test.go`, `test/e2e/server_ops_rolling_upgrade_test.go`, the kind test's step l2, `test/manual-validation.md` S66 and S76, the migrated-store gate's refusal text in `deploy/helm/podium/templates/_pod.tpl`, and the documentation pages DOC-1 lists. Each is ported in the step that owns it.
- **The unsigned-left hint changes.** `logSigningSummary` prints it on the boot log, in a run, and in the dry run. Three assertions quote the old text: `internal/serverboot/signpass_test.go` (the record-absent test), `internal/serverboot/rehash_boot_test.go`, and `test/e2e/boot_rehash_test.go`.
- **A signed ingest does not change the digest.** A row a signing registry ingests between the dry run and the run is at the current hash and signed under the current key, so it is class `migrated` and excluded. A test that needs a changed plan inserts an unsigned row under `--include-unsigned`, deletes an object body, sets the completion record, or edits the key set.
- **The sentinel carries no command prefix.** `signStoredRows` already wraps every error with `sign-stored-rows: %w`. A sentinel whose text starts with `sign-stored-rows:` would print the prefix twice.
- **The dry run and the run must build the header the same way.** Both call one constructor, `newPlanHeader`. A second header built inline in `dryRunSignStoredRows` would let the two digests drift apart while each path passes its own tests.
- **`stored=` goes at the end of the row line.** The kind test's `\S* class=` regex, the NOTES capture check `^dry-run: .* class=`, and the documented `diff` all read the existing field order. An assertion that a row line ends with `signed_by=...`, such as S76 step 8's Expect, no longer holds, and TEST-4 rewrites it.
- **A refused chart run is diffed from a streamed log.** The run Job's `plan:` lines are as many as the dry run's row lines, so step 4 streams them to `run.log` while the Job runs, as step 3 does for the dry run. A `kubectl logs` read after the Job ends is truncated on a large store.
- **Two counts appear in the dry-run output.** `N row(s) planned` counts every planned row. `over K row(s)` on the digest line counts the rows the digest covers, which excludes class `migrated`. A capture-completeness check compares the row lines with `N` and the non-`migrated` row lines with `K`.
- **The kind lane is red between S3 and S4.** S3 makes the binary refuse the chart's run Job, which still passes no `--plan-digest`, and the kind test's step l2. The kind test runs only under `make test-live-kind`. Land S4 before the next kind run.
- **The rolling-upgrade port skips without `PODIUM_POSTGRES_DSN`.** A green local `go test ./test/e2e/...` does not exercise it, and parts of `test/e2e` skip on macOS. Confirm the port against a live Postgres or in CI, and grep the output for `SKIP`.

## Current state and the gap

### The run replans, and the attestation covers rows present at run time

`sign-stored-rows` (§13.4) has a `--dry-run` that prints one `dry-run:` line per planned row and a summary (`dryRunSignStoredRows`, `internal/serverboot/signpass.go`). A real run plans again from scratch and reads nothing from a reviewed plan. `runSignStoredRows` parses only `--include-unsigned` and `--dry-run` (`parseSignStoredRowsArgs`), reloads the configuration, reopens the store in `openSignPassDeps`, and calls `signStoredRows`, which reaches `rehashPolicy` and `planRehash` through `rehashStoredHashes(ctx, d, false)` (`internal/serverboot/rehash.go`).

§13.4 makes `--include-unsigned` "the operator's attestation for every unsigned row the store holds at that time", and its stored-row admission paragraph states that "a later `sign-stored-rows --include-unsigned` signs every unsigned row present, including one such a party stored". The attestation therefore covers the rows present when the run executes, which can differ from the rows the operator read in the dry run.

The plan also depends on state outside the rows. The completion record sets the effective unsigned-row policy (`rehashPolicy`). The signer and its verification key set feed the classification and the sign decision (`classify`, `signs`). Object-store read outcomes and deadlines feed the classification (`assemble`, `applyWrongRootGuard`). The DSN, the bucket, and the key file come from the environment (`openSignPassDeps`). The compare-and-swap in `applyRehash`'s `write` (store contract in `pkg/store/store.go`, `RehashManifest`) covers only the rows in the run's own plan, and only between that plan and the write.

### The dry-run output is incomplete as a plan record

The dry-run line omits the stored content hash, and the output omits the signing key's `key_id`, the `--include-unsigned` setting, and whether the completion record is present (`dryRunSignStoredRows` discards `rehashPolicy`'s `applied` value). Rows print in store-listing order. The `Store` interface does not define that order (`ListTenants`, `ListManifestsIncludingDeleted`, `pkg/store/store.go`), and on Postgres it follows the database collation.

### The chart emulates the binding from outside the binary

The Helm chart's reviewed-dry-run gate (`podium.reviewedDryRunGate`, `deploy/helm/podium/templates/_pod.tpl`) requires `migration.reviewedDryRun` to name a succeeded dry-run Job UID with a matching image, `includeUnsigned` setting, release revision, and pod-config digest. That digest (`podium.podConfigDigest`, `deploy/helm/podium/templates/_helpers.tpl`) reads every referenced Secret's `uid` and `resourceVersion` through `lookup`. The binding covers chart runs only. A standalone run and a `kubectl exec` run, which key rotation and a rerun after the migration use (`docs/deployment/clustered.md`, Later upgrades), have none.

The command and the chart's migrate Job are both in `CHANGELOG.md` `[Unreleased]`, so changing their interface breaks no released contract. The spec defines no plan binding, flag, or refusal, so the change goes through §13.4 first.

## Decisions

- **Bind in the binary with a digest.** The dry run prints a plan digest, and a run given `--plan-digest=<digest>` computes the same digest over its own fresh plan and refuses before any write when the two differ. A persisted plan file would add a file format and a storage location to both binaries and to the chart Job, and a digest copied from the reviewed log gives the same binding. The binary is the single behavioral surface (§2.2), so standalone, `kubectl exec`, and chart runs all get the binding.
- **Frame the digest as the registry frames its other digests.** The digest is SHA-256 over §4.7.6 length framing, written `sha256:<64 lowercase hex>`, with the framed domain tag `podium/sign-stored-rows-plan/1` first, following `version.DeliveryHash`. The tag separates a plan digest from a content hash and a delivery hash, and its version lets a later change to the covered values change every digest.
- **Frame the header values first.** In order after the tag: the mode (`record-present` or `record-absent`, from `rehashPolicy`'s `applied`), `--include-unsigned` as `strconv.FormatBool` (`d.AttestUnsigned`), the signing `key_id` (`CurrentKeyID`), the decimal count of verification-only `key_id`s, and each of them in ascending byte order (`VerifyKeyIDs`). The verification key ids enter explicitly, because a key added to or removed from the set that verifies no stored row leaves every row value unchanged. `--dry-run` is not framed: the dry run and the run build the same plan through the same `rehashPolicy` and `planRehash` calls.
- **Frame each covered row's values.** Per covered row: tenant ID, artifact ID, version, stored content hash, class name (`rehashClass.String`), target hash (`row.newHash`, empty when none), sign (`class == unmigrated && row.sign`, as `strconv.FormatBool`), and signature state (`signatureState`: the verifying `key_id`, `unsigned`, or `unverified`). The write decision is not framed separately, because the class fixes it. Each row frames a fixed number of values, so the stream is unambiguous without a row count. Rows are ordered by ascending byte comparison of (tenant ID, artifact ID, version), which is the primary key in both SQL stores, so the order is total and independent of listing order and collation.
- **Exclude rows of class `migrated`.** Such a row is at the current hash, its signature is absent or verifies under the signing key, and the run neither writes nor signs it (`decide`). An ingest on this release while registries serve a record-present store produces exactly such a row. Including those rows would make every concurrent ingest between the dry run and the run a mismatch. A planted unsigned row under `--include-unsigned` is class `unmigrated` with sign set, so the digest covers it, and a row that leaves `migrated` for another class enters the covered set.
- **Exclude notes, signature bytes, and bodies.** The note carries object-store error text that varies between reads and does not change what the run does. The operator reviews the signature state, and the compare-and-swap on the stored signature guards the bytes between the run's plan and its write.
- **Print what the digest covers.** The dry-run row line gains a trailing `stored=<content hash>` field. The dry run prints rows in the canonical order, then the header line, then the existing summary and signing lines, then `dry-run: plan digest sha256:<hex> over <K> row(s)`. One renderer produces the row and header lines for the dry run and for the mismatch listing, so the two listings differ only in their prefix.
- **Require the digest with `--include-unsigned` outside `--dry-run`.** `--plan-digest` is required whenever `--include-unsigned` is given without `--dry-run`, and optional in every other invocation, where it is compared when given. `--plan-digest` with `--dry-run` and a value that is not `sha256:` followed by 64 lowercase hex digits are usage errors. Key rotation without `--include-unsigned` keeps working without a digest, and the documentation recommends one.
- **Refuse before any write and print the run's plan.** On a mismatch the run writes no row, no audit event, and no completion record. It prints its own plan to stdout, one `plan:` line per row in the dry-run format, then the header line and `plan: plan digest sha256:<hex> over <K> row(s)`. The error reads `sign-stored-rows: plan changed since the reviewed dry run: this run's plan digest is sha256:<a>, the reviewed digest is sha256:<b>; no row was written; rerun with --dry-run, review it, and pass its digest`.
- **Exit with status 3 on a changed plan.** `SignStoredRowsExitCode` maps the sentinel to 3, so a scripted caller, such as a Job wrapper or an operator's script, tells a changed plan from a failed write (1) and a usage error (2). The refusal is a local command status that no API client receives, so no §6.10 code is added.
- **Compare after planning and before any write.** The comparison runs in `rehashStoredHashes` after `planRehash` and before `refuseStrandedSignature` and `applyRehash`, through a new `rehashDeps.ReviewedPlan string` that the boot leaves empty.
- **Refuse on a transient object-store failure.** A read that fails between the dry run and the run turns a row `body_unavailable` with an empty target, and `deadlineSpent` spreads that to every later object-held row. The documented response is a new dry run once the object store answers. No override flag is added.
- **Refuse a run whose completion-record mode changed.** When a registry start or another run records completion between the dry run and the run, the mode value changes and the run refuses, so the operator reviews a record-present plan. The digest does not replace the stop precondition: the command still cannot detect a previous-version process.
- **Keep the compare-and-swap as the plan-to-write guard.** The digest binds the window from the dry run to the run's plan. The compare-and-swap in `applyRehash` remains the only guard between the run's plan and its writes. A row inserted in that window is absent from the run's plan and is not written, as today.
- **Export the framing writer.** `version.WriteFramed` is exported, and the digest code lives in `internal/serverboot` beside the planner, so the §13.4 plan stays out of the §4.7.6 package and no second copy of the framing primitive exists.
- **Change the hint.** The rewrite's unsigned-left hint names the reviewed procedure, because the bare command it names today is a usage error after this change. The §13.4 sentence that describes the logged line changes with it.
- **Keep the serving preflight whole.** The chart removes only the reviewed-dry-run gate, its annotation, and its run guard. `podium.podConfigDigest` and `podium.referencedSecrets` stay unchanged, because the serving preflight uses the same digest to refuse a serving render whose values or Secrets point at a store other than the one the run migrated. A render-only digest would stop detecting an edited DSN inside `existingSecret` and let serving pods run the boot rewrite, which leaves every unsigned row of a Postgres store unsigned, under the startup probe. The Helm user keeps `get` on Secrets.
- **Require the digest for every chart run.** A pure-value guard requires `migration.planDigest` in the `sha256:<64 hex>` format for `migration.mode=run`, whatever `includeUnsigned` is, because the chart procedure always reviews a dry run. The guard sits outside `migration.preflight`, so it applies with the lookup gates off, and the binary enforces the digest in every mode.
- **Keep the other lookup gates.** The migrated-store gate, the stop gate, the image gate, and the serving preflight stay. GitOps renderers stay unsupported for the upgrade from v0.4.0, because those gates still fail closed or check nothing under `helm template`, and such controllers remap Helm hooks.

## Spec amendment: §13.4 plan digest, --plan-digest, and the attestation scope

**SPEC-1.** Anchor: `spec/13-deployment.md`, §13.4 Migrations.

(a) In the paragraph that begins "The §4.7.6 content hash is such a value.", replace the sentence that begins "For every other store it moves such a row to the new digest" and ends "and does not hold the completion record back for it." with:

> For every other store it moves such a row to the new digest when its bytes reproduce the previous release's digest, leaves it unsigned, logs how many rows it left unsigned on a line of its own after the rewrite's summary line, together with the instruction to run `sign-stored-rows --include-unsigned --dry-run`, review its report, and pass its plan digest, and does not hold the completion record back for it.

(b) In the paragraph that begins "The `sign-stored-rows` command, run as", replace the sentence that begins "Beyond the rows the rewrite signs in place of the first start" and ends "because an unsigned row carries no evidence of who stored it." with:

> Beyond the rows the rewrite signs in place of the first start, the command signs a row that carries no signature only when it is invoked with `--include-unsigned`, which is the operator's attestation for every unsigned row the reviewed dry run lists, because an unsigned row carries no evidence of who stored it. Outside `--dry-run`, `--include-unsigned` requires `--plan-digest`.

(c) In the same paragraph, replace the sentence "With `--dry-run` it reports every write it would make and makes none, the completion record included." with:

> With `--dry-run` it reports every write it would make and makes none, the completion record included. It lists every planned row with its stored content hash, in an order that does not depend on the order in which the store lists rows, and it reports a plan digest. The plan digest is a SHA-256 digest, written `sha256:` followed by 64 lowercase hexadecimal digits. It depends on whether the completion record is present, whether `--include-unsigned` is given, the signing key's `key_id`, and the set of verification-only `key_id`s. It also depends, for each planned row, on the row's tenant, artifact ID, version, and stored content hash, the outcome the command reached for the row, which determines whether it writes the row, the content hash a write would store, whether the command signs the row, and the `key_id` that verifies its stored envelope, or the envelope's absence, or its failure to verify. A row whose stored bytes reproduce its stored content hash, whose stored signature is absent or verifies under the signing key, and that the command neither writes nor signs does not enter the digest. The digest does not depend on the order in which the store lists rows. Its byte encoding belongs to the release that computes it, so a dry run and a run of different releases can compute different digests for one plan, and the run then refuses.

(d) In the same paragraph, replace the last sentence, "It exits with a failure status when a row holds the completion record back or a write fails.", with:

> It exits with a failure status when a row holds the completion record back or a write fails. Given `--plan-digest`, the command computes the plan digest of the plan it builds before it writes anything. When that digest differs from the given value, it writes no row, no audit event, and no completion record, reports its own plan in the form the dry run reports it, and exits with a failure status distinct from its other failure statuses. `--plan-digest` given with `--dry-run`, a value that is not `sha256:` followed by 64 lowercase hexadecimal digits, and `--include-unsigned` given without `--dry-run` and without `--plan-digest` are usage errors, which the command refuses before it opens the store. The digest binds the plan the command builds to the plan the operator reviewed. A row stored after the command builds its plan is absent from that plan, and the command leaves it as it is.

(e) In the paragraph that begins "Before the registry serves an artifact's manifest", replace the sentence "A later `sign-stored-rows --include-unsigned` signs every unsigned row present, including one such a party stored." with:

> A later `sign-stored-rows --include-unsigned` signs every unsigned row its reviewed dry run lists, including one such a party stored before that dry run. An unsigned row such a party stores after the dry run and before the run builds its plan changes the plan digest, and the command refuses. A row stored after the run builds its plan is absent from that plan and stays unsigned.

The sentence names an unsigned row because under `--include-unsigned` the command signs every unsigned row, so such a row always enters the digest. A row that copies an admissible row's bytes, content hash, and signature under another identity is one the command neither writes nor signs, so SPEC-1 (c) excludes it from the digest and its arrival causes no refusal (`decide`, `internal/serverboot/rehash.go:301-312`).

The §13.12 sentence "Turning signing on after the rewrite has completed leaves earlier rows unsigned until `sign-stored-rows --include-unsigned` runs (§13.4)." stays accurate and is not edited. The §4.7.9 rotation paragraph names `sign-stored-rows` without `--include-unsigned`, which needs no digest, and is not edited.

## Proposed solution

**Test-caller ports.** CODE-2 changes the dry-run output and the hint, and CODE-3 makes a bare `--include-unsigned` run a usage error.

**IMPLEMENTOR'S CHOICE:** the order of edits inside S3. Constraint: at the end of S3, `go build ./... && go vet ./... && go test ./...` compile and pass, and every test that runs `--include-unsigned` outside `--dry-run` obtains its digest from a preceding dry run through a helper, with no test deleted unless TEST-1 or TEST-2 names it.

**CODE-1 · `pkg/version/version.go`.** Rename `writeFramed` to `WriteFramed` with the doc comment: "WriteFramed writes v's length as an unsigned 64-bit big-endian integer followed by v itself, the §4.7.6 length framing. Every digest the registry frames uses it, so a domain-tagged digest outside this package frames its values the same way. A hash never fails a write. Spec: §4.7.6". Port the callers in `CanonicalContentHash` and `DeliveryHash`. No test names `writeFramed`, and the existing content-hash and delivery-hash golden tests pin the unchanged behavior.

**CODE-2 · `internal/serverboot/plandigest.go` (new), `internal/serverboot/rehash.go`, `internal/serverboot/signpass.go`.**

- `planDigestTag = "podium/sign-stored-rows-plan/1"` and `planDigestPattern = regexp.MustCompile("^sha256:[0-9a-f]{64}$")`.
- `type planHeader struct { recordPresent, includeUnsigned bool; signingKey string; verifyKeys []string }`. `newPlanHeader(applied bool, d rehashDeps) (planHeader, error)` returns an error when `d.Signer` is nil, with a comment that `openSignPassDeps` always sets a signer on the command path and the boot never reaches it; otherwise it sets `includeUnsigned` from `d.AttestUnsigned`, `signingKey` from `d.Signer.CurrentKeyID()`, and `verifyKeys` from a sorted copy of `d.Signer.VerifyKeyIDs()`. `dryRunSignStoredRows` and `checkReviewedPlan` both call it.
- `canonicalPlan(plan []rehashRow) []rehashRow` returns a copy sorted by `TenantID`, then `ArtifactID`, then `Version`, each by Go string comparison, which is byte order.
- `planDigest(h planHeader, rows []rehashRow) (digest string, covered int)` frames, through `version.WriteFramed` into one `sha256.New()`: the tag; `record-present` or `record-absent`; `strconv.FormatBool(h.includeUnsigned)`; `h.signingKey`; `strconv.Itoa(len(h.verifyKeys))`; each verify key. Then, for each row of `rows` whose class is not `classMigrated`: `TenantID`, `ArtifactID`, `Version`, `rec.ContentHash`, `class.String()`, `newHash`, `strconv.FormatBool(row.class == classUnmigrated && row.sign)`, and `signatureState(row)`. It returns `"sha256:" + hex` and the covered count. A code comment lists these literal encodings and names the golden test that pins them. Cite `// Spec: §13.4`.
- `writePlanRows(w io.Writer, prefix string, rows []rehashRow)` writes each row as `%s: %s class=%s target=%s write=%t sign=%t signed_by=%s stored=%s`, with `target=-` when the target is empty. `writePlanHeader(w, prefix, h)` writes `%s: plan mode=%s include_unsigned=%t signing_key=%s verify_keys=%s`, the verify keys comma-joined or `-` when there are none.
- `rehashDeps` gains `ReviewedPlan string`, documented as the digest the operator passed with `--plan-digest`, empty on the boot path, where no comparison runs.
- `checkReviewedPlan(d rehashDeps, applied bool, plan []rehashRow) error` returns nil when `d.ReviewedPlan` is empty. Otherwise it builds the header, sorts the plan, and computes the digest. On a match it returns nil. ## Edge cases and accepted failure modes

Each row names the section that governs its outcome. The outcome column states the result in brief and does not restate the mechanism.

| Case | Outcome | Governing text; documented in |
|:--|:--|:--|
| An unsigned row inserted between the dry run and the run, under `--include-unsigned` | The run refuses with exit 3 and writes nothing | SPEC-1 (d), (e); `docs/reference/cli.md`, `docs/deployment/operator-guide.md` |
| A row inserted after the run builds its plan | Not written, and left unsigned until a later reviewed run | SPEC-1 (d), (e); `docs/deployment/operator-guide.md` |
| A signed ingest on this release between the dry run and the run | The run proceeds, and the new row is untouched | SPEC-1 (c) exclusion; `docs/reference/cli.md` |
| A row purged, or its body deleted, between the dry run and the run | The run refuses with exit 3 when the row was covered; a purged `migrated` row changes nothing | SPEC-1 (c), (d); `docs/reference/cli.md` |
| An object-store read that fails in the run and succeeded in the dry run, or the reverse | The run refuses with exit 3; the operator reruns the dry run once the object store answers | SPEC-1 (c), (d); `docs/deployment/clustered.md` Recovering from a failed run |
| The completion record set between the dry run and the run | The run refuses with exit 3 | SPEC-1 (c), (d); `docs/deployment/clustered.md` step 4 |
| A `verify:` line added or removed, or the signing key replaced, after the dry run | The run refuses with exit 3 | SPEC-1 (c), (d); `docs/deployment/operator-guide.md` |
| `--include-unsigned` differs between the dry run and the run | The run refuses with exit 3 | SPEC-1 (c), (d); `docs/reference/cli.md` |
| A store, DSN, bucket, or Secret change after the dry run that leaves every covered value identical | Not detected by the digest; on the chart, a Secret or value change after the run is refused by the serving preflight | Non-goals; SPEC-1 (d) "binds the plan the command builds to the plan the operator reviewed"; `docs/deployment/clustered.md` gate list |
| A dry run and a run of different releases | The run refuses with exit 3 when the encoding differs | SPEC-1 (c) last sentence; `docs/reference/cli.md` |
| `--include-unsigned` outside `--dry-run` without `--plan-digest`, `--plan-digest` with `--dry-run`, or a malformed digest | Exit 2 with the usage text; the store is not opened | SPEC-1 (d); `docs/reference/cli.md` |
| A rotation run without `--include-unsigned` and without a digest | Runs as today | SPEC-1 (b); `docs/deployment/operator-guide.md` |
| A record-absent run while a previous-version process serves the store | Not detected | §13.4 precondition, unchanged; `docs/reference/cli.md` |
| A chart run render without `migration.planDigest`, or with a malformed one | Refused at render, with or without `migration.preflight` | CHART-1; `docs/deployment/clustered.md` step 4 |
| A chart run Job whose plan changed | The Job fails with exit 3, `helm upgrade` exits non-zero, and the serving preflight refuses serving until a later run succeeds | SPEC-1 (d); CHART-1; `docs/deployment/clustered.md` step 4 |
| A chart render with `migration.preflight=false` | The lookup gates are off; the run guard and the binary's digest check still apply | CHART-1; `docs/deployment/clustered.md` gate list |
| A GitOps renderer that runs `helm template` | Unsupported for the upgrade from v0.4.0, as today | `docs/deployment/clustered.md` GitOps renderers |
| The boot's first-start rewrite | Unchanged; no digest is read or compared | SPEC-1 leaves the rewrite paragraph's behavior unchanged except the hint text |

## Non-goals

- Binding the window between the run's own plan and its writes. The compare-and-swap in `applyRehash` stays the guard there, and a row inserted in that window stays unwritten until a later run.
- Detecting a store, DSN, or bucket change that leaves every covered plan value identical, such as a byte-identical copy of the store or a second store whose rows classify the same way. The digest binds what the run does to the rows the operator reviewed and does not identify the store.
- Persisting a plan file, or accepting a plan as input in place of re-planning.
- Adding a §6.10 error code, an environment variable, or a `registry.yaml` key. The refusal is a local command status.
- Binding the boot-time §13.4 rewrite to a reviewed plan. A registry start keeps its current behavior.
- Removing the chart's Secret lookup or the `get` on Secrets permission. The serving preflight still needs them, and a change to that trade-off is a separate proposal.
- Making GitOps renderers such as Argo CD a supported path for the upgrade from v0.4.0, or moving the stop, image, migrated-store, or serving gates into the binary.
- Changing the stop precondition in record-absent mode. The command still cannot detect a previous-version process.
- Changing `migrate-to-standard` (§13.10), the admission check, or the signing key rotation rules of §4.7.9.

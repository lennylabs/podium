# Proposal 0030: Bind a sign-stored-rows run to its reviewed dry run with a plan digest, refuse an unreviewed boot rewrite, and drop the chart's cluster lookups

- Issue: (to be filed)
- Status: Implemented (2026-09-27). Verified 2026-09-27 after 6 adversarial review rounds (2 findings fixed); OD-1 (option B) and OD-2 (option A) resolved by the owner.
- Date: 2026-09-26

This document stages the proposed spec, code, test, and documentation changes. It does not modify any spec, code, or doc file. Apply the changes in the staged sections after sign-off.

## Summary

**What changes.**

- §13.4 defines a **plan digest** that `sign-stored-rows --dry-run` reports, and a `--plan-digest` flag that binds a run to the plan the operator reviewed. A run whose own plan has a different digest writes nothing and exits with a status of its own. Outside `--dry-run`, `--include-unsigned` requires `--plan-digest`, so the §13.4 attestation covers the rows the reviewed dry run listed (SPEC-1).
- `internal/serverboot` computes the digest over a domain-tagged, §4.7.6-framed stream built from the plan header and every row the run writes, signs, or refuses, in a canonical row order. The dry run prints its rows in that order, with the stored content hash, a plan header line, and a final digest line. `pkg/version` exports the framing writer the digest reuses (CODE-1, CODE-2).
- `serverboot.RunSignStoredRows` parses `--plan-digest`, applies the new usage rules, and maps a changed plan to exit status 3 in both `podium-server sign-stored-rows` and `podium admin sign-stored-rows` (CODE-3).
- The Helm chart reads nothing from the cluster. It drops `migration.reviewedDryRun`, `migration.storeReady`, `migration.preflight`, and `migration.unprobedStart`. It also drops the `lookup`-based gates (the migrated-store gate, the stop gate, the image gate, the reviewed-dry-run gate, and the serving preflight), the `.Release.IsInstall` and `.Release.IsUpgrade` guards, the pod-config digest and the Secret reads behind it, and the Deployment and Job record annotations. In either signing mode, a registry pod over a store that holds a manifest row and no §13.4 completion record refuses to start (SPEC-2), and the chart relies on that refusal in place of the serving preflight. A values-only guard requires `migration.previousImage` on a migration render and refuses a Job image equal to it, and a signing-off migration render requires `migration.includeUnsigned=false`. The startup and liveness probes render in both signing modes. The migrate Job runs as a `post-install` and `post-upgrade` hook in both signing modes, a new value `migration.planDigest` is passed to the run Job as `--plan-digest`, and a GitOps controller such as Argo CD runs the upgrade as four value commits (CHART-1, CHART-2).
- A governed registry start (`unmigratedStoreGoverned`, CODE-4), in either signing mode, over a store that holds a manifest row and no §13.4 completion record refuses within the SPEC-2 (c) scope, as SPEC-2 (a) specifies. The co-located SQLite store and a store with no manifest row keep the automatic first-start rewrite, and a governed start over a store with no manifest row ingests only after the completion record exists (SPEC-2 (a), CODE-4, TEST-5, TEST-6, DOC-2). The docker-compose evaluation stack and a signing-off SQLite store outside the key file's directory that hold v0.4.0 rows therefore run `sign-stored-rows` once before their upgraded start (DOC-1, DOC-2).
- With signing off (`PODIUM_SIGN=none`), `sign-stored-rows` runs the §13.4 rewrite without a signer instead of refusing. It moves each reproducible unsigned row to the new digest, signs no row, records completion under the existing rule, and refuses `--include-unsigned` with `config.signature_provider_unavailable` when the flag comes with `--dry-run` or `--plan-digest`; a bare `--include-unsigned` stays a usage error. The plan digest frames an empty signing `key_id` when signing is off, and the dry run reports a signed row it does not check as `signed_by=unchecked` (SPEC-3, CODE-5).
- The upgrade procedure, the CLI reference, the error-code reference, the operator guide, the progressive-adoption page, the single-node page, the runbook, `CHANGELOG.md`, the unit, integration, end-to-end, chart, and kind tests, and manual scenarios S20, S46, S66, S75, and S76 follow (DOC-1, DOC-2, TEST-1 through TEST-7).

**Fixed decisions.**

- The binding lives in the binary. No plan file is persisted, and the operator carries the digest from the dry-run log to the run (Decisions).
- The digest is `sha256:` followed by 64 lowercase hex digits, over §4.7.6 length framing, led by the framed domain tag `podium/sign-stored-rows-plan/1` (CODE-2).
- The digest covers a header of the completion-record mode, the `--include-unsigned` setting, the signing `key_id`, and the verification-only `key_id`s in ascending byte order, then each covered row in ascending byte order of (tenant ID, artifact ID, version) (CODE-2).
- The digest excludes exactly the rows of class `migrated`. The spec states the same set in behavioral terms (SPEC-1 (c), CODE-2).
- The digest excludes per-row notes, stored signature bytes, and resource bodies. It covers the signature state (the verifying `key_id`, `unsigned`, `unverified`, or, with no signer, `unchecked`) (CODE-2, CODE-5).
- `--plan-digest` with `--dry-run` is a usage error. A malformed digest is a usage error. `--include-unsigned` without `--dry-run` and without `--plan-digest` is a usage error. All three are checked inside `parseSignStoredRowsArgs`, before the store opens, and exit 2. In every other invocation `--plan-digest` is optional and compared when given, so a rotation run without `--include-unsigned` needs no digest (CODE-3).
- A changed plan writes no row, no audit event, and no completion record, and prints the run's own plan as `plan:` lines in the dry-run format (Decisions).
- A changed plan returns `ErrSignStoredRowsPlanChanged`, declared in `internal/serverboot/signpass.go`, and exits 3. No §6.10 code is added (CODE-3).
- The unsigned-left hint names the reviewed procedure: a `--include-unsigned --dry-run`, its review, and a run with its plan digest (SPEC-1 (a), CODE-2).
- The comparison runs in `rehashStoredHashes` after `planRehash` and before `refuseStrandedSignature` and `applyRehash`. The boot leaves `rehashDeps.ReviewedPlan` empty; its only changes are CODE-4's refusal and its pre-ingest record check (CODE-2, CODE-4).
- The boot refusal applies in both signing modes (OD-1, resolved). It applies only when the store holds a manifest row, including a soft-deleted one, so a fresh store's first start records completion. A start that finds a row reads the record again and refuses only when it is still absent, so a replica starting beside a peer's first start proceeds (CODE-4).
- The refusal applies the SPEC-2 (a) co-location rule in both signing modes, and the key file need not exist in either. CODE-4 gives the key-path resolution and the rule for an unresolvable default key location.
- The refusal runs after `refuseUnpersistedSigningKey` and `refuseGeneratedSigningKey`, before `registrySignerFor`, and whatever the bind outcome. A store read error in its record read, row scan, or re-read fails the start, so the refusal fails closed. CODE-4 gives its exit status and error text.
- The boot keeps `MintUnsigned` from `mintUnsignedOnFirstRun` (CODE-4).
- The refusal reuses `keyCoLocatedWithStore`, `DataMigrationApplied`, and the row scan of `refuseGeneratedSigningKey`, extracted into `firstStoredRow`. It adds no store method, sentinel, §6.10 code, flag, environment variable, or `registry.yaml` key (CODE-4).
- For the starts the refusal governs, `refuseUnrecordedIngest` runs after the rewrite block and before the bootstrap ingest, and it fails the start when the completion record is absent. It shares the predicate `unmigratedStoreGoverned` with the refusal (CODE-4).
- A transient object-store failure between the dry run and the run refuses the run, and no override flag is added. A completion-record mode change also refuses (Decisions).
- The compare-and-swap in `applyRehash` stays the only guard between the run's plan and its writes (Decisions, Non-goals).
- The chart calls no `lookup` and reads no `.Release.IsInstall`, `.Release.IsUpgrade`, or `.Release.Revision`, so `helm template`, `helm install`, and `helm upgrade` render one set of manifests from one set of values. The Helm user needs no permission beyond applying the chart's objects, and GitOps controllers are supported for the upgrade from v0.4.0 (CHART-1).
- In both signing modes, the chart relies on the SPEC-2 boot refusal: a registry pod over a store that holds a manifest row and no completion record exits at start within the SPEC-2 (c) scope, so no chart check stands between a serving render and the store. The Decision "Drop the serving preflight" records what the pod writes before it exits (CHART-1).
- The stop gate is dropped. The procedure's zero-replica step and its `kubectl wait` are the stop check, a migration render requires `replicaCount=0`, and the plan digest refuses a run after any covered write between the dry run and the run's plan (Decisions).
- The chart requires `migration.planDigest` for `migration.mode=run` whatever `migration.includeUnsigned` is (CHART-1).
- A `dry-run` or `run` render requires `migration.previousImage` and refuses a rendered image equal to it. The value is required, because an optional one leaves the check off for the operator who kept the previous tag (CHART-1).
- The migrate Job runs as a `post-install` and `post-upgrade` hook. `migration.storeReady`, `migration.preflight`, and the guards that refused a migration mode on install are deleted (CHART-1).
- Signing off is a mode of `sign-stored-rows`, selected by `PODIUM_SIGN`, which a registry start also reads. No flag or subcommand is added, so an operator who turned signing off with `podium serve --sign none` sets `PODIUM_SIGN=none` for the command (CODE-4, CODE-5).
- With signing off, `--include-unsigned` with `--dry-run` or with `--plan-digest` refuses with `config.signature_provider_unavailable` before the store opens, and exits 1. A bare `--include-unsigned`, with neither flag, remains the exit-2 usage error that `parseSignStoredRowsArgs` reports before `loadBootConfig` reads the signing mode (CODE-3). Every other invocation that passes argument parsing runs (CODE-5).
- The dry run applies the stranded-signature refusal that the run applies, in both signing modes (CODE-2, CODE-5).
- With signing off, the plan header's signing `key_id` is the empty string and it has no verification `key_id`s. A signed row's signature state is `unchecked` (CODE-2).
- `migration.unprobedStart` is deleted. A signing-off chart deployment follows the signing-on procedure with `migration.includeUnsigned=false` (CHART-2).

## Current state and the gap

### The run replans, and the attestation covers rows present at run time

`sign-stored-rows` (§13.4) has a `--dry-run` that prints one `dry-run:` line per planned row and a summary (`dryRunSignStoredRows`, `internal/serverboot/signpass.go`). A real run plans again from scratch and reads nothing from a reviewed plan. `runSignStoredRows` parses only `--include-unsigned` and `--dry-run` (`parseSignStoredRowsArgs`), reloads the configuration, reopens the store in `openSignPassDeps`, and calls `signStoredRows`, which reaches `rehashPolicy` and `planRehash` through `rehashStoredHashes(ctx, d, false)` (`internal/serverboot/rehash.go`).

§13.4 makes `--include-unsigned` "the operator's attestation for every unsigned row the store holds at that time", and its stored-row admission paragraph states that "a later `sign-stored-rows --include-unsigned` signs every unsigned row present, including one such a party stored". The attestation therefore covers the rows present when the run executes, which can differ from the rows the operator read in the dry run.

The plan also depends on state outside the rows. The completion record sets the effective unsigned-row policy (`rehashPolicy`). The signer and its verification key set feed the classification and the sign decision (`classify`, `signs`). Object-store read outcomes and deadlines feed the classification (`assemble`, `applyWrongRootGuard`). The DSN, the bucket, and the key file come from the environment (`openSignPassDeps`). The compare-and-swap in `applyRehash`'s `write` (store contract in `pkg/store/store.go`, `RehashManifest`) covers only the rows in the run's own plan, and only between that plan and the write.

### The dry-run output is incomplete as a plan record

The dry-run line omits the stored content hash, and the output omits the signing key's `key_id`, the `--include-unsigned` setting, and whether the completion record is present (`dryRunSignStoredRows` discards `rehashPolicy`'s `applied` value). Rows print in store-listing order. The `Store` interface does not define that order (`ListTenants`, `ListManifestsIncludingDeleted`, `pkg/store/store.go`), and on Postgres it follows the database collation.

### A non-co-located first start rewrites without review

A signing start that finds no completion record runs the whole rewrite before it serves (`internal/serverboot/serverboot.go:956-979`). Outside the SQLite store in the key file's directory, it leaves every unsigned row unsigned, records completion, and serves (`mintUnsignedOnFirstRun`, `internal/serverboot/rehash.go:105-111`; `keyCoLocatedWithStore`, `internal/serverboot/signing.go:144-147`). No operator reviews that run. The record is set only by `applyRehash` (`rehash.go:466-471`) and cleared by `migrate-to-standard` (`cmd/podium/admin_migrate.go:356-364`), so a migrated target and a store whose record was deleted also rewrite at boot. The existing start refusals cover a stranded signature and a key that would be generated (`refuseGeneratedSigningKey`, `rehash.go:669-710`), and they do not stop an unreviewed rewrite. A signing-off start that finds no completion record runs the same rewrite over any store, signing no row (`internal/serverboot/serverboot.go:966-976`).

### A signing-off deployment cannot run the command

`openSignPassDeps` refuses with `config.signature_provider_unavailable` when signing is off, before it opens the store (`internal/serverboot/signpass.go:122-124`). §13.4 states that refusal. The rewrite it guards already runs without a signer: the boot passes a nil `Signer` when signing is off (`internal/serverboot/serverboot.go:966-976`), `signs` then signs nothing, `refuseStrandedSignature` refuses a signed row whose hash needs rewriting, and `logSigningSummary` logs nothing (`internal/serverboot/rehash.go`). `TestRun_SigningOffRewritesUnsignedRowsWithoutSigning` (`internal/serverboot/rehash_boot_test.go:641`) pins that behavior at boot. Because of the refusal, a signing-off chart deployment cannot use the migrate Job. The chart refuses `migration.mode` with `signing.mode=none` (`deploy/helm/podium/templates/_pod.tpl:36-38`). Such a deployment runs the rewrite at boot through `migration.unprobedStart`, which removes the startup and liveness probes, forces one replica and `Recreate`, and skips the serving preflight (`_pod.tpl:45-49`, `deployment.yaml:56-75`, `_helpers.tpl:180-189`, `NOTES.txt:60-66`, `values.yaml:282-287`; `docs/deployment/clustered.md`, Upgrade with signing off). That path runs no dry run and so cannot carry a plan digest.

### The chart emulates the binding from outside the binary

The Helm chart's reviewed-dry-run gate (`podium.reviewedDryRunGate`, `deploy/helm/podium/templates/_pod.tpl`) requires `migration.reviewedDryRun` to name a succeeded dry-run Job UID with a matching image, `includeUnsigned` setting, release revision, and pod-config digest. That digest (`podium.podConfigDigest`, `deploy/helm/podium/templates/_helpers.tpl`) reads every referenced Secret's `uid` and `resourceVersion` through `lookup`. The binding covers chart runs only. A standalone run and a `kubectl exec` run, which key rotation and a rerun after the migration use (`docs/deployment/clustered.md`, Later upgrades), have none.

The chart's other render checks read the cluster for one reason: the registry runs the §13.4 rewrite at boot over any store without the completion record (`internal/serverboot/serverboot.go:955-979`). The serving preflight (`podium.servingGate`) keeps pods off an unmigrated store by reading the live Deployment, the migrate Job, and every referenced Secret (`podium.podConfigDigest`, `podium.referencedSecrets`). The stop gate lists the release's pods. The image gate reads the `pre-migration-image` annotation that `podium.migrationAnnotations` writes, and the migrated-store gate reads the `stored-row-format` annotation. `migration.storeReady` and the install guards (`deploy/helm/podium/templates/_pod.tpl:50-55`) stand in for the preflight where no Deployment exists. Under `helm template` these checks fail closed or check nothing, so GitOps controllers are unsupported, and the Helm user needs `get` on Deployments, Jobs, and Secrets and `list` on Pods.

The command and the chart's migrate Job are both in `CHANGELOG.md` `[Unreleased]`, so changing their interface breaks no released contract. The spec defines no plan binding, flag, or refusal, lets a start outside the co-located store rewrite without review in either signing mode, and has `sign-stored-rows` refuse with signing off, so the change goes through §13.4 and §13.12 first.

## Decisions

- **Bind in the binary with a digest.** The dry run prints a plan digest, and a run given `--plan-digest=<digest>` computes the same digest over its own fresh plan and refuses before any write when the two differ. A persisted plan file would add a file format and a storage location to both binaries and to the chart Job, and a digest copied from the reviewed log gives the same binding. The binary is the single behavioral surface (§2.2), so standalone, `kubectl exec`, and chart runs all get the binding.
- **Frame the digest as the registry frames its other digests.** The digest is SHA-256 over §4.7.6 length framing, written `sha256:<64 lowercase hex>`, with the framed domain tag `podium/sign-stored-rows-plan/1` first, following `version.DeliveryHash`. The tag separates a plan digest from a content hash and a delivery hash, and its version lets a later change to the covered values change every digest.
- **Frame the header values first.** The header frames these values in order after the tag: the mode (`record-present` or `record-absent`, from `rehashPolicy`'s `applied`), `--include-unsigned` as `strconv.FormatBool` (`d.AttestUnsigned`), the signing `key_id` (`CurrentKeyID`, or the empty string when no signer is configured), the decimal count of verification-only `key_id`s, and each of them in ascending byte order (`VerifyKeyIDs`). The verification key ids enter explicitly, because a key added to or removed from the set that verifies no stored row leaves every row value unchanged. `--dry-run` is not framed: the dry run and the run build the same plan through the same `rehashPolicy` and `planRehash` calls.
- **Frame each covered row's values.** Each covered row frames its tenant ID, artifact ID, version, stored content hash, class name (`rehashClass.String`), target hash (`row.newHash`, empty when none), sign (`class == unmigrated && row.sign`, as `strconv.FormatBool`), and signature state (`signatureState`: the verifying `key_id`, `unsigned`, `unverified`, or, with no signer, `unchecked`). The write decision is not framed separately, because the class fixes it. Each row frames a fixed number of values, so the stream is unambiguous without a row count. Rows are ordered by ascending byte comparison of (tenant ID, artifact ID, version), which is the primary key in both SQL stores, so the order is total and independent of listing order and collation.
- **Exclude rows of class `migrated`.** Such a row is at the current hash, its signature is absent or verifies under the signing key (with signing off, its signature is not checked), and the run neither writes nor signs it (`decide`). An ingest on this release while registries serve a record-present store produces exactly such a row. Including those rows would make every concurrent ingest between the dry run and the run a mismatch. A planted unsigned row under `--include-unsigned` is class `unmigrated` with sign set, so the digest covers it, and a row that leaves `migrated` for another class enters the covered set.
- **Exclude notes, signature bytes, and bodies.** The note carries object-store error text that varies between reads and does not change what the run does. The operator reviews the signature state, and the compare-and-swap on the stored signature guards the bytes between the run's plan and its write.
- **Print what the digest covers.** The dry-run row line gains a trailing `stored=<content hash>` field. The dry run prints rows in the canonical order, then the header line, then the existing summary and signing lines, then `dry-run: plan digest sha256:<hex> over <K> row(s)`. One renderer produces the row and header lines for the dry run and for the mismatch listing, so the two listings differ only in their prefix.
- **Require the digest with `--include-unsigned` outside `--dry-run`.** `--plan-digest` is required whenever `--include-unsigned` is given without `--dry-run`, and optional in every other invocation, where it is compared when given. `--plan-digest` with `--dry-run` and a value that is not `sha256:` followed by 64 lowercase hex digits are usage errors. Key rotation without `--include-unsigned` keeps working without a digest, and the documentation recommends one.
- **Refuse before any write and print the run's plan.** On a mismatch the run writes no row, no audit event, and no completion record. It prints its own plan to stdout, one `plan:` line per row in the dry-run format, then the header line and `plan: plan digest sha256:<hex> over <K> row(s)`. The error reads `sign-stored-rows: plan changed since the reviewed dry run: this run's plan digest is sha256:<a>, the reviewed digest is sha256:<b>; no row was written; rerun with --dry-run, review it, and pass its digest`.
- **Exit with status 3 on a changed plan.** `SignStoredRowsExitCode` maps the sentinel to 3, so a scripted caller, such as a Job wrapper or an operator's script, tells a changed plan from a failed write (1) and a usage error (2). The refusal is a local command status that no API client receives, so no §6.10 code is added.
- **Compare after planning and before any write.** The comparison runs in `rehashStoredHashes` after `planRehash` and before `refuseStrandedSignature` and `applyRehash`, through a new `rehashDeps.ReviewedPlan string` that the boot leaves empty.
- **Refuse on a transient object-store failure.** A read that fails between the dry run and the run turns a row `body_unavailable` with an empty target, and `deadlineSpent` spreads that to every later object-held row. The documented response is a new dry run once the object store answers. No override flag is added.
- **Refuse a run whose completion-record mode changed.** When a registry start or another run records completion between the dry run and the run, the mode value changes and the run refuses, so the operator reviews a record-present plan. The digest does not replace the stop precondition: the command still cannot detect a previous-version process.
- **Keep the compare-and-swap as the plan-to-write guard.** The digest binds the window from the dry run to the run's plan. The compare-and-swap in `applyRehash` remains the only guard between the run's plan and its writes. A row inserted in that window is absent from the run's plan and is not written, as today.
- **Export the framing writer.** `version.WriteFramed` is exported, and the digest code lives in `internal/serverboot` beside the planner, so the §13.4 plan stays out of the §4.7.6 package and no second copy of the framing primitive exists.
- **Change the hint.** The rewrite's unsigned-left hint names the reviewed procedure, because the bare command it names today is a usage error after this change. The §13.4 sentence that describes the logged line changes with it.
- **Drop the serving preflight.** In either signing mode, a registry pod over a store that holds a manifest row and no completion record exits at start within the SPEC-2 (c) scope, so the preflight guards no stored row the binary does not. The preflight also kept new-version pods from opening the store at all. Without it, a refused pod first applies this release's additive schema and seeds the default tenant and the bootstrap admin and operator grants (`internal/serverboot/serverboot.go:843-882`), on a store v0.4.0 pods may still serve and before the procedure's step-2 backup. The §13.4 additive guarantee (`spec/13-deployment.md:80`) covers that write: the schema stays readable and writable by the previous binary, which `TestServerOps_RollbackBeforeFinalize` (`test/e2e/server_ops_rolling_upgrade_test.go:516`) pins, and the tenant and grant writes are idempotent seeds. A serving render whose values point at another store serves that store when it is migrated and refuses at start when it is not. `podium.podConfigDigest`, `podium.referencedSecrets`, the Secret reads, and the Job and Deployment record annotations lose their only readers and are deleted. The failure moves from the render to the rollout: the pod exits, its log names `sign-stored-rows`, the rollout does not progress, and `helm upgrade --wait` or an Argo CD sync reports it. The procedure runs the migrate Job before any serving render in both signing modes (CHART-2).
- **Require the digest for every chart run.** A pure-value guard requires `migration.planDigest` in the `sha256:<64 hex>` format for `migration.mode=run`, whatever `includeUnsigned` is, because the chart procedure always reviews a dry run. The guard reads values only, so `helm template` applies it, and the binary enforces the digest in every mode.
- **Refuse an unreviewed boot rewrite outside the co-located store.** In either signing mode, a start over any store other than the SQLite store in the key file's directory refuses when it finds no completion record and the store holds a manifest row. `sign-stored-rows` performs the rewrite in its place, behind its dry run and, with signing on, its plan digest. The co-located SQLite store keeps the automatic rewrite, where the key and the rows share one fate on disk.
- **Cover signing off with the default key location.** A signing-off rewrite signs no row, but it still moves every stored row to a new digest with no review, and a chart that skips the migrate Job would otherwise run it under the startup probe beside any v0.4.0 pod a rolling update keeps (OD-1). A signing-off start resolves the key path as a signing start does, through `sign.KeyFilePath`, which returns `PODIUM_SIGN_KEY_PATH` when set and `~/.podium/standalone/registry-signing.key` otherwise. In both signing modes, the test compares directories and does not require the file, so a signing start over the zero-configuration standalone store that holds v0.4.0 unsigned rows and has no key file yet is exempt, generates the key, and mints signatures for those rows under 0029's rule. The zero-configuration standalone store sits in the directory of the default key location and keeps the automatic rewrite, and a signing-off SQLite store in the directory of a set `PODIUM_SIGN_KEY_PATH` is exempt the same way. A signing-off SQLite store in neither, such as one at a custom `PODIUM_SQLITE_PATH` with the variable unset, is refused like any other store, and `sign-stored-rows` in its signing-off mode (SPEC-3) is its only rewrite path. A default key location that cannot be resolved, because the process has no home directory, cannot show co-location, so the store is treated as outside it; a signing start keeps its resolution error, because it cannot load a key without the path.
- **Exempt an empty store.** A store with no manifest row has nothing to review, and its first start must record completion before it ingests, so the rows its ingests store are not refused on the next start. A memory store is always empty at open.
- **Ingest only after the record exists on a governed store.** Over an empty governed store, a start whose listener did not bind, whose rewrite held a row, or whose record write failed would otherwise run the bootstrap ingest without the record, and every later start of every replica would then be refused, so `refuseUnrecordedIngest` re-reads the record after the rewrite block and fails the start before the ingest (CODE-4). Running the empty rewrite on a failed bind is rejected, because the bind guard exists for a start whose address a previous-version process still holds, and recording completion under such a process leaves the rows it ingests afterwards at the previous digest with the record set. Skipping the ingest on every bind failure is rejected, because it changes the co-located starts that heal on their next start today. CODE-4 and the Edge cases table state which error each failure returns and what the next start does.
- **Refuse before the signer loads, whatever the bind outcome.** The Fixed decisions state the placement. The loader creates a missing key file (`registrySignerFor`, `internal/serverboot/signing.go:80`), so a refusal placed after it would generate a key. The refusal writes no key file and stays within the SPEC-2 (c) scope, so it needs no bound listener, and an operator whose bind also failed reads the refusal. The generated-key refusal takes precedence because, when a stored row carries a signature, a missing key file must be pointed at the key that signed it before any rewrite, and a new key would strand that signature. That refusal fires only when a stored row is signed. Over a store whose rows are all unsigned and whose key file is absent, which is the common signing-on upgrade of a v0.4.0 Postgres store or a moved SQLite store with `PODIUM_SIGN_KEY_PATH` naming a new path, this refusal fires instead, and `sign-stored-rows` cannot run until a key exists, because it never generates one (SPEC-3 (a)). Its error therefore names `podium admin signing-key generate` before the dry run in that case (CODE-4).
- **Re-read the record after finding a row.** A peer's first start over an empty store records completion before its bootstrap ingest, which `refuseUnrecordedIngest` guarantees. A second start that read no record and then finds the peer's rows reads the record again and refuses only when it is still absent.
- **Keep the boot's unsigned-row policy.** The boot still sets `MintUnsigned` from `mintUnsignedOnFirstRun`. A row stored between the refusal check and `planRehash` is then moved and left unsigned, as 0029 does, rather than signed.
- **Reuse the existing surfaces for the refusal.** The predicate is `keyCoLocatedWithStore` over the path `registrySigningKeyPath` resolves, the record read is `DataMigrationApplied`, and the row scan is the one `refuseGeneratedSigningKey` already makes, extracted into a shared helper. No store method, sentinel, §6.10 code, flag, environment variable, or `registry.yaml` key is added.
- **Run the command without a signer when signing is off.** `openSignPassDeps` loads no key and resolves no key path when signing is off, and it leaves `Signer` nil. The command then runs the rewrite the boot runs with signing off. A separate subcommand or flag would duplicate the configuration read and the store open, and it would still need this branch. The command reads the signing mode from `PODIUM_SIGN` through `loadBootConfig` and has no `--sign` flag. `podium serve --sign none` sets `PODIUM_SIGN` only inside its own process (`cmd/podium/serve.go:92`), so a command run beside a start configured with that flag runs with signing on unless the operator sets `PODIUM_SIGN=none` for it: with `PODIUM_SIGN_KEY_PATH` unset `refuseUnpersistedSigningKey` refuses it, with the variable naming an absent file the key loader refuses it, and with a present key it plans a signing-on migration. The signing-off refusal message and every page that gives its repair therefore name `PODIUM_SIGN=none` for the command's environment (CODE-4, DOC-2).
- **Refuse only `--include-unsigned` with signing off.** The flag is an attestation that the command signs, and with no signer it signs nothing. The refusal keeps `config.signature_provider_unavailable`, which `openSignPassDeps` already returns for this mode (`internal/serverboot/signpass.go:123`). It runs after `loadBootConfig`, because the mode is configuration, and before the store opens. It therefore applies only to an invocation that passes `parseSignStoredRowsArgs`: `--include-unsigned` with `--dry-run` or with `--plan-digest`. A bare `--include-unsigned` stays the exit-2 usage error in both signing modes (SPEC-1 (d), CODE-3). A record-present run with signing off is allowed. It rewrites a reproducible unsigned row still at the previous digest, such as one a restore brought back, and it refuses a signed one.
- **Refuse stranded signatures in the dry run.** `dryRunSignStoredRows` calls `refuseStrandedSignature` after `planRehash`, at the point `rehashStoredHashes` calls it. With a signer the call is a no-op, so signing-on output is unchanged. Without the call, a signing-off dry run would print a digest for a plan the run refuses.
- **Frame signing off as an empty signing `key_id`.** A registry-managed `key_id` is 16 hex digits (`sign.KeyIDFor`, `pkg/sign/registry_managed.go:79-82`), and the command's loader requires a private key, so an empty value cannot collide with a key. The header layout stays the same, and the digest of a signing-off plan differs from every signing-on digest.
- **Report an unchecked signature as `unchecked`.** With no signer, `row.signedBy` is always empty, so `signatureState` would report every signed row as `unverified`. The NOTES dry-run branch tells the operator that `unverified` means the signing Secret lacks the key (`deploy/helm/podium/templates/NOTES.txt:20-27`), and a signing-off deployment has no signing Secret.
- **Delete `migration.unprobedStart`.** Once the command runs with signing off, the migrate Job serves both signing modes. The chart's single migration path keeps its probes, its strategy, and the reviewed dry run for every deployment.
- **Drop the stop gate.** The gate sees only the release's pods. Moving it into the Job would add a ServiceAccount, a Role that lists pods, and a Kubernetes client or a `kubectl` image. The remaining checks cover what it covered. A migration render requires `replicaCount=0`. The dry run writes nothing. A run requires a digest from a dry run, and that dry run's render already set the Deployment to zero replicas. A covered write between the dry run and the run's plan, such as a v0.4.0 pod in its grace period ingesting a row, changes the digest, and the run refuses. A process that writes after the run plans leaves its row at the previous content hash, and admission refuses that row with `materialize.content_hash_mismatch`, as it did for a process the gate could not see. The zero-replica step and its `kubectl wait` remain.
- **Replace the image gate with a values-only check.** A `dry-run` or `run` render requires `migration.previousImage` and refuses when the rendered image equals it. The v0.4.0 `podium-server` ignores its arguments, so a Job on that image starts a registry that never exits. The value is required because an optional one leaves the check off for the operator who kept the previous tag.
- **Drop `migration.storeReady` and the install guards.** In either signing mode, a serving install over a v0.4.0 store starts pods that exit at start, and a start over an empty store records completion (SPEC-2), so the acknowledgement guards nothing. `migration.previousImage` is required only with a migration mode.
- **Run the Job on install as on upgrade.** The hook is `post-install,post-upgrade`, and the guard that refused a migration mode on `helm install` is deleted. An install over an existing store can run its dry run in the install itself, and a controller that renders every revision as an install renders the Job.
- **Support GitOps controllers.** With no `lookup` and no release-state read, `helm template` renders what `helm upgrade` renders. Argo CD maps `post-install` and `post-upgrade` to PostSync and `before-hook-creation` to BeforeHookCreation. The upgrade is four commits: `replicaCount: 0`; `migration.mode: dry-run`; `migration.mode: run` with `migration.planDigest`; and the serving values. A sync that repeats a hook reruns the committed step's Job. A repeated dry run writes nothing. A repeated run over the store its first run migrated computes a different digest, exits with status 3, and writes nothing.
- **Drop `migration.preflight`.** It turned the `lookup` gates off and told the annotation writer that the rewrite had completed. Neither exists after this change.

A store with no manifest row keeps the automatic first-start rewrite in both modes, and with signing off `sign-stored-rows` in its signing-off mode is the only rewrite path for a store that is not standalone (SPEC-3, CODE-5). The refusal names `sign-stored-rows` and its dry run in both modes, and `--include-unsigned` and `--plan-digest` only with signing on. SPEC-2, CODE-4, the Decisions, the Edge cases, TEST-3, TEST-5, TEST-6, the S76 changes, and DOC-1 and DOC-2 state the consequences. Option A, which exempted signing off and accepted a skipped signing-off migrate Job, and option C, an opt-in that kept `migration.unprobedStart`, are rejected.

**OD-2. `sign-stored-rows` with signing off (SPEC-3, CODE-5, CHART-2). Resolved (2026-09-26): option A.** The owner's decision of 2026-09-26, recorded in the Status line and in Redesign 1, includes the signing-off command path. The chart has one migration procedure for both signing modes, and `migration.unprobedStart` is deleted together with its guard, its probe removal, its NOTES branch, its values, its render test, and the `Recreate` switch. Option B, which kept the command's refusal with signing off, is unavailable under the OD-1 resolution, because the boot refuses a signing-off store outside the co-located SQLite store and that store would then have no rewrite path.

## Non-goals

- Binding the window between the run's own plan and its writes. The compare-and-swap in `applyRehash` stays the guard there, and a row inserted in that window stays unwritten until a later run.
- Detecting a store, DSN, or bucket change that leaves every covered plan value identical, such as a byte-identical copy of the store or a second store whose rows classify the same way. The digest binds what the run does to the rows the operator reviewed and does not identify the store.
- Persisting a plan file, or accepting a plan as input in place of re-planning.
- Adding a §6.10 error code, an environment variable, or a `registry.yaml` key. The plan-digest refusal is a local command status, and the boot refusal is a start failure with exit status 1.
- Binding the boot-time §13.4 rewrite to a reviewed plan. Outside the co-located store, a start refuses instead in either signing mode (SPEC-2), and where the boot rewrite still runs it reads no digest.
- Moving the stop check into the migrate Job or into the binary. The zero-replica step and its `kubectl wait` remain the stop check, and the command still cannot detect a previous-version process.
- An Argo CD end-to-end test. `TestChart_ReadsNothingFromTheCluster` pins that `helm template` renders what `helm upgrade` renders, and the hook mapping is Argo CD's documented behavior.
- Changing the stop precondition in record-absent mode. The command still cannot detect a previous-version process.
- A separate subcommand or flag for the signing-off rewrite. `PODIUM_SIGN` selects the behavior.
- Changing what `migrate-to-standard` (§13.10) copies or clears, the admission check, or the signing key rotation rules of §4.7.9. SPEC-2 (b) changes only what the target's start does.

# Proposal 0065: Take a git layer's username and token as write-only members apart from `repo` in the layer API, the CLI, the web UI, and declared layers

- Issue: (to be filed)
- Status: Applied to spec (2026-11-11). Signed off as staged, with OD-3 to OD-6 settled under their defaults as recorded in "Open questions". Verified on 2026-11-11 after 11 adversarial review rounds (12 findings fixed).
- Date: 2026-11-10

This document stages spec, code, test, and documentation changes. It does not modify any spec, code, test, or doc file. Apply the changes in the staged sections after sign-off. The change is backward-incompatible: a registration whose `http` or `https` `repo` carries URL userinfo is refused, the `force_repo_overwrite` member and `--force-repo-overwrite` flag are removed, and a re-registration of an `ssh://` layer with the remote a read reports, which 0.6.0 refused with `redacted_repo`, stores that remote without its login name (D-9, D-2 matrix X7). It ships in 0.7.0, a MINOR release, after proposal 0054.

File and line citations are to `main` at `3662db49`, the merge of proposal 0054 (PR #178), unless they name another revision. A citation of 0.6.0 behavior names the tag `v0.6.0`. The files those citations name, `pkg/registry/server/layers.go`, `cmd/podium/layer.go`, `internal/serverboot/`, `internal/repourl/`, `pkg/layer/source/`, and `web/`, are unchanged between `v0.6.0` and `3662db49`.

## Summary

**What changes.**

- **Spec, §7.3.1.** A `git` layer on an `http` or `https` remote takes its credential through the write-only members `repo_username` and `repo_token`, and the boolean `clear_repo_credential` removes it. URL userinfo on an `http` or `https` `repo` is refused with `details.constraint: "url_credential"`. The `redacted_repo` guard and `force_repo_overwrite` become a keep rule for a re-registration that sends back the reported `repo`. The patch semantics, the lifecycle-event exemption, and the Errors list follow, a new paragraph names the declared-layer `username` and `token` keys, and the layer object gains the boolean `repo_credential`, carried on a layer whose update takes the members and omitted on every other layer, which reports whether a credential is stored and carries no part of it (SPEC-1 to SPEC-4).
- **Registry, `internal/repourl` and `pkg/registry/server`.** Shared predicates decide which `repo` takes a credential and which is refused, and one helper builds the userinfo from the members. The register and update handlers accept the members, refuse bad input before they write, keep or rotate the credential, and drop the guard, and `wireLayer` returns a `LayerObject` wrapper that adds `repo_credential` on a layer where the one applicability predicate, `credentialApplies`, holds (D-12, CODE-1, CODE-2).
- **Declared layers, `internal/serverboot`.** `source.git.username` and `source.git.token` join the credential into the seeded `repo`. A declaration that sets neither key is seeded as 0.6.0 seeds it, a credential in the userinfo of `source.git.repo` included, and each start logs a line telling the operator to move that credential to the keys. Startup aborts only for a declaration that sets a key: alongside userinfo in `source.git.repo`, on a `repo` that takes no credential, with a token that is not a string or is empty or null, or against the member rules (CODE-3).
- **Stored rows, `pkg/store` and `internal/serverboot`.** Each start whose listener binds rewrites every SQLite and Postgres layer row whose `repo` and `repo_userinfo` differ from the form its next write would take, for every tenant and including soft-deleted rows, before it serves. It changes no other column and logs the count. A row that still holds a URL credential whole in `repo` therefore takes 0054's two-column form at the first 0.7.0 start. The §13.4 stored-form paragraph states this (SPEC-5, CODE-6, TEST-6).
- **CLI and web UI.** `podium layer register` and `podium layer update` take `--repo-username`, `--repo-token-file`, and `--clear-repo-credential`, and `--force-repo-overwrite` is removed. The web register and edit dialogs gain Username and Token fields, which the edit dialog renders only on a layer whose layer object carries `repo_credential` (D-19, D-22), the layer panel marks a layer that holds a credential, the edit dialog offers the removal checkbox only on such a layer, and `web/bundle` is rebuilt (CODE-4, CODE-5).
- **Tests, manual validation, docs, and CHANGELOG.** Unit, integration, end-to-end, and vitest cases pin the members, the refusals, the keep rule, the declared keys, the presence member, and the start-time rewrite, and the guard tests are rewritten (TEST-1 to TEST-6). S89 is rewritten, and 0054's S103 and S58's step 1 and step 3 expectations follow (MV-1). The layer, HTTP API, CLI, and operator pages and the `[Unreleased]` CHANGELOG section follow (DOC-1 to DOC-4).

**Watch out for.**

- **The keep switch moves.** Putting the keep at the old guard line (`pkg/registry/server/layers.go:1462-1473`) hands alice's token to an admin-defined layer. D-13 and CODE-2 step 3 place it.
- **A `[redacted]` re-registration runs on the admin arm.** A `repo` of `[redacted]` resolves to go-git's file transport, so `isFileTransportRepo` (`pkg/registry/server/layer_capabilities.go:75-84`) classifies it as a host path, and the local-source rule (`layers.go:1447`) runs before the keep. The owner of a user-defined layer without the tenant `admin` role gets `403 auth.forbidden` with `local_source`, and the layer write rule refuses every other such caller first. A registry with no identity provider configured, or in public mode, refuses neither (D-2 matrix X6, D-9). TEST-2 (b) pins the `local_source` row.
- **A 0.6.0 process answers a 0.7.0 request as 0.6.0 does.** During a roll, a 0.6.0 replica drops the credential members, accepts URL userinfo, and ignores the declared `username` and `token` keys. The D-2 matrix states each outcome once, and DOC-1 step 4 and DOC-4 reduce it to the operator rules that the matrix lists after its evidence. Where another section's wording differs from a cell, the cell governs.
- **The registration refusals stay above the lookup.** A refusal moved below `lookupLayerForWrite` reads a stored layer. D-13 and CODE-2 step 3 place the refusals.
- **A reported value can itself be refused.** A remote registered as `https://git.acme.com/acme/a%40b c.git` is reported as `https://git.acme.com/acme/a@b%20c.git`, which carries `@` after its host. Sending that value back is refused with `url_credential` before the keep rule runs (D-9). `TestLayerRepoCredential_ReportedValueIsRedactedOnce` pins this outcome.
- **Unknown members are ignored.** `json.Decoder` without `DisallowUnknownFields` drops `force_repo_overwrite`, so an older client that sends it with the reported value has its credential kept (D-9). The CHANGELOG and the HTTP reference say so.
- **`repo_username` needs presence on update.** `json.Unmarshal` into `LayerRegisterRequest` cannot tell an absent `repo_username` from `""`, and the two mean different things on an update (D-4). Read presence from the body, as `decodeVisibilityPatch` does for the visibility members.
- **The declared token is a `yaml.Node`.** yaml.v3 skips a custom unmarshaler on a null node (gopkg.in/yaml.v3 `decode.go:407-409`) and sets a `yaml.Node` field (`decode.go:492-494`), and an unset `${VAR}` expands to the empty string before parsing (`internal/serverboot/yaml_config.go:265-279`), so `token: ${UNSET}` parses as a present null. A `string` field cannot tell that from an absent key.
- **A declaration without the keys is never refused.** 0.6.0 configurations carry credentials, empty userinfo, token-only userinfo, and `[redacted]`-class values in `source.git.repo`. Every D-16 startup refusal therefore sits behind `declaresCredentialKeys`, and no check reads the `repo` of a declaration that sets neither key (D-2 matrix X9, X10).
- **go-git re-encodes the userinfo.** `Endpoint.String` writes the password-only userinfo through `url.PathEscape` (go-git v5.19.2 `plumbing/transport/common.go:169-186`) before net/http builds the header, so only the end-to-end test that runs the real transport pins a token with reserved characters (TEST-4 (a) step 4).
- **The memory-store handler suites say nothing about the SQL columns.** `newGuardHarness` and `layers_test.go` run on `store.NewMemory()`. TEST-2 (g) carries the SQLite evidence.
- **An unconditional rewrite puts an old token back.** An `UPDATE` without the scanned-value conjuncts, or a `PutLayerConfig` of the read config, overwrites a registration or rotation that another replica commits during the start. D-20 and CODE-6 step 2 own the conditional statement, and TEST-6 (c) pins it on both stores.
- **The store open is the wrong place for the rewrite.** `podium admin migrate-to-standard` opens its source through `OpenSQLite` (`cmd/podium/admin_migrate.go:289`). D-20's rejected alternatives place the rewrite.
- **An org schema can lack `repo_userinfo`.** `ensureOrg` adds the column only on a process's first use of the org (`pkg/store/postgres.go:344-381`). The Postgres pass reaches each tenant through `p.org`, so the additive migration runs before the scan (CODE-6 step 2).
- **The local-source table registers credential URLs.** The `register/` arm of `TestLocalSource_RepositoryStrings` (`pkg/registry/server/layer_local_source_test.go:476-489`) posts each `repoCases` row as a `git` registration, and the rows `unparseable`, `hostless-https-url-with-userinfo`, and `https-url-with-userinfo` (`:410`, `:417-418`) are `url_credential` refusals after S6. TEST-2 (ii) rewrites that arm.
- **The username rule is wider than RFC 7617.** A failed clone's transport error renders the URL through net/http's `stripPassword`, which writes the raw username followed by `:***@` (Go `net/http/client.go:1047-1053`), and `RedactCloneError` removes userinfo with a pattern that stops at `/`, whitespace, and `"` (`pkg/layer/source/redact.go:24`). Refusing those characters in a username is what keeps the username out of the `ingest.source_unreachable` message (D-6), and TEST-1 (e) pins the accepted usernames on a refused connection. Narrowing the check to `:` and control bytes reopens the leak.
- **The wire test enumerates request and response names.** `TestLayerEndpoint_RequestAndResponseAgreeOnNames` (`pkg/registry/server/layer_wire_test.go:360`) fails on the new members until its `requestOnly` set changes. It also reflects on `store.LayerConfig` for the response, which is no longer the layer object. Point it at `server.LayerObject`, and make `jsonTagNames` (`:396-411`) recurse into an anonymous struct field with no JSON tag, as `encoding/json` does. Otherwise it reports one member named `LayerConfig`.
- **`repo_credential` reads `CloneRepo()`.** `RegisteredRepo.Present()` is false for a config that holds the registered value whole in `Repo`, which the memory store's map and a handler-built config can do, so a value read from it reports no credential on a row whose clone presents one. The `credentialApplies` gate omits the member on an `ssh://` row, so `Present()` being true for an `ssh://git@host/x.git` login name reaches the member only if the value is computed outside that gate.
- **`credentialApplies` tests the source type.** A `local` layer that 0.6.0 registered can hold a credential URL. Without the `git` conjunct an update admits the credential members on such a layer and the layer object carries `repo_credential` there. D-12 states the reason under "Source type", and CODE-2 step 2 owns the conjunct.
- **Do not add the member to `store.LayerConfig`.** `layer_change_predicates_test.go:95-104` requires every field to be classified, and D-7 and D-21 forbid a store field. `LayerObject` embeds `store.LayerConfig`, so a `MarshalJSON` later added to `store.LayerConfig` would be promoted and drop the member. The `team-web` arm of the `layerObjectMembers` set-equality test reports that (TEST-2 (f)).
- **Rebuild the web bundle.** `web/web.go` embeds `web/bundle`, and CI fails on a stale bundle (`.github/workflows/test.yml:219-235`).
- **Parts of `test/e2e` skip silently on macOS.** Run the end-to-end steps with `-v` and grep the output for `SKIP` before claiming they passed. None of the target files carries a darwin skip today.
- **Line numbers drift.** Anchor each edit by the quoted text, and treat cited line numbers as hints.

## Current state and the gap

### The credential reaches the registry only inside `repo`

§7.3.1 states that `repo` "may carry a credential in the userinfo of its URL" and names no other channel (`spec/07-external-integration.md:128`). The register and update bodies decode into one struct, `LayerRegisterRequest` (`pkg/registry/server/layers.go:726-759`; the register decode at `:1357`, the update decode at `:1230`). Its credential-related members are `Repo` and `ForceRepoOverwrite`, and it has no username, password, or token member.

The update handler applies neither `patch.SourceType` nor `patch.Repo` (`layers.go:1250-1256`, confirmed by the assignments at `:1277-1320`), and §7.3.1 says "An update does not change `repo`". The only API route that sets or rotates a credential is therefore a full re-registration that re-sends the URL. That re-registration rebuilds the record from the request alone (`layers.go:1475-1487`), resets the order and the ingest history, and mints a new webhook secret.

### Reads remove the credential, so the guard exists

Every response reports `repo` with the userinfo removed (`reportedRepo` and `wireLayer`, `layers.go:344-361`). A client that sends back a layer object it read would drop the credential. That is why §7.3.1 carries the `redacted_repo` refusal and the `force_repo_overwrite` member (`spec/07-external-integration.md:130`; `layers.go:755-772` and `:1462-1473`), and why the CLI carries `--force-repo-overwrite` (`cmd/podium/layer.go:240`, `:282`).

### The CLI and the web UI inherit the single channel

`podium layer register` takes the credential only inside `--repo` (`cmd/podium/layer.go:231`, `:258`), and `podium layer update` has no repo or credential flag (`cmd/podium/layer.go:79-93`). The web register form collects the credential in one Repository text field (`web/ui/src/surfaces/RegisterLayerForm.tsx:61`, `:209`, `:338-347`). The update form's `LayerUpdate` type has no repo or credential member (`web/ui/src/api.ts:538-548`; `web/ui/src/surfaces/UpdateLayerForm.tsx:88-101`), so the web UI cannot rotate a credential at all.

Operators hand-assemble the URL and percent-encode reserved characters (`docs/deployment/layers.md:153-162`), and the docs at `layers.md:168` and `:174` tell them to re-send the credential-bearing `--repo` on every re-registration.

### Declared layers carry the same userinfo

A layer declared in `registry.yaml` carries the credential in `source.git.repo`, and `yamlGitSource` has no other credential key (`internal/serverboot/yaml_config.go:231-246`). The boot seed copies the value verbatim (`internal/serverboot/serverboot.go:746`) and re-seeds it through `PutLayerConfig` at every start (`serverboot.go:633-645`). `${ENV_VAR}` interpolation is a raw-byte substitution before YAML parsing (`yaml_config.go:265-279`), so an interpolated token must already be percent-encoded and YAML-safe.

### Proposal 0054 holds the storage split

Proposal 0054 is merged to `main` (`3662db49`). Its spec text is commit `2a427a9a`. The SQLite and Postgres stores write the URL userinfo into `layer_configs.repo_userinfo`, apart from a userinfo-free `repo`. Its D-20 rules out any HTTP member, CLI flag, `registry.yaml` key, or SDK change for 0054 itself. The read rule is `SplitLayerRepo` and `recombineLayerRepo` (`pkg/store/layer_repo.go:55-87`). The write rule is `LayerRepoColumns` (`:113-132`), which returns the bare `repo` and the userinfo, and which refuses, through `registeredLayerRepo` (`:91-101`), a config whose `RegisteredRepo` does not redact to its `Repo`. The SQLite and Postgres writers bind both columns from it (`pkg/store/sqlite.go:826-848`, `pkg/store/postgres.go:1267-1307`), and the memory writer calls `registeredLayerRepo` (`pkg/store/memory.go:459`). Nothing rewrites a stored row's form. `OpenSQLite` and `OpenPostgres` add the column and rewrite no row (`pkg/store/schema_migrate_test.go:197-250`). A row in the whole form takes the two-column form only at its next `PutLayerConfig`, and a soft delete and a restore leave it as it is (`checkLayerRepoEarlierFormRow`, `pkg/store/layer_repo_test.go:351`). A 0.6.0 process reads both forms and writes the whole form with a NULL `repo_userinfo` (`pkg/store/sqlite.go:823-848` at `v0.6.0`).

### The clone needs no change

Verification corrected the premise that an empty username needs an explicit go-git `BasicAuth`. `basicAuthFromEndpoint` returns nil for an empty username (go-git v5.19.2 `plumbing/transport/http/common.go:489-495`), but `Endpoint.String` still writes a password-only userinfo (`plumbing/transport/common.go:169-186`), and net/http turns `req.URL.User` into an `Authorization: Basic` header (`net/http/client.go:251`). A scratch program confirmed that `url.UserPassword(u, t).String()` joined into the URL reaches the wire as exactly `(u, t)` for `("", t)`, for a username containing `@`, and for a token containing `@/:?#%` and a space. Joining the separate members into the stored userinfo therefore works through the unchanged `pkg/layer/source/git.go:48-57`, and neither the `LayerSourceProvider` SPI nor `source.LayerConfig` changes.

### The gap

No client surface takes the repository URL, a username, and a token as separate inputs, and no surface rotates a token without re-entering the URL. This proposal adds those inputs to the HTTP API, the CLI, the web register and update forms, and the declared-layer configuration. 0054's manual scenario is S103 (`proposals/0054-*.md:357-368`, `test/manual-validation.md:11059`), so this proposal rewrites S89 rather than adding a scenario ID.

## Decisions

- **D-1. Relationship to proposal 0054.** This proposal exposes 0054's storage split to clients. It keeps 0054's §7.3.1 storage sentences verbatim, from "Where the registered value parses as a URL" through "In this section the stored `repo` is the registered value, in whichever form the store holds it." 0054's D-20 bound 0054 alone, and this proposal deliberately adds the HTTP members, CLI flags, and `registry.yaml` keys it excluded. It also replaces the part of 0054's D-2 that kept the `redacted_repo` guard, `force_repo_overwrite`, and `--force-repo-overwrite`. 0054 is merged to `main` at `3662db49`, and this proposal is based on that commit. It replaces 0054 D-1's rule that an existing row takes the new form at its next write with the start-time rewrite of D-20. It also amends the §13.4 paragraph that 0054 added in `57ee3b63`, which exempted a change of stored form from any start-time rewrite (SPEC-5).
- **D-2. Release vehicle: 0.7.0, a MINOR.** Refusing URL userinfo on a registered `http` or `https` `repo`, which breaks existing scripts, and removing `force_repo_overwrite` and `--force-repo-overwrite` are backward-incompatible. Under `.claude/rules/code-best-practices.md` they land in a MINOR bump with no compatibility shim, legacy flag, or dual code path. The stored form is the one 0054 writes, so 0054's rollback floor of 0.6.0 is unchanged and this proposal adds none. Every 0.7.0 start whose listener binds rewrites stored rows into that form (D-20), so a store reaches the floor at the first such start rather than at a row's first 0.7.0 write. The floor governs the store. It does not settle how a 0.6.0 process reads a request or a configuration written for 0.7.0. The matrix below states every cross-version outcome. The preamble, D-9, the edge-case rows, DOC-1 step 4, and DOC-4 cite its cells as `X<n>-0.6.0` or `X<n>-0.7.0` where they state one, and the cell governs where another section's wording differs.

- **D-3. Wire members.** The register and update bodies gain `repo_username` (string), `repo_token` (string), and `clear_repo_credential` (boolean), and `force_repo_overwrite` is removed from `LayerRegisterRequest`. The names carry the `repo_` prefix because the layer object and the bodies are flat and the credential belongs to `repo`. The name `repo_token` was chosen over `password` because most supported providers issue a token. The documentation states that it carries a password where the provider issues one, as AWS CodeCommit does. The layer object gains the response member `repo_credential` (boolean, D-22). It takes the `repo_` prefix for the same reason, and it names the thing `clear_repo_credential` removes.
- **D-4. Username semantics.** On a registration, an omitted or empty `repo_username` is an empty username. On an update that carries `repo_token`, a present `repo_username`, the empty string and JSON `null` included, sets the username, and an omitted one keeps the username of the stored credential where that credential is written as `<username>:<token>`, and is the empty username otherwise. A stored username the D-6 rule refuses cannot be kept: a row an earlier release stored inside `repo`, such as `https://a%3Ab:tok@git.acme.com/acme/x.git`, decodes to the username `a:b`, so an update that carries `repo_token` and omits `repo_username` on such a row is refused with `400 registry.invalid_argument` and a message naming `repo_username`, and the operator sends a username with the token. Falling back to an empty username was rejected, because it reports success and the next clone fails for every provider that checks the username. A non-empty username is preserved and presented exactly as sent, with no trimming, defaulting, or case folding. The registry supplies no default username, because a default that fits one provider breaks another. The provider set this covers: GitHub and GitLab personal access tokens (any non-empty username), GitHub App installation tokens (`x-access-token`), GitLab deploy tokens (the generated username), Bitbucket API tokens (the account username or `x-bitbucket-api-token-auth`), Bitbucket access tokens (`x-token-auth`), Azure DevOps personal access tokens (empty username), and AWS CodeCommit (the IAM Git username). Keeping the stored username on an update follows the §7.3.1 patch convention that an omitted member keeps its stored value, and it protects the web edit dialog, which shows whether a credential is stored (D-22) but never its username.
- **D-5. Token semantics.** `repo_token` is required to set a credential and is never empty. A non-empty `repo_username` without `repo_token` is refused, so a username cannot be changed without re-sending the token. A present empty `repo_username` without a token has no effect. The form that puts the token in the username with no password (`https://<token>@host`) cannot be written through the members, because every listed provider accepts the token as the password. A stored row in that form keeps working. At its next rotation it holds no stored username under D-4, so it takes the `<username>:<token>` form with the username the request names, or an empty one.
- **D-6. Member validation.** A request is refused with `400 registry.invalid_argument` when its username contains `:`, `/`, `"`, or a space, or when its username or token contains a control character. RFC 7617 excludes `:` and control characters from a basic credential, and a `:` in the username would be split into the password on the wire. `/`, `"`, and the space are refused so that the username stays out of a failed clone's message (D-14). On a transport-level failure, such as a refused connection, go-git returns net/http's `*url.Error` unwrapped (go-git v5.19.2 `plumbing/transport/http/common.go:71-87`), and net/http renders the URL with the raw, unescaped username followed by `:***@` (Go `net/http/client.go:1047-1053`). `RedactCloneError` removes userinfo with the pattern `([A-Za-z][A-Za-z0-9+.\-]*://)[^/\s"]*@` (`pkg/layer/source/redact.go:24`), which stops at `/`, ASCII whitespace, and `"`, so a username such as `acme ci` or `acme/ci` would reach the `ingest.source_unreachable` message. TEST-1 (e) drives that path with a member-built `user:token` credential against a refused connection, and TEST-2 (c) pins the refusal of `acme ci/bot`. Tabs and the other ASCII whitespace bytes are control characters. Extending `RedactCloneError` to remove the known username was rejected, because it changes `RedactCloneError`'s redaction for every scheme, and no listed provider issues a username with these characters. The message names the member and carries no part of either value. These refusals carry no `details.constraint`, on the precedent of the `force_push_policy` and `git_provider` format refusals.
- **D-7. Storage reuses 0054 with no new column, store field, or SPI change.** The registry percent-encodes the members with `url.UserPassword(username, token).String()` and joins the result into the userinfo of `repo` with `repourl.Join`. The result is the registered value, held exactly as 0054 holds a URL-userinfo registration: `LayerConfig.RegisteredRepo`, the `repo_userinfo` column on SQLite and Postgres, and the memory map. `CloneRepo`, `reportedRepo`, `layerConfigEqual`, `LayerRepoColumns`, `pkg/layer/source/git.go`, and the `LayerSourceProvider` SPI are unchanged. An empty username needs no explicit `BasicAuth`, because go-git and net/http send the header from the URL ("The clone needs no change", above).
- **D-8. URL userinfo in an `http` or `https` `repo` is refused.** A registration whose `repo` is an `http` or `https` URL carrying userinfo, an empty userinfo included, is refused with `400 registry.invalid_argument` carrying `details.constraint: "url_credential"`. So is a registration whose `repo` §7.3.1 would report as `[redacted]`: a schemed value that does not parse, whatever its scheme, or an `http` or `https` value with `@` after its host. The refusal reads no source type, for the reason D-12 states under "Source type". The message carries no part of the `repo`. For an `http` or `https` `repo` it names `repo_username` and `repo_token`, on every source type; those members apply only once the registration names a `git` source (D-12). For any other scheme it states that the `repo` does not parse as a URL, because D-12 refuses the members on such a `repo`. Such a value already fails to clone, because go-git's `NewEndpoint` falls through to `parseURL`, which returns the `url.Parse` error (`plumbing/transport/common.go:209-225`), so refusing it at registration breaks nothing that worked. Accepting userinfo as today, and refusing it only when the members are present, were both rejected, because both keep two channels for one concern. A newly registered layer therefore never reports `[redacted]`. Other schemes keep accepting userinfo in `repo`, such as `ssh://git@host/x.git`, where the userinfo is a login name.
- **D-9. The guard becomes a keep rule.** The `redacted_repo` refusal, `force_repo_overwrite`, and `--force-repo-overwrite` are retired. A `register` request is kept to the stored remote when every condition holds:
  - its ID names a stored layer, a soft-deleted one inside its recovery window included;
  - the stored source type and the request's source type are both `git` (D-12, Source type);
  - the stored `repo` is an `http` or `https` URL carrying userinfo, an empty userinfo included, or a value reported as `[redacted]`;
  - the request's `repo` equals, byte for byte, the value a read reports for the stored `repo`;
  - the registration resolves to the stored layer's class and, for a user-defined layer, to its stored owner;
  - it carries neither `repo_token` nor `clear_repo_credential: true`.

  A kept request stores the stored registered value with its credential in place of the reported value it carries. A request carrying the reported value that resolves to another class, or on a user-defined layer to another owner, and carries no `repo_token`, stores the carried `repo` with no credential. An admin-defined layer's owner is a body field that names no authorized subject, so a change of that owner alone does not prevent the keep. A tenant admin may re-register a user-defined layer (`layers.go:413-420`), and without this clause an admin who re-registers alice's personal layer as an admin-defined public one would inherit alice's personal token. A request naming a different remote that omits `repo_token` stores no credential, so a stored credential is never presented to another host; 0054 records this hazard (`proposals/0054-*.md:544`). A stored `ssh://git@host/x.git` is outside the keep, so a registration carrying `ssh://host/x.git` stores that value as sent. 0.6.0 refused that registration with `redacted_repo` (`redactedRepoResubmitted`, `pkg/registry/server/layers.go:768-772` at `v0.6.0`; D-2 matrix X7-0.6.0), and in 0.7.0 it succeeds and drops the login name. go-git then uses the registry process's operating-system user name for an empty SSH user (go-git v5.19.2 `plumbing/transport/ssh/auth_method.go:185-192`, reached through `DefaultAuthBuilder(c.endpoint.User)` at `plumbing/transport/ssh/common.go:250`), so a remote that expects `git` fails the next ingest. DOC-1 step 1 states this change and tells the operator to re-register such a layer with the full `ssh://` `repo`, login name included. DOC-3 step 2 links to that statement, and DOC-4 records the change. A `repo` of `[redacted]` resolves to go-git's file transport (`pkg/registry/server/layer_capabilities.go:75-84`), so the local-source rule, which runs before the keep, refuses that re-registration from the owner of a user-defined layer whom the layer write rule admits and the admin arm does not. The layer write rule runs first (`layers.go:1408-1411`) and refuses with a bare `403 auth.forbidden` every caller it does not admit (D-2 matrix X6). A registry started with no identity provider configured, or one started in public mode, admits every caller on the admin arm (§7.3.1), so neither rule refuses that re-registration there. Without that scoping no request could store the reported value over such a row, because D-12 refuses `clear_repo_credential` on a non-`http` remote. The keep does not reach a reported value that itself falls in the D-8 class: `https://git.acme.com/acme/a%40b c.git` is reported as `https://git.acme.com/acme/a@b%20c.git`, and sending that back is refused with `url_credential` before the keep is evaluated (D-13). The update endpoint changes such a layer's credential without the URL. JSON decoding ignores unknown members, so an older client that sends `force_repo_overwrite: true` with the reported value has the credential kept. `register` stays a full replacement in every other respect: it resets the order, the registration time, and the ingest history, and mints a new webhook secret.
- **D-10. Clearing is an explicit boolean.** `clear_repo_credential: true` stores no credential. On an update it removes the stored credential. On a registration it stores the carried `repo` without one and opts out of the keep rule, which makes it the one-call successor to `--force-repo-overwrite`. Treating an empty `repo_token` as the clear signal was rejected, because the §7.3.1 patch semantics read an empty source member as "leave", and the web update form sends every field it holds on each submit. The boolean mirrors `rotate_webhook_secret` and the CLI's `--clear-groups`. A request carrying `repo_token` together with `clear_repo_credential: true` is refused.
- **D-11. Update rotates the credential without the URL.** An update carrying `repo_token` replaces the stored credential. The new registered value is the stored registered value with its userinfo and `@` removed byte for byte (`repourl.WithoutCredential`, which is `repourl.Split(...).Bare` or the stored value when it has no userinfo), joined with the new userinfo. The username follows D-4. An update carrying `clear_repo_credential` stores that base, and an update carrying neither keeps the stored credential. An update never changes the remote, so "An update does not change `repo`" becomes a statement about the remote. The handler sets `cfg.Repo` and `cfg.RegisteredRepo` from `store.SplitLayerRepo(registered, sql.NullString{})`, so `Repo == Split(RegisteredRepo).Clean` holds and 0054's `LayerRepoColumns` accepts the write (its `registeredLayerRepo` check, `pkg/store/layer_repo.go:95-98`, called at `:114`).
- **D-12. Applicability.** This decision is the one definition of where the credential members apply. Every other section cites it as "the D-12 rule" or by a consumer number below. A change to the rule is made here, in `credentialApplies` (CODE-2 step 2), and in each consumer it affects.

  **Rule.** `repo_token`, a non-empty `repo_username`, and `clear_repo_credential` apply where `credentialApplies(sourceType, repo)` holds: the source type is `git`, and `repo` is an `http` or `https` URL that §7.3.1 does not report as `[redacted]`. The `repo` half is `repourl.TakesCredential` (CODE-1 step 3), and `credentialApplies` adds the source type (CODE-2 step 2).

  **Inputs.**
  - On a registration: the request's `source_type` and the `repo` it carries.
  - On an update, and for `repo_credential`: the stored source type and the stored registered `repo`, read through `CloneRepo()`.
  - For a declaration: `git` and the declared `source.git.repo`.

  An update never changes the result for its layer, because `source_type` is immutable on update, an update changes only the userinfo of the remote (D-11), and `TakesCredential` ignores the userinfo. The D-20 rewrite changes only the stored form, which `CloneRepo()` reads through. A registration and each start's declared seed are the only writes that change the inputs.

  **Source type.** The register handler stores the carried `repo` on every source type (`pkg/registry/server/layers.go:1475-1487`), as 0.6.0 did (`:1479` at `v0.6.0`), so a stored `local` layer can hold an `http` or `https` credential URL. No source presents such a `repo` to a remote: only the `git` source reads `repo` (`pkg/layer/source/git.go:40-60`), the reingest runner builds a provider for `git` and `local` alone (`internal/serverboot/reingest.go:135-144`), the `local` provider reads the path alone (`pkg/layer/source/local.go:22-36`), and the webhook ingest refuses a non-`git` layer (`pkg/registry/server/webhook_ingest.go:53-56`). D-8 therefore refuses a credential URL on a new registration of any source type: a refusal scoped to `git` would let a `local` registration store one, and refusing it on another source breaks nothing that worked. The `git` conjunct keeps a stored one out of every consumer below, and the keep rule requires `git` as the stored source type and as the request's (D-9), so a credential never moves between a `git` and a non-`git` layer. A credential an earlier release stored on a non-`git` layer is therefore inert: the members are refused on it, the layer object omits `repo_credential`, and a re-registration of the layer, which the keep rule does not reach, replaces it. The D-20 rewrite reads no source type and splits such a row like any other, which moves the userinfo between two columns and presents it nowhere. No other section restates this reason.

  **Consumers.** The list is exhaustive. Each consumer is specified at the site named, and that site cites this decision.
  1. The register and update refusal, `repoCredentialError` (CODE-2 steps 2 to 4). A request that carries `repo_token`, a non-empty `repo_username`, or `clear_repo_credential: true` where the rule does not hold is refused with `400 registry.invalid_argument`, no `details`, and a message naming the member. A request that carries none of them, a present empty `repo_username` included, is not refused on this ground.
  2. The layer object (D-22). `wireLayer` calls `credentialApplies` with the stored inputs and carries `repo_credential` exactly where the rule holds, so the member's presence is the rule's update half as the registry evaluates it.
  3. The keep rule (D-9), which requires `git` as the stored source type and as the request's. Its stored-`repo` condition, a URL credential or a `[redacted]`-class value (`repourl.CarriesURLCredential`), is its own: it reaches a stored `[redacted]`-class value, which the rule excludes, so that a reported `[redacted]` can be sent back.
  4. The declared keys (D-16, CODE-3). A declaration that sets `username` or `token` on a `repo` where the rule does not hold aborts startup. The start log line for a declared URL credential fires where neither key is set, the rule holds for the declared `repo`, and that `repo` carries userinfo. The seed calls `repourl.TakesCredential` directly, because a declared `source.git` block is a `git` source.
  5. The web edit dialog (D-19, CODE-5 step 4). It renders the Username and Token pair on a layer whose object carries `repo_credential`, so it reads the rule from consumer 2 and evaluates no pattern over `repo`. The register dialog and the CLI evaluate only the rule's source-type conjunct, through the selected arm (consumer 8), and they report the consumer-1 refusal for the `repo` half.
  6. D-2 matrix X5 states the 0.6.0 and 0.7.0 outcomes of a member where the rule does not hold.
  7. `repourl.WithCredential` returns `ErrCredentialRemote` for a `bare` that `TakesCredential` rejects. Every caller applies the rule first, so that return is a guard.
  8. The client-side source-type gates. `podium layer register` refuses `--repo-username`, `--repo-token-file`, and `--clear-repo-credential` without `--repo` with exit 2 before any request (D-18, CODE-4 step 3), and the register dialog sends `repo_username` and `repo_token` only on the git arm (D-19, CODE-5 step 3). Only the `--repo` arm and the git arm send `source_type: "git"` (`cmd/podium/layer.go:258-260`, `web/ui/src/surfaces/RegisterLayerForm.tsx:208-211`), so each gate applies the rule's `git` conjunct through the selected arm and leaves the `repo` half to consumer 1. `podium layer update` and the edit dialog name a stored layer and carry no copy of the conjunct.

  D-8's `url_credential` refusal reads `repourl.CarriesURLCredential` and no source type, and the D-20 rewrite reads 0054's split class. Neither reads this rule.

  - A pattern over the reported `repo` in the edit dialog. It is a second implementation of the rule in another language, and no test can pin it against `credentialApplies`. The pattern `/^https?:\/\//i` hid the pair on a legacy `http` or `https` value with userinfo and no host, which a read reports as `https:` (`internal/repourl/repourl_test.go:39`) and the rule admits. - **D-16. Declared layers.** The `registry.yaml` `source.git` block gains `username` and `token` keys with the rules of `repo_username` and `repo_token`. `token` is meant to be written as `${ENV_VAR}` (§13.12, `spec/13-deployment.md:646`). The operator writes the value unencoded, and a token containing a YAML-significant character is quoted. The `token` field is decoded as a `yaml.Node` so that presence survives a null. A declaration sets a key when `username` is non-empty or the `token` node is present.

Where the D-12 rule holds for that `repo` and it carries userinfo, an empty userinfo included (D-12 consumer 4), each start logs `declared git layer <id> carries URL userinfo in source.git.repo; declare its credential in source.git.username and source.git.token`. The line names no part of the `repo` or the credential. The registry cannot rewrite the operator's file, so the line repeats at every start until the declaration changes. The registry cannot tell an entry written for 0.6.0 from one added for 0.7.0, so a new entry in this form is accepted on the same terms, and the log line steers it to the keys.

  Two alternatives were rejected. The first was splitting such a `repo` into a username and a token and seeding it as if the keys had been declared. go-git decodes the userinfo and re-encodes it before net/http builds the header (go-git v5.19.2 `plumbing/transport/common.go:169-186`), so every value the split could rejoin reaches the remote as the same pair the whole value sends. The forms 0.6.0 accepted that the key rules refuse would need a fallback to the whole value anyway: a token in the username with no password (`https://<token>@host`, D-5), an empty userinfo, and a percent-encoded username the D-6 rule refuses. The second was refusing the form only for a declared ID with no stored row. That breaks a fresh or recovered database started from an existing configuration.

  A declaration that sets a key aborts startup, with an error that names the layer and the key and carries no part of the `repo` or the credential, in these cases:
  - the D-12 rule does not hold for the `repo` (D-12 consumer 4);
  - the `repo` is an `http` or `https` URL that carries userinfo of its own, an empty userinfo included. Here the error names `source.git.repo`, because the registry cannot tell which credential the operator meant;
  - the `token` node is not a scalar;
  - `token` is present and empty or null, which catches an unset environment variable;
  - `username` is set without a token;
  - `username` or `token` fails the D-6 rule.

  Every startup refusal therefore requires a key 0.6.0 does not read, and 0.7.0 refuses no configuration that 0.6.0 starts on because of its `repo` (D-2 matrix X9, X10). The seed joins the keys into `lc.Repo` as D-7 describes, and 0054's write rule splits it. A declared URL credential is seeded as declared and is not held to the D-6 rule, so a username in it that D-6 refuses can reach the `ingest.source_unreachable` message of a failed clone, as it can on 0.6.0 and for a row an earlier release stored with such a username.

Declared precedence.** The declaration is authoritative for the credential, on the same footing as visibility (`spec/07-external-integration.md:140`) and `git_provider` (`serverboot.go:756-758` re-seeds an omitted key as empty). Preserving a stored credential when the declaration omits one was rejected: it contradicts "the declaration is authoritative for the fields it carries" as the seed implements it, and it leaves an operator unable to remove a credential through the configuration. Nothing in `pkg/registry/server` records which layers are declared, so an update does not refuse a credential change on a declared layer.
- **D-18. CLI.** `podium layer register` and `podium layer update` gain `--repo-username <name>`, `--repo-token-file <path|->`, and `--clear-repo-credential`, and `--force-repo-overwrite` is removed. `--repo-token-file -` reads standard input. The CLI refuses each of the following with exit 2 before sending: a non-empty `--repo-username` without `--repo-token-file`; `--repo-token-file` together with `--clear-repo-credential`; on `register`, any credential flag without `--repo`, which applies the source-type conjunct of the D-12 rule on the client (D-12 consumer 8); and an empty or unreadable token file. `repo_username` is sent together with `repo_token` whenever `--repo-username` is set, the empty string included, using the `setFlags` presence helper (`cmd/podium/admin_tenant.go:55`).

Web UI.** On the git arm, `RegisterLayerForm` gains an optional Username field and an optional Token field rendered as `type="password"` with `autoComplete="new-password"`, so the browser does not autofill the reader's own site password into it. The register dialog has no stored layer to read a gate from, so it evaluates only the source-type conjunct of the D-12 rule, through the selected arm: it sends the pair on the git arm alone (D-12 consumer 8). The web UI holds a reused ID (`RegisterLayerForm.tsx:576-588`), so the D-9 keep rule is reached only through the API and the CLI.

That is the form the row's next write would take, so the rewrite adds no class:
  - A value the write rule splits is split, an `ssh://` login name included.
  - A value the write rule holds whole, beside a NULL `repo_userinfo`, is already in that form and is not written. This covers an scp-like remote, a path, a userinfo-free URL, and a `[redacted]`-class value.
  - A `repo_userinfo` that the read rule ignores is set to NULL, and the `repo` beside it is unchanged. This covers a column beside one of the values the write rule holds whole, such as the earlier credential that a 0.5.2 Postgres re-registration to an scp-like remote or a path leaves (X12). Under §13.4 this is a change of stored form (SPEC-5): it records no completion, appends no §8.1 event, and needs no `sign-stored-rows` run.

  The rewrite runs at every start, with no completion record, because a 0.6.0 replica writes the whole form during a roll and after a rollback. A converted row is a fixed point (0054 `TestLayerRepoColumns_RoundTrip`), so a later start writes nothing. - **D-22. Credential-presence member.** This resolves Q-1 of the draft in favor of the member.

  **Definition.** A layer object carries the boolean `repo_credential` where the D-12 rule holds for the layer's stored source type and stored registered `repo`, read through `CloneRepo()` (D-12 consumer 2), and omits it on every other layer. Its presence is therefore D-12's update applicability as the registry evaluates it. Where carried, it is true when that `repo` carries userinfo, an empty userinfo included, and false otherwise. Its presence is exactly the condition under which an update carrying `clear_repo_credential` is not refused under D-12, and its value is exactly the condition under which that update changes the stored `repo`, so the web UI offers no credential control the registry refuses or ignores.

  **Why it reads the registered value.** Where the member is carried, its value comes from the registered value in whichever form the store holds it, so a `git` row on an `http` or `https` remote outside the `[redacted]` class that an earlier release stored with URL userinfo reports true whether or not the D-20 rewrite has reached it. The read rule's handling of `repo_userinfo` applies unchanged (`pkg/store/layer_repo.go:71-87`), and the D-12 rule reads its result through `CloneRepo()`:
  - An X12 stale credential on an `http` or `https` remote reports true, which is what the next clone presents.
  - An X13 cleared column on an `http` or `https` remote reports false.
  - An X12 or X13 row on an `ssh://` or other non-`http` remote omits the member, because the D-12 rule does not hold for its `repo`. A non-`git` row that an earlier release stored with URL userinfo omits it too (D-12, Source type).
  - A column value the read ignores, such as one beside an scp-like `repo`, omits the member, because the D-12 rule does not hold for an scp-like `repo`.

  **Implementation.** `wireLayer` reads `r := cfg.CloneRepo()`. When `credentialApplies(cfg.SourceType, r)` holds, it sets the member to `repourl.CarriesURLCredential(r)`. Otherwise it leaves the member unset, and the `omitempty` tag omits it. `repoCredentialError` calls the same function, so the refusal and the member read one expression, and its source-type conjunct is the one D-12 states under "Source type". `RegisteredRepo.Present()` is rejected, because it is true for an `ssh://` login name and false for a config holding the registered value whole in `Repo`. No store field holds the member, so `layerConfigEqual`, `wakesWatchers`, and the §8.1 events are unchanged: a change of the member alone records what D-15 states and wakes nothing. The member discloses presence, and no part of the credential, to every caller the layer read returns the layer to, on the footing of `repo` itself.

  **Consumers.**
  - `podium layer list` prints the response body (`cmd/podium/layer.go:317-341`), so it reports the member with no CLI change.
  - The web layer panel marks a git row whose member is true.
  - The edit dialog renders the Username and Token pair on a layer that carries the member, and the removal checkbox on a layer whose member is true (D-19), so a first credential can be set on a layer whose member is false (X2, X13).
  - A client reads an absent member as a layer whose update takes no credential member, which is also what a 0.6.0 replica's response means, because 0.6.0 drops the members (X4, X17).

## Spec amendment: §7.3.1 Repository credentials, and setting, replacing, and removing a repository credential

**SPEC-1.** `spec/07-external-integration.md`, §7.3.1. Three edits, in one commit with SPEC-2 and SPEC-3.

**Rationale.** The paragraph names URL userinfo as the only credential channel, and it says that a registration that reuses an ID supplies the full credential-bearing `repo`. This proposal changes both statements. The storage sentences 0054 landed stay verbatim, so 0054's store rule is unaffected (D-1, D-7). 0054's sentence "A registration accepts that value and retains it unchanged, and the ingest clones with the registered value." is the only definition of "registered value" in the spec, so the replacement restates the term before the storage sentences that use it.

**Edit 1, the credential paragraph.** Anchor: the paragraph that begins "**Repository credentials.** A `git` layer's `repo` may carry a credential in the userinfo of its URL". The current text is the paragraph 0054 landed in `2a427a9a` (`spec/07-external-integration.md:128`). Replace the whole paragraph with:

> **Repository credentials.** A `git` layer whose `repo` is a URL with the scheme `http` or `https` takes its repository credential, a username and a token, through the `repo_username` and `repo_token` members of the registration and update bodies, apart from `repo`, under the rule on setting, replacing, and removing a repository credential below. The registered value of a `git` layer is the `repo` its registration carries, with the credential that registration carries held as the URL userinfo of that value, `<username>:<token>` percent-encoded and followed by `@` after the first `://`, so that the remote receives the username and the token exactly as sent. Where the re-registration rule below applies, the registered value is the stored one. A `repo` with another scheme may carry userinfo of its own, such as the login name in `ssh://git@git.acme.com/acme/x.git`, and that userinfo is part of the registered value. A layer registered while a registration accepted a credential inside `repo` holds that credential as the URL userinfo of its registered value, and the rule below replaces and removes it on the same terms as one set through the members. The ingest clones with the registered value. ### CODE-1. `internal/repourl`: credential join, applicability, and refusal predicates

Targets: `internal/repourl/repourl.go`.

**Rationale.** The registry handler and the declared-layer seed apply one rule for which `repo` takes a credential, which `repo` is refused, and how the members become userinfo. `internal/repourl` already owns the classifier the store and the git source share (`repourl.go:1-6`), and its only importers are `pkg/store` and `pkg/layer/source`. Putting the rule there avoids a second copy in `pkg/registry/server` and `internal/serverboot`. 0054 left `internal/repourl/repourl.go` unchanged, and its `pkg/store/layer_repo.go` calls the same `Split` and `Join`, so CODE-1 builds on them as they stand on `main`.

1. Rewrite the package doc comment at `repourl.go:1-6`: the package classifies a layer's repo value and builds the userinfo of a credential taken from separate members, and the store, the git source, the registry layer handler, and the declared-layer seed share it so they apply one class rule.
2. Add the sentinels `ErrCredentialRemote`, `ErrCredentialUsername`, and `ErrCredentialToken`, each created with `errors.New` and a message that names the failed condition and carries no value.
3. Add `TakesCredential(repo string) bool`. It returns true when `parseRepo` reports the value safe and returns a URL whose scheme is `http` or `https`. `url.Parse` lowercases the scheme, so `HTTPS://` qualifies. The value's own userinfo does not affect the answer, so the update path can test the stored registered value.
4. Add `CarriesURLCredential(repo string) bool`. It returns true when `parseRepo` reports the value unsafe, and true for an `http` or `https` URL whose `User` is non-nil, which covers `https://@h/x`. Its doc comment states that the class is the whole `[redacted]` class whatever the scheme, so it includes a schemed value of any scheme that `url.Parse` rejects, such as `ssh://git@host:org/x.git`, and that a caller tells that sub-case apart with `Unsafe` and the scheme.
5. Add `WithoutCredential(repo string) string`. It returns `Split(repo).Bare` when `Split` succeeds and `repo` otherwise. Its doc comment names its one caller, the update handler's rotation and clear path in `pkg/registry/server/layers.go`.
6. Add `CredentialUsername(registered string) string`. It returns `u.User.Username()` when the registered value parses with userinfo that carries a password (`u.User.Password()` reports true), and the empty string otherwise. A legacy `https://<token>@host` value therefore holds no username (D-4, D-5).
7. Add `WithCredential(bare, username, token string) (string, error)`:
   - `ErrCredentialRemote` when `TakesCredential(bare)` is false or `bare` carries userinfo of its own;
   - `ErrCredentialUsername` when `username` contains `:`, `/`, `"`, a space (`0x20`), or a byte below `0x20` or equal to `0x7f`, with a comment that names the `RedactCloneError` pattern as the reason for `/`, `"`, and the space (D-6);
   - `ErrCredentialToken` when `token` is empty or contains a byte below `0x20` or equal to `0x7f`;
   - otherwise `Join(bare, url.UserPassword(username, token).String())`.

   After the join it confirms that `Split(joined)` succeeds with `Bare == bare`, and returns `ErrCredentialRemote` when it does not. That branch cannot run, because `url.UserPassword(...).String()` escapes `@`, `/`, `?`, `#`, `:`, `%`, and space, and `Join` inserts after the first `://`, which `schemeRE` guarantees is the scheme separator. It carries a comment that says so, on the precedent of the 0054 D-13 self-check.

## Non-goals

- SSH key authentication. An scp-like or `ssh://` remote keeps cloning through go-git's ambient SSH auth on the registry host (`pkg/layer/source/git.go:48-56` sets no `Auth`). The credential members do not apply to such a remote, and its URL userinfo, a login name, is accepted as today.
- Bearer-header-only authentication, such as Azure DevOps with a Microsoft Entra ID access token. A static basic credential cannot carry it.
- Short-lived credentials that need refresh, such as GitHub App installation tokens and AWS temporary credentials through `git-remote-codecommit`. An operator rotates a short-lived token on a schedule with `podium layer update --repo-token-file -`, and the registry mints and refreshes nothing.
- An explicit go-git `BasicAuth`, or any change to `pkg/layer/source/git.go`, `source.LayerConfig`, or the §9.1 `LayerSourceProvider` SPI. The joined userinfo reaches the remote unchanged, and 0054 D-10 already rejected `BasicAuth` because of its same-host redirect behavior.
- Encryption of the credential at rest (0054 D-3).
- Changing the remote through `update`. A different repository URL still requires a re-registration.
- Refusing or altering URL userinfo on schemes other than `http` and `https`, apart from the `[redacted]` class D-8 refuses.
- Validating a credential against the remote at registration or update. Neither operation ingests, and a wrong credential surfaces as `ingest.source_unreachable` at the next ingest.
- An SDK surface. Neither podium-py nor podium-ts has a layer-registration or layer-update call.
- Recording in the §8.1 audit fields which member an update changed.
- A terminal prompt with echo disabled for the token. `--repo-token-file -` reads standard input, and no new dependency is added.
- A `podium layer update` line or member-mapping flags in the §7.3.1 Layer CLI block, which names neither for any member today.

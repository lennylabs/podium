# Proposal 0068: Carry a skill's string-valued Podium fields under SKILL.md metadata, and serve the resolved values on every read path

- Issue: (to be filed)
- Status: Applied to spec (2026-11-15). Verified after 4 adversarial review rounds (2 findings fixed).
- Date: 2026-11-15

This document stages spec, code, test, manual-validation, and documentation changes. It does not modify any spec, code, test, or doc file. Apply the changes in the staged sections after sign-off. The change reverses maintainer decision D2.5 and the matching non-goal of proposal 0058 (see "Relationship to D2.5 and proposal 0058"; the maintainer confirmed the reversal on 2026-11-15). It is backward-incompatible: `SKILL.md` `metadata` keys that Podium ignored become meaningful, and a stored row that carries them changes the values a load serves while its search columns keep the values the earlier release stored (D-9). It ships in a MINOR release.

Proposal numbering note: SPEC-3 was dropped in review, and its reasons are recorded under Non-goals. SPEC-2 Edit 5 was removed in Redesign 1, and the §4.7 edit that SPEC-2 gained in its place is numbered Edit 6 for the same reason. SPEC-2 Edits 3 and 4, CODE-5, CODE-6, and checklist steps S6 and S7 were removed when the maintainer chose the §13.4 exemption of D-9 over a stored-row rewrite, and Edit 6 now states the §4.7, §4.7.4, and §4.7.6 exceptions for a row that an earlier release stored. SPEC-2 Edit 7, the §13.2.2 and §13.10 public-mode sentences, continues that numbering. The remaining identifiers keep their numbers so the review record stays traceable.

## Summary

**What changes.**

- **Spec §4.3.4, §4, §4.3, and the quickstart (SPEC-1, SPEC-4).** `SKILL.md` `metadata` can carry `when_to_use`, `tags`, `sensitivity`, `search_visibility`, `deprecated`, `replaced_by`, and `release_notes` as strings in fixed encodings. An `ARTIFACT.md` value takes precedence when `ARTIFACT.md` states the key. Lint warns on a value that does not follow its encoding and errors on a stated `ARTIFACT.md` value that differs from a decoded `metadata` value. The overview sentences that place every Podium-only field in `ARTIFACT.md` follow.
- **Spec §13.4, §4.7, §13.2.2, and §13.10 (SPEC-2).** Stored-row admission serves the resolved fields for every skill row, a plain skill included. The tags, sensitivity, search visibility, and deprecation flag of a skill row that an earlier release stored are exempt from the §13.4 rewrite rule. No release-time rewrite recomputes them, and every reader that does not admit the row, search and `latest` resolution included, reads them as stored. Search and load can therefore disagree for such a row until the skill is published at a new version. §4.7, §4.7.4, and §4.7.6 state the matching exceptions for such a row's vector, its place in default search, and `latest`. §13.2.2 and §13.10 state that a public-mode registry also serves such a row at the sensitivity its `SKILL.md` `metadata` resolves to, even when the earlier release stored it while public mode was enabled.
- **Spec §6.5, §7.3.2, and §8.1 (SPEC-5, SPEC-6).** `artifact.deprecated` fires on a skill's resolved `deprecated` value. The `podium-mcp` content cache gains a stated exception: a record cached under a release that resolved these fields differently keeps its cached sensitivity and delivery record until the cache drops it.
- **`pkg/manifest`, `pkg/lint`, the walk, and ingest (CODE-1, CODE-2, CODE-3).** One resolver, `manifest.ResolveSkillFields`, replaces `ResolveSkillVersion`. The filesystem walk and ingest call it through `ArtifactRecord.ResolveSkillFields`, and lint gains the ignored-value warning, the metadata mismatch check, and the revised Podium-only diagnostic.
- **Admission (CODE-4).** `pkg/registry/core` admission resolves from the admitted bytes through `manifest.ResolveStoredSkill`. No store method, data-migration marker, or start-time pass is added (D-9).
- **SDK overlays and the scaffold (SDK-1, CODE-7).** The TypeScript and Python workspace overlays read `metadata.tags` of a skill with no `ARTIFACT.md` when the value is in one restricted single-line form, and a Go-generated corpus pins both SDKs to Go's decoding. `podium artifact scaffold --type skill` writes `--tags`, `--sensitivity`, and `--when-to-use` under `metadata` instead of refusing them.
- **Tests, manual validation, and docs (TEST-1, TEST-2, MV-1, DOC-1).** Unit, integration, and end-to-end tests pin the encodings, precedence, lint, admission, the stored-row exemption, and the scaffold, and a corpus generated from `manifest.ResolveStoredSkill` pins the SDK overlay tag reading. `test/manual-validation.md` gains S107 and edits S01, S17, S18, and S19. The authoring, reference, getting-started, deployment, and upgrade-notes pages, the README, and the CHANGELOG follow.

**Fixed decisions.**

- D-1: the metadata-eligible set is `when_to_use`, `tags`, `sensitivity`, `search_visibility`, `deprecated`, `replaced_by`, and `release_notes`. `sandbox_profile`, `effort_hint`, `model_class_hint`, `source`, `audit_redact`, `lint_suppress`, the structured fields, and the type-specific fields stay `ARTIFACT.md`-only.
- D-2: each key is the `ARTIFACT.md` field name with no prefix (maintainer decision, 2026-11-15).
- D-3: the encodings are fixed: comma-separated `tags`, one `when_to_use` situation per line, the enum values for `sensitivity` and `search_visibility`, `true` or `false` for `deprecated`, one line for `replaced_by`, and any string for `release_notes`. An empty string, which a YAML null such as `~` decodes to, is absent.
- D-4: precedence is by key presence in `ARTIFACT.md`. A stated key wins whatever its value, and every Go resolver reads presence from the raw frontmatter keys. The SDK overlays apply no precedence, because they read no `metadata` field for a skill that has an `ARTIFACT.md` (D-10). A `metadata` value that does not follow its encoding is ignored under the new warning `lint.skill_metadata_field_ignored`, which carries no suppression, and a decoded value that differs from a stated `ARTIFACT.md` value is a `lint.skill_artifact_field_mismatch` error.
- D-5: a sequence or mapping under `metadata` stays a `SKILL.md` parse failure. The layer ingest fails as a whole, the reingest endpoint answers `422 ingest.lint_failed`, and the message names the key.
- D-6: `manifest.ResolveSkillFields` is the one Go resolution rule. `manifest.ResolveStoredSkill` wraps it for readers that hold stored bytes.
- D-7: the synthesized `ARTIFACT.md`, its byte recognizers, the delivery-record serialization, and `LoadArtifactResult` are unchanged.
- D-8: §13.4 admission resolves the fields from the admitted bytes for every skill row.
- D-9: no release-time rewrite recomputes stored rows (maintainer decision, 2026-11-15). SPEC-2 Edit 2 exempts the resolved catalog columns of a skill row that an earlier release stored from the §13.4 rewrite rule, so search reads that row's stored columns while a load serves its resolved values, and the CHANGELOG tells operators to publish an affected skill at a new version.
- D-10: the SDK overlays take `tags`, and no other field, from `SKILL.md` `metadata`, only for a skill with no `ARTIFACT.md`, and only from a value in the SDK-1 readable form. They take no tag from any other value. `test/vectors/skill-metadata-tags.json`, generated from `manifest.ResolveStoredSkill`, pins both SDKs. A both-files skill whose `ARTIFACT.md` states no `tags` therefore has no tags in an SDK overlay (maintainer decision, 2026-11-15).
- D-11: the skill scaffold writes `--tags` and `--sensitivity` as quoted `metadata` values and `--when-to-use` as a `when_to_use: |` literal block under `metadata` (CODE-7), and writes no default sensitivity.
- D-12: the Podium-only diagnostic names `metadata.<key>` for a metadata-eligible field and the `ARTIFACT.md` overlay for the rest.
- D-13: the change is backward-incompatible and ships in a MINOR release. The 0.6.0-to-0.7.0 rolling upgrade and the rollback without a backup restore stay as the layer-credential change states them, and the operator empties each `podium-mcp` content cache after the registry rolls and after a rollback.
- D-14: the spec lands first in one commit, then the manifest resolver, the walk and ingest, lint, admission, the SDKs, the scaffold, tests, manual validation, and docs, with the CHANGELOG last.

**Watch out for.**

- **This proposal reverses a recent decision.** D2.5 (accepted 2026-11-08) and proposal 0058 D-12 placed every Podium-only field in the hand-written overlay and named `metadata` keys as a non-goal. The maintainer confirmed the reopening for the D-1 fields on 2026-11-15 ("Relationship to D2.5 and proposal 0058").
- **The walk writes resolved values into `rec.Artifact` before lint runs.** After CODE-2, `rec.Artifact` already holds the value filled from `metadata`, so a lint rule that compares `metadata` with `rec.Artifact` never sees an explicit `deprecated: false`, `sensitivity: ""`, or `tags: []` in `ARTIFACT.md`. CODE-3 re-parses `rec.AuthoredBytes`.
- **A plain skill's `ArtifactBytes` is the synthesized document, which states `type` and `version`.** Key presence comes from `rec.AuthoredBytes` in the walk and from `rec.Frontmatter` in admission. Both are empty for a plain skill (`pkg/registry/filesystem/walk.go:24-34`).
- **The synthesized document is recognized by exact bytes in Go and in both SDKs.** Adding a field to it changes the delivery_hash of every plain-skill row. D-7 keeps it unchanged, and `TestAdmit_PlainSkillRowServesItsAdmittedSkill` keeps asserting its bytes.
- **Publishing at a new version is the only repair for a row an earlier release stored.** Re-ingesting identical bytes is an idempotent no-op (`pkg/registry/ingest/ingest.go:857-858`). `podium admin reembed` projects from the stored columns and writes no column (`pkg/registry/core/reembed.go:221-223`). Neither changes such a row, so the upgrade notes route operators to neither. A both-files skill whose `ARTIFACT.md` declares `version` takes its new version in `ARTIFACT.md`, because that value is the version and lint refuses a different `major.minor.patch` `metadata.version` (§4.3.4), so the DOC-1 upgrade-notes step names the field to raise per file layout.
- **The `podium-mcp` content cache keys on the content hash.** This change alters no stored content hash, so a record cached before the upgrade revalidates by HEAD or `304` and keeps its cached sensitivity and delivery record (`cmd/podium-mcp/main.go:1452-1520`, `cmd/podium-mcp/resolution_cache.go:427-456`). SPEC-6 states the exception, and the CHANGELOG has the operator empty each consumer cache.
- **Removing the scaffold refusal breaks existing tests at once.** `TestScaffold_Skill_RefusesTags`, `TestScaffold_Skill_RefusesFlagsInDefinitionOrder`, and every `assertSkillOverlayRefusal` call site in `test/e2e` assert exit 2. CODE-7 converts them in its own commit, and the helper is deleted because the `unused` linter rejects it.
- **The SDK overlays parse frontmatter by hand.** A line parser cannot reproduce YAML, so SDK-1 defines the one form the SDKs read and drops every other value. A YAML form found later can fall outside that form, where the SDK already drops it and only a corpus case is added. It can also fall inside the form, which is a defect in the form that SDK-1 fixes. Each such change lands in SDK-1 and `test/vectors/skill-metadata-tags.json` and in no other section of this proposal. D-10, the edge-case table, and DOC-1 refer to SDK-1 and do not restate it.
- **`metadata` decodes into `map[string]string`.** An unquoted `deprecated: true` decodes as `"true"`, a `|` block decodes with a trailing newline, and `tags: [a, b]` fails with `cannot unmarshal !!seq into string` and no key name (yaml.v3 v3.0.1).
- **Parts of `test/e2e` skip silently on macOS.** Run the end-to-end steps with `-v` and grep the output for `SKIP` before claiming a pass.
- **Line numbers drift.** Anchor each edit by the quoted text, and treat cited line numbers as hints.

## Current state and the gap

### SKILL.md carries the version alone

§4.3.4 lets a skill carry one Podium value in `SKILL.md`: the version, as `metadata.version`. The field allocation table marks `when_to_use`, `tags`, `sensitivity`, `search_visibility`, `deprecated`, `replaced_by`, and `release_notes` as "Not present" in `SKILL.md`. Ingest lint errors on these keys at the `SKILL.md` top level and tells the author to move them to `ARTIFACT.md` (`pkg/lint/skill_rules.go:35-67`, `pkg/manifest/skill_fields.go:30-60`). The only `metadata` key the code reads is `version` (`pkg/manifest/skill_version.go:58-69`). A skill that sets one tag or a sensitivity label therefore needs a second, hand-written file.

§4.3.4 gives two reasons for the split: the fields keep their YAML types, and `skills-ref validate` passes without warnings. The second reason does not apply to string values under `metadata`. The upstream validator (agentskills/agentskills `skills-ref` `validator.py` and `parser.py`, read 2026-11-15) checks only that `metadata` is an allowed top-level key, converts every metadata value to a string, and inspects no value. The local stand-in checks only the description and compatibility lengths (`pkg/lint/skill_rules.go:210-240`), which is consistent with that reading. Podium already decodes `metadata` as `map[string]string` (`pkg/manifest/types.go:222`). The YAML-type reason does apply to the structured fields. It also applies, in a different form, to the caller-interpreted scalars `sandbox_profile`, `effort_hint`, and `model_class_hint`: consumers read them from the served `ARTIFACT.md` document (`cmd/podium-mcp/main.go:2441-2447`, `:2474-2480`; `pkg/adapter/compatibility.go:31`), and for a plain skill the served document is the synthesized one.

The repository holds no non-fixture skill overlays to measure how many skills set only discovery fields. Three of the five fixture overlays set only string-encodable fields (`testdata/registries/reference/org-defaults/onboarding/welcome/ARTIFACT.md`, `_shared/payment-helpers/routing-validator/ARTIFACT.md`, and `org-defaults/plain-skills/overlay-unversioned/ARTIFACT.md`), and two of those three set `sensitivity: low` beside `license` or `description`, which §4.3.4 already says not to repeat in `ARTIFACT.md`. One fixture sets structured fields (`team-finance/finance/close/run-variance/ARTIFACT.md:9-14`). The motivation is the authoring burden of a second file for string values, and it is not a measured majority.

### Resolution happens at one ingest point and nowhere on the load path

Ingest resolution happens at `ArtifactRecord.ResolveSkillVersion` (`pkg/registry/filesystem/walk.go:46-52`), called at `walk.go:374` and `:409` and at `pkg/registry/ingest/ingest.go:1207` and `:1242`. The resolved record fills the stored columns (`ingest.go:1313-1336`), and the public-mode floor (`ingest.go:603-607`), the deprecation flip (`ingest.go:705`), the search filters (`pkg/registry/core/core.go:1258-1272`, `:1347`), the scope preview (`pkg/registry/core/dependents.go:140`), and the embedding projection (`pkg/registry/projection/projection.go:30-39`) read those columns.

The load path reads other values. §13.4 stored-row admission re-derives sensitivity, deprecation, and replacement from the admitted bytes. For a plain skill it builds an artifact from type and description only and sets `Tags` to nil, and for a both-files skill it never reads `SKILL.md` `metadata` (`pkg/registry/core/admit.go:91-102`, `:202-214`, `:228-234`). A metadata-derived value would be lost on every `load_artifact` and in the §4.7.10 delivery record unless admission resolves it too.

### Stored rows can already hold these keys

Rows stored by an earlier release can hold these `metadata` keys, because nothing lints or reads them today (`pkg/lint/skill_rules.go:130-204`). Their stored columns are empty, so after an upgrade admission and search would disagree about them until something recomputes the columns. §13.4 requires that recomputation for a release that changes how a stored value is computed. No store method writes a row's derived columns: `PutManifest` is the immutability anchor, and `RehashManifest` replaces only the hash and the signature (`pkg/store/store.go:420-436`). The only data-migration marker is `content-hash-framing` (`store.go:516-523`). Re-ingesting identical bytes is an idempotent no-op that never updates the columns (`ingest.go:692`, `:858`). SPEC-2 Edit 2 exempts these columns from the §13.4 recomputation requirement (D-9).

### The synthesized document and the SDK overlays

The synthesized `ARTIFACT.md` is a function of the version alone, and it is recognized by exact bytes in Go (`pkg/manifest/skill_version.go:78-103`, `pkg/adapter/none.go:31`, `cmd/podium-mcp/local_search.go:132`) and in both SDKs (`sdks/podium-ts/src/skill_document.ts:59-80`, `index.ts:483`; `sdks/podium-py/podium/_skill_document.py:72-85`, `client.py:417`). Adding fields to it would change the served bytes and the delivery_hash of every unchanged plain-skill row. The delivery record already carries the served sensitivity as its own field (§4.7.10, §7.2).

The SDK workspace overlays parse frontmatter by hand and read only `metadata.version`, and a plain skill always gets empty tags there (`sdks/podium-ts/src/overlay.ts:40-106`, `:592-620`; `sdks/podium-py/podium/_overlay.py:49-103`, `:431-453`). The Go workspace overlay reads the walked record (`pkg/overlay/overlay.go:57`, `cmd/podium-mcp/local_search.go:94-118`), so it follows the walk.

A metadata value that is a YAML sequence or mapping, such as `tags: [a, b]`, fails `ParseSkill` and aborts the walk and the layer ingest (`pkg/manifest/parse.go:126-137`; `walk.go:363`, `:394`; `ingest.go:1197`, `:1227`). That failure exists today, and this change makes authors more likely to reach it.

### The scaffold refuses the fields

`podium artifact scaffold --type skill` refuses `--tags`, `--sensitivity`, and `--when-to-use` with exit 2, because §4.3.4 keeps those fields out of `SKILL.md` (`cmd/podium/artifact_scaffold.go:39-48`, `:236-252`).

## Relationship to D2.5 and proposal 0058

Maintainer decision D2.5 (`tmp/research/implementation-plan.md:71` in the main checkout, options at `:129-132`, accepted 2026-11-08 at `:276`) chose option (a), the hand-written `ARTIFACT.md` overlay, and rejected option (b), string-valued Podium fields under namespaced `metadata` keys such as `podium.tags`. Proposal 0058 (Implemented 2026-11-10, shipped in 0.6.0) wrote that choice into its summary, its D-12, and its non-goals: Podium-only fields live in the overlay "and never as top-level or `metadata` keys of `SKILL.md`" (`proposals/0058-ingest-sync-materialize-and-serve-a-plain-agent-skills-direc.md:32`, `:174`, `:1305`). The current §4.3.4 text is that decision.

This proposal supersedes D2.5 and 0058 D-12 for the D-1 fields. It also supersedes the 0058 D-10 refusal, by `podium artifact scaffold --type skill`, of `--tags`, `--sensitivity`, and `--when-to-use` (`cmd/podium/artifact_scaffold.go:40-48`), which rests on D2.5 and which D-11 replaces. The reason for reopening is new evidence about the premise: §4.3.4 justifies the split partly by `skills-ref validate`, and the upstream validator inspects no `metadata` value, so string values under `metadata` raise no warning. The overlay stays supported for every Podium-only field, and it remains the only home for the fields D-1 excludes.

The only form of option (b) the maintainer reviewed before this proposal used prefixed keys (`podium.tags`). On 2026-11-15 the maintainer confirmed the reopening for the D-1 fields (former Q-3) and kept the unprefixed keys of D-2 with that history in view (former Q-2).

## Decisions

- **D-1. Field set.** `SKILL.md` `metadata` carries `sensitivity`, `search_visibility`, `deprecated`, `replaced_by`, `release_notes`, `tags`, and `when_to_use`. The structured fields (`mcpServers`, `requiresApproval`, `runtime_requirements`, `sbom`, `target_harnesses`, `external_resources`, `audit_redact`, `lint_suppress`, and the type-specific fields) stay `ARTIFACT.md`-only. The caller-interpreted scalars `sandbox_profile`, `effort_hint`, and `model_class_hint` and the provenance field `source` also stay `ARTIFACT.md`-only, although each has a string value. Consumers read them from the served `ARTIFACT.md` document: the `podium-mcp` sandbox and runtime gates (`cmd/podium-mcp/main.go:2441`, `:2474`, `:2495`) and the compatibility derivation (`pkg/adapter/compatibility.go:31`). For a plain skill that document is the synthesized one, so a `metadata` value would silently fail open at the sandbox gate. `release_notes` has no reader today (it is read only at `pkg/manifest/types.go:111`). It is included so that every scalar universal field in the "Not present" row of the §4.3.4 table moves together, and the shared resolver handles it at no extra cost.
- **D-2. Key names.** Each key carries the `ARTIFACT.md` field name with no prefix, following the `metadata.version` precedent. The collision risk with third-party `metadata` keys is accepted. A colliding value that does not follow its encoding is ignored with a lint warning. A colliding value that follows its encoding takes the Podium meaning, and for `tags` and `deprecated` that meaning matches the plain-English one. The maintainer kept the unprefixed names on 2026-11-15 (former Q-2). Two facts were in view: the only form of D2.5 option (b) reviewed earlier used prefixed keys (`podium.tags`), and the repository records no survey of the `metadata` keys that other Agent Skills tools write.
- **D-3. Encodings.** `sensitivity` is `low`, `medium`, or `high`. `search_visibility` is `indexed` or `direct-only` (`pkg/manifest/types.go:34-46`). `deprecated` is `true` or `false`; an unquoted YAML boolean already decodes to that string. `replaced_by` is one line. `release_notes` is any string. `tags` is comma-separated: each element is trimmed of white space, no element may be empty, and the value holds no line break. `when_to_use` has one situation per line: each line is trimmed, empty lines are dropped, and at least one line must remain. A metadata value that is the empty string counts as absent and raises no warning. An unquoted YAML null (`~`, `null`, `Null`, or `NULL`, the forms yaml.v3 v3.0.1 resolves to null at `resolve.go:54`) decodes into the `map[string]string` entry as the empty string (`decode.go:581-583`, `:847-849`), so it is absent as well.
- **D-4. Precedence and lint.** A field takes its `ARTIFACT.md` value when `ARTIFACT.md` states the key, whatever the value, and otherwise takes the decoded `metadata` value. Every resolver (the walk, ingest, admission, and the Go workspace overlay, which reads the walked record) reads which keys `ARTIFACT.md` states from its raw top-level frontmatter keys, because a zero value (an empty string, an empty list, or `false`) cannot distinguish an absent key from a stated one. The SDK overlays apply no precedence, because they read no `metadata` field for a skill that has an `ARTIFACT.md` (D-10). A `metadata` value that does not follow its encoding is ignored under a new warning code, `lint.skill_metadata_field_ignored`, which names the key, the value, and the encoding. The warning carries no suppression, because §4.3.4 grants a suppression flag only for the `skills-ref` check. When `ARTIFACT.md` states the key and the `metadata` value decodes, the two must be equal. A mismatch is an error under the existing `lint.skill_artifact_field_mismatch` code, which blocks ingest as `ingest.lint_failed`. Lint compares the authored `ARTIFACT.md` values parsed from `AuthoredBytes`, because the walk has already written the resolved values into `rec.Artifact`. Lint codes are not §6.10 codes, so no matrix cell is added.
- **D-5. Non-string metadata values.** A metadata value that is a YAML sequence or mapping stays a `SKILL.md` parse failure, with the outcome every unparsable `SKILL.md` has today. ## Spec amendment: §6.5 content cache, records cached before the fields resolved

**SPEC-6.** `spec/06-mcp-server.md` §6.5.

**Rationale.** The `load_artifact` ETag is the content hash (`pkg/registry/server/server.go:1222-1224`, §7.2), and the `podium-mcp` content cache stores each verified record's sensitivity, delivery hash, and delivery signature under that hash (`cmd/podium-mcp/main.go:3007-3029`). A HEAD revalidation or a `304` therefore keeps a record cached before the upgrade, and the offline modes serve a pinned record without contacting the registry (`cmd/podium-mcp/main.go:1452-1494`). §6.5 calls the content cache immutable and names the registry-assigned skill version as its only exception, so the stale sensitivity and delivery record would be an unstated second exception. Making the validator change with the served record was weighed and rejected: it would change the strong ETag of every row and the §7.2 conditional-request contract for one upgrade, where an operator step that empties the cache closes the gap once.

**Edit 1.** Anchor: the bullet that begins "**Content cache.** Maps `content_hash` to manifest bytes + bundled resources." Insert this sentence directly before its last sentence, "Its body and bundled resources are the bytes the registry serves.":

> A skill whose `SKILL.md` `metadata` carries a field that §4.3.4 lists under **Podium fields in `metadata`** is a second exception, for its sensitivity and its §4.7.10 delivery record: a record of it cached while the registry ran a release that resolved those fields differently from the release now serving it keeps reporting the cached sensitivity and delivery record until the cache no longer holds it, because a HEAD revalidation and a `304` confirm the content hash only. The changelog of a release that changes that resolution names the step that empties the cache.

### SDK-1. TypeScript and Python workspace overlays read `metadata.tags`

Targets: `sdks/podium-ts/src/overlay.ts` (`readPlainSkill` `:592-620` and a new function beside `parseFrontmatter`) and `sdks/podium-py/podium/_overlay.py` (`_read_plain_skill` `:431-455`, including its `open` call at `:439`, and a new function beside `_parse_frontmatter`). `FrontmatterFields`, `parseFrontmatter`, `readMetadataValue`, `readMetadataVersion`, `readPackage`, and their Python counterparts are unchanged.

- `metadataTags(skillMD: string): string[]` (TypeScript) and `_metadata_tags(skill_md: str) -> list[str]` (Python), each with `// Spec: §4.3.4, §6.4`, return the tags of the readable form and `[]` for every input outside it.
- **The frontmatter.** The function delimits it as Go's `SplitFrontmatter` does (`pkg/manifest/parse.go:36`), and not as `parseFrontmatter` does. The `SKILL.md` text begins with `---` followed by an LF or a CR LF. The text is split into lines at each LF, and a CR directly before an LF is removed. The function receives the file's text with its line ends unchanged. `_read_plain_skill` therefore opens `SKILL.md` with `newline=""` in place of the default universal-newline mode (`_overlay.py:439`), which turns every lone CR and every CR LF into LF before any function sees the text, and `_metadata_tags` splits with `split("\n")` rather than `splitlines()`, which also splits at CR, U+0085, U+2028, and U+2029. `readPlainSkill` already reads the text unchanged (`overlay.ts:606`). The change also makes the Python `skill_raw` keep the file's CR LF line ends, so the Python overlay materializes `SKILL.md` with the bytes the file holds (`client.py:422-423`, written as bytes at `:157-159`), as the TypeScript overlay already does (`index.ts:489`), and `test_overlay_plain_skill_keeps_crlf_skill_raw` (TEST-1) pins it. `_parse_frontmatter` splits with `splitlines()` and joins the body with LF (`_overlay.py:61-69`), so its fields and its body do not change. The frontmatter lines are the lines after the first line, up to the first later line that begins with `---`. A `SKILL.md` that does not begin that way, or that has no later line beginning with `---`, is outside the form. `parseFrontmatter` ends the frontmatter only at a line that is `---` after trimming (`overlay.ts:59-63`, `_overlay.py:64`), so it reads past a `---x`, `--- # c`, or `----` line at which Go's frontmatter ends.
- In these conditions, white space means the space and the tab, and a blank line is empty or white space only. An implementation does not use `trim()` or `strip()` for these tests, because both remove characters that yaml.v3 does not treat as white space.
- **The readable form.** Every condition holds:
  1. Exactly one frontmatter line begins with `metadata:`, and the rest of that line is empty or white space only. A flow-form `metadata: {...}` and a `metadata:` line that carries a comment, an anchor, or a tag are outside the form.
  2. The block is the lines after that line up to the next line that begins at column 0 with a character other than `#`. The child indent is the indentation of the first block line that is neither blank nor a comment, and it consists of one or more spaces. A comment line is one whose first character after its indentation is `#`.
  3. Exactly one block line at the child indent has the key `tags`. A line's key is the text before its first `:`, with trailing spaces removed and one pair of matching surrounding quotes removed.
  4. That line consists of the child indent, `tags:`, one or more spaces, the value V, and optional trailing spaces, and it contains no tab.
  5. V takes one of three forms. A plain V matches `[A-Za-z0-9][A-Za-z0-9 ,._/-]*` and is not `null`, `Null`, or `NULL`, and its content is V without its trailing spaces. A double-quoted V is `"C"`, where C is zero or more characters from U+0020 to U+007E other than `"` and `\`. A single-quoted V is `'C'`, where C is zero or more characters from U+0020 to U+007E other than `'`.
  6. Every line after the `tags` line is empty or white space only, up to the next block line that is indented no deeper than the child indent and is neither blank nor a comment, or up to the end of the block. No block line after the `tags` line holds a `*` that begins the line after its indentation or follows a space or a tab and that a character other than a space or a tab follows. Such a `*` starts an alias. yaml.v3 compares mapping keys for duplicates only between nodes of the same kind (yaml.v3 v3.0.1 `decode.go:775`), so an alias key that resolves to `tags`, written as `*k : z`, as `? *k` and `: z`, or as a `?` line followed by a deeper-indented `*k` line, replaces the value of the `tags` line with no error. A `*` that a space follows, as in a `* item` line of a block scalar, keeps the form.
  7. Splitting the content on `,` and trimming spaces from each element leaves no empty element (D-3). The elements, in order, are the tags.
  8. The frontmatter holds no CR, U+0085, U+2028, U+2029, or U+FEFF. yaml.v3 reads the first four as line breaks (yaml.v3 v3.0.1 `yamlprivateh.go:124-130`) and skips a U+FEFF at the start of a line (`scannerc.go:1545`), so each can start a line that the line reader does not see. A CR before an LF is already removed by the line split. The condition applies in both SDKs only because each function receives the file's line ends unchanged, as the frontmatter bullet states. Under Python's universal-newline mode a lone CR would reach `_metadata_tags` as an LF, and the Python overlay would read a frontmatter that the TypeScript overlay puts outside the form.
  9. The first frontmatter line that is neither blank nor a comment begins at column 0. A root mapping indented deeper ends at the first column-0 line, and `yaml.Unmarshal` decodes only the first document (`yaml.go:156-173`), so yaml.v3 decodes `  name: x` followed by a column-0 `metadata:` block with no error and no `metadata`.
  10. No frontmatter line before the `tags` line begins with `...` or `%`, holds a `[` or a `{`, or holds a `"` or a `'` that begins the line or follows a space or a tab. A line that consists of zero or more spaces, a key that begins with an ASCII letter and holds only ASCII letters, digits, `_`, and `-`, then `:`, one or more spaces, a double-quoted or single-quoted value as condition 5 defines it, and optional trailing spaces is exempt, so `version: "1.0.0"` before the `tags` line keeps the form. A `...` at column 0 ends the YAML document. A `%` at column 0 is always a directive token in yaml.v3, whatever the parser state (yaml.v3 v3.0.1 `scannerc.go:725-727`). The directive unrolls the indentation to -1, which closes the root mapping (`scannerc.go:1142-1146`), and the parser then ends the document implicitly (`parserc.go:385-404`), so yaml.v3 decodes the lines before the directive and none after it. A quoted scalar or a flow collection opened on an earlier line continues across later lines, and a quoted scalar applies no indentation check (`scannerc.go:2435-2458`), so it can hold the `metadata:` line or the `tags` line as text. Outside a flow collection, yaml.v3 starts a quoted scalar only where a token starts, which is at the start of a line or after a space or a tab, so an apostrophe inside a word, as in `the user's guide`, keeps the form.
- The form is sound for a `SKILL.md` that Go parses. In block context yaml.v3 reads a plain scalar of these characters as its text without trailing spaces, and it reads a quoted scalar with no escape and no inner quote as its content. It decodes every non-null scalar into the `map[string]string` entry as that text (yaml.v3 v3.0.1 `decode.go:616`). The excluded words are the only plain values of these characters that resolve to null (`resolve.go:54`). Condition 6 excludes every continuation line. Conditions 8 to 10 and the delimiting rule make the `metadata:` line and the `tags` line the lines that yaml.v3 reads as the `metadata` key and its `tags` entry. No earlier line holds them as text, no hidden line break splits them, no `...` line or `%` directive line ends the YAML document before them, and the frontmatter ends where Go's ends. A line after the `tags` line does not change that reading when Go parses the `SKILL.md`. yaml.v3 refuses a second scalar `tags` or `metadata` key with `mapping key "tags" already defined`, a top-level alias key that resolves to `metadata` with `field metadata already set` (`decode.go:924`), and an alias with no anchor with `unknown anchor` (`decode.go:218`), and a merge key `<<` does not override a key that the mapping states. Its duplicate check compares only nodes of the same kind (`decode.go:775`), so an alias key in the `metadata` block that resolves to `tags` would replace the `tags` value with no error, and condition 6 excludes every alias after the `tags` line in that block. An alias key before the `tags` line does not change the reading, because the later `tags` line replaces it. The SDK records no reason for a dropped value, so no list of excluded forms exists to maintain.

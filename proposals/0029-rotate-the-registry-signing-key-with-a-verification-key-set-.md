# Proposal 0029: Rotate the registry signing key with a verification key set, and sign stored rows on operator demand

- Issue: (to be filed)
- Status: Applied to spec (2026-09-25). Verified 2026-09-24 after 14 adversarial review rounds (50 findings fixed). OQ-1 and OQ-2 resolved by the owner.
- Date: 2026-09-24

This document stages the proposed spec, code, test, and documentation changes. It does not modify any spec, code, or doc file. Apply the changes in the staged sections after sign-off.

## Summary

**What changes.**

- The registry-managed key file at `PODIUM_SIGN_KEY_PATH` gains zero or more `verify:` lines. The `public:` key and the `verify:` keys form the registry's **verification key set**. The registry signs under the `private:` key alone and verifies a stored envelope under any key of the set, so a rotation keeps every row the retired key signed admitted (SPEC-1, SPEC-5, CODE-1, CODE-3).
- The verifying consumers, `podium-mcp` and `podium verify`, resolve a verification key set: `PODIUM_SIGNATURE_VERIFY_KEY` takes a comma-separated list, and the key-file fallback reads the `public:` line and every `verify:` line. `PODIUM_SIGNATURE_KEY_ID` and the `KeyID` field of `sign.RegistryManagedKey` are removed. The §4.7.9 rule governs every party that verifies a delivery signature; the language SDKs, server-source `podium sync`, and raw HTTP callers verify nothing today and are unchanged (SPEC-1, SPEC-3, CODE-1).
- `podium-mcp` treats a cached record whose delivery signature fails under its current key set as a §6.5 cache miss on every path that serves a cached record: the `always-revalidate` HEAD match, the conditional-request 304, the `offline-first` cache hit, and the §7.4 degraded-network fallback. A refetch that cannot reach the registry returns the §7.4 cache-miss outcome for the mode and never delivers the failing record. In `offline-only` such a record is refused with `materialize.signature_invalid` rather than answered as a cache miss (SPEC-2, SPEC-3, CODE-6).
- A one-shot operator command, `sign-stored-rows`, runs as `podium-server sign-stored-rows` and `podium admin sign-stored-rows`. It re-signs under the signing key every row whose envelope a verification-only key verifies and whose stored bytes reproduce its stored hash or the previous release's digest, and, when the §13.4 rewrite has not completed, performs that rewrite in place of the first start, signing every unsigned row that start would sign. Beyond that, it signs unsigned rows only under `--include-unsigned`. `podium admin signing-key generate|rotate` writes the key file (SPEC-4a, CODE-2, CODE-4, CODE-5).
- `store.RehashManifest` gains an `oldSignature` compare-and-swap argument, which is the write path the command and the rewrite share (CODE-2).
- The automatic first-start rewrite, and `sign-stored-rows` standing in for it without `--include-unsigned`, mint a first envelope for an unsigned row only when the store is the SQLite store in the key file's directory (SPEC-4b, CODE-7).

**Fixed decisions.**

- The key set lives in the existing key file. No registry environment variable, §6.10 error code, SPI, or meta-tool is added (Decisions).
- One signing key and many verifying keys. Sign uses the `private:` key only; Verify accepts any key of the set (SPEC-1, CODE-1).
- `key_id` is the lowercase hex of the first 8 bytes of SHA-256 over the 32-byte public key, `sign.KeyIDFor`, normative in §4.7.9. Every registry-managed envelope carries it, including one from `podium sign` (SPEC-1, CODE-1).
- `key_id` is unauthenticated and never on its own refuses an envelope a trusted key verifies. A verifier tries the named key first and then every other key (SPEC-1, CODE-1).
- `PODIUM_SIGNATURE_KEY_ID` is removed with no shim (SPEC-3, CODE-1).
- The §9.1 `SignatureProvider` interface is unchanged. The rewrite reads the verifying key through a consumer-side `keyedSigner` interface in `internal/serverboot` (CODE-4).
- The command never generates a key. An absent key file or `PODIUM_SIGN=none` refuses it with `config.signature_provider_unavailable`, and a malformed or mismatched key file refuses the command and the registry start with the same code. The code is written into the error text, as `cmd/podium/sign.go` does, because `spi.Error.Error()` returns the message alone (SPEC-4a, SPEC-5, CODE-3, CODE-5).
- Beyond the unsigned rows the first-start rewrite it stands in for would sign, the command signs an unsigned row only under `--include-unsigned`, and it never signs a row whose envelope fails under every trusted key (SPEC-4a, CODE-4).
- `podium admin signing-key generate|rotate` require `--key-file` and read no environment or default path (CODE-5).
- Both binaries expose the command over one implementation, `serverboot.RunSignStoredRows`, because the image ships only `podium-server` and a standalone operator has `podium` (CODE-5).
- With the completion record absent, the command performs the §13.4 rewrite in place of the first start and records completion. With the record present, it may run while registries on this version serve the store, because every write is a compare-and-swap (SPEC-4a, CODE-2, CODE-4).
- A lost key whose public half survives is repaired by listing that half on a `verify:` line, restarting, and running `sign-stored-rows` (SPEC-5).
- The registry's HTTP ETag and the §7.2 validator are unchanged (Non-goals).
- The rewrite keeps its existing classes. Re-signing is `classUnmigrated` with a per-row `sign` flag, and no `Force` field or `classResign` exists (CODE-4).
- The automatic first-start rewrite, and `sign-stored-rows` standing in for it without `--include-unsigned`, mint a first envelope for an unsigned row only when the store is the SQLite store in the key file's directory. A standard deployment that upgrades with signing on runs `podium-server sign-stored-rows --include-unsigned` once before its first start. This relaxes proposal 0028's OQ-14 constraint by the owner's decision of 2026-09-25 (OQ-1; SPEC-4b, CODE-7).

**Watch out for.**

- **The default cache mode replays a stale delivery pair on the HEAD path.** In `always-revalidate`, a cache hit is checked with a HEAD request, and a matching content hash serves the cached record through `deliverLoadArtifact` before the conditional GET runs (`cmd/podium-mcp/main.go`). A fix scoped to the 304 branch passes its test and leaves the default mode stuck on `materialize.signature_invalid`. CODE-6's helper serves the HEAD-match, 304, and `offline-first` paths, the degraded-network fallback runs the same check, and TEST-5 drives each one.
- **Removing the `KeyID` field, deleting a function, or changing a signature breaks callers across the tree.** Each step ports the callers it breaks, per the implementation checklist, the test-caller ports under Proposed solution, and the run-time breakages CODE-1 and TEST-8 name.
- **A bare `rotate` would rotate the operator's personal key.** On an operator's shell `PODIUM_SIGN_KEY_PATH` is unset, and `sign.KeyFilePath("")` resolves to `~/.podium/standalone/registry-signing.key`. The key tool therefore takes `--key-file` only, as `podium admin runtime register` takes `--keys-file` (`cmd/podium/admin_runtime.go`).
- **With the completion record absent, the command is the §13.4 rewrite.** The rewrite requires every previous-version process to be stopped, and the boot enforces part of that through the bind guard (`internal/serverboot/serverboot.go`). The command binds nothing and cannot detect another process. DOC-1 states this precondition unconditionally in the `docs/reference/cli.md` `sign-stored-rows` entry and in the operator guide's `sign-stored-rows` passage.
- **`--include-unsigned` attests every unsigned row present.** The command cannot tell a planted row from a legitimate one. `--dry-run` lists the unsigned rows before the operator attests them.
- **The D-clustered documentation test executes the recipe DOC-1 replaces.** `test/e2e/standard_deployment_test.go` finds the key-generation block in `docs/deployment/clustered.md` by the `env -i` marker and requires exactly two stdout lines, where `signing-key generate` prints its own. DOC-1 changes the marker and the line assertions in the same commit; S8 has already ported the test's key-file reads.
- **`test/e2e` skips parts of itself on macOS.** A green local run is not evidence. Grep the run output for `SKIP`.
- **The audit-anchor key shares the key-file codec.** `loadOrGenerateAuditSigner` (`internal/serverboot/audit_anchor.go`) keeps its own file and ignores any `verify:` line; the §8.6 anchor key is not rotated by this proposal.

## Current state and the gap

Proposals 0026, 0028, and 0027 are implemented on this branch and ship in one unreleased MINOR. Together they leave the registry-managed key (§4.7.9) with no safe rotation, and they leave stored rows with no signing path after the first-start rewrite.

### Rotation strands the catalog

Stored-row admission (§13.4 check 3) calls `r.admitSigner.Verify(ctx, rec.ContentHash, rec.Signature)` (`pkg/registry/core/admit.go`). The signer is the single boot provider `registrySignerFor` builds (`internal/serverboot/serverboot.go`), and it is wired into ingest, the first-start rewrite, admission, and the delivery signer. `sign.RegistryManagedKey` holds one `PrivateKey`, one `PublicKey`, and one `KeyID` (`pkg/sign/registry_managed.go`), and `Verify` checks against that one key. After a rotation, every row the retired key signed fails with `materialize.signature_invalid` for every reader. §4.7.9 states that every version stored before the rotation stays refused until a new version is ingested.

A rerun of the first-start rewrite does not repair this. `classify` marks a row whose envelope fails under the configured key `classSignatureUnverified`, and `applyRehash` skips it (`internal/serverboot/rehash.go`), because a retired-key envelope and a forged one both return `ErrSignatureInvalid`.

On the consumer side, delivery signatures are verified by `podium-mcp` (`buildSignatureProvider` and `registryManagedVerifyKey`, `cmd/podium-mcp/main.go`) and by `podium verify` (`registryManagedVerifier`, `cmd/podium/sign.go`). Each resolves exactly one public key, from `PODIUM_SIGNATURE_VERIFY_KEY` or from the key file's first `public:` line (`pkg/sign/keyfile.go`). §4.7.9 states "A consumer holds one verification key", so each consumer switches keys at the same instant as the registry, with no overlap. A `podium-mcp` cache keeps replaying a pre-rotation delivery pair on its HEAD-match and 304 paths, which is why `docs/deployment/operator-guide.md` tells operators to clear every consumer's cache on rotation.

The language SDKs, server-source `podium sync`, and raw HTTP callers receive `delivery_hash` and `delivery_signature` and verify neither, as §4.7.10 designs them (`sdks/podium-py/podium/client.py`, `sdks/podium-ts/src/index.ts`). They hold no key today, so a key set neither helps nor breaks them. The registry publishes no public key; keys are distributed out of band (§4.7.9).

### Stored rows cannot be signed later

Ingest short-circuits an existing row with the same hash as idempotent before its signing block (`pkg/registry/ingest/ingest.go`). The only production writer of a stored row's signature is the first-start rewrite, through `store.RehashManifest` (`pkg/store/store.go`). The rewrite runs only while the `content-hash-framing` completion record is absent and sets it on completion (`internal/serverboot/rehash.go`). On a signing registry, admission refuses every unsigned row with `materialize.signature_missing`. A registry that turns signing on after its first start therefore cannot load anything it stored earlier (§13.12). The routes that make the rewrite run again are restoring a pre-upgrade backup, recreating a `migrate-to-standard` target (`cmd/podium/admin_migrate.go`), and deleting the record by hand. The `RehashManifest` compare-and-swap also refuses to replace a non-empty signature when the hash is unchanged (`pkg/store/memory.go`), so no store method can re-sign a row.

### Proposal 0028's OQ-14 limit

Proposal 0028's OQ-14 accepts a related limit, stated in §13.4 and §13.12. A party that can write the metadata store without holding the key can delete the completion record and have the next start sign unsigned rows it inserted, because the rewrite mints an envelope for every unsigned reproducible row. An operator-triggered command closes its own trigger and leaves the automatic rerun open. The v0.4.0 default was signing off, so on the upgrade to this release every store's rows are unsigned, and the automatic first start is what signs them without any operator command. The owner's OQ-14 resolution requires that the first start of this release keeps signing every unsigned row of a store that was never rewritten. OQ-1 asks whether to relax that for stores whose write access can be separated from the key.

## Decisions

- **Put the key set in the existing key file.** The file at `PODIUM_SIGN_KEY_PATH` keeps its `private:` and `public:` lines and gains zero or more `verify:` lines. A `verify:` line serves both a retired key and a key staged for a multi-replica roll. The chart already mounts this one file from one Secret (`deploy/helm/podium/values.yaml`), so the Helm values need no new field, and no registry variable is added.
- **Sign with one key and verify with many.** The registry signs every ingest row, every rewrite and command row, and every delivery record with the `private:` key. Admission, the rewrite, and the command verify a stored envelope under `{public} ∪ verify:`. The change lives inside `sign.RegistryManagedKey` (a new `Trusted []ed25519.PublicKey` field), so the one boot provider keeps feeding every call site unchanged.
- **Select by `key_id` without refusing on it.** `key_id` sits in the unsigned JSON envelope. A verifier tries the key the envelope names first and then every other key, so a forged or stale `key_id` costs a few extra Ed25519 checks and never refuses a valid envelope. Making the fingerprint normative lets third-party verifiers compute it and lets the command's summary name each key.
- **Remove `PODIUM_SIGNATURE_KEY_ID`.** The consumer's trusted public keys already decide which envelopes it accepts, so a pin on the unauthenticated envelope field adds no check. Two sources for one fact would drift during a rotation. Podium is pre-1.0, so a set value is no longer read and no shim is added.
- **State the consumer rule in §4.7.9 for every verifier.** The rule covers any party that verifies a delivery signature, including a raw API caller that chooses to verify. `PODIUM_SIGNATURE_VERIFY_KEY` takes a comma-separated list; the key-file fallback reads `public:` and every `verify:` line; an undecodable entry refuses the start with the existing `config.signature_provider_unavailable`.
- **Leave the SDKs, server-source sync, and raw HTTP callers unverified.** §4.7.10 designs them that way. Adding verification to them and publishing the key set from the registry are OQ-2.
- **Recover a stale cached delivery signature through a cache miss.** The rule is stated on the §6.5 cache, for every path that serves a cached record, including the §7.4 degraded-network fallback, and not on one transport response. With the registry unreachable, a failing record is a cache miss and takes the §7.4 outcome for the mode. The registry's ETag is unchanged, because the bridge constructs the content-hash validator itself and a key id in the server ETag would disable the 304 path. `offline-only` fails closed.
- **Expose the command on both binaries over one implementation.** The image ships only `podium-server` (`Dockerfile`), so a Kubernetes Job needs `podium-server sign-stored-rows`. A standalone operator has `podium`, so `podium admin sign-stored-rows` mirrors the existing `podium serve` and `podium-server` pair. Both call `serverboot.RunSignStoredRows`. The command's authority is possession of the key file plus the process invocation, both outside the metadata store.
- **Re-sign on evidence; sign unsigned rows only on attestation.** A row whose envelope verifies under a `verify:` key and whose bytes reproduce its stored hash carries cryptographic evidence. An unsigned row carries none, so outside the first-start rewrite the command signs it only under `--include-unsigned`, and `--dry-run` lists what the operator would attest.
- **Let the command stand in for the first start.** When the completion record is absent, the command performs the full §13.4 rewrite, signs every unsigned row the first start would sign, and records completion. Its unsigned-row policy there is the first start's policy or `--include-unsigned`, so a run without the flag cannot record completion over rows the first start would have signed, which proposal 0028's OQ-14 resolution requires to be signed. This lets a standard deployment run it as a Job before the first start, with no window of `signature_missing` refusals. When the record is present, the command may run while registries on this version serve, because every write is a compare-and-swap.
- **Extend `RehashManifest` with `oldSignature`.** The compare-and-swap becomes: stored `content_hash` equals `oldHash` and stored signature equals `oldSignature`. The existing rule that an unchanged hash writes only onto an empty signature is the special case `oldSignature=""`, so two replicas still cannot both sign one row. One method keeps one write path for the stored hash and signature.
- **Stage the OQ-14 closure separately.** Restricting the automatic rewrite's unsigned-row minting to the co-located SQLite store relaxes a constraint the owner set in proposal 0028. SPEC-4b and CODE-7 carry it; the owner confirmed it on 2026-09-25 (OQ-1).
- **Make lost-key recovery possible from the public half.** An operator who retained the lost key's public half, for example from a consumer's configuration, generates a new key, lists the lost public key as `verify:`, and runs the command.

## Spec amendment: §4.7.9 verification key set, key_id, and rotation

**SPEC-1.** Anchor: `spec/04-artifact-model.md`, §4.7.9 Signing.

(a) Replace the first bullet of the key-model list, which begins "**Registry-managed key.** One Ed25519 keypair per registry deployment", with:

> - **Registry-managed key.** One Ed25519 signing keypair per registry deployment, held in the key file at `PODIUM_SIGN_KEY_PATH` and generated on first run when absent. The key file carries the signing keypair on a `private:` line and a `public:` line, and zero or more `verify:` lines, each a base64 Ed25519 public key trusted for verification only. The signing public key and the `verify:` keys form the registry's **verification key set**. The registry signs under the signing key alone, across every tenant that deployment serves, and verifies a stored signature under any key of its verification key set (§13.4). The registry signs at ingest by default (§13.10).

(b) Insert a new paragraph immediately after the paragraph that begins "The signature the registry mints at ingest attests the artifact's `content_hash`":

> Every registry-managed envelope carries a `key_id`, the lowercase hexadecimal encoding of the first 8 bytes of the SHA-256 digest of the signing key's 32-byte public key, including an envelope `podium sign` mints. A verifier checks the signature first under the key of its verification key set whose `key_id` the envelope names, when one does, and then under each other key in its set, and accepts the envelope when any of them verifies it. The `key_id` is not covered by the signature and never on its own refuses an envelope that a trusted key verifies.

(c) Replace the paragraph that begins "The consumer verifies the signature it is served under the registry's public key, which it holds." with:

> The consumer verifies the signature it is served under the registry's verification key set, which it holds. It resolves that set in one order, which is normative here and cross-referenced everywhere else: the value of `PODIUM_SIGNATURE_VERIFY_KEY`, one or more base64 Ed25519 public keys separated by commas, and otherwise the `public:` line and every `verify:` line of the registry-managed key file at `PODIUM_SIGN_KEY_PATH`, which defaults to `~/.podium/standalone/registry-signing.key` (§13.10). A set `PODIUM_SIGNATURE_VERIFY_KEY` is authoritative: the key file is consulted only when the variable is unset, and a set value with an entry that is empty or does not decode to an Ed25519 public key refuses the start with `config.signature_provider_unavailable`, naming the variable, rather than falling through to the file. The second source resolves only where the registry runs on the same machine under the same user account, because the registry writes that file readable by its owner alone; every other deployment supplies the variable. `podium sign` needs the private half and resolves it from the `private:` line of the same file, on the same path resolution, with no variable carrying a private key value. A consumer resolves this material once, at startup, and refuses to start with `config.signature_provider_unavailable` when its policy is above `never` and no usable material resolves (§6.9). Under `never` it resolves none and verifies nothing. No configuration file carries key material. This rule governs every party that verifies a delivery signature.

(d) Replace the paragraph "A registry deployment that serves one store from more than one process resolves `PODIUM_SIGN_KEY_PATH` to the same key file in every process. A consumer holds one verification key, so a process signing under a different key mints envelopes that consumer refuses (§13.12)." with:

> Every registry process serving one store signs under a key that the verification key set of every other such process contains, and in steady state every process holds the same signing key. A multi-replica rotation first adds the new public key as a `verify:` line to every process and only then changes any process's signing key (§13.12). A consumer accepts a delivery signature under any key in its set, so a consumer holding the new key and the retired key verifies across the rotation.

(e) Replace the paragraph that begins "Rotating the registry-managed key invalidates every signature made under the retired key" with:

> Rotating the registry-managed key replaces the signing keypair and keeps the retired public key on a `verify:` line, so the §13.4 stored-row admission keeps admitting every row the retired key signed while the registry signs every new envelope under the new key. Each consumer adds the new public key to its verification key set before any process signs under it, and keeps the retired key until every process signs under the new one. The `sign-stored-rows` command (§13.4) re-signs the stored rows under the new key and reports how many stored rows remain signed under each verification-only key. When a run that exits with a success status reports none under the retired key, the operator removes that key's `verify:` line from every process and the key from every consumer's set. ## Open questions

**OQ-1. Should the automatic rewrite's unsigned-row signing be restricted to the co-located SQLite store?** Resolved by the owner on 2026-09-25: yes. SPEC-4b, CODE-7, TEST-7, and the matching DOC-1 text apply. This relaxes the second constraint the owner set in proposal 0028's OQ-14, "the first start of this release still signs every unsigned row of a store that was never rewritten", for Postgres and for a SQLite store outside the key file's directory. v0.4.0 defaulted signing off, so every standard deployment that upgrades with signing on would then run `podium-server sign-stored-rows --include-unsigned` once, as a Job before its first start. A zero-configuration standalone start is unaffected. The closure is partial: a party with store write access can still plant an unsigned row that a later `--include-unsigned` run attests. Confirming applies SPEC-4b, CODE-7, TEST-7, and the conditional DOC-1 text. Keeping the limit leaves them out, and the rest of this proposal stands unchanged. The default is to keep the limit.

**OQ-2. Should a follow-up add delivery verification to the language SDKs and server-source `podium sync`, and should the registry publish its verification key set?** Resolved by the owner on 2026-09-25: yes, as a separate follow-up proposal, which also carries opt-in replay protection for every client. A key set helps only a party that verifies. §4.7.10 makes these consumers unverified by design, and a raw HTTP caller has no Podium-provided verifier or key endpoint. Adding verification would give them the same rotation behavior under the §4.7.9 rule, at the cost of per-SDK key configuration and a key-distribution design. This proposal stages neither. The default is to file the follow-up.

## Non-goals

- Delivery-signature verification in the Python and TypeScript SDKs, in server-source `podium sync`, or for raw HTTP callers. §4.7.10 keeps them unverified, and the key-set rule applies to them once they verify (OQ-2).
- A registry endpoint that publishes its verification key or key set. Keys stay out of band (§4.7.9).
- Author-key signing, Sigstore-keyless verification correctness, and any registry signing mode other than `registry-key`.
- Signing a row's identity, layer, or version. The stored signature still attests the content hash alone (proposal 0028's OQ-13 follow-up).
- Replay protection for delivery records. The record carries no nonce or timestamp.
- Rotation of the §8.6 audit-anchor key. It keeps its own file and loader, and it adopts `sign.KeyIDFor` and the shared key-file codec only.
- A Helm template or hook for the `sign-stored-rows` Job. A value left enabled would re-attest unsigned rows on every upgrade, so the chart documentation shows a one-off Job manifest.
- Automatic expiry or time bounds on verification-only keys.
- Re-attesting rows signed under a compromised key without trusting that key. Those rows are re-signed by trusting the key, restored from a backup, or re-ingested at a new version.
- Any change to the registry's HTTP ETag or to the §7.2 validator.

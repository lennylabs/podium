## Summary

**What changes.**

- §4.7.10 stops exempting server-source `podium sync` and the language SDKs from the delivery check, and gains a normative verification procedure keyed to the wire fields. §4.7.9 states the registry-managed envelope format, a per-consumer policy order and default, the meaning of "a verification key is configured", and the empty-variable rule. §6.2, §6.5, §6.6, §6.9, §7.2, §7.5, §7.5.2, §7.6, §7.6.1, §7.6.2, §7.8, §11, §13.11.6, §13.12, and §14 follow, and a new §7.6.3 states the SDK client-surface contract (SPEC-1 to SPEC-9). The read CLI (§7.6.1) stays unchecked, and §4.7.10 and §7.6.1 state that exception.
- Only `podium-mcp` compares ingest times. Server-source `podium sync` and the SDKs frame the served `artifact_revision` into the record they verify and compare it with no earlier value (SPEC-1, SPEC-9). §4.7.10 and §6.5 are corrected so that they no longer describe sync and the SDKs as consumers that verify nothing, and the §6.5 statement that the §7.5.3 lock detects rollback is deleted, because no code compares a lock with a later load.
- The registry serves `sensitivity` on each `ok` batch entry, so a client can rebuild the batch delivery record from the entry alone (`pkg/registry/server/batch_load.go`, CODE-6).
- The Go delivery check moves out of `cmd/podium-mcp` package main. `pkg/sign` gains `DeliveryCheck` and `ResolveVerifier`, `pkg/version` gains the resource-digest and link-check helpers, `pkg/manifest` gains `ManifestBodyOf`, and `cmd/podium-mcp` switches to them (CODE-1, CODE-2, CODE-5). `pkg/version` gains `DecodeJSONObject`, `DecodeBase64`, `ParseLoadResponse`, and `ParseBatchResponse`, the Go form of the §4.7.10 decoding steps, and the `pkg/sign` envelope decoder, the MCP server, and sync call them (CODE-1, CODE-2, CODE-3, CODE-5).
- Every consumer decodes a `load_artifact` body or a batch body by one byte-level procedure (SPEC-2(b)): a UTF-8 JSON rule, exact member names with typed values, canonical base64, byte-compared resource paths, and the record framing. A body or entry that fails the procedure is refused with `materialize.content_hash_mismatch`, and the MCP server's unspecified `materialize.invalid_base64` becomes that code (CODE-1, CODE-3, CODE-5, CODE-7, CODE-8).
- `pkg/sync` decodes the delivery fields, checks every fetched body, and runs the shared check on every server-source record behind a fail-closed guard. `cmd/podium` builds one memoized resolver per invocation and passes it to every sync path, and `pkg/sync` calls it at the one resolution point CODE-3(b) names for the SPEC-6(a) predicate, so `cmd/podium` holds no per-route condition (CODE-3, CODE-4).
- The Python SDK (`sdks/podium-py/podium/_delivery.py`, `_config.py`, `client.py`, and the `[verify]` extra in `pyproject.toml`) and the TypeScript SDK (`sdks/podium-ts/src/delivery.ts`, `config.ts`, `index.ts`) recompute `delivery_hash` on every registry-served load and `ok` batch entry, check every fetched or decoded body, and apply the §4.7.9 policy with the registry-managed verifier (CODE-7, CODE-8).
- A Go-generated vector file `test/vectors/delivery-record.json` carries cases for every step of the §4.7.10 verification procedure and pins each case's outcome, from raw response bytes to the delivery hash or the refusal code, together with base64, the envelope, the manifest-body derivation, the key list, and the key file, across the Go, Python, and TypeScript suites. Each case's outcome is declared in the Go source from SPEC-2, so the spec governs Go and the generated file governs the SDKs. Tests, docs, the changelog, and manual scenario S65 follow (TEST-1 to TEST-6, DOC-1, CL-1, MV-1).

**Fixed decisions.**

- Server-source sync and both SDKs verify (user decision). The spec edit lands first, because §4.7.10 forbids the code today.
- The change adds no §6.10 error code, environment variable, `sync.yaml` key, endpoint, or SPI. The codes are `materialize.content_hash_mismatch`, `materialize.signature_invalid`, `materialize.signature_missing`, and `config.signature_provider_unavailable`.
- A body that fails the §4.7.10 step 6 check fails with `materialize.content_hash_mismatch` in every consumer. The MCP server changes from today's unspecified `materialize.fetch_failed` wrapping for this case.
- Policy order for every consumer: the consumer's own explicit configuration, then `PODIUM_VERIFY_SIGNATURES`, then `defaults.verify_signatures`, then the consumer default. The default is `always` for the MCP server and server-source sync. The SDK default is `always` when a verification key is configured and `never` otherwise.
- "A verification key is configured" fails closed: an SDK key-list argument, a non-empty `PODIUM_SIGNATURE_VERIFY_KEY`, a non-empty `PODIUM_SIGN_KEY_PATH`, or a file present at the default key path, whether or not it parses. A variable set to the empty string counts as unset.
- Server-source sync and the SDKs verify with the registry-managed verifier and read no `PODIUM_SIGNATURE_PROVIDER` (SPEC-4(e), CODE-4). `podium-mcp` keeps the variable with the values proposal 0043 leaves it, `registry-managed` and `noop`. OD-3 records the alternative.
- Every consumer decodes a response body, a batch body, and an envelope by the SPEC-2(b) steps, and Go conforms where its standard decoders differ. Base64 is accepted only in canonical form, so a line break is refused everywhere, and an unpaired surrogate escape is refused. Go reads a `load_artifact` body only through `version.ParseLoadResponse` and its exact-name member maps. OD-1 and OD-2 in "Open questions" record the alternatives.
- The SDKs recompute `delivery_hash` under every policy, including `never`. The §6.4 overlay path is exempt.
- The shared Go check lives in `pkg/sign` (`sign.DeliveryCheck`). The manifest-body derivation is one function, `manifest.ManifestBodyOf`, used by the MCP server and sync.
- The Python SDK resolves its policy and keys in `Client.__init__`. The TypeScript SDK resolves them in `Client.fromEnv`, or, for a directly constructed client, once in a memoized promise awaited before its first registry request. `new Client(...)` stays free of I/O and of Node imports.
- The Python Ed25519 primitive comes from `cryptography` as the optional extra `podium-sdk[verify]` (OQ-1 asks the reviewer to confirm). §7.6.3 states the refusal when the extra is missing, and the documented Python install commands, the user install lines and the contributor test instructions alike, name the extra (SPEC-7(b), DOC-1 items 3, 10, 12, 13, and 14). Hash recomputation uses `hashlib` alone. TypeScript computes SHA-256 and verifies Ed25519 through the Web Crypto API (`globalThis.crypto.subtle`), which Node 20 provides, and adds no dependency. The one runtime rule this proposal makes is CODE-8 "Runtime boundary"; whole-SDK edge-runtime support is a Non-goal, and OD-4 records the alternative.
- Every consumer frames a fetched `manifest_body_url` document and its derived body as the fetched bytes. An SDK returns and materializes that document as text decoded with U+FFFD replacement, and SPEC-1 and SPEC-7(b) state this as the one exception to identical materialized output.
- The procedure fixes the outcome of the members the record frames and the members a consumer reads to fetch and verify. A Go consumer reads a member outside the record, such as `layer`, by exact name and refuses it at the wrong JSON type, and an SDK copies it without a type check (SPEC-2(b) closing paragraph).
- An SDK refuses a `PODIUM_VERIFY_SIGNATURES` or `defaults.verify_signatures` value other than `never` or `always` and never treats it as unset (SPEC-7(b)).
- Vectors regenerate with `UPDATE_GOLDEN=1 go test ./test/vectors/` through `internal/testharness.AssertGoldenFile`. No `UPDATE_VECTORS` variable is introduced.
- Server-source sync resolves its policy and key set at the point SPEC-6(a) states and CODE-3(b) implements, through one memoized `sync.DeliveryCheckFunc` that `cmd/podium` passes to every sync call. `cmd/podium` holds no per-command condition for it, and a `*sync.DeliveryConfigError` exits 2 (CODE-3, CODE-4).
- Only `podium-mcp` compares ingest times (§6.5). Sync and the SDKs frame `artifact_revision` verbatim and add no revision check, state, or public field (SPEC-9, CODE-5).
- An unkeyed server-source sync against a remote registry now exits 2 with `config.signature_provider_unavailable` on every route that resolves under SPEC-6(a), which the CODE-4 route table lists. This is a pre-1.0 MINOR-bump break with no shim or legacy flag. The §7.8 Pattern A workflow, the §13.11.6 migration procedure, and the §14.5, §14.6, §14.11, and §14.15 scenarios set the verification key (SPEC-6(c), SPEC-6(d)).

CODE-5 updates them.
- **There must be one manifest-body derivation.** The MCP server derives the body through `manifest.ParseSkill` or `manifest.ParseArtifact`, and leaves it unset on a YAML parse error (`cmd/podium-mcp/large_resources.go`). The SDKs use a delimiter regex that ignores YAML. `manifest.ManifestBodyOf` is the delimiter split, the MCP server and sync both call it, and the vectors pin the CRLF, leading-blank-line, no-trailing-newline, and no-frontmatter cases.
- **JavaScript's default string sort orders UTF-16 code units.** A path in U+E000 to U+FFFF sorts after a non-BMP path under `Array.prototype.sort` and before it in UTF-8 byte order. TypeScript sorts with a byte-wise comparison of the `TextEncoder` UTF-8 encodings. Python's `sorted` on `str` orders code points, which equals UTF-8 byte order for a string that holds no unpaired surrogate. The §4.7.10 JSON rule refuses a body that holds an unpaired surrogate escape, so no path that reaches the sort holds one. The vectors carry a pair of such paths.
- **Go's standard decoders are not the procedure.** `json.Unmarshal` into a struct matches member names case-insensitively, treats `null` as the zero value, and replaces an unpaired surrogate escape with U+FFFD. `base64.StdEncoding` skips `\r` and `\n` and accepts non-zero pad bits. Struct decoding also decodes every occurrence of a repeated name, so a mistyped earlier occurrence or a mistyped case variant of a field's name fails the whole decode with an `UnmarshalTypeError` even though step 1 or step 2 accepts the body. The Go consumers therefore read every member of a `load_artifact` body only through `version.ParseLoadResponse` and the exact-name member maps it returns, and never struct-decode the whole body, and `pkg/sign` decodes envelopes only through `version.DecodeJSONObject` and `version.DecodeBase64`. A new Go consumer that unmarshals the body into its own struct reproduces every divergence TEST-1 pins and refuses bodies the SDKs verify.
- **The SDK parsers drop the earlier of two same-named members.** `json.loads` and `JSON.parse` keep only the later member, so a depth or surrogate check on the parsed value never sees the earlier one, which the Go byte scan refuses. Both SDKs run the depth and surrogate scan on the decoded text before parsing (CODE-7, CODE-8). Python also parses numbers with `parse_int=_JsonNumber`, because converting an integer longer than 4300 digits raises `ValueError` on a body Go and TypeScript accept. `plain_json` converts each `_JsonNumber` back after the step-2 checks, so a link's `size` in `LoadedArtifact.large_resources` stays an `int`.
- **A path-keyed plain object drops `__proto__` in TypeScript.** Assigning `obj["__proto__"] = v` sets the prototype. `delivery.ts` keys every path-keyed collection with `Map`, every path-keyed public object that `index.ts` builds from those maps is built with `Object.fromEntries` (CODE-8), and a TEST-1 case serves a resource named `__proto__`.
- **Both SDKs fetch a link's `url` member before its `presigned_url` today.** `_apply_manifest_body_url` and `_materialize_canonical` (`client.py`) and `normalizeLink` (`sdks/podium-ts/src/index.ts`) prefer `url`, which the registry never serves, so a body that adds an unknown `url` member would be fetched from a different place than Go fetches it. CODE-7 and CODE-8 read the exact-name `presigned_url` alone. A caller-built Python `LoadedArtifact` whose `large_resources` link is keyed `url` therefore raises `MaterializeError`, so TEST-4 migrates the existing caller-built cases in `test_client.py` to `presigned_url`, and CL-1(a) records the key.
- **The Python batch path drops each reference's `content_hash`.** `BatchResult.materialize` (`client.py`) builds `{"url": ...}` alone, so a presigned batch resource would never be checked. CODE-7 carries the hash.
- **Both SDKs write a resource before fetching the next.** "Fetch all, check all, then write" requires restructuring `_materialize_canonical` and `materializeCanonical`, so a later mismatch leaves no earlier file of the artifact on disk.
- **The SDK suites become non-hermetic under the new default.** A developer with `~/.podium/standalone/registry-signing.key` or `PODIUM_SIGNATURE_VERIFY_KEY` gets `always` in every existing test. TEST-4 and TEST-5 isolate `HOME` and the signing variables suite-wide.
- **The end-to-end CLI and the booted server have different `HOME` directories.** `runBin` gives each CLI subprocess its own `HOME` (`test/e2e/helpers_test.go`), so the CLI never finds the server's key file, and `mergeEnv` does not scrub the signing variables from the developer's shell. TEST-3 adds a helper that points `PODIUM_SIGN_KEY_PATH` at the server's key file.
- **End-to-end tests skip silently on macOS.** Run `test/e2e` on Linux, or grep the output for `SKIP`, before claiming the fixture migration is complete.
- **`test/integration/delivery_attestation_test.go` borrows `sensitivity` from a single load to recompute a batch hash.** CODE-6 removes the workaround; a test that still borrows it hides a missing field.
- **This proposal builds on proposal 0043, which has landed.** 0043 restricts the MCP server's `PODIUM_SIGNATURE_PROVIDER` to `registry-managed` and `noop`, deletes `buildSignatureProvider`, replaces the §6.2 `PODIUM_SIGSTORE_TRUST_ROOT_PEM_FILE` row, and rewrites the §6.2 `PODIUM_SIGNATURE_PROVIDER` row and the §6.9 "no verification material" row. 0043's S2 (SPEC-2, SPEC-3) lands before S1, and 0043's S6 (CODE-5) lands before S4 and S7. ## Current state and the gap

Only `podium-mcp` recomputes `delivery_hash` and applies the §4.7.9 policy to `delivery_signature` (`cmd/podium-mcp/main.go` `verifyServedArtifact`, `verifyDeliveryHash`, and `enforceSignaturePolicy`). The spec says this is intended. §4.7.10 states that "Server-source `podium sync` (§7.5) and the language SDKs (§7.6.2) receive the delivery fields and neither recompute nor verify them", and §6.6 step 2 presents the check as an MCP step. The code matches the spec in three places.

### Server-source sync checks nothing

`serverLoadResponse` (`pkg/sync/server.go`) decodes no `version`, `sensitivity`, `delivery_hash`, or `delivery_signature`. Its `large_resources` entries decode only `presigned_url`, and `fetchServerRecord` writes the fetched large-resource bodies without checking them. The only digest check is `restoreManifestDocument`, which also never re-derives `manifest_body` from a fetched document. `pkg/sync` never reads `defaults.verify_signatures`, although `pkg/sync/config.go` declares it.

### Both SDKs pass the fields through unverified

The Python SDK copies the fields on single loads and on batch envelopes (`sdks/podium-py/podium/client.py`), with a comment saying they are passed through unverified. The TypeScript SDK does the same (`sdks/podium-ts/src/index.ts`). Neither SDK has SHA-256, Ed25519, or §4.7.6 framing code. Neither checks a fetched `manifest_body_url` document or a fetched large resource against its link hash.

### Raw HTTP clients have no procedure

§7.2 defines `delivery_hash` and `delivery_signature` and gives no procedure. The registry-managed envelope format, a `{"key_id","signature"}` JSON object with a standard-base64 Ed25519 signature over the 32 raw digest bytes (`pkg/sign/registry_managed.go`, `pkg/sign/sigstore.go`), appears nowhere in the spec, and its code comment calls it internal to one deployment. §7.2 also never defines `manifest_body_url`, `resources_base64`, or the link object, and §13.12 names the link field `url` where the registry serves `presigned_url`.

The SDKs, server-source sync, and raw HTTP callers therefore trust whatever the network delivers, and the registry's §13.4 stored-row admission is their only protection.

### Gaps that block a direct port

- The §7.6.2 batch envelope carries no `sensitivity` (`pkg/registry/server/batch_load.go`). The batch `delivery_hash` frames `res.Sensitivity` (`pkg/registry/server/delivery.go`), so an SDK cannot recompute a batch entry's hash from the envelope alone.
- The reusable glue lives in package main of `cmd/podium-mcp`, where `cmd/podium` cannot import it: `verifyDeliveryHash`, `resolveSyncYAMLPolicy`, the `registry-managed` arm of `resolveVerifier` (proposal 0043 removed `buildSignatureProvider`), and `registryManagedVerifyKey` in `cmd/podium-mcp/main.go`, and `verifySignaturesFromSyncYAML` in `cmd/podium-mcp/cliconfig.go`.
- No cross-language test vectors exist. The only delivery-hash vector is the Go literal in `pkg/version/version_test.go`.
- §4.7.9 defines one consumer default, `always` (§6.2). A default that depends on whether a key is configured needs its own definition; without one, a set but malformed `PODIUM_SIGNATURE_VERIFY_KEY` could select `never` and fail open.
- Python's standard library has no Ed25519 primitive, and the Python SDK declares no runtime dependencies (`sdks/podium-py/pyproject.toml`). Node 20 (`engines >=20`, `sdks/podium-ts/package.json`) carries SHA-256 and Ed25519 both in `node:crypto` and in the global Web Crypto `crypto.subtle`. The TypeScript SDK targets the Node versions its `engines` field names, and CODE-8 "Runtime boundary" lists its existing Node touchpoints.

## Decisions

- **Implement verification in sync and the SDKs (user decision).** Every `pkg/sync` entry point that loads from a server source runs the check: `Run`, `Watch`, `Override`, `FetchRecords`, `ResolveEffectiveView`, `Render`, and `RunMarketplace`, all through `resolveRecords`, which also resolves the policy and key set on first use (CODE-3(b)). `SaveAs` and `ProfileEdit` load no record and are unchanged. `Override` (`pkg/sync/override.go`) writes its toggle change to `sync.lock` before it calls `Run`, and `Run` with `PreserveToggles` reads those toggles back from disk, so a refused record leaves the toggle change recorded and writes no materialized file and no materialized-path update; the next manual `podium sync` resets the toggles (§7.5.5). §7.5 (SPEC-6) states this outcome.
- **Error codes are reused.** `materialize.content_hash_mismatch` covers a missing or differing delivery hash, a body that fails the §4.7.10 step 6 check, and a `load_artifact` body or batch entry that fails §4.7.10 steps 1 to 4, which `podium-mcp` reported as `materialize.invalid_base64` for non-canonical base64. `materialize.signature_invalid`, `materialize.signature_missing`, and `config.signature_provider_unavailable` keep their meanings.
- **One code for a link mismatch in every consumer.** The spec names no code for a fetched body that fails the §4.7.10 step 6 check, and the MCP server wraps it as `materialize.fetch_failed`, which the spec never defines. Sync and the SDKs report `materialize.content_hash_mismatch`, and leaving the MCP server on a different code for the same failure would make the deployment modes diverge (§2.2). The MCP server changes, and §6.6 step 1 and §6.9 state the code.
- **Server-source sync uses the MCP server's policy and key resolution.** The order is `PODIUM_VERIFY_SIGNATURES`, then `defaults.verify_signatures` across the §7.5.2 scopes (with the stale-`never` warning), then `always`, followed by the §4.7.9 key order. Sync reads no provider name (SPEC-4(e), CODE-4). An unkeyed server-source sync against a remote registry, such as CI with no `PODIUM_SIGNATURE_VERIFY_KEY`, now exits 2 with `config.signature_provider_unavailable`. A keyed sync against a registry that serves an empty `delivery_signature` fails with `materialize.signature_missing`. A sync on the standalone registry's own machine resolves the default key file and needs no setup.
- **The glue moves into `pkg/` and is not copied.** `pkg/materialize` is the disk writer (atomic writes, merges, and the seccomp sandbox), and its only internal import is `pkg/adapter`. The delivery check is a hash-and-signature concern whose parts already live in `pkg/version` (`DeliveryRecord`, `DeliveryHash`) and `pkg/sign` (`EnforceVerification`, `ErrSignatureMissing`). `sign.DeliveryCheck` sits in `pkg/sign/delivery.go` and imports `pkg/version`, which imports nothing internal, so no cycle forms. Verifier construction goes to `pkg/sign/consumer.go`, the manifest-body derivation to `pkg/manifest`, and `sync.yaml` policy discovery to `pkg/sync`.
- **The SDKs always recompute.** Recomputing `delivery_hash` needs no key, so it runs on every registry-served single load and every `ok` batch entry under every policy.
- **Only `podium-mcp` compares ingest times (§6.5).** Sync and the SDKs frame `artifact_revision` verbatim, because the delivery hash covers it, and do nothing else with it. They check no format, keep no mark or session reference, write the value to no `sync.lock` field, return no `materialize.stale_resolution`, and add no public SDK field, as proposal 0040's Non-goals state. A comparison in sync would need persisted state per target and a reset command, and the SDKs hold no cache directory to key a mark under. The delivery check this proposal adds needs neither. The §6.5 check (`checkFreshness` in `cmd/podium-mcp/main.go`) stays in `cmd/podium-mcp` and runs after the shared `DeliveryCheck.Verify` (CODE-5).
- **SDK policy order.** The constructor argument (`verify_signatures=`, `verifySignatures:`), then `PODIUM_VERIFY_SIGNATURES`, then `defaults.verify_signatures` across the §7.5.2 scopes, then the SDK default. The SDK default is `always` when a verification key is configured and `never` otherwise, so SDK use against public and standalone registries with no key distributed keeps working. Proposal 0038 relied on the same reasoning for anonymous SDK use.
- **"Configured" fails closed.** A key is configured when the SDK client is given a key list, `PODIUM_SIGNATURE_VERIFY_KEY` is non-empty, `PODIUM_SIGN_KEY_PATH` is non-empty, or a file exists at `~/.podium/standalone/registry-signing.key`. A configured key that does not parse selects `always`, and construction or the first request then refuses with `config.signature_provider_unavailable`. An explicit `never` parses nothing, consistent with proposal 0031.
- **An empty variable is unset.** This matches the Go code (`pkg/sign/keyfile.go` treats `""` as unset for both key variables, and `cmd/podium-mcp` falls through to `sync.yaml` on an empty `PODIUM_VERIFY_SIGNATURES`), and §4.7.9 states it so the SDKs, which can distinguish set-empty from unset, behave the same way.
- **Sync and the SDKs read no provider name.** §4.7.10 states that a consumer verifies `delivery_signature` with the registry-managed verifier. After proposal 0043 the MCP server accepts only `registry-managed` and `noop`, and `noop` verifies nothing, so a provider name gives a consumer no choice of verifier and can only add a refusal. In the `podium` binary the variable is also the `--provider` default of `podium sign` and `podium verify`, which accept `sigstore-keyless`. If `podium sync` read it, a value valid for one subcommand would refuse another. Reading it in sync with the MCP server's values was rejected for that reason (OD-3). The earlier argument for reading it, one shared Go resolution, holds without it, because `sign.ResolveVerifier` takes no provider name (CODE-2).
- **SDK key-list argument.** Both SDKs accept the verification key set as a constructor argument (`verify_keys=` in Python, `verifyKeys:` in TypeScript) in the `PODIUM_SIGNATURE_VERIFY_KEY` list syntax, and it takes the variable's place in the §4.7.9 order. A caller that holds its keys outside the environment and the key file supplies them this way, and the two SDKs keep one contract.
- **Where each SDK resolves.** Python's I/O is synchronous, so `Client.__init__` resolves and raises (`from_env` constructs through it). The TypeScript constructor is synchronous and the SDK's file reads are asynchronous (`config.ts`, `overlay.ts`), so `new Client(...)` performs no I/O. `Client.fromEnv` awaits the resolution before constructing, and a directly constructed client resolves once, in a memoized promise that every method sending a request to the registry awaits first (CODE-8). Either way the refusal happens before any registry request, whichever method the caller invokes first, which matches the Python client's refusal at construction.
- **The TypeScript delivery check uses Web Crypto.** `delivery.ts` uses `globalThis.crypto.subtle` (`digest("SHA-256", ...)`, and `importKey("raw", key, { name: "Ed25519" }, false, ["verify"])` with `verify({ name: "Ed25519" }, ...)`), `TextEncoder` and `TextDecoder`, `DataView.setBigUint64` for the length framing, a byte-wise `Uint8Array` comparison for the path sort, and `atob` and `btoa` for base64, all of which Node 20 provides. The TEST-1 vectors pin the result against Go in the Node 20 CI lanes (the `typescript` jobs, named `podium-ts`, in `.github/workflows/test.yml` and `release.yml`). `node:crypto` would serve equally in Node. Web Crypto keeps `delivery.ts` inside the CODE-8 "Runtime boundary".
- **An invalid policy value from the environment or `sync.yaml` refuses in the SDKs.** A `PODIUM_VERIFY_SIGNATURES` or `defaults.verify_signatures` value other than `never` or `always` is an error, never an unset value, because treating it as unset would fall to the SDK default and a misconfigured `always` on an unkeyed client would silently select `never`. The Go consumers refuse the same values (`loadConfig` in `cmd/podium-mcp/main.go`). The SDKs raise `ValueError` (Python, at construction) or reject with `Error` (TypeScript, from `fromEnv` or the memoized resolution), with a message naming the value and its source, as for the constructor argument.
- **SDK failure surface.** A single load raises (Python) or rejects with (TypeScript) `RegistryError` whose `code` is the §6.10 code. A batch entry that fails becomes `status == "error"` carrying that `RegistryError`, and the other entries load. `materialize()` fetches and checks every large resource before writing any file of the artifact and raises `materialize.content_hash_mismatch` on a mismatch. An invalid policy value raises `ValueError` (Python) or throws `Error` (TypeScript), matching the existing cache-mode validation.
- **The batch envelope gains `sensitivity`.** Deriving it from the served frontmatter would put YAML parsing into each SDK's hash input. Exempting the batch path would leave `load_artifacts` unverified. Borrowing the value from a single load is a test workaround.
- **The load-time recompute uses link and reference hashes.** A large resource contributes its link's `content_hash`, and a batch resource its reference's `content_hash`, as `verifyDeliveryHash` does today. The consumer then runs the §4.7.10 step 6 check on each body it fetches or decodes before returning or writing it, so the attestation covers every byte.
- **The wire decoding is one algorithm, and Go conforms to it.** The SDKs and raw HTTP clients now decode the response and the envelope. Each language's standard decoders differ on inputs the registry never emits:
  - Go: struct decoding folds member-name case, reads `null` as the zero value, and replaces an unpaired surrogate escape with U+FFFD; `base64.StdEncoding` skips `\r` and `\n` and accepts non-zero pad bits.
  - Python: `json.loads` accepts `NaN` and, given bytes, a byte order mark, keeps unpaired surrogates, raises `ValueError` on an integer literal longer than 4300 digits, and drops the earlier of two same-named members before any check on the parsed value can see it.
  - TypeScript: `JSON.parse` keeps unpaired surrogates, drops the earlier of two same-named members, and places a repeated member at its first position, `Buffer.from(s, "base64")` accepts the URL-safe alphabet, missing padding, and stray characters, and the `atob` that CODE-8 uses in its place accepts whitespace, missing padding, and a non-zero pad bit.

  §4.7.10 (SPEC-2(b)) therefore states the decoding as steps: a JSON rule, exact typed members, canonical base64, and byte-compared paths. §4.7.9 (SPEC-2(a)) applies the same JSON and base64 rules to the envelope. Each rule picks the reading that every language can implement in a few lines. For base64 that reading is the round trip: a value is accepted when re-encoding its decoded bytes reproduces it, so line breaks are refused everywhere. For surrogates it is refusal, because `JSON.parse` cannot report the order of two names that collide after replacement. Where a Go library behaves differently, Go changes. OD-1 and OD-2 record the alternatives. The registry emits compact `encoding/json` output, canonical `StdEncoding` (`encodeBinaryInlineResources` in `pkg/registry/server/server.go`, and `Server.batchResource` in `batch_load.go`), valid UTF-8, and one placement per path. `Sign` has marshalled `{key_id, signature}` with `StdEncoding` since the envelope existed (0ed8fc0d, fe2d1118). The rules therefore refuse no body and no envelope, stored or served, that any release produced, including the rows that stored-row admission (`Registry.admitSignature`, `pkg/registry/core/admit.go`) and the rehash pass (`rehashPlanner.classify`, `internal/serverboot/rehash.go`) verify through the same decoder. The comment in `pkg/sign/registry_managed.go` that calls the envelope format internal is corrected (CODE-2).
- **A path is served once, compared as bytes.** The registry places each resource reference in exactly one of `resources` and `large_resources` (`Server.handleLoadArtifact` in `pkg/registry/server/server.go`). The Go consumers overwrite an inline body with the fetched one before hashing (`fetchServerRecord` in `pkg/sync/server.go`, `mcpServer.fetchLargeResources` in `cmd/podium-mcp/large_resources.go`), but the SDKs return the inline map unchanged, so an inline body added at a linked path would be returned under an authentic hash. SPEC-2(b) step 4 refuses a `load_artifact` body that names one path in both maps, and a batch entry whose `resources` array names a path more than once. Paths compare as UTF-8 bytes with no normalization. A name repeated inside one JSON object is resolved by step 1 (the later member is used) in all three languages' parsers, so it is not a repeated path. `ParseLoadResponse` and `ParseBatchResponse` apply the rule in Go, and no separate path helper exists.
- **A fetched manifest document is framed as bytes.** The registry frames `string(res.Frontmatter)` and `string(res.SkillRaw)` byte for byte (`deliveryRecordOf` in `pkg/registry/server/delivery.go`), and sync frames the fetched bytes (`restoreManifestDocument` in `pkg/sync/server.go`). The SDKs therefore frame the fetched bytes and decode only the text they return, with each invalid UTF-8 sequence replaced by U+FFFD, as the TypeScript SDK's `TextDecoder` already does (`Client.loadArtifact` in `sdks/podium-ts/src/index.ts`). `materialize()` writes that text (`_materialize_canonical` in `sdks/podium-py/podium/client.py`), while sync writes the fetched bytes (`fetchServerRecord` and `restoreManifestDocument` in `pkg/sync/server.go`), so SPEC-1 and SPEC-7(b) state the difference as an exception to identical materialized output. Requiring UTF-8 at ingest was rejected because it adds an ingest refusal and a spec rule outside this proposal's scope. Having `materialize()` write the fetched bytes was rejected because it adds a byte-carrying field to each SDK's returned artifact type solely for manifest documents that are not valid UTF-8.
- **The vectors govern the SDKs, and the spec governs the vectors.** `test/vectors/delivery-record.json` is written by one Go test through `internal/testharness.AssertGoldenFile` and regenerated with `UPDATE_GOLDEN=1`. Each case states its expected outcome in the Go test source, written from SPEC-2: `ok` with the delivery hash, or the refusal code. The generator fails when Go's result differs from that statement, so a Go library deviation fails in Go before it reaches the file. Without the variable, the Go test fails when the file differs from what Go computes, so a serialization change fails the Go, Python, and TypeScript suites together. Python and TypeScript run their own decoders on each case's raw bytes, and they take the record tag and field order from module constants that mirror `pkg/version.DeliveryHash`. A change to the record, such as proposal 0040's `/2`, is then one spec edit to §4.7.10 and to §7.2 "Record fields", one constant per language, a regenerated file, and a code edit at each site the Watch-out bullet on record changes lists. The vector keys derive from a fixed test-only seed.
- **The procedure stops at the record.** It fixes the outcome of every member the record frames and of the members a consumer reads to fetch and verify, which §7.2 "Record fields" (SPEC-2(e)) names, and step 2 ignores every other member, `extends_pin` included, which no consumer reads. A Go consumer still reads some members outside the record into typed values: `layer` in sync and on the MCP server, and `size` and `content_type` of a link on the MCP server. It reads each one by exact name from the member maps `version.ParseLoadResponse` returns (`Served.Members`, `Link.Members`) and unmarshals that single raw value, so a case variant or an earlier repeated occurrence of the name never reaches the decode. Such a consumer refuses a body in which the exact-name member it reads has the wrong JSON type. An SDK applies no type check to these members and proceeds: the Python SDK copies a link's `size` and `content_type` into `large_resources` as parsed (CODE-7), and the TypeScript SDK copies each into `LargeResourceLink` only when it has the declared JSON type and otherwise leaves it `undefined` (CODE-8). The registry serves each of these members with the type §7.2 "Other response members" gives it, and either outcome materializes only bytes the verified record covers. Extending typed decoding to every non-record member in three languages was rejected as unbounded.
- **Python Ed25519 is an optional extra.** `podium-sdk[verify]` pulls `cryptography>=42`. A client whose resolved policy is `always` and that cannot import `cryptography` refuses construction with `config.signature_provider_unavailable`, naming the extra, and §7.6.3 (SPEC-7(b)) states that refusal. An SDK with no key configured runs under `never` and needs only `hashlib`. A standalone user on the registry's own machine has a key file at the default path and so resolves `always`, which is why the documented Python install commands name the extra (DOC-1 items 3, 10, 12, and 14). The contributor test instructions install `-e '.[verify]'` (DOC-1 item 13), because the TEST-4 signing cases fail without the extra. OQ-1 asks the reviewer to confirm this over a required dependency or a vendored verifier.
- **Resolution is lazy.** `pkg/sync` resolves the policy and key set at the one point CODE-3(b) names, which implements the SPEC-6(a) predicate, through the resolver `cmd/podium` passes. `cmd/podium` holds no per-command condition for it, and the CODE-4 route table lists the routes as consequences. Predicting the load in `cmd/podium` was rejected because it copies conditions that live in `pkg/sync` (the early returns in `Run`, `Override`, `RunMarketplace`, and `ResolveEffectiveView`), and each copy drifts from its source. A second resolve in `Override` before its `WriteLock` was rejected for the same reason (OD-5). It copies `Run`'s source condition into `Override` only to avoid writing a toggle change that a refused record already leaves in the lock, and the next manual `podium sync` resets that change (§7.5.5). The cost is that a resolution refusal leaves in place what the invocation completed before it, as SPEC-6(a) states.
- **The read CLI stays unchecked, and the spec says so.** `podium artifact show` prints a served record and writes nothing to a harness target (`artifactShow` in `cmd/podium/main.go`). Extending the check to it would add a second refusal surface and a key requirement to a browse command, so §4.7.10 scopes the check to the MCP server, server-source sync, and the SDKs, and §4.7.10 and §7.6.1 state that the read CLI runs no delivery check (SPEC-1, SPEC-7(c)). §7.6.1's interchangeability sentence names the verification outcome as the exception, so an SDK refusal of a record the read CLI prints is specified behavior rather than drift.

## Spec amendment: §4.7.10 consumers of the delivery check

**SPEC-1.** `spec/04-artifact-model.md`, §4.7.10 "Delivery Attestation". Replace the paragraph that begins "On a `load_artifact` call the MCP server recomputes the delivery hash" and ends "they differ in the attestation channel." with:

> The MCP server (§6.6), server-source `podium sync` (§7.5), and the language SDKs (§7.6.3) run the delivery check on every registry-served record they return or materialize. The read CLI (§7.6.1) prints a served record without the delivery check and writes nothing to a harness target. On each `load_artifact` response, and on each `ok` entry of a §7.6.2 batch response, the consumer reconstructs the delivery record by the verification procedure below, recomputes the delivery hash, and compares it to the served value before it reads any policy input out of the record, caches it, returns it, or writes any byte to disk. A response or entry that carries no `delivery_hash` fails the comparison. A failed comparison is refused with `materialize.content_hash_mismatch` under every §4.7.9 policy. The consumer then applies its §4.7.9 verification policy to `(delivery_hash, delivery_signature)`. Only the MCP server compares the served ingest time with an earlier one (§6.5). Server-source `podium sync` and the language SDKs frame it into the record they verify and compare it with no earlier value, so a `latest` answer whose ingest time is below one they received earlier is delivered. A §6.4 workspace overlay load is served from the consumer's own filesystem, carries no delivery record, and is outside the check. A filesystem-source `podium sync` composes and materializes in one process, so it has no delivery to attest, computes no delivery hash, and runs no delivery check. The delivery-hash comparison is identical across these consumers and modes (§2.2). The materialized output is identical across them as well, except that a language SDK returns and materializes a `manifest_body_url` document that is not valid UTF-8 as text decoded with U+FFFD replacement (§7.6.3). The consumers differ in the §4.7.9 policy they apply when none is configured and in how a refusal surfaces (§6.9).

SPEC-1 lands in the same spec commit as SPEC-2, which supplies the procedure the paragraph cites, SPEC-5, which adds the batch `sensitivity` member the batch recompute needs, and SPEC-7, which creates §7.6.3 and states the read-CLI exception in §7.6.1.

## Spec amendment: §4.7.9 and §4.7.10 verification procedure and envelope format

**SPEC-2.** Every anchor below lands in the S1 commit.

(a) `spec/04-artifact-model.md`, §4.7.9 "Signing". Insert a new paragraph immediately before the paragraph that begins "Every registry-managed envelope carries a `key_id`":

> A registry-managed envelope is a JSON text that satisfies the §4.7.10 JSON rule and whose top-level value is an object. Its `signature` member is a string holding the canonical base64 encoding (§4.7.10) of a 64-byte Ed25519 signature. The signed message is the 32-byte SHA-256 digest that the attested `sha256:<hex>` value encodes, rather than the text of that value. Its optional `key_id` member is a string. A verifier reads these two members by exact name, ignores every other member (including one whose name differs from `signature` or `key_id` only in letter case), and treats a member whose value is `null` as absent. An absent `key_id`, or one that names no key in the verification key set, names no key. An envelope is refused with `materialize.signature_invalid` when it fails the JSON rule, when its top-level value is not an object, when it has no `signature`, when its `signature` or `key_id` is present and is not a string, or when its `signature` is not the canonical encoding of exactly 64 bytes. The registry writes the envelope as `{"key_id":"<key_id>","signature":"<base64>"}` with no whitespace.

(b) `spec/04-artifact-model.md`, §4.7.10. Insert two new paragraphs immediately after the SPEC-1 paragraph and before the paragraph that begins "The attestation states that the registry composed and served these bytes.":

> **Verification procedure.** A consumer verifies a `load_artifact` response body (§7.2), and each `ok` entry of a §7.6.2 batch response body, by the steps below. A refusal in steps 1 to 6 uses `materialize.content_hash_mismatch`.
>
> 1. *JSON rule.* The body is an RFC 8259 JSON text. It is valid UTF-8, carries no byte order mark, and nests arrays and objects no deeper than 64 levels, where the top-level array or object is level 1. Its top-level value is an object, or for a batch body an array of objects. `NaN` and `Infinity` are not JSON. In a member name or a string value, a `\u` escape of a UTF-16 surrogate is valid only as a high surrogate escape followed directly by a low surrogate escape, and a body that holds any other surrogate escape fails the rule. The depth and surrogate conditions apply to the whole text, including a member that a later member of the same name replaces. When two members of one object have the same name, the later member is used. A body that fails this rule yields no record and is refused; for a batch, the whole call is refused.
> 2. *Members.* The consumer reads, by exact name, the members that §7.2 "Record fields" names for a `load_artifact` body and the §7.6.2 "Delivery record" bullet names for a batch entry, and it ignores every other member, including `extends_pin`, `layer`, and a link object's `size` and `content_type`. A member whose value is `null` is absent. An absent string is the empty value, and an absent `resources_base64` or `inline_base64` is false. A body or entry is refused when one of these members is present with a JSON type other than the one §7.2 "Record fields" gives it in a `load_artifact` body or the §7.6.2 "Delivery record" bullet gives it in a batch entry, when a link object's `presigned_url` is absent or empty, or when a batch reference has no `path`. A batch reference whose `presigned_url` is non-empty is a link reference, and the consumer ignores its `inline` and `inline_base64` after this type check. Every other batch reference is an inline reference, and its body is its `inline` value, empty when `inline` is absent.
> 3. *Base64.* A base64 value is accepted only in its canonical form: decoding it with the RFC 4648 §4 alphabet and re-encoding the bytes with that alphabet and `=` padding must reproduce the value exactly. A line break, whitespace, a URL-safe character, missing padding, or a non-zero pad bit makes a value non-canonical. When `resources_base64` is true every `resources` value is base64, and when an inline batch reference's `inline_base64` is true its `inline` value is base64. A non-canonical value is refused.
> 4. *Paths.* A resource path is the UTF-8 encoding of its decoded string, compared byte for byte without normalization. A `load_artifact` body whose `resources` and `large_resources` name the same path is refused. A batch entry whose `resources` array names a path in more than one reference is refused.
> 5. *Record.* Each record field other than a resource content hash is the UTF-8 encoding of the member that §7.2 "Record fields" names for it, read from the `load_artifact` body or, for a batch entry, from the member the §7.6.2 "Delivery record" bullet gives it. The resource content hash of a path in `large_resources` is that link's `content_hash`, including an empty one. The resource content hash of every other `resources` path is `sha256:` followed by the lowercase hexadecimal SHA-256 digest of its body, which is the UTF-8 encoding of the value, or the decoded bytes when `resources_base64` is true. A batch entry takes each resource content hash from its reference's `content_hash`. When a `load_artifact` body carries `manifest_body_url`, the consumer fetches the document its link names, checks the fetched bytes by step 6, places the document in `skill_raw` for a skill and in `frontmatter` for every other type, and derives the manifest body from it. The record frames the document and the derived body as the fetched bytes, unmodified. The derivation applies one rule. The document opens with `---`, an optional CR, and an LF. The frontmatter closes at the earliest later position that holds an optional CR, an LF, and `---`. The body is every byte after that closing `---`, with leading CR and LF characters removed. A document that does not open and close this way has an empty body. The document step does not apply to a batch entry.
> 6. *Bodies.* Each body fetched through a link, and the body of each inline batch reference after step 3, is checked before the consumer returns or writes it. The check compares `sha256:` and the lowercase hexadecimal digest of the body with the link's or reference's `content_hash` as exact strings, and a body that does not match is refused. A link or reference whose `content_hash` is empty is not checked on its own. For a large-resource link or a batch reference, the empty value is the resource content hash the record frames, so it fails step 7. A `manifest_body_url` document is framed into the record itself, so an empty link `content_hash` skips only this check, and step 7 still covers the document's bytes.
> 7. *Compare and verify.* The consumer serializes and hashes the record by the canonical serialization above and compares the result with `delivery_hash` as exact strings. An absent or empty `delivery_hash`, or any difference including letter case, is refused with `materialize.content_hash_mismatch`. The consumer then applies its §4.7.9 policy to `(delivery_hash, delivery_signature)`, and it decodes the envelope by the §4.7.9 envelope rule only when that policy verifies a signature.
>
> The steps run before any policy input is read out of the record and before anything is cached, returned, or written. Every resource body, manifest document, and record field the consumer returns or writes is framed into the record or checked against a content hash the record frames. A member the steps do not read, such as `layer`, a link object's `size` and `content_type`, and the §4.7.4 lifecycle members `deprecated`, `replaced_by`, and `deprecation_warning`, lies outside the record, and a consumer that returns it returns it unattested. The touchpoints that exist today stay as they are and are outside this rule: the constructor's `process.env.PODIUM_OVERLAY_PATH` read, `fromEnv` (and `config.ts`), the §6.4 overlay lookup (`overlayIndex` and `overlayForDomain` in `index.ts`, and `resolveOverlayPath` and `LocalOverlay.load` in `overlay.ts`), the `process.env` reads in `resolveDeviceFlow` and `login`'s `process.stderr` writes, and `materialize()` (the `node:fs/promises` import in `materializeCanonical`). The three bounded touchpoints that CODE-8 adds on the calls listed above are these:
  - `delivery.ts` imports no `node:` module, statically or dynamically, and references no `Buffer` or `process`.
  - `resolveVerification`, which `verification()` runs before every registry request, loads `node:fs/promises` and `node:path` only through the guarded import the `config.ts` bullet states and reads `process` only through `globalThis.process?.`.
  - The stale-`never` `process.emitWarning` runs only after a `sync.yaml` read succeeded, so it is reached only where a `node:` import already succeeded.

  No module gains a static `node:` import, so importing the SDK stays safe as the header comment of `config.ts` states. A runtime without `crypto.subtle` is outside the `engines` range, and a load there fails with the runtime's own error. TEST-5 "runtime boundary" pins the rule.
- `ClientOptions` gains `verifySignatures?: "never" | "always"` and `verifyKeys?: string`. The constructor validates an explicit `verifySignatures` as it validates `cacheMode` (throw `Error` on a bad value) and performs no I/O.
- `Client.fromEnv` awaits `resolveVerification` before `new Client(...)`, so an unusable key under `always` rejects `fromEnv` with `RegistryError("config.signature_provider_unavailable", ...)`. A directly constructed client resolves once, in a memoized promise held by a private `verification()` method; that promise rejects with the same code, or with the invalid-policy `Error`. Every `Client` method that sends a request to the registry awaits `verification()` before its first request: the private `get` helper (which carries `loadDomain`, the catalog read, `searchDomains`, `searchArtifacts`, `loadArtifact`, `dependentsOf`, and `previewScope`), the `loadArtifacts` batch POST, `subscribe` before its fetch, and `resolveDeviceFlow` before its `discoverIdp` call against the registry, which `startLogin` and `login` reach. The sites outside `get` each issue their own request, so TEST-5 pins each one separately. A request site added later, including proposal 0038's login changes, awaits it the same way. Presigned object-store fetches are not registry requests and do not await it. A client built by `fromEnv` holds an already-resolved promise. `client.verifySignatures` is a getter returning the resolved policy, or `undefined` before resolution. The stale-`never` warning goes through `process.emitWarning`.
- `delivery.ts` gains `manifestBodyOf(doc: Uint8Array): Uint8Array`, the §4.7.10 derivation over bytes, and it replaces `manifestBodyFrom`, whose only caller is `loadArtifact`. `loadArtifact` calls `parseLoadResponse`, which refuses a shared path and every other step-1 to step-4 failure with `RegistryError("materialize.content_hash_mismatch", ...)` before the manifest fetch. It checks the `manifest_body_url` link `content_hash` on the raw `arrayBuffer()` bytes, derives the body with `manifestBodyOf`, and places the document and body bytes, never the decoded text, into the record that `parseLoadResponse` returned through `placeManifestDocument`, the `delivery.ts` port of `Served.PlaceManifestDocument`. It recomputes, applies the policy, and only then sets `data.manifest_body` and `data.skill_raw` or `data.frontmatter` to the `TextDecoder` (non-fatal) decoding of those bytes, as `loadArtifact` decodes the document today.
- Batch parsing runs `parseBatchResponse`, which refuses a body that fails step 1 as a whole, so `loadArtifacts` rejects with `RegistryError("materialize.content_hash_mismatch", ...)` and returns no entries, including those of a chunk it already fetched (SPEC-7(b)). Per entry it classifies each reference by SPEC-2(b) step 2, as CODE-1's `ParseBatchResponse` does, and refuses a repeated path, a non-canonical `inline` value, a mistyped member, and a reference with no `path`, then checks each decoded `inline` body against its reference hash and verifies each `ok` entry; a failure becomes `status: "error"` with the `RegistryError`.
- `materializeCanonical` fetches and checks every large resource before the first write of the artifact, including `ARTIFACT.md`.
- Every per-body check in this SDK (the `manifest_body_url` document, a batch `inline` body, and a large resource) is the §4.7.10 step 6 check, as CODE-7 states for Python.
- `index.ts` keeps exporting `RegistryError`; `delivery.ts` helpers are not re-exported.

## Open questions

**OQ-1. Python Ed25519 source.** The draft stages `cryptography>=42` as the optional extra `podium-sdk[verify]`: a client whose resolved policy is `always` refuses construction with `config.signature_provider_unavailable` when the package is missing, and a client under `never` needs only `hashlib`. The alternatives are a required runtime dependency, which would be the SDK's first and would make every install carry `cryptography`, or a vendored pure-Python RFC 8032 verifier, which needs no dependency but is cryptographic code the project maintains itself. The §7.6.3 sentence on the missing extra (SPEC-7(b)) and the `[verify]` install commands (DOC-1 items 3, 10, 12, 13, and 14) follow the answer, and either alternative removes them. Does the reviewer accept the optional extra?

Each OD below records a decision whose default the text above applies. A reviewer who picks the alternative reverses the default in every section the OD names.

**OD-1. Scope of the decoding rules.** Default applied: every consumer decodes a `load_artifact` body, a batch body, and an envelope by the byte-level SPEC-2(b) and SPEC-2(a) rules, Go through `pkg/version/served.go` (CODE-1) and the SDKs through its ports (CODE-7, CODE-8), and TEST-1 pins each outcome from the spec. The alternative keeps struct decoding for the record, specifies only the envelope rule and canonical base64, and keeps each Go consumer's own record builder and a separate shared-path helper. Under the alternative, Go matches `FRONTMATTER` case-insensitively and reads `null` as empty while the SDKs do not, so consumers in different languages refuse different crafted records, although the delivery hash still refuses a forged body because each consumer frames the bytes it read. The default makes one rule authoritative and removes the SDK line-break strip, the TypeScript base64 regex, the `null` `key_id` special case, and `materialize.invalid_base64`. Every input the default refuses is one no release emits. Does the reviewer accept the default?

**OD-2. Unpaired surrogate escapes.** Default applied: SPEC-2(b) step 1 refuses a body that holds a surrogate escape outside a high-low pair. Go detects it in the `checkJSONText` byte scan, and the SDKs port the scan and run it before parsing (CODE-1, CODE-7, CODE-8). The alternative replaces each unpaired surrogate with U+FFFD and uses the later of the colliding names. It needs a TypeScript JSON tokenizer, because `JSON.parse` keeps a repeated name at its first position: with `{"\ud800":1,"\udbff":2,"\ud800":3}`, Go yields 3 and a `JSON.parse` rebuild yields 2. The default is the smaller rule, and the registry never emits an unpaired surrogate. Does the reviewer accept the default?

**OD-3. Whether server-source sync reads `PODIUM_SIGNATURE_PROVIDER`.** Default applied: server-source sync and the SDKs read no provider name, `sign.ResolveVerifier` takes the policy and the two key values, and `podium-mcp` keeps its provider switch in `resolveVerifier` (SPEC-4(e), CODE-2, CODE-4, CODE-5, TEST-3 case 18). The alternative has sync read the variable with the `podium-mcp` values, `registry-managed` and `noop`, through one `sign.ResolveVerifier(policy, name, verifyKey, keyPath)` moved from `resolveVerifier` in `cmd/podium-mcp/main.go`, and refuse any other value with `config.invalid`. The alternative gives the two consumers one configuration surface. Its cost is that a shell exporting `PODIUM_SIGNATURE_PROVIDER=sigstore-keyless` for `podium verify` makes a records-loading `podium sync` exit 2. The default holds because the variable gives sync no choice of verifier and can only add refusals. Does the reviewer accept the default?

**OD-4. TypeScript runtime scope.** Default applied: CODE-8 "Runtime boundary" is a non-regression rule, so CODE-8 adds no Node touchpoint that can fail a call that succeeds today, and whole-SDK edge-runtime support is a Non-goal. The alternative restores a guarantee that the whole load path runs in an edge runtime: guards on the §6.4 overlay lookup and on the constructor's `process.env.PODIUM_OVERLAY_PATH` read, a coded refusal for a runtime without `crypto.subtle`, SPEC-7(b) sentences stating the portability, the matching edge-case rows, and TEST-5 overlay, `process`, and `crypto` cases. The default holds because the SDK makes no edge-runtime guarantee today (`engines >=20` in `sdks/podium-ts/package.json`) and several existing calls already reach Node touchpoints. Does the reviewer accept the default?

**OD-5. Batch override resolution before `WriteLock`.** Default applied: `Override` resolves only through its `Run` call at the CODE-3(b) resolution point, so a resolution refusal leaves the toggle change in `sync.lock`, the same outcome as a refused record (SPEC-6(a), CODE-4 route table, TEST-3 case 22, TEST-6). The alternative resolves in `Override` before its `WriteLock`, so that a resolution refusal writes no toggle change. It copies `Run`'s source condition into `Override` as a second resolution site. The default keeps one resolution point, and the next manual `podium sync` resets the toggle change (§7.5.5). Does the reviewer accept the default?

## Non-goals

- Server-source sync and the SDKs gain no provider choice (SPEC-4(e)). The registry-managed key is the only delivery signer (§4.7.10).
- Neither the SDKs nor sync recompute the §4.7.6 `content_hash`. It names the stored pre-merge artifact, and the §7.5.3 lock keeps pinning the registry's value verbatim.
- No content cache is added to the SDKs or to sync, and the §6.5 cache-miss rule is unchanged.
- The attestation's limits in §4.7.10 are unchanged apart from SPEC-9(a), which names server-source `podium sync` and the SDKs among the consumers that do not detect a replay. The attestation still gives no proof that the merge is faithful, and no revision check is added to sync or the SDKs (Decisions).
- No new environment variable, `sync.yaml` key, §6.10 error code, endpoint, or SPI.
- `podium verify <artifact>` and `podium sign` (`cmd/podium/sign.go`) are not edited. `registryManagedVerifier` already resolves through `sign.VerificationKeys`.
- The other base64 decoders in `pkg/sign` keep their behavior: the Sigstore envelope's `signature` and `timestamp` (`decodeEnvelope` in `pkg/sign/sigstore.go`), the transparency-log fields (`pkg/sign/inclusion.go`, `pkg/sign/rekor.go`), and key parsing (`PublicKeyFromBase64` in `registry_managed.go` and `decodePrivateKey` in `keyfile.go`, both after `strings.TrimSpace`). SPEC-2(a) governs only the registry-managed envelope, and no consumer this proposal changes verifies a Sigstore envelope. The TEST-1 `verify_key_list` and `key_file` sections pin key-list and key-file parsing.
- Delivery verification for `podium artifact show` and the other read-CLI commands that print a served record. They write nothing to a harness target, §4.7.10 and §7.6.1 state the exception (SPEC-1, SPEC-7(c)), and a follow-up can extend the check to them.
- The omission of `Token` in `runWorkspaceTarget`'s `sync.Options` (`cmd/podium/main.go`) and in the `Options` that `Override` passes to `Run` is pre-existing and not fixed here.
- No asyncio variant of the Python SDK. Edge-runtime support for the TypeScript SDK as a whole is out of scope. The SDK targets the Node versions its `engines` field names, and §7.6's mention of edge runtimes describes consumers without setting a runtime contract. CODE-8 "Runtime boundary" keeps working each call that reaches no Node touchpoint today. It adds no guard to the overlay lookup, the constructor, `fromEnv`, the device flow, or `materialize()`, and it gives a runtime without `crypto.subtle` no §6.10 code. A follow-up proposal that specifies edge support owns those.
- No per-request timeout on SDK object-store fetches. The gap predates this proposal.

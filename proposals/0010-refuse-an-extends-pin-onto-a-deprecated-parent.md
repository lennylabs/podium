## Summary

**What changes.**

- `resolveExtendsPin` (`pkg/registry/ingest/ingest.go`) gains a deprecation map alongside the three maps it already builds, and filters deprecated candidates out of the selection set for a range reference and for an unpinned reference.
- The same function refuses an exact or content-hash pin that names a deprecated version, and refuses a range or unpinned reference left with no non-deprecated candidate, returning the existing `ingest.invalid_artifact`. The read path's §4.7.6 fallback to the full candidate set is deliberately not mirrored at ingest.
- The same function's `latest` selection is brought to the §4.7.6 definition, the most recently ingested non-deprecated version, in place of the highest semver among all candidates.
- §4.6's extends paragraph and §4.7.6 gain the sentences that state whether a child may extend a deprecated parent version, how a range or unpinned reference selects when a candidate is deprecated, and that a range or unpinned reference left with no non-deprecated candidate is refused at ingest. The spec is silent on all three today.

**Fixed decisions.**

- §4.6 settles the merge question. `load_artifact` conforms and the four column-reading surfaces are the non-conforming ones.
- Folding the inherited flag into the child's stored `deprecated` column is rejected.
- Resolving the chain on the search path is rejected.
- The refusal reuses `ingest.invalid_artifact`. No new §6.10 error code is introduced.
- The all-deprecated refusal is a second empty-candidate arm carrying its own message that names deprecation. The messages on the existing `no parent artifact %q ingested yet` and `no parent version satisfies %q` arms are left unchanged.
- The `TestSearchArtifacts_FiltersReadMergedFields` subtest "child of a deprecated parent is still returned" is deleted rather than re-fixtured with a live candidate alongside the deprecated one.
- `mergeChain` is out of scope. Proposal 0011 carries it.
- The §8.4 window and the purge's existing extends-pin guard for parents are out of scope.

## The defect

`mergeChain` inherits `deprecated` from the parent (`pkg/manifest/merge.go`, `pkg/registry/core/core.go`), so `load_artifact` reports a child of a deprecated parent as deprecated and attaches the §4.7.4 warning. Four other surfaces read the stored column, which the child never set, and therefore disagree:

- the `search_artifacts` default-exclusion filter (`pkg/registry/core/core.go`), so the child stays in default results,
- the search descriptor's frontmatter block, which is the child's authored bytes with only `extends:` removed,
- `EffectiveView`, which `podium sync` consumes (`pkg/registry/core/effective_view.go`),
- and impact analysis (`pkg/registry/core/dependents.go`).

§4.6 settles which side is right. Its "Omitted fields" paragraph states that a child omitting a frontmatter field inherits the parent's value, and it names `deprecated` among the fields a child overrides only by setting one. The `load_artifact` behavior conforms. The four column-reading surfaces are the non-conforming ones.

## Reachability

An earlier reading of this defect called it narrow, on the reasoning that a parent deprecated after the child was ingested cannot reach the child, because §4.7.6 pins an exact parent version at the child's ingest time. The pin claim is true and the conclusion drawn from it was wrong.

`resolveExtendsPin` (`pkg/registry/ingest/ingest.go`) builds its candidate set by filtering `ListManifests` on `ArtifactID` alone. It captures each candidate's version, content hash, type, and frontmatter, and never reads `Deprecated`. `version.Resolve` receives version strings and cannot filter on deprecation either. So the ordinary workflow reaches the divergence:

1. `shared/parent@1.0.0` is live. `finance/child@1.0.0` declares `extends: shared/parent@1.x`, or no pin at all, and is ingested.
2. The parent team deprecates by publishing `shared/parent@1.0.1` with `deprecated: true`, which is the only way to deprecate: the flag is per-version and there is no in-place toggle (`pkg/store/store.go`).
3. The child is published at a new `version:`, `finance/child@1.1.0`, which every maintenance release of the child does. That version has no stored row, so ingest runs the full path and `resolveExtendsPin` selects `1.0.1`, the deprecated version, and pins it.
4. `load_artifact` now reports `finance/child@1.1.0` as deprecated. Search still lists it, and `podium sync` still reports it live.

The reach is a child version bump rather than any re-ingest. An unchanged re-ingest of `finance/child@1.0.0` re-resolves the pin at `pkg/registry/ingest/ingest.go:644` but never persists it: the content hash covers the authored bytes alone (`ingest.go:1253-1267`), so a parent deprecation does not move it, `GetManifest` finds the row with an equal hash, and ingest counts the artifact idempotent and continues without calling `PutManifest` (`ingest.go:752-759`). Changed bytes at the same version are recorded as a conflict, also without a write (`ingest.go:760-766`). `pkg/registry/ingest/extends_conformance_test.go:259-262` and `docs/authoring/extends.md:43` both state the same thing: the child picks up a newer parent only when it is published at a new `version:`. Nothing unusual happens at any step of the sequence above.

## A second divergence in the same resolver

§4.7.6 defines `latest` as "the most recently ingested non-deprecated version". An unpinned `extends: shared/parent` parses to the latest pin, and the resolver selects the highest semver among all candidates, blind to both deprecation and ingest order. It implements neither half of the spec's definition. This is a spec-versus-code divergence independent of the merge behavior above, in the same function, and any resolution that touches candidate selection should close it in the same edit.

## Resolutions

**Refuse or re-resolve at ingest.** `resolveExtendsPin` gains a deprecation map alongside the three it already builds. For a range or unpinned reference, deprecated candidates are filtered out of the selection set before resolution, which repairs the §4.7.6 `latest` divergence at the same time and keeps the step-3 workflow working by re-pinning onto the live version. Refusal covers an exact or content-hash pin naming a deprecated version, where the author asked for that version explicitly, and a range or unpinned reference left with no non-deprecated candidate. The existing `ingest.invalid_artifact` covers every arm, and reusing it creates no §6.10 matrix obligation, where a new code would require a spec entry, a matrix axis, and an annotated test.

The all-deprecated arm is stated for the unpinned reference as well as the range, and it refuses rather than falling back. `LoadArtifact` answers the same question the other way: when every version of an artifact is deprecated it restores the full candidate set so a caller still receives bytes with the §4.7.4 warning (`pkg/registry/core/core.go:1593-1607`, pinned by `pkg/registry/core/latest_skips_deprecated_test.go:49-52`). That fallback serves a read of an already-stored artifact, where refusing would deny the caller content that exists. Ingest is a write of a new row, where the author can correct the source, and a fail-closed refusal keeps the induction in the paragraph below intact: if the unpinned arm fell back, a newly ingested record could still carry a deprecated ancestor and the case would remain open. The two behaviors are deliberately different and each is pinned by its own test.

The refusal keeps the resolver's existing empty-candidate arm intact and adds a second one. The pre-filter check that reports `no parent artifact %q ingested yet` (`pkg/registry/ingest/ingest.go:1458-1463`) still fires when no version of the parent is stored at all. The new post-filter check fires when the unfiltered candidate set is non-empty and the deprecation-filtered selection set is empty, which is the case where versions are stored and every one of them is deprecated, and its message names deprecation so the report does not tell an author the parent was never published. The existing `no parent version satisfies %q` arm (`ingest.go:1476-1480`) keeps its message, because it is the generic failure for any pin that no live candidate satisfies. Both arms are surfaced by the caller at `ingest.go:644-650` as a `RejectedArtifact` carrying `Code: "ingest.invalid_artifact"` and a `Reason` prefixed `extends:`.

This closes the case rather than snapshotting it. `(tenant, artifact_id, version)` is immutable and `deprecated` is per-version, so a pinned parent's flag cannot change after the check, and by induction over the chain no newly ingested record can carry a deprecated ancestor.

The failure mode to weigh is that an author who deliberately keeps a child on a deprecated parent version can no longer publish it, because the exact or content-hash pin naming that version is refused. Deprecation is per-version and immutable, so the refusal reaches only a child version being ingested for the first time; it does not retroactively reject a child already stored against a parent version that was live at the time. The range-skip half avoids the refusal entirely whenever a live candidate remains.

**Persist the inherited flag.** This option is rejected, and it is recorded here because the reasoning is not obvious. Folding `deprecated` into the child's column arms the §8.4 hard purge against the child ninety days after its own publication, because `stampDeprecation` anchors `DeprecatedAt` to `IngestedAt` and the purge's extends-pin guard protects a row that is pinned rather than a row that pins. A variant that folds the flag while leaving `DeprecatedAt` unset makes the row permanently unpurgeable with no migration, but it requires a non-persisted signal so `PutManifest` skips the stamp, which is an SPI-contract change across three backends. Either variant also has to suppress the `artifact.deprecated` webhook event, because `deprecatedFlip` reads the folded value and would announce a deprecation nobody performed, and has to answer §4.7.4, because `replacedByOf` recovers the upgrade target from the child's stored frontmatter and would report a deprecation with no target.

**Resolve on the search path.** This option is rejected. It reinstates the per-candidate chain walk proposal 0009 deleted, whose absence 0009 records as a fixed decision, and it repairs one of the four diverging surfaces while leaving the other three.

**The existing test the change removes.** `TestSearchArtifacts_FiltersReadMergedFields` carries a subtest named "child of a deprecated parent is still returned" (`pkg/registry/core/extends_test.go:726-736`). It stores `shared/parent@1.0.0` with `deprecated: true` as the only `1.x` candidate and ingests a child declaring `extends: shared/parent@1.x`. S2 alone breaks it. Filtering that candidate out leaves the selection set empty, and the resolver already fails closed on an empty set: either the pre-existing `no parent artifact %q ingested yet` arm (`pkg/registry/ingest/ingest.go:1458-1463`) fires, or `version.Resolve` returns `ErrInvalidPin` on an empty candidate slice (`pkg/version/version.go:120-125`) and `resolveExtendsPin` wraps it as `no parent version satisfies %q` (`ingest.go:1476-1480`, the return at `ingest.go:1479`). S2 therefore deletes the subtest. S3 adds its own refusal check ahead of resolution, firing when the unfiltered candidate set is non-empty and the deprecation-filtered selection set is empty, and that check carries the message naming deprecation. S3 rewrites neither existing failure message: `no parent artifact %q ingested yet` (`ingest.go:1458-1463`) and `no parent version satisfies %q` (`ingest.go:1476-1480`, the return at `ingest.go:1479`) keep their current text, because the second arm is the generic failure for any unsatisfiable range or unpinned reference and fires whenever `version.Resolve` finds no match, including against a selection set of live candidates (`pkg/version/version.go:120-125`). Rewriting it to name deprecation would report a deprecation failure for a child whose parent line was never deprecated, such as a child declaring `extends: parent@2.x` against a tenant that stores only a live `parent@1.0.0`. S3 also leaves the content-hash arm's `no parent version with content hash sha256:%s` return (`ingest.go:1473-1475`) as it stands and refuses a content-hash pin onto a deprecated version through its own check, which `TestResolveExtendsPin_ContentHashPinOntoDeprecatedRefused` pins. Re-fixturing it with a live version alongside the deprecated one is rejected, because the child would then pin the live version and the case would assert nothing about a deprecated ancestor. Deleting it costs no `// Spec:` citation, because the annotation sits on the parent function (`pkg/registry/core/extends_test.go:698`) and the remaining subtests keep it. The search-path divergence the subtest recorded becomes unreachable for a newly ingested child, since no accepted child can pin a deprecated parent version and a stored version's flag never flips. Rows already stored against a deprecated parent still diverge, and Decision 3 leaves their repair open.

**Sites with no test staged.** The filesystem source resolves `extends:` by layer precedence and never selects a version pin (`pkg/registry/filesystem/extends.go:29-49` resolves a different-ID parent to the effective record for that ID and a same-ID parent to the next-lower layer), so the candidate-selection rule has no site there and the §11 equivalence check is unaffected.

## Decisions taken

The three decisions below were left to the reviewer while the document was drafted. They are recorded as taken at sign-off, each following the recommendation the Resolutions section already argued, so the implementation has no open question to guess at. Each is reversible by amending this section and re-running the implementation.

1. **The range-skip and the exact-pin refusal are both taken.** The refusal alone leaves the ordinary workflow in "Reachability" broken: a child on a range pin re-pins onto the deprecated version on its next ingest and is then refused, so an author who changed nothing sees a publish fail. The skip re-pins onto the live version instead and refusal is reserved for the case where the author named the deprecated version explicitly.

3. **Children already stored against a deprecated parent are not repaired.** A repair means rewriting `extends_pin` on a row `(tenant, artifact_id, version)` immutability forbids. Republishing the child at a new version takes the corrected resolution, which matches how proposal 0009 left its own affected rows.

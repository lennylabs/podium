# Proposal 0009: Index and serve the §4.6-merged manifest for an extends child

- Issue: (to be filed)
- Status: Implemented (2026-08-19). Converged after 9 adversarial review rounds (21 findings fixed).
- Date: 2026-08-19

## Summary

**What changes.**

- §4.6 states that an omitted or empty child scalar inherits the parent's value, and it states that rule once, over the fields in the merge table as well as the fields outside it (`spec/04-artifact-model.md`, "Default for unlisted fields"). The §4.6 layer-resolution sentence gains a cross-reference to the §9.1 `LayerComposer` row so the `extends:` half of resolution is discoverable from the search path.
- §4.7 names the §4.6-resolved frontmatter as the source of the artifact embedding projection, so an artifact is indexed under the `description` and `tags` that `load_artifact` and `search_artifacts` serve for it. The staged obligation is scoped to those two fields, and the staged text says nothing about `name` or `when_to_use`, because neither SQL store has a column for them (`spec/04-artifact-model.md`, "Artifact embeddings").
- Ingest folds the pinned parent into the stored record's indexed columns, restricted to the columns every store backend persists: `Description`, `Tags`, `Sensitivity`, and `SearchVisibility` (`pkg/registry/ingest/ingest.go`).
- The `search_artifacts` result loop carries the stored `Sensitivity` column and a frontmatter block with the `extends:` key removed, and the per-result `mergedSensitivity` chain walk is deleted (`pkg/registry/core/core.go`).
- The duplicated §4.7 artifact projection collapses into one exported function in a new `pkg/registry/projection` package, imported by `pkg/registry/ingest` and `pkg/registry/core` (`pkg/registry/ingest/ingest.go`, `pkg/registry/core/reembed.go`).
- Tests pin the ingest fold at the ingest level, pin the folded columns across the memory, SQLite, and Postgres backends in the cross-backend integration suite, and pin search-versus-`load_artifact` agreement, parent-only-term recall, and the hidden-parent descriptor at the core and end-to-end levels (`pkg/registry/ingest/`, `pkg/registry/core/`, `test/integration/`, `test/e2e/`).
- The documentation pages that restate §4.6's omitted-field rule, name the artifact projection's fields, and document the `search_artifacts` result's `frontmatter` field are corrected to match the staged spec edits and CODE-2, and the release's CHANGELOG entry carries the operator note for versions already ingested (`docs/`, `CHANGELOG.md`).

**Fixed decisions.**

- The proposal stages no §4.6 paragraph asserting that search filtering, ranking, and descriptors read the merged manifest. §4.6 and the §9.1 `LayerComposer` row already make that normative.
- The fold is computed at ingest and written to the stored indexed columns. The spec does not name the computation point, and the implementation does.
- The fold is one level deep. A parent is always stored before its child is accepted, so the parent record's own columns are already folded and ingest performs no chain walk.
- The fold's field set is `Description`, `Tags`, `Sensitivity`, and `SearchVisibility`. `Name`, `WhenToUse`, and `ReplacedBy` are not folded into the record, because neither SQL store persists them.
- Inherited `deprecated` is not persisted. Writing it stamps `DeprecatedAt` and arms the §8.4 hard purge against a child whose author never deprecated it.
- The stored authored bytes are untouched: `Frontmatter`, `ContentHash`, `Body`, and `SkillRaw` keep the child's authored ARTIFACT.md.
- No new store column, table, or migration. The merged frontmatter is not persisted.
- The search descriptor's frontmatter block is the child's authored block with the `extends:` key removed at the YAML node level, so every other key the child authored survives byte-for-byte in value even when `manifest.Artifact` does not declare it. It is not the merged serialization.
- Both the strip and the sensitivity assignment live in the `SearchArtifacts` result loop. `descriptorOf` is unchanged, because `load_domain`'s notable entries clear `Frontmatter` and carry no `sensitivity` key.
- `mergedSensitivity` is deleted rather than generalized. The search path performs no per-result chain walk.
- `manifest.MergeExtends` stays the single canonical fold for ingest, `load_artifact`, and the filesystem source.
- An empty child scalar is treated as an omitted one. `manifest.Artifact` cannot distinguish the two, and its scalars are not converted to pointers.
- The collapsed projection keeps the reembed semantics: an empty entry inside `when_to_use` or `tags` is dropped rather than joined into a blank line.
- The reproduction and its fixtures use `type: agent`. A skill with an empty description is an error-severity lint diagnostic and never reaches the store.
- Podium is pre-1.0. A version already ingested with an empty inherited description keeps its unfolded columns permanently, because re-ingesting unchanged bytes is classified as idempotent before the write. The repair is publishing a new version of the child, and no backfill path is added.

**Watch out for.**

- **The ingest fold and the read-time merge do not share an input for skills.** Ingest indexes a skill's `Name` and `Description` from SKILL.md, while `mergeChain` parses each record's stored `Frontmatter`, which for a skill is the ARTIFACT.md that omits both (`pkg/registry/ingest/ingest.go`, `pkg/registry/core/core.go`). The divergence is named as a non-goal rather than silently inherited; the fold's field set excludes `Name` for the same reason.
- **The HTTP API reference guarantees a verbatim frontmatter string for every search result.** `docs/reference/http-api.md` states that each result's `frontmatter` is the artifact's verbatim YAML frontmatter, and CODE-2 falsifies that for an extends child: the block is re-encoded from the parsed mapping with the `extends` key deleted, which also normalizes comments, quoting, and indentation, and it is empty when the stored block cannot be decoded. That sentence is staged in "Documentation changes" and is part of step S6.
- **Ingest takes the §4.7 projection at two sites.** `embedAndStore` runs on the inline path, and `commitManifest` computes the same text again to enqueue the vector-outbox row specified in §4.7 "Dual-write semantics for external vector backends" when a managed backend is configured (`pkg/registry/ingest/ingest.go`). Any design in which the projection reads something other than the stored record has to feed both sites the same text, or a managed backend and a collocated one index different text for the same artifact, which is the §2.2 deployment-mode divergence this change must not introduce. CODE-1 closes that by keeping the projection a pure function of the stored record.
- **The two projection copies have already drifted.** The ingest copy joins `WhenToUse` and `Tags` with `strings.Join`, and the reembed copy drops empty entries first, so the same record embeds differently at ingest than under `podium admin reembed`. Collapsing them picks the reembed semantics, which changes the ingest-time projection for records holding an empty list entry.

## Current state and the gap

### Ingest stores the child's authored frontmatter and indexes it

An artifact that inherits `description` through `extends:` is stored and indexed with the child's authored value, so `search_artifacts` cannot find it by the description it serves and reports an empty one when it does surface.

`manifestRecordFor` sets the record's `Description` from `rec.Artifact.Description` and consults no parent (`pkg/registry/ingest/ingest.go`). The §4.7.6 extends block in the ingest loop resolves and validates a pin and ends at `mr.ExtendsPin = pin`, folding nothing. Both halves of hybrid retrieval are then computed from that record: the §4.7 embedding projection at `composeEmbeddingText`, mirrored in `pkg/registry/core/reembed.go`, and the lexical projection at `tokensFor` (`pkg/registry/core/core.go`). `joinNonEmpty` drops the empty field silently, so the vector input degrades to name plus when_to_use plus tags with no trace of the omission, and a full `podium admin reembed` reproduces the same projection rather than repairing it, because it reads the same stored columns.

### The read path disagrees with the index

`manifest.MergeExtends` copies the child's description only when it is non-empty (`pkg/manifest/merge.go`), and `mergeChain` surfaces the merged scalars back onto the record on the `load_artifact` branch of `assembleResult` (`pkg/registry/core/core.go`). Search takes a different route: `descriptorOf` copies `m.Description`, `m.Tags`, and `frontmatterBlock(m.Frontmatter)` straight off the stored record, and the only chain-aware call on the search path is `mergedSensitivity`, for one field. `search_artifacts` and `load_artifact` therefore report different descriptions for the same artifact.

The descriptor's frontmatter block is the child's authored ARTIFACT.md, still carrying the `extends:` line that names the parent, which §4.6 forbids surfacing under "Hidden parents". The leak is confined to the search result loop: the notable-list `descriptorOf` call sites pass through `addCandidate`, which clears `Frontmatter` so the §7.6.1 notable schema stays distinct from the search schema. The pre-rank filters compound the divergence: `deprecated` and `search_visibility` are evaluated unmerged even though §4.6 classifies the latter as "Scalar; most-restrictive" and inherits the former.

### The hazards the original report posited are narrower than it claimed

A child whose parent is not already stored is rejected at ingest with `ingest.invalid_artifact` (`no parent artifact %q ingested yet`, `pkg/registry/ingest/ingest.go`), and records commit one at a time inside the ingest loop, so a same-batch parent that sorts after the child is rejected rather than deferred. §4.7.6 pins the parent to an exact version, and `(tenant, artifact_id, version)` is immutable in every store implementation (`pkg/store/memory.go`, `pkg/store/postgres.go`). There is no propagation event to invalidate on, and no ordering hazard inside a batch.

The pinned parent's record is nevertheless read a second time, by the fold, after `resolveExtendsPin` has already listed it. That read can fail: the store can return an error, and the §8.4 retention purge can hard-delete the parent row between the listing and the read. The window is narrow, it is not the same hazard the original report posited, and the fold handles it explicitly per Decision 17 rather than folding a zero-valued parent into the child.

### What the spec leaves undetermined

§4.6 already determines the served result: layer resolution runs on every `search_artifacts` call, the §9.1 `LayerComposer` row defines that resolution as applying merge semantics and `extends:` resolution (`spec/09-extensibility.md`), and §4.6 "Hidden parents" says the registry serves the merged manifest without surfacing the parent. None of those sentences pins what text is *indexed*. A conforming implementation could index the child's authored frontmatter, merge only at read time, and still fail to return the child for a term that appears only in the parent's `description`. §4.7's projection paragraph is the only place that can settle it, and it says the projection is "built from frontmatter only" purely to exclude the prose body.

§4.6 leaves one smaller ambiguity. The table row reads "Scalar; child wins" for `description`, and the universal sentence that follows it is scoped by a heading naming unlisted fields, so "child wins" admits a reading in which an omitted child scalar wins with its empty value. `pkg/manifest/merge.go` already implements inheritance on empty, and `pkg/registry/filesystem/extends_test.go` already asserts it for a table-listed field.

### Why the gap survived

Every description-bearing extends fixture gives the child its own description (`pkg/registry/core/extends_test.go`, `pkg/registry/ingest/extends_conformance_test.go`), and the projection unit tests build bare records that never set `ExtendsPin` (`pkg/registry/core/coverage_gaps_test.go`, `pkg/registry/ingest/projection_internal_test.go`). The one existing omitted-scalar inheritance test covers the filesystem `Walk` merge path that `podium sync` enables rather than the ingest path that writes the index.

## Decisions

1. **The read-time result is already an obligation, and the proposal does not restate it.** §4.6 lists `search_artifacts` among the calls the registry resolves layers on, the §9.1 `LayerComposer` row defines that resolution as including `extends:` resolution, and §4.6 "Hidden parents" forbids surfacing the parent. The code already derives that reading and cites it: `pkg/registry/core/core.go` merges sensitivity "so the search and load_artifact surfaces report the same value (§4.6)" and strips `extends:` on the load path because "the parent's ID must not be surfaced to the requester". A new §4.6 paragraph asserting the same rule would duplicate it and create a second place to keep in sync.

2. **The stored record's indexed columns become the §4.6-merged values, computed at ingest.** The vector index and the BM25 projection are both derived from those columns (`pkg/registry/ingest/ingest.go`, `pkg/registry/core/core.go`), and no read-time merge can repair a vector row that was already written. Merging at ingest is the only point that fixes both halves of hybrid retrieval, and it lets the pre-rank filters read merged values without a per-candidate store read.

3. **The spec does not name the computation point.** Nothing observable distinguishes an ingest-time fold from a correctly invalidated read-time one, so §4.7's staged sentence defines the projection over the resolved frontmatter and leaves where the fold runs to the implementation. §4.7.6 already prescribes ingest-time pinning, which is the spec-level fact the implementation depends on.

4. **An eagerly computed fold needs no invalidation.** §4.7.6 pins the parent to an exact version at the child's ingest time and states that parent updates do not propagate until the child is re-ingested, and `(tenant, artifact_id, version)` is immutable in every store. The pinned parent's content cannot change under the child.

5. **Chain correctness at ingest is inductive rather than recursive.** A parent is always stored before its child is accepted, so the parent record's own indexed columns are already folded and folding one level covers the whole chain. Ingest needs no chain walk of its own. The induction holds for records ingested after this change lands. A parent that was itself an extends child and was stored before this change carries unfolded columns, and a child ingested afterwards folds those stale columns one level. The repair is the same as decision 14's, and the edge-case table records the outcome.

6. **The fold's field set is bounded by what the stores persist.** `Description`, `Tags`, `Sensitivity`, and `SearchVisibility` round-trip on the memory, SQLite, and Postgres backends. `Name`, `WhenToUse`, and `ReplacedBy` are not persisted by either SQL store, so writing merged values into them would hold only in memory and only until the record is read back, which would make the change behave differently per deployment mode. BM25 on the SQL backends therefore sees the merged description and tags. A merged `name` or `when_to_use` reaches neither the BM25 projection nor the vector projection, which is a pre-existing gap this change neither closes nor appears to close. The §4.7 staged text is written to match: it makes the resolved-frontmatter obligation normative over `description` and `tags`, and it states nothing about `name` or `when_to_use`. A staged sentence about those two fields could not hold either, because the ingest-time projection reads them off the in-flight record while `ReembedOne` reads the record back from a store that has no column for them (`pkg/registry/core/reembed.go`, `pkg/store/sqlite.go`, `pkg/store/postgres.go`). On the SQL backends the two projections therefore disagree on those fields: ingest sees the child's authored values, and every projection taken after a store round-trip sees the empty string, which `joinNonEmpty` drops. That divergence is pre-existing, recorded here and beside the CODE-3 test, and left open. Widening the obligation to all four projection fields would require a new store column, which is a non-goal, and would put a sentence in `spec/` that no conforming standard or standalone deployment could satisfy.

7. **Inherited `deprecated` is not persisted.** `PutManifest` calls `stampDeprecation` on every backend, which stamps `DeprecatedAt` from `IngestedAt`, and `PurgeDeprecatedManifests` hard-deletes the row once the §8.4 window passes. The purge's extends-pin guard protects the pinned parent rather than the child, so a persisted inherited flag would delete a child whose author never deprecated it. Resolving the §4.7.4 default-exclusion filter over an inherited flag is deferred; the accepted behavior and its cost are in "Edge cases and accepted failure modes" and in proposal 0010, which drafts the resolution.

8. **The stored authored bytes are untouched.** `Frontmatter`, `ContentHash`, `Body`, and `SkillRaw` keep the child's authored ARTIFACT.md, because the content hash is computed over them, §6.6 step 2 verifies against them, and `assembleResult` ships them as `RawFrontmatter` so a consumer of a merged manifest can still reproduce the hash. Only the derived index columns change.

9. **The search descriptor hides the parent rather than serving a merged serialization.** §4.6 "Hidden parents" forbids surfacing the parent's existence and ID, which removing the `extends:` key satisfies. A descriptor carrying the full merged serialization is a stronger obligation that no spec section states today, and it would cost a chain walk per result.

    The fix lands in the `SearchArtifacts` result loop rather than in `descriptorOf`. `descriptorOf` is shared with `load_domain`'s notable-list call sites, which pass through `addCandidate` and clear `Frontmatter` for the §7.6.1 notable schema, so those sites leak nothing and gain nothing. Placing the strip in `descriptorOf` would instead run a YAML round-trip on every extends child in the notable candidate pool and discard the result one line later. The same reasoning keeps the `Sensitivity` assignment in the search loop: `addCandidate` clears only `Frontmatter`, so setting `Sensitivity` inside `descriptorOf` would add a `sensitivity` key to every notable entry for a sensitivity-declaring artifact, and the §7.6.1 notable entry is `{id, type, summary, source, folded_from}`.

    The strip removes the `extends` key from the parsed YAML mapping node rather than round-tripping through `manifest.ParseArtifact` and `manifest.SerializeArtifact`. `manifest.Artifact` is a closed struct with no catch-all map and `ParseArtifact` unmarshals non-strictly, so a typed round-trip would silently discard every frontmatter key the struct does not declare. §4.6 Edit A names "any extension-type fields not declared by their `TypeProvider`" among the inheritable fields, and the §4.1 extension types a deployment registers through the §9 `TypeProvider` SPI are exactly that case, so a typed round-trip would make an extends child's descriptor lose frontmatter that a non-extends artifact's descriptor keeps.

    The strip fails closed. When the frontmatter cannot be split, decoded, or re-encoded, or when the rewritten block still reads back as naming a parent per decision 18, the descriptor's frontmatter block is the empty string. Falling back to the raw block would surface the parent's ID to a requester who may have no access to the parent's layer, which is the case the §4.6 hidden-parent rule exists for, and the existing `frontmatterBlock` already returns `""` when the block cannot be split.

10. **The per-result chain walk is deleted rather than extended.** After the ingest fold, the stored `Sensitivity` column is already the most-restrictive value across the chain, computed by the same `manifest.MergeExtends` that `mergeChain` uses, so `mergedSensitivity` returns what the column already holds. Deleting it leaves the search path free of store reads, where extending it would have cost up to `top_k` chain walks per query.

11. **`manifest.MergeExtends` stays the single canonical fold.** Ingest, `load_artifact` via `mergeChain`, and the filesystem source via `resolveExtends` all route through it, so the §2.2 single behavioral surface holds across standard, standalone, and filesystem-registry deployments.

12. **An empty scalar is treated as an omitted one.** `manifest.Artifact` declares `Description string`, so the parsed model cannot distinguish an absent `description:` key from `description: ""`, and `MergeExtends` already inherits on empty. SPEC-1 writes that reading into §4.6 rather than converting the model's scalars to pointers.

13. **The reproduction and its tests use a non-skill type.** A skill's description comes from SKILL.md and an empty one is an error-severity lint diagnostic that aborts that artifact's ingest (`pkg/lint/lint.go`, `pkg/registry/ingest/ingest.go`), so a skill fixture would be rejected before it reached the projection.

14. **No compatibility shim, and no repair for a version already stored.** Podium is pre-1.0. A re-ingest of the affected layer does not repair it: the ingest loop compares the stored `ContentHash` to the incoming one and, on a match, counts the record idempotent and `continue`s before `PutManifest` and before the embedding block, and the fold changes no hash input because the hash is taken over the authored bytes decision 8 leaves untouched. `podium admin reembed` does not repair it either, because the re-embed reads the stored columns. The fold therefore applies to versions ingested after this change lands, and a version stored before it keeps its unfolded `Description`, `Tags`, `Sensitivity`, and `SearchVisibility` for as long as it exists. The repair available to an author is publishing a new version of the child, which is a new `(tenant, artifact_id, version)` row and takes the fold. The operator note lives in the CHANGELOG entry rather than in a backfill path, and an ingest-level test pins the idempotent skip so the repair semantics are asserted rather than assumed.

15. **The duplicated §4.7 projection is collapsed, on the reembed semantics, as its own step.** The two copies produce different text for a record holding an empty `when_to_use` or `tags` entry, and nothing rejects that input. The surviving implementation drops empty entries, which is what `pkg/registry/core/coverage_gaps_test.go` already asserts for the reembed path. The collapse is not a dependency of the fold or the descriptor fix, and it is sequenced first only so the ingest-level test asserts the merged projection through one exported function.

16. **The §13.10 public-mode sensitivity floor is evaluated again on the folded value.** §13.10 states that public mode rejects ingest of a `sensitivity: medium` or `sensitivity: high` artifact, and its carve-out keeps serving artifacts stored before public mode was enabled, so a parent at `high` is reachable in a registry whose floor is `medium`. Before this proposal the floor read the value the child authored, and a child that authored none was stored at `low`. After the fold the child's indexed column is the most-restrictive value across the chain, so leaving the floor on the authored value alone would have ingest accept, store, and serve a record whose own indexed sensitivity is exactly the level §13.10 refuses. The floor therefore runs twice in the ingest loop: once on the authored value, which keeps every non-extends artifact out before the fold's extra store read, and once on `mr.Sensitivity` after the fold. The second evaluation is a new ingest rejection condition rather than an index-column change: a child that authors no `sensitivity:` and inherits `high` is refused with `ingest.public_mode_rejects_sensitive` where it was previously accepted, and the edge-case table records that outcome. It reuses the existing §6.10 code and adds none. The analogous `search_visibility` case is not a rejection, because §4.6 makes `direct-only` a visibility rule rather than an ingest gate.

17. **The fold's parent read fails closed on its two failure modes.** The fold reads the pinned parent by `(tenant, artifact_id, version)`. A store error is not an authoring defect, so it aborts the `Ingest` call with a wrapped error, which is the convention the rest of the loop already takes for a store failure. An `ErrNotFound` means the parent went away between `resolveExtendsPin`'s listing and this read, which the §8.4 purge can do, and it rejects the child with `ingest.invalid_artifact` and the reason `extends: parent <pin> not found`. Accepting the child on either arm would index it under its unresolved columns, and decision 14 records that no later pass repairs a stored version. Neither arm adds a §6.10 code.

18. **The parent strip's fail-closed set is scoped to what the manifest parser resolves.** Deleting the top-level `extends` key from the mapping node is not sufficient on its own. `manifest.ParseArtifact` resolves YAML merge keys, so a child can carry the operative `extends:` inside an anchored mapping it merges in with `<<:`, and deleting an anchored `extends` value strands the aliases into it, which leaves a block that is broken YAML rather than a parent-free header. The helper therefore re-reads the block it rewrote and returns `""` unless that block decodes and resolves no `extends` value. The predicate is the hidden-parent obligation stated over the parser's reading rather than over the literal top-level key, and it is scoped to it: an `extends` value under a key the parser never resolves is the child's authored text and survives with every sibling key, which is what the edge-case row for an undeclared key promises.

## Spec amendment: §4.6 omitted fields

**Edit A.** In the paragraph of §4.6 that begins "**Default for unlisted fields.**", replace the span that runs from the bold lead-in through the end of the second sentence, which is the sentence carrying the field enumeration and ending "…and any extension-type fields not declared by their `TypeProvider`." The replacement text restates the enumeration, so the replaced span includes it. The replacement text is:

> **Omitted fields.** If a child omits a frontmatter field, or sets an empty scalar, the parent's value is inherited unchanged. When both the parent and the child declare a value, a field in the table merges per its row, and every other field takes the child's value: `deprecated`, `replaced_by`, `effort_hint`, `model_class_hint`, `sbom`, `rule_mode`, `rule_globs`, `rule_description`, `hook_event`, `hook_action`, `server_identifier`, `target_harnesses`, `input`, `output`, and any extension-type fields not declared by their `TypeProvider`.

## Proposed solution

### CODE-1: ingest folds the pinned parent into the stored record's indexed columns

In the §4.7.6 extends block of the ingest loop (`pkg/registry/ingest/ingest.go`), after `resolveExtendsPin` returns the pinned parent and before the record is written, fold the parent into the record through `manifest.MergeExtends` and write the result back to four fields of the `store.ManifestRecord`: `Description`, `Tags`, `Sensitivity`, and `SearchVisibility`. Cite `// Spec: §4.6` on the fold and `// Spec: §4.7` on the projection consequence.

The parent's own record is read from the store by the pin, and its columns are already folded by decision 5, so the fold is one level deep and the loop gains no chain walk. The read carries the two failure arms decision 17 fixes: a store error aborts the `Ingest` call, and an `ErrNotFound` rejects the child with `ingest.invalid_artifact`.

After the fold, re-evaluate the §13.10 public-mode sensitivity floor against the folded `Sensitivity` and reject the child with `ingest.public_mode_rejects_sensitive` when it sits at or above the floor, per decision 16. The floor check on the authored value stays where it is, above the fold, so a non-extends artifact is refused without the fold's store read. Extract the rejection into one helper so both call sites produce the same reason string and code.

Do not write `Name`, `WhenToUse`, or `ReplacedBy` back to the record. Neither SQL store persists them (`pkg/store/postgres.go`, `pkg/store/sqlite.go`), so a merged value there would exist only until the record is read back.

Do not write `Deprecated` back to the record, for the reason in decision 7.

The merged `name` and `when_to_use` do not reach the vector projection. The projection stays a pure function of the stored `store.ManifestRecord` and reads the folded columns alone, so it produces the same text at every site that takes it. Passing a separately merged `manifest.Artifact` into the embedding call was considered and rejected on two grounds. Ingest takes the projection at two sites, `embedAndStore` on the inline path and the `commitManifest` enqueue of the §4.7 "Dual-write semantics for external vector backends" outbox row on the managed-backend path (`pkg/registry/ingest/ingest.go`), so a merged value threaded through one of them alone would index different text on a managed backend than on a collocated one for the same artifact. And `ReembedOne` reads the record back from the store (`pkg/registry/core/reembed.go`), where neither SQL backend persists `name` or `when_to_use`, so a merged value at ingest would silently change an extends child's vector the first time `podium admin reembed` ran over it. That is the same index-versus-served divergence this proposal exists to remove, and it contradicts the byte-identity CODE-3 mandates.

### CODE-2: the search result carries the stored sensitivity and hides the parent

`descriptorOf` is unchanged. Both changes land in the `SearchArtifacts` result loop of `pkg/registry/core/core.go`, which is the sole `descriptorOf` call site that serves a frontmatter block and the call site whose wire form carries `sensitivity`; decision 9 records why.

1. Replace `d.Sensitivity = r.mergedSensitivity(ctx, sc.rec)` with `d.Sensitivity = sc.rec.Sensitivity`. After CODE-1 the stored column is the most-restrictive value across the chain, computed by the same `manifest.MergeExtends` that `mergeChain` uses, so it equals what `mergedSensitivity` returned and what `load_artifact` serves. Rewrite the comment above it to say that the record's columns are §4.6-merged at ingest so no read-time fold runs on the search path.
2. When `sc.rec.ExtendsPin != ""`, replace `d.Frontmatter` with `frontmatterBlockHidingParent(sc.rec.Frontmatter)`. When `ExtendsPin == ""`, leave the value `descriptorOf` produced, which keeps the existing descriptor-frontmatter test green and keeps the common path free of a YAML decode.

Delete `mergedSensitivity`. Add no `mergedRecord` helper: `resolveExtendsChain` and `mergeChain` gain no second caller.

**New helper: `frontmatterBlockHidingParent`.** Unexported, in `pkg/registry/core/core.go` beside `frontmatterBlock`, with the signature `func frontmatterBlockHidingParent(src []byte) string` and the citation `// Spec: §4.6 hidden parents`.

- **State it reads.** Only its `src` argument, which is the record's stored `Frontmatter` column. It holds no state and it performs no store read.
- **Behavior.** It splits the frontmatter with `manifest.SplitFrontmatter`, decodes the header into a `yaml.Node` document, deletes the `extends` key and its value from the top-level mapping node, re-encodes the mapping, re-reads the re-encoded block into a `map[string]any` and requires that it decode and resolve no `extends` value per decision 18, and returns the result fenced in the same `---` form `frontmatterBlock` uses. Decoding to a node rather than to `manifest.Artifact` is what preserves keys the struct does not declare; `pkg/manifest/parse.go` already reads frontmatter through `map[string]yaml.Node` for the same reason.
- **Callers.** One: the `SearchArtifacts` result loop, on the `ExtendsPin != ""` branch. It is unexported and gains no other caller in this change.
- **What happens when it does not fire.** On any failure to split, decode, re-encode, or re-read the rewritten block, it returns `""`, so the descriptor carries no frontmatter block at all. It fails closed, because the raw block is the block that names the parent and §4.6 makes hiding the parent a privacy obligation. The observable result is a search result whose `frontmatter` key is absent, and the call still returns a result rather than an error, which matches the non-erroring posture `frontmatterBlock` already takes on an unsplittable block.
- **Tests that pin it.** `TestSearchArtifacts_DescriptorHidesParent`, `TestSearchArtifacts_DescriptorFrontmatterUndecodable`, and `TestSearchArtifacts_DescriptorKeepsUndeclaredKeys` in `pkg/registry/core/extends_test.go`, at the integration level, plus the end-to-end case that pins the consumer-visible JSON.

### CODE-3: one §4.7 artifact projection

Add `pkg/registry/projection` holding one exported function, `func Artifact(mr store.ManifestRecord) string`, carrying the §4.7 doc comment and the `// Spec: §4.7` citation. Import it from `pkg/registry/ingest` and `pkg/registry/core`, and delete `composeEmbeddingText` and `joinNonEmpty` from both `pkg/registry/ingest/ingest.go` and `pkg/registry/core/reembed.go`.

The neutral package follows the `pkg/domain/embedding.go` precedent, which sits beside its consumers rather than inside one of them. `pkg/manifest` is not an option, because it does not import `pkg/store` and the function takes a `store.ManifestRecord`, and exporting from `pkg/registry/ingest` would add a production edge from the read path to the ingest package and its transitive audit, lint, objectstore, and version set.

A re-ingest of unchanged bytes does not recompute them, for the reason in decision 14. No migration is added.

Update the `tokensFor` doc comment (`pkg/registry/core/core.go`) to name the new function, and leave `tokensFor` itself alone: it produces a different output type and is correctly not unified.

## Resolved questions

Both were put to the reviewer on 2026-08-19 and settled as staged. They are recorded here rather than deleted, because each names an alternative a later reader would otherwise re-derive.

**Question 1.** **Whether the descriptor should carry a merged frontmatter block rather than the authored block minus the `extends` key.** The staged design deletes the `extends` key at the YAML node level, which satisfies §4.6 "Hidden parents" at zero store reads and covers the call site that serves a frontmatter block. A merged descriptor frontmatter is a stronger obligation that no spec section states today, and it costs a chain walk per returned result, bounded by `top_k`. Choosing it means a new §4.6 or §7.6.1 sentence and a different CODE-2. **Resolved: keep the staged strip.** No spec section states an obligation to serve a merged descriptor, the strip satisfies §4.6 "Hidden parents", and the alternative costs a chain walk per returned result. The consequence the reviewer accepted with it is that re-encoding the remaining mapping normalizes comments, quoting, and indentation, so `docs/reference/http-api.md` stops promising a verbatim block; DOCS-1 stages that correction.

**Question 2.** **Whether a change that applies only to newly ingested versions is acceptable in a MINOR bump.** Folding `search_visibility` into the stored column changes what `search_artifacts` returns for a child of a `direct-only` parent: it stops being indexed. That is what §4.6 and `load_artifact` already report for it, so it is a convergence rather than a regression. The change reaches only versions ingested after it lands, because the ingest loop skips a record whose content hash is unchanged and the fold changes no hash input, so an existing catalog keeps both its stale empty descriptions and its stale `direct-only` inclusions until each affected child is republished at a new version. **Resolved: land it forward-only.** The alternative is an admin re-fold that rewrites the four indexed columns for records with a non-empty `ExtendsPin`, which is a new command surface and a non-goal today.

The CHANGELOG note carries both consequences rather than the empty descriptions alone. A child of a `direct-only` parent is currently indexed and stops being indexed once it is republished, so an operator who republishes an affected child sees it disappear from search. That is convergence with what §4.6 and `load_artifact` already report for it, and it reads as a regression without the note.

Two further questions were removed from this proposal and carried to [proposal 0010](0010-skill-frontmatter-merge-and-inherited-deprecation.md), which drafts them together: whether an inherited `deprecated` flag should be resolved on the search path or refused at ingest, and the `mergeChain` defect behind what this proposal called the skill fold asymmetry.

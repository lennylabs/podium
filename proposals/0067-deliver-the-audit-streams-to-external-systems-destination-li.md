# Proposal 0067: Deliver the audit streams to external systems: destination lists, an HTTP and OTLP forwarder, a stdout destination, and a versioned record format

- Issue: (to be filed)
- Status: Implemented (2026-11-12). Verified after 7 adversarial review rounds (9 findings fixed).
- Date: 2026-11-11

This document stages spec, code, test, chart, and documentation changes. It does not modify any spec, code, test, or doc file. Apply the changes in the staged sections after sign-off. The change is backward-incompatible: the audit record gains a hashed `schema_version` member, an `http(s)` audit destination receives NDJSON batches asynchronously in place of one JSON object per synchronous request, a destination URL that carries userinfo refuses startup, and a value that contains a comma now names more than one destination. It ships in a MINOR release.

## Summary

**What changes.**

- **Spec §8.1, §8.3, §8.4, §8.5, and §8.6.** §8.1 defines the audit record format, its `schema_version`, `hash` as the deduplication key, and `prev_hash` linkage as the receiver's gap check. §8.3 turns each audit stream into a list of destinations (file, HTTP, OTLP, and stdout) and fixes the delivery, transport, and OTLP mapping contract. §8.4 and §8.5 assign retention and redaction of delivered records to the receiving system, and §8.6 states which records carry an unresolvable `prev_hash` without a loss and that every rewrite closes with an event (SPEC-1 to SPEC-4).
- **Spec §13.12, §6.2, §6.8, §9.1, §13.1, §13.10, §1, and §4.7.** §13.12 rewrites the audit rows, adds the verification, transport, and queue rows, and lists the `config.audit_sink_unavailable` causes. §6.2 and §9.1 follow. §6.8 states that the MCP server flushes its local stream and exits on stdin EOF, SIGINT, or SIGTERM. The claim that audit lives in the Postgres or SQLite metadata store is removed everywhere it appears (SPEC-5, SPEC-6).
- **`pkg/audit`.** One `audit.Stream` per process chains each event once and fans it out. A byte-bounded in-memory forwarder batches, retries, and authenticates delivery to HTTP and OTLP receivers, a stdout destination writes JSON lines, and retention, erasure, anchoring, and the schedulers act through the stream. A JSON Schema for the record is committed beside the package (CODE-1 to CODE-5, SCHEMA-1).
- **Binaries, metrics, and chart.** `internal/serverboot`, `cmd/podium-mcp`, and the offline `podium admin` forms open the stream through one `audit.Open` or `audit.OpenFile`, refuse unusable configurations with `config.audit_sink_unavailable`, and flush and then seal the stream on shutdown through `Stream.Shutdown`. `podium-mcp` also flushes on SIGINT and SIGTERM. `pkg/metrics` adds a queue-depth gauge and a dropped-record counter, and the Helm chart defaults `config.auditLogPath` to `stdout` and gains an opt-in transport secret (CODE-6, CODE-7, DEPLOY-1).
- **Tests, manual validation, and docs.** Unit, integration, and end-to-end tests pin hashing, parsing, delivery, refusals, and shutdown flushing. `test/manual-validation.md` gains S105, S106 (a registry stream through a stock OpenTelemetry Collector to a file and to S3), an S41 rewrite, and an S104 edit that waits for each asynchronously delivered record, `docs/reference/audit-events.md` documents the record and the collector path, and every page that describes a single audit path or endpoint is rewritten (TEST-1 to TEST-3, MV-1, DOC-1).

- **The serve context is cancelled before the 15 s HTTP drain starts.** The shutdown signal cancels it (`internal/serverboot/serverboot.go:892`), and `serveUntilShutdown` starts `srv.Shutdown` only after it sees that cancellation (`:1941-1953`). A forwarder tied to that context stops delivering during the drain. CODE-6 item 1 states which context `audit.Open` receives.

## Current state and the gap

Podium has two audit streams (§8.1): the registry stream selected by `PODIUM_AUDIT_LOG_PATH` (§13.12) and the `podium-mcp` local stream selected by `PODIUM_AUDIT_SINK` (§6.2). Each value names exactly one sink. An `http(s)` URL selects `audit.EndpointSink`, and any other value selects `audit.FileSink` (`internal/serverboot/audit_anchor.go:40-58`, `cmd/podium-mcp/main.go:668-684`). The selection logic exists twice, as two copies of `isAuditEndpoint` (`internal/serverboot/audit_anchor.go:63`, `cmd/podium-mcp/main.go:688`). The spec says only that both streams "can be redirected to external SIEM / log aggregation independently" (§8.3). It defines no delivery, authentication, batching, TLS, or wire-format contract. It defines no `schema_version`, no published schema, no stdout sink, no OTLP export, and no erasure semantics for a file that a tailer has already shipped.

### Endpoint delivery loses events and cannot authenticate

`EndpointSink.Append` sends one synchronous POST per event, on the request path, and sets only `Content-Type`. It uses an `http.Client` with a fixed 10 s timeout and the default transport (`pkg/audit/endpoint.go:36`, `:49`, `:55-86`). It has no retry, queue, or batching, and no setting for headers, a custom CA, or a client certificate. The only credential path is URL userinfo, which Go turns into HTTP Basic authentication, and the error strings echo the raw URL (`endpoint.go:44`, `:47`, `:84`). Receivers that authenticate by header only (Elasticsearch `ApiKey`, `Authorization: Splunk <token>`, and `DD-API-KEY`) and receivers that require mutual TLS are unreachable. The default client also follows redirects.

Eleven non-test emit paths discard the `Append` error with `_ =` and neither log nor count it: `pkg/registry/server/audit_context.go:227`, `internal/serverboot/audit_emitter.go:63`, `internal/serverboot/reingest.go:199`, `internal/serverboot/readonly_audit.go:18` and `:35`, `internal/serverboot/vector_outbox.go:168`, `pkg/audit/scheduler.go:65` and `:125`, and `cmd/podium-mcp/main.go:731`, `:772`, and `:808`. Three paths handle it: `internal/serverboot/rehash.go:625-629` and `:648` log and count it, `pkg/registry/server/layers.go:1365-1366` returns it, and `pkg/audit/anchor.go:47` returns it to a caller that logs it. `EndpointSink` advances `lastHash` before the POST (`endpoint.go:64`) and never rolls it back, so a failed POST leaves an unreported `prev_hash` gap at the receiver.

This path is the production posture of the shipped chart. The chart runs three replicas (`deploy/helm/podium/values.yaml:12`) on a read-only root filesystem (`values.yaml:141-143`) with no writable volume, so the default file sink fails to open. With anchoring off, the registry logs "audit sink disabled" and runs with no audit at all (`internal/serverboot/serverboot.go:1078-1091`). The values comment (`values.yaml:101-106`) and `docs/deployment/clustered.md` tell operators that an `http(s)` endpoint is the only working option.

### No vendor-neutral export exists

Tracing exports over OTLP (§13.8, `pkg/tracing/tracing.go:72-85`), but no OpenTelemetry log SDK or log exporter is a dependency. The OTLP log protobuf types are already in the module graph: `go.opentelemetry.io/proto/otlp v1.11.0` and `google.golang.org/protobuf v1.36.11` are direct requirements in the first `require` block (`go.mod:25`, `:27`), which proposal 0066's span-scrub test made direct (commit `6a5895c3`, `test/integration/mcp_trace_scrub_test.go`). The OTLP module carries `collector/logs/v1` and a `LogRecord` with `EventName`, `TraceId`, `Body`, and `Attributes`.

### The file sink is unsafe to tail

`FileSink` appends to one file and never rotates it (`pkg/audit/file.go:98`). Erasure always rewrites the log, and retention rewrites it when it drops events or ages out query text (`pkg/audit/retention.go:127-128`, `:154`, `:283`). Both rewrite paths go through `rewriteWithChain`, which writes `path+".tmp"` and renames it over the original (`retention.go:414-442`). An inode-tracking tailer re-ships every surviving record. A fingerprint-tracking tailer either re-ships everything or resumes at a stale offset in a file whose lines shifted. Records already shipped keep their unredacted identities, and §8.5 assigns downstream redaction to the endpoint sink only. No stdout sink exists, and in `podium-mcp` standard output carries the MCP protocol (`cmd/podium-mcp/main.go:148`).

A retention pass that only ages out query text rewrites and re-chains the file but appends no closing event (`retention.go:131-137`), and `runRetentionOnce` re-anchors only after a drop (`internal/serverboot/audit_retention.go:65-71`). §8.6 says the registry anchors again "after a §8.4 retention pass moves the head", and a redaction-only pass moves it.

### The chain cannot be checked downstream

`EndpointSink.lastHash` lives only in process memory and starts empty at every process start (`endpoint.go:27-32`, `:41-50`). §8.6 requires automated gap detection, but the only detector is the verify scheduler, which takes a `*audit.FileSink`. That pointer is nil for an endpoint, and `EndpointSink.Verify` is a no-op (`endpoint.go:89-91`, `audit_anchor.go:193-196`). The checks a receiver can apply with the existing members are not written down anywhere. `FileSink.Verify` already accepts a log written by several processes as a forest of per-writer chains, in which every non-empty `prev_hash` must name an earlier `hash` (`file.go:126-158`). A receiver can apply the same check to forwarded records without recomputing a hash.

The spec also contradicts the code on where audit lives. §1 (`spec/01-overview.md:9`, `:91`), §4.7 (`spec/04-artifact-model.md:701`), the §9.1 `RegistryStore` row, §13.1, and the §13.10 standard-versus-standalone table place audit in a Postgres or SQLite table. The §9.1 `RegistryAuditSink` row, §13.12, §8.5, and the code use a file or an endpoint, and neither store schema has an audit table (`pkg/store/postgres.go:165`, `pkg/store/sqlite.go:75` hold only an audit-volume quota column).

### No published record format exists

The wire record has no `schema_version` and no machine-readable schema, and no spec text lists its members. The only description is the `jsonEvent` struct (`pkg/audit/file.go:171-183`) and the §8.1 prose about `caller.*` and `tenant`. The §8.1 tenant rule shows how a new member can enter the hashed body without breaking existing records: an empty tenant adds nothing (`pkg/audit/audit.go:200-204`), and `TestEvent_UnlabeledHashUnchanged` (`pkg/audit/caller_fields_test.go:161`) pins a legacy hash.

## Decisions

- **D-1. Scope.** The gaps above land in one proposal, as the user requested, numbered 0067. Proposal 0066, now Implemented, records the self-reported client software as a hashed `caller.client` member and scrubs query text from exported spans. It edits the same audit record, hashed body, `EraseUser` signature, `EndpointSink`, and end-to-end test, so "Relationship to proposal 0066" fixes how this proposal applies on top of it.
- **D-2. Destination lists.** `PODIUM_AUDIT_LOG_PATH` and `PODIUM_AUDIT_SINK` each take a comma-separated list of destinations. Whitespace around an element is trimmed, and an empty element inside a list refuses startup. A destination is a file path, an `http://` or `https://` URL (the HTTP destination), an `otlp+http://` or `otlp+https://` URL (the OTLP destination), or the token `stdout`. `PODIUM_AUDIT_SINK` also keeps the token `default`, meaning `~/.podium/audit.log`, and the registry keeps treating `default` as a file path, as it does today. An element that contains `://` with any other scheme refuses startup, and so does an element with a recognized scheme that does not parse as a URL, such as `http://%zz`. Today the registry logs such a value and runs with no audit (`internal/serverboot/audit_anchor.go:41-46`). A list names at most one file destination and names no element twice. An empty `PODIUM_AUDIT_LOG_PATH` resolves to the default file, an unset `PODIUM_AUDIT_SINK` disables the local stream, and a `PODIUM_AUDIT_SINK` set to an empty value resolves to the default file, all as today. Each process chains each event once and writes the chained record to every destination in its list, so OTLP is an additional destination that can sit beside a file. §8.6 calls SIEM mirroring the operational integrity backstop, and today an operator who ships the stream loses the anchored local file. A path that contains a comma now parses as two destinations. Podium is pre-1.0, so the change carries no escape syntax and no shim.
- **D-3. One chaining point per process.** Each process that writes an audit stream holds one `audit.Stream`, which implements `audit.Sink`, the §9.1 `RegistryAuditSink` and `LocalAuditSink` seam (`pkg/audit/audit.go:223-240`). The stream holds one mutex across chaining an event and handing it to its destinations, so every destination receives the process's records in chaining order. With a file destination, the chain head is `FileSink.lastHash`, recovered from the file's last line when the file opens (`file.go:45-50`), and the stream keeps no copy of it. Without one, the stream holds the head itself and starts it empty. The file's last line can belong to any process that writes the file, so a stream's first record can link into another process's chain, and a restarted registry continues the chain it left. A shared file is a forest of per-writer chains, which `FileSink.Verify` already accepts. A §8.4 or §8.5 rewrite re-chains every record from an empty `prev_hash` and renames the result over the file (`pkg/audit/retention.go:414-442`), and D-23 records what that rewrite and a failed write leave for another process that writes the same file. Registry replicas never share a chain, and each `podium-mcp` process chains its own records.
- **D-4. Hashed `schema_version`.** `Event.SchemaVersion` enters the §8.6 hashed body under the §8.1 present-only rule. `canonicalBody` appends `schema_version=<n>` as the last part of the body, after the tenant part and after any `caller_client_*` parts that proposal 0066 adds, only when the value is greater than 0. The stream sets it to `audit.SchemaVersion` (1) on every event it chains, so 0 always means a record written before the member existed, and every such record keeps its hash. The member round-trips through `jsonEvent`, `eventForJSON`, and `eventFromJSON`, because `FileSink.Verify` and `rewriteWithChain` rebuild events from JSON. No stream identifier or sequence number is added. `hash` already identifies a record for deduplication, and `prev_hash` linkage already exposes a lost interior record (§8.1, §8.6). Per-type retention drops records from the middle of the file, so a sequence number hashed into the file would show gaps that are not losses.
- **D-5. Delivery modes.** The file and stdout destinations are written synchronously inside `Append`, and the HTTP and OTLP destinations are asynchronous: `Append` hands the serialized record to a bounded per-destination queue and returns, and a background sender batches, delivers, and retries. `Append` returns an error exactly when it did not chain the event: the file destination's write error, or `ErrSealed` once `Stream.Shutdown` has sealed the stream. It never returns another destination's failure, a stdout write error included. SPEC-2 Loss accounting states what each destination receives or counts, and CODE-1 states the mechanism. A receiver deduplicates on `hash`.
- **D-6. Delivery constants.** The spec fixes the delivery values, so §13.12 needs no override for them: SPEC-2 Delivery states the batch limits, the send cadence and its suspension while a retry delay is pending, the request timeout, the redirect refusal, the status classes, the backoff and its `Retry-After` rule, the rule that a record leaves its queue only when delivered or counted, and the shutdown flush budget, and SPEC-2 Observability states the drop-log interval. `audit.ShutdownTimeout` names the flush budget in code (CODE-1), and CODE-6 item 4 places the call. `PODIUM_AUDIT_QUEUE_MAX_BYTES` (default 67108864, 64 MiB) is the one operator-tunable value. SPEC-2 retries a 415 rather than splitting the batch, because a 415 refuses the media type of the whole request, and splitting would drop every record of the stream as `rejected`. SPEC-2 lets `Retry-After` lengthen a backoff and never shorten it, so a `Retry-After` of 0 or an HTTP-date in the sender's past cannot turn the backoff into an immediate retry loop against a refusing receiver.
- **D-7. In-memory queue.** The queue lives in process memory, and there is no spool, for the reasons the spool bullet of the Non-goals gives. SPEC-2 Delivery defines an abnormal exit, SPEC-2 Loss accounting states what the shutdown flush counts and what an abnormal exit loses, and D-22 records which signals each process handles. A deployment that needs delivery to survive a restart points the HTTP or OTLP destination at a local collector or agent with a persistent queue, such as the OpenTelemetry Collector's `file_storage` queue, a Vector disk buffer, or a Fluent Bit filesystem buffer. The file destination remains Podium's durable, anchored copy.
- **D-8. Overflow and drop accounting.** A full queue never blocks the request path. A record that does not fit in a destination's queue is still chained and written to the other destinations, and it is dropped for that destination with reason `queue_full`, even when the queue is empty because the record is larger than `PODIUM_AUDIT_QUEUE_MAX_BYTES`. A record larger than 1 MiB is classified first, as `rejected`, so its reason does not depend on the bound. The loss appears at that receiver as a `prev_hash` that names no record it received. SPEC-2 Loss accounting is the one definition of the drop reasons. Every count reaches the observer and the log through one stream method, `Stream.dropped` (CODE-1). No destination holds the `Observer`, so a drop is never counted without being logged. The line is written whether or not an observer is set, at most once per destination and reason per minute, because the 11 `_ =` emit sites stay as they are (`cmd/podium-mcp/main.go:731`, `:772`, `:808`; `internal/serverboot/audit_emitter.go:63`, `reingest.go:199`, `readonly_audit.go:18`, `:35`, `vector_outbox.go:168`; `pkg/audit/scheduler.go:65`, `:125`; `pkg/registry/server/audit_context.go:227`) and a `podium-mcp` without `PODIUM_MCP_METRICS_ADDR` has no other signal.
- **D-9. Transport settings.** Four process-wide variables configure every HTTP and OTLP destination of the process. `PODIUM_AUDIT_HEADERS_FILE` names a file with one `Name: value` request header per line, where blank lines and lines that begin with `#` are ignored, and the names `Host`, `Content-Length`, and `Content-Type` are refused. `PODIUM_AUDIT_TLS_CA_FILE` names a PEM CA bundle that replaces the system trust store for audit destinations. `PODIUM_AUDIT_TLS_CERT_FILE` and `PODIUM_AUDIT_TLS_KEY_FILE` name the client certificate and key for mutual TLS and must be set together. The registry reads each file at start whenever its variable is set. `podium-mcp` reads and validates the four variables and `PODIUM_AUDIT_QUEUE_MAX_BYTES` only when `PODIUM_AUDIT_SINK` is set, after the check that returns no stream for an unset value (`cmd/podium-mcp/main.go:669-671`), because a process with no local stream has no destination for them to configure. A `podium-mcp` with `PODIUM_AUDIT_SINK` unset therefore starts whatever these variables hold. Secret values come from files only and are never logged. Error text names the variable that holds the refused setting. It names a headers file by its path and line number, and it names a destination as `scheme://host/path` with no userinfo and no query. A destination URL that carries userinfo refuses startup, and HTTP Basic authentication is supplied as an `Authorization: Basic ...` line in the headers file.
- **D-10. OTLP transport.** The OTLP destination sends OTLP/HTTP protobuf `ExportLogsServiceRequest` messages to the URL with the `otlp+` prefix removed, and to the path `/v1/logs` when that URL's path is empty or `/`. It uses the SPEC-2 delivery rules and the D-9 transport. It is built from `go.opentelemetry.io/proto/otlp v1.11.0` and `google.golang.org/protobuf v1.36.11`, which `go.mod` already requires directly (`go.mod:25`, `:27`), so the destination adds no module. No `go.opentelemetry.io/otel/log`, `sdk/log`, or `otlploghttp` module is added. The destination reads neither `PODIUM_TRACING` nor any `OTEL_EXPORTER_OTLP_*` variable, so enabling tracing never starts audit export. Audit records and traces correlate through the record's `trace_id`.
- **D-11. OTLP mapping.** Each record maps to one OpenTelemetry `LogRecord`. `time_unix_nano` and `observed_time_unix_nano` come from `timestamp`. `severity_number` is 9 (INFO), and `severity_text` is `INFO`. `event_name` is the audit `type`. `trace_id` is the hex-decoded `trace_id`, left empty when that value is not 32 hexadecimal characters. `body` is a string holding the record's JSON exactly as the file destination writes the line, without the newline, so a verifier can parse it and recompute the hash. The attributes are `podium.audit.schema_version` as an integer value, and `podium.audit.hash`, `podium.audit.prev_hash` when non-empty, and `podium.tenant` when the record names a tenant, each as a string value. Caller identity stays in the body and is not copied into attributes. The resource carries `service.name` and `service.instance.id`. `service.name` is `podium-registry` for the registry and `podium-mcp` for `podium-mcp`, the names `tracing.Init` already uses (`internal/serverboot/serverboot.go:1886`, `cmd/podium-mcp/main.go:137`). `service.instance.id` is a random RFC 4122 version 4 UUID the stream generates when it opens, carried only in the resource and outside the hashed body. The scope name is `github.com/lennylabs/podium/audit`. A response whose `partial_success.rejected_log_records` is greater than 0 counts that many drops with reason `rejected`.
- **D-12. Redaction and sampling.** §8.2 redaction and §8.4 sampling stay in the emitters, before `Append` (`internal/serverboot/audit_emitter.go:29-65`, `cmd/podium-mcp/main.go:727-808`). Every destination therefore receives the same redacted record, and an event that sampling drops never reaches the stream.
- **D-13. Stdout destination.** The `stdout` destination writes one JSON line per record to standard output in a single `Write` call under the stream mutex. It is valid only in the registry process, and `podium-mcp` refuses it because standard output carries the MCP protocol. It is synchronous, so a stalled reader of standard output blocks audited requests and the registry's exit, and the D-8 promise that the request path never blocks covers only the HTTP and OTLP destinations. SPEC-2 Delivery fixes the queue-before-stdout order, and the abnormal-exit item of SPEC-2 Loss accounting states what an exit that ends the stall loses. When the list names `stdout`, the registry ignores SIGPIPE on platforms that have it, so a broken pipe surfaces as an `EPIPE` write error, counted with reason `write_error`, and the process keeps serving. The error is never returned to the emitter (D-5). A list that names `stdout` while `PODIUM_TRACING=stdout` also writes spans to standard output refuses startup, because span and audit writes larger than `PIPE_BUF` can interleave within a line. The §13.4 `sign-stored-rows` command also prints summary lines to standard output (`internal/serverboot/signpass.go:63`). Each audit record stays one complete JSON line, and the documentation says that a JSON-parsing collector separates the two.
- **D-14. File destination ownership.** The file destination is Podium-owned storage: §8.4 retention, §8.5 erasure, and §8.6 anchoring and verification act on it and rewrite it. The spec states descriptively that a rewrite replaces the file through a rename, so a deployment ships the stream through a stdout, HTTP, or OTLP destination listed beside the file. It states no rule on operators that the registry cannot enforce. The file destination gains no rotation and no append-only mode, because §8.4 bounds its size. For every other destination, the receiving system owns retention and redaction of what it received. The documentation adds that the same holds for records a tailer shipped from the file.
- **D-15. Rewrites and closing events.** Every rewrite of the file destination closes with an event that records the superseded head as `context.superseded_head`. A retention pass that drops an event or ages out query text appends `audit.retention_enforced` with `context.dropped` and `context.queries_redacted`, and an erasure appends `user.erased` as today. The registry re-anchors after every rewrite, which matches §8.6 "a retention pass moves the head". The closing event is sequenced under the stream mutex and handed to every non-file destination, and so is every `audit.anchored`, `audit.anchor_failed`, and `audit.gap_detected` event. A receiver accepts a closing event whose `prev_hash` it never received when it holds the record that `superseded_head` names.
- **D-16. Startup refusals.** `config.audit_sink_unavailable` widens to every audit configuration that cannot be used, in both binaries. The following causes refuse startup whatever the anchoring setting: an empty element in a list, an element with an unrecognized `://` scheme, an element with a recognized scheme that does not parse as a URL, two file destinations, an element named twice, userinfo in a destination URL, `stdout` in `podium-mcp`, `stdout` in the registry beside `PODIUM_TRACING=stdout`, a headers, CA, certificate, or key file that cannot be read or parsed, only one of the certificate and key variables set, a non-empty `PODIUM_AUDIT_QUEUE_MAX_BYTES` that is not a positive base-10 integer, a file destination that `NewFileSink` cannot open because its path is unset and the home directory cannot be resolved, its parent directory cannot be created, or an existing file cannot be read (`pkg/audit/file.go:33-51`), and a file destination that `NewFileSink` opens but that cannot be opened for appending, such as a file the registry can read but not write or an absent file in an existing read-only directory. A file destination refuses for either cause even when it is the only destination. `podium-mcp` checks the transport and queue causes only when `PODIUM_AUDIT_SINK` is set (D-9). `Open` detects the append cause with `probeAppend`, and every error `Open` returns wraps `ErrConfig` (CODE-1). Today a lone file destination that `NewFileSink` cannot open is logged, and with anchoring off the registry runs with no audit sink (`internal/serverboot/serverboot.go:1078-1091`) and `sign-stored-rows` runs without one (`internal/serverboot/signpass.go:191-197`). That is a fail-open path: with no sink the erase endpoint answers success without recording `user.erased` and leaves the file unredacted (`pkg/registry/server/layers.go:1360-1362`), and the retention scheduler does not start (`internal/serverboot/audit_retention.go:23-25`). The reviewer removed the exception (OD-2), so the warning, `ErrFileUnavailable`, and the `sinkErr` parameter of `loadAnchorSigner` are gone (CODE-6 items 2 and 6). `podium-mcp` refuses a file destination it cannot open with the same code, where today it returns an uncoded error (`cmd/podium-mcp/main.go:638-641`). No new error code and no §6.10 matrix cell is added, because the `config.*` startup codes live in §13.12 and `docs/reference/error-codes.md`.
- **D-17. Schema version and published schema.** `schema_version` is 1 for the record format this proposal defines, and a change to the record's members or their meaning increments it. A new event type is not such a change. The JSON Schema (draft 2020-12) is committed at `pkg/audit/schema/audit-event.v1.schema.json` and is never edited after release. Its `$id` is the raw-content URL of the file on `main`. No production code embeds it; a test loads it. `docs/reference/audit-events.md` links to it and documents the Elastic Common Schema (ECS) field mapping, which a collector transform applies. Podium emits neither ECS nor OCSF natively.
- **D-18. Code placement.** The new code lives in `pkg/audit`, the canonical package for the concern. A single `audit.Open` replaces both copies of `isAuditEndpoint`, and both binaries call it, so the deployment modes cannot diverge. The offline admin forms call `audit.OpenFile`, which never starts a network destination. `pkg/audit` reports to Prometheus through an injected `audit.Observer`, so `pkg/metrics` stays the only Prometheus dependency (`pkg/metrics/metrics.go:1-5`). Clocks come from `internal/clock`, randomness is injected, and the forwarder's tick and sleep go through unexported test hooks.
- **D-19. Metrics.** Two series cover the D-8 signal and the existing §13.8 wording ("gauges for queue depths", "error rate"). `podium_audit_queue_depth{destination}` is a gauge of queued, undelivered records, with `destination` set to `http` or `otlp`. `podium_audit_dropped_total{destination,reason}` is a counter, with `destination` set to `file`, `stdout`, `http`, or `otlp`, and `reason` set to `queue_full`, `rejected`, `shutdown`, or `write_error`. `audit.Observer` has `AddQueued(kind string, delta int)` and `Dropped(kind, reason string, n int)`. A forwarder reports deltas and never sets an absolute value, so two destinations of one kind in one list sum into one gauge. A delta model is correct only when the observer sees every record from the first one, so the observer is an `OpenOptions` field fixed at `Open` and the stream has no method that attaches one later. The registry builds its metrics registry before it opens the stream (CODE-6 item 3). A persistent delivery failure shows as a rising queue depth and the rate-limited log line, and no separate failure counter is added.
- **D-20. Chart.** `config.auditLogPath` defaults to `stdout`, as Q-2 resolves, so the Deployment and the migrate Job each render `PODIUM_AUDIT_LOG_PATH=stdout` and every chart install records audit. The records then sit in the cluster's container log pipeline, under the platform's retention and outside the reach of §8.5 erasure (SPEC-3 Edit 3), and a list with no file destination runs no anchoring or verification (SPEC-5 Edit 4, the SPEC-5 Edit 5 verification row). The values comment names a file path on a writable volume, an `http(s)` URL, and an `otlp+http(s)` URL as the values that replace or join the default. The chart renders the default as an `env:` entry, and an `env:` entry takes precedence over the `existingSecret` that reaches both pods through `envFrom` (`deploy/helm/podium/templates/_pod.tpl:59-65`, `docs/deployment/clustered.md:160`), so the default overrides a `PODIUM_AUDIT_LOG_PATH` that the secret carries. An installation that sets its audit destination in the secret moves it to `config.auditLogPath` on upgrade, or its records go to the container log instead of its receiver. An explicit empty value renders no variable. When the secret carries no `PODIUM_AUDIT_LOG_PATH`, the pods keep the home-directory file, which the read-only root filesystem cannot hold, so the Deployment's pods and the migrate Job refuse startup with `config.audit_sink_unavailable` (D-16). When the secret carries one, the secret's value applies. The chart gains `audit.transportSecret`, an opt-in Secret mounted read-only at `/etc/podium/audit` in the Deployment and the migrate Job, which sets only the transport variables for the keys it lists.
- **D-21. Order of work and compatibility.** The spec edits land first, in one commit. `pkg/audit` follows, then the binaries and the chart, then the tests, manual validation, and docs, with the CHANGELOG last. The change is backward-incompatible: the record gains a hashed member, an `http(s)` value now posts asynchronous NDJSON batches in place of one JSON object per synchronous request, URL userinfo is refused, and a comma separates destinations. It ships in a MINOR release.
- **D-22. Signals.** `podium-mcp` handles SIGINT and SIGTERM by ending as it ends on stdin EOF, because an MCP host can signal before or during the stdin-EOF flush (OD-1). No other process gains a handler. The registry keeps starting its shutdown on the first SIGINT or SIGTERM and aborting a stuck drain on the second (`internal/serverboot/serverboot.go:892`, `:1948`). `sign-stored-rows` keeps the default action for both signals, because a handler would change how the chart's migrate Job, a hook with `activeDeadlineSeconds`, ends (`deploy/helm/podium/templates/migrate-job.yaml:40`, `:44-46`). `podium-mcp` does not wait for a tool call in progress, because a registry request from `podium-mcp` has no client timeout (`cmd/podium-mcp/main.go:596`). SPEC-6 Edit 10 states when the handler applies and how the process ends, the SPEC-2 Delivery shutdown paragraph states which records a call in progress still makes and defines an abnormal exit, and SPEC-2 Loss accounting states what that exit loses. CODE-6 item 5 places the handler.
- **D-23. Shared file destinations.** This proposal adds no coordination between processes that write one file destination, because such files exist today and this proposal adds no writer of a file and no rewrite. The rewrite-by-another-process item of SPEC-2 Loss accounting names those files. The file write and the rewrite keep today's mechanics, and a pass that changes nothing writes nothing (CODE-1 `file.go`, CODE-5 item 1). The rewrite-by-another-process and stored-part items of SPEC-2 Loss accounting state the outcomes. Re-reading the head after another process's rewrite is rejected, because §8.6 file verification reports a dangling `prev_hash` as `ErrChainBroken` (`pkg/audit/file.go:143-153`), and a re-read would turn that detected loss into an undetected one and forward to receivers a `prev_hash` they never received. Removing a stored part from a file that another process appends to is rejected, because it can delete that process's record. A follow-up proposal on multi-writer file integrity decides between an advisory lock across processes, held across the append, any removal of a stored part, and a rewrite's read through its rename, and detection with recovery.

Operators who need per-project scoping point `PODIUM_AUDIT_SINK` at a workspace path such as `${WORKSPACE}/.podium/audit.log`.
>
> **Destinations.** `PODIUM_AUDIT_LOG_PATH` (§13.12) lists the registry stream's destinations, and `PODIUM_AUDIT_SINK` (§6.2) lists the local stream's, independently. Each is a comma-separated list, and whitespace around an element is ignored. An element is one of the following:
>
> - A file path, the file destination. Each record is one line of JSON.
> - An `http://` or `https://` URL, the HTTP destination. Records are sent in `POST` requests whose body has the media type `application/x-ndjson` and holds one record per line.
> - An `otlp+http://` or `otlp+https://` URL, the OTLP destination. Records are sent as OTLP/HTTP protobuf log export requests to the URL with the `otlp+` prefix removed, and to the path `/v1/logs` when that URL's path is empty or `/`.
> - The token `stdout`, the stdout destination. Each record is one line of JSON on the process's standard output. Only the registry accepts it, because the MCP server's standard output carries the MCP protocol.
>
> A list names at most one file destination and names no element twice. An empty element, an element whose `scheme://` prefix is none of the above, and an element with one of the above prefixes that does not parse as a URL refuse startup (§13.12). A file path that contains a comma cannot be listed.
>
> The §8.2 redaction directives and the §8.4 sampling rates apply before an event is chained, so every destination receives the same redacted record and a sampled-out event reaches no destination. The process then chains the event once (§8.6) and writes the chained record to every destination in its list. Every destination therefore carries the same member values for that event: the file, stdout, and HTTP destinations write the record's JSON, and the OTLP destination carries it as the log record body. A destination receives a process's records in the order the process chained them, apart from the repeats that delivery below allows.
>
> Each process chains its own records. Registry replicas do not share a chain, and each MCP server process chains its own local records. When the list names a file destination, a starting process continues the chain from the last record in that file, which any process that writes the file may have appended. Otherwise the first record a process chains carries an empty `prev_hash`. A §8.4 or §8.5 rewrite replaces the file destination through a rename, so a deployment ships the stream through a stdout, HTTP, or OTLP destination listed beside the file rather than by tailing the file.
>
> **Delivery.** The file and stdout destinations are written before the emitting operation continues, so a write that blocks, such as a write to a stalled reader of standard output, delays that operation. The registry keeps running when a write to standard output fails.
>
> The HTTP and OTLP destinations are written asynchronously. The process places the record in that destination's queue and continues, and a background sender delivers it, so the emitting operation never waits for or fails because of an HTTP or OTLP receiver. The process places a record in every HTTP and OTLP queue before it writes that record to the stdout destination, so a record whose stdout write blocks is already queued, or counted as dropped, for each HTTP and OTLP destination. Each queue is bounded by `PODIUM_AUDIT_QUEUE_MAX_BYTES` (§13.12). The sender sends a batch when it holds 500 records or 1 MiB of serialized records, and at least once per second while records are queued and no retry delay (below) is pending. While a retry delay is pending, the sender sends nothing until the delay ends or the shutdown flush stops the sender. Each request times out after 10 seconds, and redirects are never followed. A response with a 2xx status delivers the batch. A 400, 413, or 422 response splits the batch in half and sends each half again. A single record that is still refused is dropped (Loss accounting). A network error and every other status, 3xx included, is retried after a delay drawn uniformly between zero and a cap. The cap starts at 1 second and doubles after each consecutive failure up to 60 seconds. A `Retry-After` header raises the delay to its value, up to 60 seconds, when that value is larger than the drawn delay, and never shortens the drawn delay.
>
> A record leaves its queue only when it is delivered or counted as dropped, so a batch the sender has sent without a 2xx response stays queued and counts toward the bound. A persistent retryable failure drops nothing by itself: it holds the queue until `queue_full` drops begin, and the queue-depth gauge and a rate-limited log line report it. The queues live in process memory. A deployment that needs delivery to survive a process restart points the HTTP or OTLP destination at a local collector that keeps a persistent queue.
>
> A process flushes its queues once while it ends, after it has stopped taking new work and its work in flight has finished or its shutdown deadline has passed. It flushes however it ends, including a refusal to start or a stop on an error after its queues exist, except on an abnormal exit. At that flush the process stops each background sender, then sends the whole queue in chain order, a batch the sender sent without a 2xx response included, for up to 5 seconds, and drops the rest with reason `shutdown`. When the flush ends, the process seals its stream. A record it chains before the seal takes effect, including one it is chaining at that moment, is accounted for under Loss accounting, and the process chains no record after the seal, so an operation still running after the seal records no further audit event. An abnormal exit is a crash, a signal that ends the process by its default action (SIGKILL included), or a forced termination such as a Windows `TerminateProcess` call. The MCP server ends on SIGINT or SIGTERM as §6.8 states, and its shutdown deadline for a tool call in progress is the arrival of that signal.
>
> **Loss accounting.** When the list names a file destination, an event is chained only when its record is written to the file. When that write fails, the chain head does not advance, no other destination receives the record, the write's failure is reported to the operation that emitted the event, and the record is counted once, as dropped for the file destination with reason `write_error`. No other destination's failure is reported to the emitting operation. A §8.4 or §8.5 rewrite that fails leaves the file unchanged and emits no closing event. Every record the process chains is written to the stdout destination and delivered at least once to each HTTP and OTLP destination in the list, or it is counted as dropped for that destination with exactly one of these reasons:
>
> | Reason | Condition |
> | --- | --- |
> | `write_error` | The write to standard output failed, or, for the file destination, the write that would have chained the record failed (above). |
> | `rejected` | The record is larger than 1 MiB, the receiver refused it in a request that held it alone, or it is among the records an OTLP receiver's partial-success response reports as rejected. |
> | `queue_full` | The record is at most 1 MiB and did not fit in the destination's queue when the process chained it, including a record larger than `PODIUM_AUDIT_QUEUE_MAX_BYTES`. |
> | `shutdown` | The record was still queued when the shutdown flush ended, or the process chained it after the shutdown flush started. |
>
> A loss is counted in every case except the following:
>
> - **Abnormal exit.** When the process exits abnormally, as the Delivery shutdown paragraph defines it, a record it has chained but whose write to its stdout destination has not returned, such as a write blocked on a stalled reader, and the records still queued for an HTTP or OTLP destination are lost.
> - **Rewrite by another process.** When another process also writes the file destination, such as several MCP server processes on the local file or `sign-stored-rows` beside a serving registry (§13.4), a record that a process appends after another process's §8.4 or §8.5 rewrite has read the file and before that rewrite's rename is lost from the file, and it stays at the appending process's other destinations. A process keeps its own chain head across another process's rewrite, so the next record it chains can carry a `prev_hash` that the file no longer holds, and §8.6 verification of the file reports that record as a gap whether or not a record was lost. When the appending process chains no later record, no check detects the loss.
> - **Stored part of a failed write.** A write to the file destination that fails after it stored part of the record leaves that part in the file, and the failed record is counted with `write_error` (above). The next record written to the file joins that part in one line that cannot be parsed, so that record is missing from the file while it stays at the process's other destinations. §8.4 retention, §8.5 erasure, and §8.6 anchoring and verification of the file fail on that line until an operator removes the part.
>
> A receiver keeps one copy per `hash` (§8.1), and a record dropped for a destination appears to that destination's receiver as a missing record (§8.1).
>
> **Transport.** The HTTP and OTLP destinations of a process take their request headers, CA bundle, and client certificate from the §13.12 audit transport settings. A header value and URL userinfo are never logged, and an error or log line names a destination by its scheme, host, and path. A destination URL that carries userinfo refuses startup (§13.12).
>
> **OTLP mapping.** The OTLP destination maps each record to one OpenTelemetry log record:
>
> | Log record field | Value |
> | --- | --- |
> | `time_unix_nano`, `observed_time_unix_nano` | The record's `timestamp` |
> | `severity_number`, `severity_text` | `9`, `INFO` |
> | `event_name` | The record's `type` |
> | `trace_id` | The record's `trace_id` decoded from hexadecimal, or empty when it is not 32 hexadecimal characters |
> | `body` | A string holding the record's JSON, byte for byte as the file destination writes the line, without the line ending |
> | Attributes | `podium.audit.schema_version` as an integer value, and `podium.audit.hash`, `podium.audit.prev_hash` when it is non-empty, and `podium.tenant` when the record names a tenant, each as a string value |
>
> Caller identity stays in the body and is not copied into attributes. The resource carries `service.name`, which is the name the process uses for §13.8 tracing, and `service.instance.id`, a random identifier the process generates when it opens the stream. The instrumentation scope name is `github.com/lennylabs/podium/audit`. The OTLP destination reads no `OTEL_EXPORTER_OTLP_*` variable and is independent of `PODIUM_TRACING` (§13.8).
>
> **Observability.** Every dropped record is counted per destination kind and reason, and the queued records of the HTTP and OTLP destinations are reported as a queue depth per destination kind (§13.8). Dropped records are also logged, whether or not metrics are enabled, in at most one line per destination and reason per minute. A log line names a destination by its file path, as `stdout`, or by its scheme, host, and path.

## Proposed solution

### CODE-1. `pkg/audit`: `Stream`, destination parsing, and `schema_version`

Targets: `pkg/audit/stream.go` (new), `pkg/audit/destination.go` (new), `pkg/audit/observer.go` (new), `pkg/audit/audit.go`, and `pkg/audit/file.go`.

- `audit.go`: add `Event.SchemaVersion int` and `const SchemaVersion = 1`. `canonicalBody` appends `schema_version=<n>` as its last part, after the tenant part and after any `caller_client_*` parts from proposal 0066, only when `SchemaVersion > 0` (`// Spec: §8.1, §8.6`).
- `observer.go`: `type Observer interface { AddQueued(kind string, delta int); Dropped(kind, reason string, n int) }`, and the reason constants `ReasonQueueFull = "queue_full"`, `ReasonRejected = "rejected"`, `ReasonShutdown = "shutdown"`, and `ReasonWriteError = "write_error"`. They land here because `Append` counts `write_error` in this step and CODE-2 and CODE-4 both use them. `observer.go` also holds the stream's two reporting methods. `func (s *Stream) dropped(kind destKind, name, reason string, n int)` is the only caller of `Observer.Dropped` and the only writer of the drop log line, where `name` is the destination's file path, `stdout`, or `redactedURL`. `func (s *Stream) queued(kind destKind, delta int)` is the only caller of `Observer.AddQueued`. Each skips the observer call when `Observer` is nil. Each also returns at once when its `n` or `delta` is 0: it makes no observer call, and `dropped` writes no log line, so a count of nothing never reaches the observer or the drop log, and a forwarder `close` that delivered every record records nothing (CODE-2). Every destination is constructed with these two methods bound to its kind and name and never receives the `Observer`, so no drop site can count without logging. Neither method takes `s.mu`, because `Append` calls them while it holds `s.mu` and the sender goroutines call them without it. **IMPLEMENTOR'S CHOICE:** the limiter's type and bookkeeping. There is one limiter per stream with its own mutex. It writes through `log.Printf` at most one line per destination name and reason per minute (the SPEC-2 interval), measured against `OpenOptions.Clock` (`clock.Real{}` when nil). A line names the destination by `name`, with the reason and the count, and never contains a header value, URL userinfo, or a query.
- `file.go`: add `SchemaVersion int \`json:"schema_version,omitempty"\`` to `jsonEvent`, placed before `Hash`, and carry it through `eventForJSON` and `eventFromJSON`. Add an unexported `appendChained(e Event) (Event, []byte, error)` that chains under `f.mu`, writes the line, and returns the chained event and its JSON line without the newline. `Append` calls it. It keeps the write mechanics of `FileSink.Append` (`pkg/audit/file.go:98-106`) unchanged: it opens the path with `os.O_APPEND|os.O_CREATE|os.O_WRONLY` and mode `0o644`, writes the whole line in one call, and sets `lastHash` only after that write succeeds. After a failed open or write it returns the error with `lastHash` unchanged, and the `Append` bullet below counts it. It removes no part of a line that a failed write stored, and it reads the head from the file only through `NewFileSink`, as D-23 decides. `FileSink` gains no field.
- `destination.go`: `type destKind string` with the values `file`, `stdout`, `http`, and `otlp`, which are also the metric label values (D-19). `parseDestinations(value string, opts OpenOptions) ([]destSpec, error)` applies D-2: trim each element, refuse an empty element inside a list, map `default` to the default file when `opts.Local` is set, refuse an unrecognized `scheme://` prefix, an `http`, `https`, `otlp+http`, or `otlp+https` element that `url.Parse` rejects, two file destinations, an element named twice, URL userinfo, `stdout` when `opts.Local` is set, and `stdout` when `opts.TracingStdout` is set. A whole value of `""` maps to the default file `~/.podium/audit.log`. Every refusal wraps `ErrConfig` and names the list variable, which is `PODIUM_AUDIT_SINK` when `opts.Local` is set and `PODIUM_AUDIT_LOG_PATH` otherwise. The `opts.TracingStdout` refusal also names `PODIUM_TRACING` (SPEC-5). `redactedURL(u *url.URL) string` returns `scheme://host/path`. Every refusal names an element that contains `://` by `redactedURL` when `url.Parse` accepts it, and by its scheme alone when `url.Parse` rejects it, and never echoes the raw element, because any such element, whatever its scheme, can carry userinfo or a query that holds a credential (D-9, SPEC-5). This covers the unrecognized-scheme, unparseable-URL, element-named-twice, and userinfo refusals. A file element is named by its path.
- `stream.go`:
  - `var ErrConfig = errors.New("audit: configuration unusable")`. Every error `Open` returns wraps it, so a caller refuses on any `Open` error, and the package defines no second sentinel for a file it cannot open (D-16, OD-2).
  - `type OpenOptions struct { Local bool; Service string; HeadersFile, CAFile, CertFile, KeyFile string; QueueMaxBytes int64; TracingStdout bool; Stdout io.Writer; Observer Observer; Clock clock.Clock; Rand io.Reader }`. `Local` is set only by `podium-mcp`: it accepts `default` and refuses `stdout`. A nil `Rand` uses `crypto/rand.Reader`, a nil `Stdout` uses `os.Stdout`, and a nil `Clock` uses `clock.Real{}`. Neither binary nor the offline forms set `Rand`, `Stdout`, or `Clock` (CODE-6 items 1, 5, 6, and 8), so production takes these defaults, and tests set them to inject randomness, a failing or recording writer, and a frozen clock. `Observer` is the D-19 observer. The stream reads it at every count, from the first `Append` onward, and nothing sets or clears it after `Open`; a nil `Observer` makes every count a no-op. `QueueMaxBytes` bounds the `memQueue` of each network destination (CODE-2). A value of 0 or less takes `DefaultQueueMaxBytes` (67108864, the §13.12 default), so a test or library caller that leaves the field unset gets the default bound, and `Open` never refuses the field. `func ParseQueueMaxBytes(raw string) (int64, error)` is the one check of the environment value, and both binaries call it (CODE-6 items 1 and 5). An empty `raw` returns `DefaultQueueMaxBytes`. Any other `raw` must parse with `strconv.ParseInt(raw, 10, 64)` to a value greater than 0. Otherwise the function returns an error that wraps `ErrConfig`, names `PODIUM_AUDIT_QUEUE_MAX_BYTES`, and quotes the value (`// Spec: §13.12`).
  - `func Open(ctx context.Context, value string, opts OpenOptions) (*Stream, error)` parses the list, loads the transport files (CODE-2), opens the file destination, generates `service.instance.id` from `opts.Rand`, and starts one forwarder per network destination on a context the stream owns. Starting the forwarders is its last step, after every step that can fail, so an `Open` that returns an error leaves no goroutine and nothing to close. It opens the file destination in two steps: `NewFileSink`, which creates the parent directory and recovers the head (`pkg/audit/file.go:33-51`), and then an unexported `probeAppend(path string) error` on `FileSink.Path()`. `probeAppend` opens the path with `os.O_APPEND|os.O_CREATE|os.O_WRONLY` and mode `0o644`, the flags `appendChained` uses (the `file.go` bullet above), and closes it. It writes no byte, so an existing file keeps its content and head, and an absent file is created empty, which `lastChainHash` and `Verify` read as an empty chain. `Open` is its only caller. `OpenFile` does not probe, because the offline forms have no other destination to protect and write the file only through `rewrite`, which replaces it through a rename and reports its own failure. A `NewFileSink` failure and a `probeAppend` failure each return an error that names the list variable, the path, and the cause and wraps `ErrConfig`, whatever else the list names, so every binary refuses it whatever the anchoring setting (D-16, CODE-6 item 2). A caller that ran past such an error would hold no audit stream, and after a probe failure `NewFileSink` has already read a file that `rewriteWithChain` can still replace through a rename, so neither erasure nor retention would reach it. A file that becomes unwritable after the probe is a write failure under D-5. Every other refusal wraps `ErrConfig` as well. In S2 the constructors for the `http`, `otlp`, and `stdout` kinds do not exist yet, so `Open` refuses such an element with an error that wraps `ErrConfig` and names the list variable and the kind. S3, S4, and S5 each replace that refusal with their constructor, and no binary calls `Open` before S7, so no released build carries it.
  - `func OpenFile(path string, opts OpenOptions) (*Stream, error)` opens a file-only stream for the offline admin forms. Its errors name the path and no variable, because the forms take the path from `--audit-path` (CODE-6 item 8).
  - `*Stream` implements `audit.Sink`. `Append` locks `s.mu`, sets `SchemaVersion` and a default timestamp from `opts.Clock`, and chains: through `s.file.appendChained` when a file exists, and against `s.head` otherwise. It then hands the chained event and its line to every other destination, still under `s.mu`: first to the queue of every HTTP and OTLP destination, and then to the stdout destination, whatever order the list names them in, so a record whose stdout write blocks is already queued, or counted as dropped at the push, for each network destination (SPEC-2 Delivery, `// Spec: §8.3`). `TestStream_QueuesNetworkCopiesBeforeStdoutWrite` (TEST-1) pins the order. When `appendChained` returns an error, `Append` hands the record to no other destination, calls `s.dropped` for the file destination with `ReasonWriteError` and 1, and returns the file's error. The file's error and `ErrSealed`, below, are the only errors `Append` returns (D-5). A stdout write error goes to `s.dropped` with `ReasonWriteError` and is not returned, and a network destination never returns one.
  - `Verify(ctx)` delegates to the file, or returns nil without one. `File() *FileSink` returns the file destination or nil. `Close(ctx) error` runs `close(ctx)` on every forwarder concurrently, each on `ctx`, and waits for all of them (CODE-2), then cancels the context the stream owns, so a hung receiver cannot spend the flush budget of another destination. `TestStream_CloseFlushesDestinationsConcurrently` (TEST-1) pins the concurrency. `Close` is idempotent: a call after the first flushes nothing and returns the first call's result, and no sender goroutine outlives the first call. `const ShutdownTimeout = 5 * time.Second` is the SPEC-2 flush budget (`// Spec: §8.3`). `Shutdown()` calls `Close` with a context from `context.WithTimeout(context.Background(), ShutdownTimeout)`, so a cancelled serve context never shortens the flush, logs a non-nil result through `log.Printf`, and then calls `Seal`. `Seal` (below) fixes what happens to an `Append` in progress and to every later one. `Shutdown` is the one call a process makes when it ends (CODE-6 item 4).
  - `File`, `Close`, `Shutdown`, and `Seal` are nil-receiver-safe: on a nil `*Stream`, `File` returns nil, `Close` returns nil, and `Shutdown` and `Seal` return at once. `podium-mcp` holds a nil stream when `PODIUM_AUDIT_SINK` is unset (CODE-6 item 5), the registry schedulers and `loadAnchorSigner` reach the file through `File()`, and these are the methods called on a stream directly. The registry never holds a nil stream, because `run` refuses every `openAuditStream` error (CODE-6 item 2). `Append` and `Verify` are not nil-receiver-safe, because a nil stream is never stored where they are called.
  - `func AsSink(s *Stream) Sink` returns a nil interface when `s` is nil and `s` otherwise, following the `auditObserver` precedent (CODE-6 item 3). `LocalAuditSink` and `RegistryAuditSink` are aliases of `Sink` (`pkg/audit/audit.go:237-240`, the `type` block holding both aliases), so one helper serves both binaries. It is the one conversion from a stream to an interface value: every site that stores or passes the stream as an `audit.Sink` or `audit.LocalAuditSink` calls it (CODE-6 items 1, 5, and 6), so the `== nil` guards downstream keep working. Without it a nil stream becomes a non-nil interface holding a nil pointer, every guard passes, and the first `Append` panics on `s.mu`.
  - Between `Close` and `Seal`, an `Append` or a `rewrite` closing event chains the record and writes it to the file and stdout destinations, and each HTTP and OTLP destination counts it `shutdown` through the CODE-2 push-after-close rule.
  - `var ErrSealed = errors.New("audit: stream sealed")`. `Seal()` locks `s.mu`, sets a `sealed bool` field that `s.mu` guards, and unlocks. `Append` and `rewrite` read `sealed` directly after they lock `s.mu`, and on a sealed stream they return `ErrSealed` at once: the event is not chained, reaches no destination, and is neither counted nor logged, and `rewrite` leaves the file unchanged. Because `Seal` takes `s.mu`, an `Append` that holds the lock when `Seal` is called finishes its chaining write and its hand-off to every destination, a closed forwarder's `shutdown` count and the drop log line included, before `Seal` returns. A record therefore cannot be chained and then left neither delivered nor counted when the process exits after `Seal`. `Seal` releases the lock before it returns, so a later `Append` returns `ErrSealed` rather than blocking, and no goroutine is left waiting on `s.mu` (the TEST-2 `goleak.VerifyTestMain` would report one). A second `Seal` changes nothing, and nothing unseals a stream. `Seal` does not close the forwarders. `Shutdown` is its only production caller and calls it after `Close` returns, so every entry point in the CODE-6 lifecycle table seals its stream when it ends. Without the seal, an entry point could exit while a producer it does not join sits between its chaining write and its hand-off, and the record would stay in the file uncounted for every network destination at a normal exit. The registry's `run` does not join the retention, anchor, and verify schedulers (`internal/serverboot/audit_retention.go:37`, `internal/serverboot/audit_anchor.go:160`, `:206`) or the vector-outbox worker (`internal/serverboot/vector_outbox.go:140`), and a handler can still run after the 15 s `srv.Shutdown` deadline (`internal/serverboot/serverboot.go:1941-1953`). `podium-mcp` does not wait for a tool call in progress (CODE-6 item 5). A producer that runs after the seal gets `ErrSealed` from `Append` or `rewrite`, handles it on its existing error path, which for the D-8 `_ =` emit sites discards it, and records nothing (`// Spec: §6.8, §8.3`).
- The head has one owner (D-3): `s.head` is used only when `s.file` is nil.
- `EndpointSink` stays in this step and is deleted in CODE-6, where its last callers go.

### CODE-2. `pkg/audit`: forwarder, transport, and the HTTP destination

Targets: `pkg/audit/forwarder.go` (new), `pkg/audit/transport.go` (new), and `pkg/audit/httpdest.go` (new). The `Observer` interface and the reason constants are in CODE-1.

- `forwarder.go`:
  - A byte-bounded `memQueue` per network destination, sized by the `QueueMaxBytes` value `Open` resolves (CODE-1). A push first counts a record larger than 1 MiB as `rejected`, because no request may carry it, and then counts a record that does not fit in the remaining bound as `queue_full`, even when the queue is empty. Neither enters the queue or reports `AddQueued`. The forwarder reports every count through the two methods the stream binds to it (CODE-1) and holds no `Observer`.
  - One sender goroutine per network destination, running on a sender context that the forwarder derives from the stream's context and that only `close` cancels. It cuts a batch at 500 records or 1 MiB and on a 1 s tick. Neither the tick nor a size cut starts a request while a backoff sleep is pending: the one sender goroutine sends its next request, the held batch, only when the sleep returns, and a tick that fires during the sleep sends nothing (SPEC-2 Delivery; `TestHTTPDest_HeldBatchCountsTowardBound` pins it). The sender peeks a batch from the head of the queue without removing it. It removes records, and reports `AddQueued(kind, -n)` for them, only when they are delivered (a 2xx response) or counted as dropped (`rejected`). A split resends each half from the same held records. Each request and each backoff sleep take the sender context, so cancelling it interrupts both, and the interrupted batch stays at the head of the queue. A held batch therefore counts toward `QueueMaxBytes` and the queue depth until it leaves the queue.
  - The SPEC-2 Delivery status classes: 2xx delivers; 400, 413, and 422 split until a single refused record is dropped with `rejected`; everything else retries. The backoff cap starts at 1 s, doubles after each consecutive failure up to 60 s whether or not the response carried `Retry-After`, and returns to 1 s after a 2xx response. **IMPLEMENTOR'S CHOICE:** how a delay is drawn from the injected `Rand` — the delay is uniform in `[0, cap]` and comes only from `OpenOptions.Rand`, and a test can inject a `Rand` that drives the draw to within 1 ms below the cap, which is how `TestHTTPDest_RetryClasses` observes the cap (TEST-2). `Retry-After` in seconds or HTTP-date gives a delay capped at 60 s, and the sleep is the larger of that delay and the attempt's draw, so `Retry-After` lengthens a backoff and never shortens the draw. An HTTP-date value is converted to a delay against `OpenOptions.Clock`, which the stream passes to each forwarder, and a date at or before that clock's `Now` gives a zero `Retry-After` delay, which leaves the draw as the sleep (`// Spec: §8.3`).
  - The failure log names the destination through `redactedURL` and the status or error, at the first failure, at each transition between failing and delivering, and at most once per minute while failing, with the minute measured against `OpenOptions.Clock`. `TestHTTPDest_FailureLogCadence` pins the cadence (TEST-2).
  - Unexported hooks `newTicker func(d time.Duration) ticker` and `sleep func(ctx context.Context, d time.Duration) error`, set from `export_test.go`, following `pkg/webhook/webhook.go:122-126`.
  - The SPEC-2 Delivery request timeout is the unexported constant `requestTimeout = 10 * time.Second`, applied through a third hook, `requestContext func(parent context.Context, d time.Duration) (context.Context, context.CancelFunc)`, whose default is `context.WithTimeout` and which only `export_test.go` replaces. Every request the forwarder sends, from the sender or from `close`, takes its context from `requestContext(parent, requestTimeout)` and releases it when the response is read. The parent is the sender context for a sender request and `close`'s `ctx` for a flush request, so a sender request ends at 10 s or when `close` cancels the sender context, and a flush request ends at the lesser of 10 s and the time left on `ctx`. The `http.Client` sets no `Timeout`, so the hook is the only request deadline. A sender request whose context ends while the sender context is still live counts as a network error under SPEC-2 Delivery and is retried, and one that ends because the sender context was cancelled leaves its batch at the head of the queue for `close`. `TestHTTPDest_HungReceiverIsBoundedByCloseDeadline` (TEST-2) pins both bounds.
  - `close(ctx)` first stops the queue from accepting records, then stops the sender, interrupting an in-flight request or a backoff sleep, and waits for the sender goroutine to exit. It then sends the whole queue from its head, the batch the sender held included, from one goroutine under the SPEC-2 Delivery batch, split, and retry rules, so records reach the receiver in chain order apart from the resend of an interrupted batch, which the receiver deduplicates on `hash`. Each request times out at the lesser of 10 s and the time left on `ctx`, through `requestContext(ctx, requestTimeout)`, and each backoff sleep ends when `ctx` expires. When the queue is empty or `ctx` has expired, it counts the `n` records that remain, when `n` is greater than 0, with `Dropped(kind, ReasonShutdown, n)` and reports `AddQueued(kind, -n)`, so the queue-depth deltas sum to 0. When no record remains, `close` makes neither call and writes no drop log line, the same rule the CODE-1 reporting methods apply to a count of 0. A push after that first step enqueues nothing, reports no `AddQueued`, and reports `Dropped(kind, ReasonShutdown, 1)`. **IMPLEMENTOR'S CHOICE:** how the forwarder marks itself closed and stops its sender — a push racing `close` either enters the queue before the flush starts or is counted as `shutdown`, never panics, and is never lost uncounted, and the sender goroutine has exited when `close` returns.
- `transport.go`: `Open` builds one `*http.Client` per stream here, and every HTTP and OTLP destination of the stream sends through that client and no other. Its transport is a clone of `http.DefaultTransport` with `TLSClientConfig.RootCAs` set from the CA file and `Certificates` from the certificate pair, and with `InsecureSkipVerify` left false so the receiver's certificate is always verified against the CA file or, when it is unset, the system trust store (fail closed; the TEST-2 server-verification cases pin it). The client sets `CheckRedirect` to a function that returns `http.ErrUseLastResponse`, so a 3xx response reaches the forwarder, which retries it under SPEC-2 Delivery. `CheckRedirect` is a field of `http.Client` and `http.Transport` has none (`net/http/client.go:77` in the Go source), so a destination that wraps the cloned transport in its own client follows up to 10 redirects and, on a redirect to another host, still copies every header other than the authentication, proxy-authentication, and cookie headers to the redirect target, `X-Audit-Token` and `DD-API-KEY` included (`net/http/client.go:814-815`, `:834-835`). A 307 or 308 redirect also re-sends the batch body. `pkg/webhook` sets the field on its client the same way (`pkg/webhook/webhook.go:425`), and `pkg/audit` writes its own one-line function rather than importing `pkg/webhook`. The client sets no `Timeout` (the `requestContext` bullet above). `TestHTTPDest_RetryClasses` and `TestOTLPDest_RedirectNotFollowed` (TEST-2) pin the redirect refusal for each destination. The headers-file parser applies D-9: it skips blank lines and lines that begin with `#`, and it refuses a line without a colon, an empty name, and the names `Host`, `Content-Length`, and `Content-Type`, compared case-insensitively. Its error names `PODIUM_AUDIT_HEADERS_FILE` and the file and line as `<path>:<n>`, with `n` counted from 1 over every line of the file, and never includes the value. The client certificate loads through `tls.LoadX509KeyPair(CertFile, KeyFile)` when both are set, and only one of the two set is refused before that call. A load error, which covers an unreadable or unparseable certificate or key file and a key that does not match the certificate, returns an error that names `PODIUM_AUDIT_TLS_CERT_FILE`, `PODIUM_AUDIT_TLS_KEY_FILE`, and both paths, wraps the load error and `ErrConfig`, and includes no content of either file. Every error wraps `ErrConfig` and names the variable of the file it concerns: an unreadable headers file names `PODIUM_AUDIT_HEADERS_FILE`, a CA file that cannot be read or holds no certificate names `PODIUM_AUDIT_TLS_CA_FILE`, and only one of the certificate and key set names both certificate variables.
- `httpdest.go`: POSTs a batch through the `transport.go` client as `application/x-ndjson`, one record line per line, with the configured headers, on the per-request context the forwarder passes it, which carries the 10 s `requestTimeout`.

### CODE-4. `pkg/audit`: stdout destination

### CODE-5. `pkg/audit`: retention, erasure, anchoring, and the schedulers through the stream

Targets: `pkg/audit/retention.go`, `pkg/audit/anchor.go`, and `pkg/audit/scheduler.go`.

1. Add one unexported `Stream` method, `rewrite(ctx context.Context, fn func(events []Event) (out []Event, closing *Event, changed bool, err error)) error`. It requires `s.File()` to be non-nil. It locks `s.mu` and then `file.mu`, the order `Append` uses, and reads every event. It calls `fn`. When `fn` returns an error, `rewrite` returns it and writes nothing. When `fn` returns `changed` false, `rewrite` returns nil at once: it calls no `rewriteWithChain`, leaves the file's bytes, its inode, and `FileSink.lastHash` untouched, ignores `out` and `closing`, and hands nothing to any destination. `rewriteWithChain` re-chains every record from an empty `prev_hash` into one chain and renames a new file over the old one (`pkg/audit/retention.go:414-442`), so running it for a pass that changed nothing would change record hashes and the head of a multi-writer file (D-3) with no closing event, which D-15 forbids, and would replace the inode for no reason. When `fn` returns a closing event, it sets `SchemaVersion` and appends it to `out`. It calls `rewriteWithChain`, which keeps its temp-and-rename mechanics, and then sets `FileSink.lastHash`, and changes no other `FileSink` state. `s.mu` and `file.mu` are in-process locks, and `rewrite` adds no lock across processes (D-23). Last, it hands the last element of `out`, the closing event as `rewriteWithChain` chained it, to every non-file destination, so the forwarded record carries the `hash` and `prev_hash` the file's closing line holds and its JSON line equals that file line byte for byte. The `*Event` that `fn` returned carries neither member, because `rewriteWithChain` sets them only on the slice it is given (`pkg/audit/retention.go:422-424`), and `rewrite` never forwards it. `TestStream_RewriteForwardsFinalClosingRecord` (item 6) pins this. When `rewriteWithChain` fails, the file keeps its pre-rewrite chain and head, and `rewrite` hands the closing event to no destination and reports no drop. The closing event describes a rewrite that did not happen and never entered the chain, so no destination has lost a record. This differs from `Append` after a failed file write, which counts the event once for the file destination with `write_error` (SPEC-2 Loss accounting). It returns only the read, `fn`, and rewrite errors. A stdout failure on the closing event is counted through `dropped` with `write_error` and not returned, because the file already holds the rewrite (D-5). `TestStream_RewriteClosingEventStdoutFailureIsCounted` (item 6) pins that rule.
2. Change the signatures to `Enforce(ctx context.Context, s *Stream, now time.Time, policies []Policy, queryRet *QueryRetention) (EnforceResult, error)`, with `type EnforceResult struct { Dropped, QueriesRedacted int }`, and `EraseUser(ctx context.Context, s *Stream, userID, salt, admin string, client *CallerClient, scope EraseScope) (int, error)`, which keeps proposal 0066's `client` parameter ("Relationship to proposal 0066"). Their bodies become the `fn` passed to `s.rewrite`. Neither takes a lock itself. `EraseUser`'s `fn` always reports `changed` true, because every erasure appends `user.erased` and rewrites the file, as it does today (`pkg/audit/retention.go:283-287`).

- **OD-1. `podium-mcp` signals. Resolved: Option B.** `podium-mcp` handles SIGINT and SIGTERM by running the same bounded drain-and-flush that stdin EOF runs, and D-22 changes accordingly. The MCP specification was checked: revision 2025-06-18 (Lifecycle, Shutdown, stdio) says the client SHOULD close the server's input, wait, then send SIGTERM, then SIGKILL; revision 2026-07-28 (Transports, stdio) says the client SHOULD close the input, wait, then forcibly terminate, which on POSIX is typically SIGTERM then SIGKILL and on Windows is `TerminateProcess`, and that servers SHOULD exit when their input reaches end-of-file. Both are SHOULD, so a host can signal first. A SIGKILL and a Windows forced termination remain abnormal exits whose queued records are lost uncounted, and SPEC-2 and the docs state that. ## Non-goals

- Native Splunk, Datadog, Elasticsearch bulk, S3, GCS, Azure Blob, Kafka, Loki, CloudWatch, Sentinel, or Chronicle destinations. Each would add a dependency and a maintenance surface (`.claude/rules/code-best-practices.md`), and the OTLP destination behind a collector reaches them.
- The OpenTelemetry log SDK (`go.opentelemetry.io/otel/log`, `sdk/log`, and `otlploghttp`), OTLP over gRPC, and reading `OTEL_EXPORTER_OTLP_*` or `PODIUM_TRACING` for audit export.
- A durable on-disk spool in Podium. A spool needs per-destination acknowledgements, an ownership check that keeps a suspended live process from being adopted, and a routing rule for adopted records when the adopter's list differs from the orphan's. A per-pod `emptyDir` spool in the chart is also deleted with the pod. A local collector with a persistent queue provides the durability, and a follow-up proposal can stage a spool with those rules.
- A SIGINT or SIGTERM handler in `sign-stored-rows`, a handler for the registry's second signal, and a wait in `podium-mcp` for a tool call in progress when SIGINT or SIGTERM arrives (D-22).

# Proposal 0027: Attest the served record and close the hidden-parent disclosures

- Issue: (to be filed)
- Status: Draft
- Date: 2026-09-15

This document stages the proposed spec, code, test, and documentation changes. It does not modify any spec, code, or doc file. Apply the changes in the staged sections after sign-off.

## Summary

**What changes.**

- A new §4.7.10 delivery attestation: the registry computes a framed digest over the record it actually serves (the identity, the merged frontmatter, the body, `SKILL.md`, and each bundled resource's path and content hash), signs it with the key it already holds, and returns `delivery_hash` and `delivery_signature` on both `load_artifact` and `POST /v1/artifacts:batchLoad`. Nothing attests the merged bytes today, and the batch path carries no integrity value of any kind.
- The `load_artifact` response stops carrying `raw_frontmatter`, `manifest_merged`, and `signature`, and the merged-manifest exclusion from the presigned manifest-body channel goes with them. Each of the three is a §4.6 disclosure or an oracle for one, and each exists only to support a recomputation the delivery attestation replaces.
- The response gains `extends`, the pinned `<id>@<version>` the child resolved at ingest, present only when the calling identity can see the parent record. The §13.10 web UI reads that field and deletes the client-side concealment gate it runs today, which decides in the browser what the server has already disclosed.
- Four further disclosure paths close: `GET /v1/dependents` filters on the queried target and on the pinned parent record rather than on the source artifact alone, two `pkg/registry/core` error messages stop interpolating the hidden parent's ID and version pin into a message that reaches the client verbatim, the search-descriptor strip is driven by the stored document rather than by the `extends_pin` column, and the cross-layer collision rejection stops naming the contributing layer to a caller who cannot read it.
- `spec/04-artifact-model.md:683` is replaced. The sentence promises that a hidden parent's "existence and ID are not surfaced to the requester", and the existence half is not deliverable: the served bytes of a merged child do not reproduce the served `content_hash`, which is a one-request boolean test for a parent that survives every change staged here. The replacement splits the guarantee into what is withheld, what the merge serves by design, and what is observable.
- §4.7.3 gains a visibility paragraph. The reverse index has been filtered per caller since it shipped and `spec/` says nothing about it, so the rule being narrowed has no section a test can cite.

**Fixed decisions.**

- The countersignature is minted at serve time, on every response, for every artifact, whether or not it declares `extends:`. It is never stored and never backfilled.
- The delivery digest is domain-separated from the §4.7.6 content hash by a framed leading tag, and it frames each bundled resource's content hash rather than its body, so no object-store read is added to the load path.
- `content_hash` stays on the wire with its §4.7.6 meaning and stays the §6.5 cache key, the §7.5.3 lock value, and the `@sha256:` pin target. A server-source consumer stops recomputing it and verifies the delivery record instead.
- The delivery-hash recomputation runs unconditionally on every load, independent of `PODIUM_VERIFY_SIGNATURES` and of `sensitivity`, and fails closed. This proposal carries its own strictness and does not depend on the sibling proposal that fixes the verification defaults and the check ordering. Until that proposal lands, the signature half of the attestation is inert under the shipped defaults (`PODIUM_SIGNATURE_PROVIDER=noop`, no verify key, no registry signing key), and no staged spec sentence claims resistance to a tampering registry.
- `pkg/sign.Provider` is not widened. The delivery hash is a `"sha256:<hex>"` string and the existing `Sign(ctx, string)` and `Verify(ctx, string, string)` take it unchanged.
- The stored ingest signature stays; the served `signature` field goes. For a merged child it attests a digest the consumer can no longer reproduce, and for every other artifact it attests a subset of the delivery record under the same key from the same party.
- A failed delivery verification reuses `materialize.content_hash_mismatch`, and a missing or invalid signature keeps `materialize.signature_missing` and `materialize.signature_invalid`. No §6.10 code is minted.
- An invisible `/v1/dependents` target answers `200 {"edges":[]}`, byte-identical to a target that does not exist and to one nothing depends on. A 404 would be the oracle this proposal removes.
- §4.6's existence guarantee is narrowed rather than restored, and the spec text says so.

**Watch out for.**

- **Dropping `raw_frontmatter` alone blanks a shipped surface.** `declaredExtends` (`web/ui/src/surfaces/ArtifactViewer.tsx:994-999`) falls back to the served `frontmatter`, which the registry has already stripped for every requester, so the outbound extends rail reads "This artifact extends nothing" for every artifact including one whose parent the reader can see. CODE-5 and CODE-11 land together or a privacy fix ships as a feature regression.
- **`manifest_merged` and the presigned-body exclusion are the same oracle read two ways.** `omitempty` makes the flag's presence exactly the predicate "this artifact extends something", and `attachManifestBody` returns early on `res.Merged` (`pkg/registry/server/server.go:1205`), so an above-cutoff merged manifest is served inline where an unmerged one is served by URL. Deleting the field and leaving the guard keeps the oracle in the response structure.
- **An ID-keyed `/v1/dependents` filter passes the case it is written for.** The §4.6 same-ID overlay makes a child extend its own canonical ID in a lower-precedence layer, so `edgesFor` records `{From: "team/overlay", To: "team/overlay"}` (`pkg/registry/ingest/ingest.go:1306-1310`). Both endpoints are "visible" by ID while the record the pin names is not, and the self-edge discloses that a layer the caller cannot read contributes that ID.
- **The delivery stream must not depend on the requesting identity.** `extends` is served per caller and is therefore excluded from the stream. A per-requester digest cannot be compared across consumers and cannot be precomputed, and the single-load and batch paths would stop agreeing.
- **Do not reuse `version.CanonicalContentHash` over the merged bytes.** Two digests with one definition, one hex encoding, one SPI, and one key means a signature over either is syntactically a signature over the other. It would also take `map[string][]byte`, which forces every large resource out of object storage on every load.
- **An ingest-stored countersignature depends on yaml.v3 and on struct field order.** `manifest.SerializeMerged` marshals a `manifest.Artifact` through `gopkg.in/yaml.v3` and splices the authored keys back, so its byte output is a function of the struct's field declaration order and of the serializer's quoting and wrapping. Adding a field to `Artifact` would invalidate every stored countersignature at once and require a re-sign migration on a release that intended no behavior change.
- **`test/e2e` skips parts of itself on macOS.** `test/e2e/artifact_extends_test.go` carries unconditional skips of its own, and the `oidc-jwt` arms skip on darwin. This proposal's central behavior is a visibility-boundary behavior, so a green local `go test ./test/e2e/...` is not evidence. Grep the run output for `SKIP`, and prefer `trusted-headers` for the new visibility arms.
- **`web/bundle/` is committed build output.** `web/icons_test.go` fails with "rebuild web/ui and commit web/bundle", so the UI change is not complete without `npm run build` in `web/ui` and the rebuilt hashed assets committed.

## Current state and the gap

### Nothing attests the bytes an `extends:` child materializes

`assembleResult` (`pkg/registry/core/core.go:1670-1693`) returns, for a child declaring `extends:`, a `Frontmatter` that is `mergeChain`'s re-serialization with the parent stripped, a `ContentHash` that is the child's stored digest over its pre-merge `ARTIFACT.md`, and a `Signature` that is the child's stored envelope over that digest. The signed value therefore covers bytes the consumer never materializes, and the bytes that reach `adapter.Materialize` and then disk are covered by nothing. `verifyContentHash` (`cmd/podium-mcp/main.go:1768-1790`) hashes `RawFrontmatter` for exactly this reason, which checks the pre-merge document and leaves the merged document unchecked.

The batch path is worse. `BatchLoadEnvelope` (`pkg/registry/server/batch_load.go:29-55`) carries a merged `Frontmatter`, a pre-merge `ContentHash`, no pre-merge companion, and no signature, so an SDK consumer has never had an integrity gate on any artifact.

### The §4.6 guarantee is contradicted on several read surfaces

`spec/04-artifact-model.md:683` states that a hidden parent's existence and ID are not surfaced to the requester. On the read path:

- `raw_frontmatter` carries the authored `extends: <parent>` line to every requester (`pkg/registry/core/core.go:1692`, `pkg/registry/server/server.go:607-611`), and the consumer writes it to a side file on its own disk (`cmd/podium-mcp/resolution_cache.go:256-267`).
- `manifest_merged` is an unconditional existence flag (`pkg/registry/server/server.go:602-606`), with a structural twin in `attachManifestBody`'s `res.Merged` early return (`:1205`).
- `GET /v1/dependents` filters `visibleIDs[e.From]` only (`pkg/registry/core/dependents.go:36-49`), so one GET against a guessed ID confirms the artifact exists and names its children. The web UI calls it.
- Two chain errors interpolate the parent. `resolveExtendsChain` returns `"%w: parent %s: %v"` with `rec.ExtendsPin` verbatim (`pkg/registry/core/core.go:1713`) and `"%w: extends cycle at %s"` with the repeating member's `<id>@<version>` (`:1704`), and `writeCoreError` passes `err.Error()` into the §6.10 message. `GetManifest` filters on `deleted_at IS NULL`, so a soft-deleted or retention-purged parent makes every load of the child answer `registry.not_found: parent acme/hidden-parent@1.2.0: ...` to anyone who can see the child.
- The search-descriptor strip runs only when `sc.rec.ExtendsPin != ""` (`pkg/registry/core/core.go:1301`). `extends_pin` arrived as a migration (`pkg/store/schema_migrate.go`), so a row written before that column existed carries the authored `extends:` key and bypasses the strip, and `FrontmatterHidingParent` applies no parent-ID test where the load path refuses a block that names the parent in any key.
- The web UI receives the parent ID in the browser and decides client-side whether to draw it (`web/ui/src/surfaces/ArtifactViewer.tsx:1009-1031`). The concealment rule is correct and it is on the wrong side of the boundary.
- A cross-layer collision rejection names the contributing layer (`pkg/registry/ingest/ingest.go:749`) in a response body a non-admin layer owner can reach through `POST /v1/layers/reingest`.

### The existence half cannot be delivered

For an artifact with no parent, the consumer recomputes §4.7.6 from the served bytes and reproduces the served `content_hash`. For a merged child it cannot, because the stored digest is over pre-merge bytes. Recompute, compare, and the answer is a parent. That survives dropping `raw_frontmatter` and `manifest_merged`, and the only closures are to withhold `content_hash` for merged artifacts, which moves the oracle to `/v1/sync/manifest` and breaks `@sha256:` pins, or to hash the merged bytes at ingest, which reverses proposal 0026's §4.7.6 rule one proposal after it lands.

## Decisions

- **Attest the served record rather than re-basing the stored one.** The defect is that the delivered bytes carry no attestation, which a second digest over the delivery closes without touching the identity every other subsystem is keyed on.
- **Mint at serve time.** The merged record is a pure function of stored state, so an ingest-time countersignature is possible and is still wrong. Its byte basis is `manifest.SerializeMerged`'s yaml.v3 output, which is a function of the `manifest.Artifact` struct's field declaration order and of the serializer's quoting and wrapping, so an unrelated struct edit would invalidate every stored countersignature and require a re-sign migration. It would also need a backfill on day one, a column on both store backends, and a rule for the §4.7.4 lifecycle fields that change after ingest. Serve-time minting has none of those and re-mints under the current key after a rotation. Its cost is an Ed25519 signature and a small SHA-256 per load, on a path that already performs a store read, a recursive chain walk, a YAML parse and re-marshal per chain member, and a presign per large resource.
- **Domain-separate the digest.** Proposal 0026 declined a tag for §4.7.6 because that digest had no sibling. It has one now, and two digests with one definition under one key is a cross-protocol confusion by construction.
- **Frame resource content hashes rather than bodies.** Each resource already carries an authoritative `sha256:` digest in `store.ResourceRef.ContentHash`, in memory when the response is assembled, and the consumer already checks fetched bytes against it. Framing bodies would download every above-cutoff resource from object storage on every load and buy nothing.
- **Keep the SPI unchanged.** `pkg/audit/anchor.go` signs an audit chain head that has no delivery record, and `internal/serverboot/signing.go` passes `signer.Sign` as a method value into `ingest.SignerFunc`. Widening `Provider.Sign` breaks both for no gain, since the delivery hash is already the `alg:hex` string the providers accept.
- **Drop the served `signature`.** For a merged child it attests a digest the consumer can no longer reproduce, which is the inert-field pattern this repository already carries twice (`ExternalResource.Signature`, `sync.Config.VerifySignatures`). For every other artifact it attests a value the delivery stream frames, under the same key, from the same party. Keeping both would invite a consumer to verify whichever is present, which reintroduces the merged-versus-unmerged behavioral difference the uniformity invariant exists to remove. A future author-signed envelope needs its own field, its own trust policy, and its own verification rules, so reserving this one for it reserves the wrong field.
- **Move the concealment rule to the server and keep the feature.** Serving a visibility-gated `extends` is the same rule the browser runs today, evaluated where the data lives. Accepting the chip's loss would delete a shipped §13.10 surface for readers entitled to it, in the name of a leak the server closes anyway.
- **Answer an invisible `/v1/dependents` target exactly as a nonexistent one.** A nonexistent target and a target with no dependents already answer identically; a third answer for "invisible" would be the oracle.
- **Do not make the merged case verify differently from the unmerged case.** A rule that refuses the `noop` provider, or requires `PODIUM_SIGNATURE_VERIFY_KEY`, only for a merged response is itself an existence oracle: the caller learns from the refusal what the response no longer tells them. The unconditional recomputation applies to every response identically, and the signature policy stays the one §4.7.9 defines.
- **Narrow the §4.6 promise rather than leaving it false.** Welding existence to ID in one sentence made every closable leak read as a total failure of both, and it is what let the shipped documentation repeat a claim no build has ever satisfied.

## Spec amendment: §4.7.10 delivery attestation

**SPEC-1.** Anchor: `spec/04-artifact-model.md`, a new `### 4.7.10 Delivery Attestation` appended after §4.7.9, which ends with the signing subsection's last paragraph. No existing subsection is edited.

> ### 4.7.10 Delivery Attestation
>
> The `content_hash` (§4.7.6) names the stored artifact. For a child declaring `extends:` the registry serves a merged re-serialization (§4.6) whose bytes do not reproduce that digest, so the record a consumer materializes is not the record the content hash names. The delivery attestation binds the served record instead.
>
> The **delivery record** is the artifact identity, type, and resolved version the response carries; the `content_hash` of the stored artifact the registry composed the response from; the served `sensitivity`; the served manifest document; the served manifest body; the served `SKILL.md`; and, for each bundled resource, its path and its content hash. Its canonical serialization uses the §4.7.6 framing: the framed ASCII tag `podium/delivery-record/1`, then the framed identity, version, type, content hash, and sensitivity in that order, then the framed manifest document, manifest body, and `SKILL.md`, then, for each bundled resource in ascending byte-wise order of its UTF-8 path, the framed path followed by the framed resource content hash. An absent `SKILL.md` frames a zero-length value. The `delivery_hash` is the SHA-256 digest of that serialization, served as `sha256:<hex>`.
>
> The serialization carries a resource's content hash rather than its body, so a consumer verifies the record before fetching any resource and the registry adds no object-store read to the read path. The lifecycle fields (§4.7.4), the contributing layer, and the per-caller `extends` reference are excluded: the first change after ingest, and the last is served per requesting identity, so including either would make the digest depend on when or by whom the record was read.
>
> The registry computes the delivery hash per response and signs it through the configured `SignatureProvider` (§9.1), serving the envelope as `delivery_signature`. It does so for every `load_artifact` response and every batch entry, whether or not the artifact declares `extends:`. The uniformity is required: an attestation served only for a merged record would make its presence a disclosure of the merge, which §4.6 forbids. A registry running without a signing key serves `delivery_hash` with an empty `delivery_signature`.
>
> The signer is a local-key provider. A network-backed provider is not admissible on the read path, because a per-response certificate request and transparency-log entry would put a network round trip inside every load.
>
> A consumer recomputes the delivery hash from the bytes it received and compares it to the served value before it reads any policy input out of the record, caches it, or writes any byte to disk (§6.6). It then applies the §4.7.9 verification policy to `(delivery_hash, delivery_signature)`. A filesystem-source `podium sync` composes and materializes in one process, so it has no delivery to attest and computes no delivery hash. The materialized output is identical in both modes (§2.2); the modes differ in the attestation channel.
>
> The attestation states that the registry composed and served these bytes. It does not state that the merge is faithful. A consumer that cannot see a hidden parent cannot obtain it and therefore cannot check that the served manifest is the §4.6 fold of the child and its pinned ancestors, so a registry that folds the wrong parent, folds a parent the child never named, or fabricates the merged document produces a delivery record that verifies. The attestation binds the record against every party in the delivery path other than the one holding the registry's signing key.

§4.7.10 is a new behavioral section and needs a citing test for `speccov-drift`; TEST-1 and TEST-3 carry the citation.

## Spec amendment: §4.6 hidden parents

**SPEC-2.** Anchor: `spec/04-artifact-model.md:683`, the paragraph beginning "**Hidden parents.**" and ending "regardless of layer membership." Replace it in full with the text below. The "Field semantics table" heading that follows is not edited.

> **Hidden parents.** When a child manifest declares `extends: <parent>` and the requesting identity cannot see the layer that contributes the parent, the registry resolves and merges the parent server-side and serves the merged manifest. This preserves layer privacy and keeps the consumer interface uniform regardless of layer membership.
>
> *Withheld.* The parent's canonical ID, version, layer, content hash, and signature are not surfaced on any read path to a requester who cannot see the layer that contributes it. The merged frontmatter names no parent, and a merged block that still resolves an `extends:` value, or that carries a key or a value standing as a reference to a chain parent, fails the read rather than being served. The search descriptor for a child declaring `extends:` carries the child's own frontmatter with its `extends:` key removed, for every requester. The reverse dependency index returns no edge whose parent endpoint the caller cannot see (§4.7.3). A failure to resolve the chain reports the artifact the caller requested and not the parent it could not reach. The `extends` field on a `load_artifact` response is present only when the caller can see the parent record, and its absence is indistinguishable from an artifact that extends nothing.
>
> *Served.* The parent's own frontmatter values reach the requester through the merge, by design. Every key the parent declares and the child does not override is served in the merged block per the field-semantics table and the omitted-field rule below, including extension-type keys, and the list-valued fields carry the parent's entries alongside the child's. The parent's description, tags, sensitivity, and search visibility are folded into the child's indexed record at ingest, so parent-authored text is reachable through search and through vector similarity on the child. A requester who receives a merged artifact has received the parent's frontmatter metadata. The parent's prose body, its bundled resources, and its `SKILL.md` are not served: the merged record carries the child's.
>
> *Observable.* The requester can determine that a merge occurred. The served `content_hash` is computed over the child's pre-merge package (§4.7.6), so for a merged artifact the served bytes do not reproduce it, and the mismatch is a reliable signal that the artifact extends something. The guarantee covers the parent's identity and its unmerged content; it does not conceal the existence of an inheritance relationship.
>
> Resolution of an `extends:` reference crosses the visibility boundary by construction, so an author who declares `extends: <parent>` learns whether that reference resolved and, when it did not, why: whether the artifact exists, whether its type matches, whether any stored version satisfies the constraint, and whether its versions are deprecated. Authoring a reference to an artifact is therefore an act that discloses that artifact's resolution to the author, whatever layer contributes it. The disclosure is scoped to the reference the author wrote and does not extend to the layer that contributes the parent.

Each of the three labelled paragraphs is behavioral. TEST-4 through TEST-9 carry the citations, including the one for *Observable*, which asserts the documented limitation rather than a fix.

## Spec amendment: §4.7.3 reverse-index visibility

**SPEC-3.** Anchor: `spec/04-artifact-model.md`, §4.7.3, after its last bullet and before the `### 4.7.4` heading. Append:

> **Visibility.** The reverse index is filtered per caller. An edge is returned only when the requesting identity can see both of its endpoints under §4.7.2 per-layer visibility: the artifact that declared the relation and the artifact the relation names. For an `extends:` edge the endpoint tested is the parent record the child pinned at ingest (§4.7.6), so a child that overlays a lower-precedence layer's artifact under the same canonical ID (§4.6) yields no edge to a caller who cannot see that layer.
>
> A query against an artifact the caller cannot see returns an empty edge list. It does not return an error, and it is not distinguishable from a query against an artifact that does not exist or one that nothing depends on. Impact analysis is therefore a view of the caller's effective composition rather than of the whole tenant, and an operator assessing the blast radius of a deprecation sees the dependents in the layers that operator can read.

The `From`-side filter has shipped since the endpoint existed and rests entirely on a code comment, so this paragraph records existing behavior as well as the change.

## Edge cases and accepted failure modes

| Case | Observable outcome | Where it is stated |
|:--|:--|:--|
| A registry that folds the wrong parent, or fabricates the merged document | Produces a delivery record that verifies. The consumer cannot obtain the parent without defeating §4.6 and so cannot check the fold | SPEC-1's last paragraph |
| A merged child loaded by a requester who recomputes §4.7.6 over the served bytes | The digests differ, which is a reliable signal that the artifact has a parent. Not closed by this proposal | SPEC-2's *Observable* paragraph; pinned by TEST-9 |
| A registry running without a signing key | `delivery_hash` is served with an empty `delivery_signature`. The recomputation still runs and still binds the served bytes to the served digest | SPEC-1; `docs/deployment/operator-guide.md` per DOC-1 |
| The shipped consumer defaults (`noop` provider, no verify key, `medium-and-above`) | The signature half verifies nothing. The recomputation is unaffected, so no artifact loses the gate it has today and a merged child gains one over the bytes it materializes | SPEC-1; Open question OQ-3; a sibling proposal owns the defaults |
| A compromised node that serves reads | Can mint a valid countersignature over forged bytes, which a consumer caches and replays offline. Every deployment runs one binary that both ingests and serves, so no node acquires a key it did not already have | SPEC-1's last paragraph |
| A delivery record captured and replayed later | Verifies. The stream carries no timestamp and no nonce, so rollback within an ID is not detectable from the record alone | OQ-2 |

## Open questions

**OQ-1. Does this proposal ship in the same release as proposal 0026?** The consumer-cache action combines to a single `rm -rf` if it does and needs its own instruction if it does not. Nothing else in the design depends on the answer.

**OQ-2. Freshness.** The delivery record carries no timestamp and no nonce, so a captured record replays. Binding a timestamp is cheap to frame and expensive to use, because the consumer then needs a clock policy and a skew tolerance, and a wrong tolerance fails closed against a correct registry. The alternative is to treat the §7.5.3 lock, which already pins `(id, version, content_hash)`, as the place rollback is detected. Left out here.

**OQ-3. The verification defaults.** Under `PODIUM_SIGNATURE_PROVIDER=noop`, an unset `PODIUM_SIGNATURE_VERIFY_KEY`, an unset `PODIUM_SIGN`, and `verify_signatures: medium-and-above`, the signature half of this attestation verifies nothing. This proposal deliberately does not fix that, because a strictness rule applied only to merged responses is itself an existence oracle and a strictness rule applied to every response is an availability break that belongs with the deployment posture rather than with the attestation. The sibling proposal that fixes the defaults and the check ordering owns it. Confirm that sequencing, and confirm whether standalone should default to `PODIUM_SIGN=registry-key`, which costs an operator nothing because the bootstrap already generates a keypair, and which would give the verification path its first non-fixture population.

**OQ-4. Does a search descriptor that fails the parent-ID test serve an empty frontmatter block or drop the result?** `FrontmatterHidingParent` returns the empty block today, so the artifact still appears in results with a missing field, while the load path fails the whole read. Those are two fail-closed postures for one condition and CODE-8 does not pick between them.

**OQ-5. Is `extends` the right wire name for a field carrying the resolved pin?** The authored reference may be a range and the served value is its resolution. Serving the pin is what the registry holds; serving the author's text would require storing it, which nothing does.

## Relationship to proposal 0026

This proposal is written against the tree after 0026 lands and is implemented. It reuses 0026's `writeFramed` primitive and its ascending-path resource order, and SPEC-6 amends the §4.7.6 paragraph 0026 stages. It moves no stored hash, adds no store column, and invalidates no `@sha256:` pin, no ingest signature envelope, and no committed `sync.lock` entry, so it forces no second migration of stored values. 0026's migration is a rewrite the registry performs once, on the first start of the new version, before it ingests or serves, and nothing here adds to it or re-triggers it. DOC-1's changelog wording extends 0026's upgrade note, which states that start and the consumer cache-directory clear.

0026's OQ-3 is resolved: its CODE-5 moves the filesystem-source sync onto the authored bytes, and its TEST-7 gives the §11 equivalence fixture the `extends:` child that detects a divergence mechanically. Nothing here changes either. After `raw_frontmatter` is gone the server-source consumer stops recomputing §4.7.6 at all, so the parties to that agreement are ingest, the filesystem-source sync, and the §6.4 overlay, and 0026's fixture is what keeps them pinned.

It also answers 0026's OQ-4, which asks whether §4.6 permits serving the pre-merge `ARTIFACT.md` bytes to a requester who cannot see the parent's layer. The answer staged here is that it does not, and that the consumer does not need them.

## Non-goals

- **A Merkle tree over the artifact's parts with the parent's leaf redacted.** It collapses on the requirement it was built for. Hiding the parent's *existence* forces a uniformly-blinded slot that is never opened for any requester, so no sibling path is ever transmitted and the tree degenerates to a flat digest plus one blinded component, which is what SPEC-1 stages without the structure. Recorded so it is not re-derived.
- **Computing and storing the merged record at ingest as a separate artifact.** It collides on the `(tenant_id, artifact_id, version)` primary key, it makes re-ingest depend on yaml.v3's serialization staying byte-stable so an unrelated serializer or struct change bricks it, and it breaks §8.4 retention, which has no concept of a derived row to purge alongside its source. Recorded so it is not re-derived.
- **Re-basing the §4.7.6 content hash onto the merged bytes.** It would close the existence oracle, and it reverses proposal 0026's rule one proposal after it lands, costs a second migration on a hash 0026 has just moved, and leaves an author unable to compute their own artifact's hash from their own source in server mode.
- **Widening `pkg/sign.Provider`, or admitting a network-backed signer on the read path.** The SPI takes the delivery hash unchanged, and a Sigstore-keyless signature per response would be a Fulcio request and a Rekor upload inside every load.
- **Storing the countersignature, adding a store column, or backfilling one.** Serve-time minting covers every stored artifact from the moment the binary restarts.
- **Minting a §6.10 error code.** The consumer's remedy is identical for a delivery mismatch and a content mismatch, and the signature outcomes already have codes, axis entries, and matrix tests.
- **Verifying the delivery record in the SDKs or in `podium sync`.** Two more implementations of the serialization is the §2.2 drift problem in two languages with no shared library. `sync.Config.VerifySignatures` stays parsed and unread, which is a defect this proposal names and does not fix.
- **Filtering `GET /v1/events` per subscriber identity.** `handleEvents` reads no identity and `PublishEvent` fans every payload, carrying an artifact's ID and layer, to every subscriber and webhook receiver in the tenant, so publishing a hidden parent discloses it with no `extends:` chain involved. It is a §4.7.2 defect on the event stream with its own design questions, and it is filed separately. SPEC-2's text is written so it stays true whether or not that is ever fixed.
- **An admin override on `/v1/dependents`.** There is none today, the `From` side has always been filtered without one, and adding one is a new capability with its own audit obligation.
- **Filtering the `DependencyInDegree` ranking signal per caller.** It is a per-request store scan on the search hot path for a weak statistical channel.
- **Closing the §4.7.9 sensitivity gate.** Under `medium-and-above` a registry that declares an artifact `low` is not verified, and reading the sensitivity out of the verified record does not change that, because a registry forging the record forges its `sensitivity:` too. Only `always` resists a hostile registry, and that is a policy question for the proposal that owns the defaults.
- **An author-signed envelope.** It needs its own field, its own trust-policy plumbing, and its own verification rules, including a `SigstoreKeyless.Verify` that inspects the signer's identity, which it does not today.
- **Binding freshness, or detecting rollback within an artifact ID.** OQ-2 records both.

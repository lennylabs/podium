# Proposal 0027: Attest the served record and close the hidden-parent disclosures

- Issue: (to be filed)
- Status: Draft
- Date: 2026-09-15

This document stages the proposed spec, code, test, and documentation changes. It does not modify any spec, code, or doc file. Apply the changes in the staged sections after sign-off.

## Summary

**What changes.**

- A new §4.7.10 delivery attestation: the registry computes a framed digest over the record it serves (the identity, the merged frontmatter, the body, `SKILL.md`, and each bundled resource's path and content hash), signs it with the registry-managed key it already holds for ingest signing, and returns `delivery_hash` and `delivery_signature` on both `load_artifact` and `POST /v1/artifacts:batchLoad`. Nothing attests the merged bytes today, and the batch path carries no integrity value of any kind.
- The `load_artifact` response stops carrying `raw_frontmatter`, `manifest_merged`, and `signature`, and the merged-manifest exclusion from the presigned manifest-body channel goes with them. Each of the three is a §4.6 disclosure or an oracle for one, and each exists only to support a recomputation the delivery attestation replaces.
- The response gains `extends`, the pinned `<id>@<version>` the child resolved at ingest, present only when the calling identity can see the parent record. The §13.10 web UI reads that field and deletes the client-side concealment gate it runs today, which decides in the browser what the server has already disclosed.
- Four further disclosure paths close: `GET /v1/dependents` filters on the queried target and on the pinned parent record rather than on the source artifact alone, two `pkg/registry/core` error messages stop interpolating the hidden parent's ID and version pin into a message that reaches the client verbatim, the search descriptor of a pinned child is held to the parent-ID test the load path applies over the child's whole pinned chain, and the cross-layer collision rejection stops naming the contributing layer to a caller who cannot read it.
- §4.6's hidden-parents paragraph is replaced. Its sentence promises that a hidden parent's "existence and ID are not surfaced to the requester", and the existence half is not deliverable: the served bytes of a merged child do not reproduce the served `content_hash`, which is a one-request boolean test for a parent that survives every change staged here. The replacement splits the guarantee into what is withheld, what the merge serves by design, and what is observable.
- §4.7.3 gains a visibility paragraph. The reverse index has been filtered per caller since it shipped and `spec/` says nothing about it, so the rule being narrowed has no section a test can cite.
- The registry takes over the part of the consumer's §4.7.6 recomputation that it can perform from the metadata store: it refuses a requested row whose stored bytes do not reproduce its stored content hash, per SPEC-10's stored-row admission (CODE-17).
- The MCP server's §7.6.2 prefetch warm-up is removed, and §7.6.2's sentence describing it is deleted. The consumer cannot verify the batch envelope, so a prefetched entry could only be an unverified cache write or no write at all.

**Fixed decisions.**

- The countersignature is minted at serve time, on every response, for every artifact, whether or not it declares `extends:`. It is never stored and never backfilled (Decisions).
- The delivery digest is domain-separated from the §4.7.6 content hash by a framed leading tag and frames each bundled resource's content hash rather than its body (SPEC-1, CODE-1).
- `content_hash` stays on the wire with its §4.7.6 meaning, as the §6.5 cache key, the §7.5.3 lock value, and the `@sha256:` pin target. The MCP server verifies the delivery record in place of recomputing it (SPEC-4, CODE-10).
- The registry refuses a requested row whose stored bytes do not reproduce its stored content hash before composing a delivery record. The check reads only the metadata store, keeps no state, and reads no signature, no chain ancestor, and no object storage (OQ-6 as narrowed, OQ-7; SPEC-10, CODE-17).
- Only the MCP server verifies the delivery record, on the `load_artifact` path. Server-source `podium sync`, the language SDKs, and a §6.4 workspace overlay load verify nothing (SPEC-1).
- The delivery signer is the registry-managed key, whatever key model signed the artifact at ingest and whatever `SignatureProvider` a deployment configures (SPEC-1, SPEC-8).
- `podium verify <artifact>` verifies the delivery pair (CODE-13).
- Every inline-only reader follows `manifest_body_url` (CODE-14, CODE-15, CODE-16), and every follower, the SDKs' included, sends the caller's token to a URL that is not SigV4 presigned (CODE-15, CODE-18).
- The delivery-hash recomputation runs unconditionally on every load, independent of `PODIUM_VERIFY_SIGNATURES` and of `sensitivity`, and fails closed. The signature half stays inert under the shipped defaults until the sibling proposal on verification defaults lands (OQ-3).
- `pkg/sign.Provider` is not widened (Decisions).
- The stored ingest signature stays, and the served `signature` field goes (Decisions, CODE-3).
- A failed delivery verification reuses `materialize.content_hash_mismatch` and amends its existing §6.9 row in place (SPEC-4b). A missing or invalid signature keeps the code the consumer serves today. No §6.10 code is minted.
- Two boundaries with proposal 0028 are assigned here. The move of the MCP server's local-sink read event below the §6.6 step-2 verification is this proposal's (CODE-10). The delivery verification on the §5.0 `resources/read` mirror is 0028's (its CODE-12), and CODE-15 adds only the manifest-body fetch. 0028's summary, CODE-3, and S11 still claim the read-event move; narrowing them to the `signature_missing` remap is a follow-up edit to 0028 for the owner.
- An invisible `/v1/dependents` target answers `200 {"edges":[]}`, byte-identical to a target that does not exist and to one nothing depends on (SPEC-3, Decisions).
- §4.6's existence guarantee is narrowed rather than restored, and the spec text says so (SPEC-2).

**Watch out for.**

- **Dropping `raw_frontmatter` alone blanks a shipped surface.** `declaredExtends` (`web/ui/src/surfaces/ArtifactViewer.tsx:994-999`) falls back to the served `frontmatter`, which the registry has already stripped for every requester, so the outbound extends rail reads "This artifact extends nothing" for every artifact including one whose parent the reader can see. CODE-5 and CODE-11 land together or a privacy fix ships as a feature regression.
- **`manifest_merged` and the presigned-body exclusion are the same oracle read two ways.** `omitempty` makes the flag's presence exactly the predicate "this artifact extends something", and `attachManifestBody` returns early on `res.Merged` (`pkg/registry/server/server.go:1205`), so an above-cutoff merged manifest is served inline where an unmerged one is served by URL. Deleting the field and leaving the guard keeps the oracle in the response structure.
- **An ID-keyed `/v1/dependents` filter passes the case it is written for.** The §4.6 same-ID overlay makes a child extend its own canonical ID in a lower-precedence layer, so `edgesFor` records `{From: "team/overlay", To: "team/overlay"}` (`pkg/registry/ingest/ingest.go:1306-1310`). Both endpoints are "visible" by ID while the record the pin names is not, and the self-edge discloses that a layer the caller cannot read contributes that ID.
- **The delivery stream must not depend on the requesting identity.** `extends` is served per caller and is therefore excluded from the stream. A per-requester digest cannot be compared across consumers and cannot be precomputed, and the single-load and batch paths would stop agreeing.
- **The per-caller `extends` field breaks the content-hash ETag.** `handleLoadArtifact` answers a matching `If-None-Match` with 304 under a strong ETag equal to the content hash (`pkg/registry/server/server.go:1043-1056`), so a cache holding one identity's body, with its `extends`, would be revalidated for an identity that cannot see the parent. CODE-3's `loadArtifactETag` folds the served `extends` into the validator.
- **Do not reuse `version.CanonicalContentHash` over the merged bytes.** Two digests with one definition, one hex encoding, one SPI, and one key means a signature over either is syntactically a signature over the other. It would also take `map[string][]byte`, which forces every large resource out of object storage on every load.
- **An ingest-stored countersignature depends on yaml.v3 and on struct field order.** `manifest.SerializeMerged` marshals a `manifest.Artifact` through `gopkg.in/yaml.v3` and splices the authored keys back, so its byte output is a function of the struct's field declaration order and of the serializer's quoting and wrapping. Adding a field to `Artifact` would invalidate every stored countersignature at once and require a re-sign migration on a release that intended no behavior change.
- **`test/e2e` skips parts of itself on macOS.** `test/e2e/artifact_extends_test.go` carries unconditional skips of its own, and the `oidc-jwt` arms skip on darwin. This proposal's central behavior is a visibility-boundary behavior, so a green local `go test ./test/e2e/...` is not evidence. Grep the run output for `SKIP`, and prefer `trusted-headers` for the new visibility arms.
- **Removing the consumer's §4.7.6 recomputation moves the stored-row gate to the registry for rows whose bundled-resource bodies the metadata store holds.** The registry frames whatever `content_hash` a row stores, so without a registry-side check such a row would verify at the consumer once `verifyContentHash` is gone. A row with a bundled resource held in object storage is served at its stored hash (Decisions, "Admit the requested row at the registry"). SPEC-10's stored-row admission is that check (CODE-17).
- **Stored-row admission refuses direct-store test fixtures.** Many tests write manifest records without ingest and give them a `ContentHash` that is not the §4.7.6 digest of their bytes. After CODE-17, each such record that reaches `assembleResult` as the requested row with every bundled resource held inline is refused, so the fixtures listed under "Tests removed or rewritten" take their hash from a shared helper in the same commit as CODE-17.
- **The wire break and every reader of the removed fields land in one commit.** `raw_frontmatter`, `manifest_merged`, and `signature` have readers in `cmd/podium-mcp`, `cmd/podium`, `pkg/sync`, and `web/ui`, and the `res.Merged` guard's removal reaches every reader that decodes only the inline manifest fields, the SDK followers that fetch the URL without the caller's token, and the `/objects` route that serves the URL, so S7 carries CODE-10, CODE-11, CODE-13, CODE-14, CODE-15, CODE-16, and CODE-18 beside the server change, and the test rewrites with them.
- **The resolution index is a cache.** `cmd/podium-mcp` writes `(id, version) → content_hash` to its bbolt `index.db` before `deliverLoadArtifact` runs (`cmd/podium-mcp/main.go:1441-1449`), so leaving that write in place records an unverified response's values on disk. CODE-10 moves it behind the verification.
- **`web/bundle/` is committed build output.** `web/icons_test.go` fails with "rebuild web/ui and commit web/bundle", so the UI change is not complete without `npm run build` in `web/ui` and the rebuilt hashed assets committed.

## Current state and the gap

### Nothing attests the bytes an `extends:` child materializes

`assembleResult` (`pkg/registry/core/core.go:1670-1693`) returns, for a child declaring `extends:`, a `Frontmatter` that is `mergeChain`'s re-serialization with the parent stripped, a `ContentHash` that is the child's stored digest over its pre-merge `ARTIFACT.md`, and a `Signature` that is the child's stored envelope over that digest. The signed value therefore covers bytes the consumer never materializes, and the bytes that reach `adapter.Materialize` and then disk are covered by nothing. `verifyContentHash` (`cmd/podium-mcp/main.go:1768-1790`) hashes `RawFrontmatter` for exactly this reason, which checks the pre-merge document and leaves the merged document unchecked.

The batch path is worse. `BatchLoadEnvelope` (`pkg/registry/server/batch_load.go:29-55`) carries a merged `Frontmatter`, a pre-merge `ContentHash`, no pre-merge companion, and no signature, so an SDK consumer has never had an integrity gate on any artifact.

### The §4.6 guarantee is contradicted on several read surfaces

§4.6's hidden-parents paragraph (`spec/04-artifact-model.md`) states that a hidden parent's existence and ID are not surfaced to the requester. On the read path:

- `raw_frontmatter` carries the authored `extends: <parent>` line to every requester (`pkg/registry/core/core.go:1692`, `pkg/registry/server/server.go:607-611`), and the consumer writes it to a side file on its own disk (`cmd/podium-mcp/resolution_cache.go:256-267`).
- `manifest_merged` is an unconditional existence flag (`pkg/registry/server/server.go:602-606`), with a structural twin in `attachManifestBody`'s `res.Merged` early return (`:1205`).
- `GET /v1/dependents` filters `visibleIDs[e.From]` only (`pkg/registry/core/dependents.go:36-49`), so one GET against a guessed ID confirms the artifact exists and names its children. The web UI calls it.
- Two chain errors interpolate the parent. `resolveExtendsChain` returns `"%w: parent %s: %v"` with `rec.ExtendsPin` verbatim (`pkg/registry/core/core.go:1713`) and `"%w: extends cycle at %s"` with the repeating member's `<id>@<version>` (`:1704`), and `writeCoreError` passes `err.Error()` into the §6.10 message on `load_artifact`. On `artifacts:batchLoad`, `batchLoadError` already replaces the not-found case with a fixed `visibility.denied` envelope (`pkg/registry/server/batch_load.go:179-186`), and only the cycle message reaches the item verbatim. `GetManifest` filters on `deleted_at IS NULL`, so a soft-deleted or retention-purged parent makes every load of the child answer `registry.not_found: parent acme/hidden-parent@1.2.0: ...` to anyone who can see the child.
- The search-descriptor strip removes the `extends:` key (`pkg/registry/core/core.go:1301`), and `FrontmatterHidingParent` applies no parent-ID test (`pkg/manifest/merge_serialize.go:454`), whereas the load path refuses a merged block that names a chain parent in any key. When a pinned child's block also names its parent in another key, such as a `delegates_to` entry or an extension key, the descriptor serves that key. The pin itself is always present. `extends_pin` has been in both SQL stores' `CREATE TABLE` since v0.1.0, every released ingest sets it or rejects the child (`pkg/registry/ingest/ingest.go:650-685`), and `podium admin migrate-to-standard` copies each record unchanged (`cmd/podium/admin_migrate.go:366-371`). The `additiveColumns` entry (`pkg/store/schema_migrate.go:66`) makes a schema apply idempotent, and the only store created without the column was a SQLite file from a pre-release build, so no released build wrote an `extends:` row with an empty pin.
- The web UI receives the parent ID in the browser and decides client-side whether to draw it (`web/ui/src/surfaces/ArtifactViewer.tsx:1009-1031`). The concealment rule is correct and it is on the wrong side of the boundary.
- A cross-layer collision rejection names the contributing layer (`pkg/registry/ingest/ingest.go:749`) in a response body a non-admin layer owner can reach through `POST /v1/layers/reingest`.

### The existence half cannot be delivered

For an artifact with no parent, the consumer recomputes §4.7.6 from the served bytes and reproduces the served `content_hash`. For a merged child it cannot, because the stored digest is over pre-merge bytes. A requester who recomputes the digest and compares it learns that a parent exists. That signal survives dropping `raw_frontmatter` and `manifest_merged`, and the only closures are to withhold `content_hash` for merged artifacts, which moves the oracle to `/v1/sync/manifest` and breaks `@sha256:` pins, or to hash the merged bytes at ingest, which reverses proposal 0026's §4.7.6 rule one proposal after it lands.

## Decisions

- **Attest the served record rather than re-basing the stored one.** The defect is that the delivered bytes carry no attestation, which a second digest over the delivery closes without touching the identity every other subsystem is keyed on.
- **Mint at serve time.** The merged record is a pure function of stored state, so an ingest-time countersignature is possible and is still wrong. Its byte basis is `manifest.SerializeMerged`'s yaml.v3 output, which is a function of the `manifest.Artifact` struct's field declaration order and of the serializer's quoting and wrapping, so an unrelated struct edit would invalidate every stored countersignature and require a re-sign migration. It would also need a backfill on day one, a column on both store backends, and a rule for the §4.7.4 lifecycle fields that change after ingest. Serve-time minting has none of those and re-mints under the current key after a rotation. Its cost is a SHA-256 over the delivery record and an Ed25519 signature per load. CODE-17's stored-row admission adds a SHA-256 over stored row bytes the load already holds and reads nothing from object storage. CODE-3's removal of the `res.Merged` guard adds an object-store dependency: every served manifest document above the inline cutoff, including a merged one that was served inline before, costs a `Stat` on every load and a consumer fetch, and fails during an object-store outage. The design accepts that, because keeping merged manifests inline keeps the structural oracle the guard's removal closes (Summary, "Watch out for"). The outage reaches only a load that needs a full response: HEAD revalidation and a matching conditional GET are answered before `attachResources` and `attachManifestBody` (`pkg/registry/server/server.go:1049-1065`, `:1089-1097`), so a consumer in any cache mode, the default `always-revalidate` included, keeps serving its verified per-ID cached record while the content hash is unchanged. DOC-1's runbook bullet states that outcome.
- **Domain-separate the digest.** Proposal 0026 declined a tag for §4.7.6 because that digest had no sibling. It has one now, and two digests with one definition under one key is a cross-protocol confusion by construction.
- **Frame resource content hashes rather than bodies.** Each resource already carries an authoritative `sha256:` digest in `store.ResourceRef.ContentHash`, in memory when the response is assembled, and the consumer already checks fetched bytes against it. Framing bodies would download every above-cutoff resource from object storage on every load.
- **Keep the SPI unchanged.** `pkg/audit/anchor.go` signs an audit chain head that has no delivery record, and `internal/serverboot/serverboot.go` takes `ingest.SignerFunc` from `signProvider.Sign` as a method value (`:909`). Widening `Provider.Sign` breaks both for no gain, since the delivery hash is already the `alg:hex` string the providers accept.
- **Drop the served `signature`.** For a merged child it attests a digest the consumer can no longer reproduce, which is the inert-field pattern this repository already carries in `ExternalResource.Signature` (`pkg/manifest/types.go:212`). For every other artifact it attests a value the delivery stream frames, under the same key, from the same party. Keeping both would invite a consumer to verify whichever is present, which reintroduces the merged-versus-unmerged behavioral difference the uniformity invariant exists to remove. A future author-signed envelope needs its own field, its own trust policy, and its own verification rules, so reserving this one for it reserves the wrong field. The field has one reader outside the consumer, `podium verify <artifact>` (`cmd/podium/sign.go:134-160`), and it moves to the delivery pair (CODE-13) rather than gaining a separate surface that serves the stored envelope. The pair the consumer verifies is the pair an ad-hoc check should verify, and a second surface serving the stored envelope would restore the field this decision removes.
- **Move the concealment rule to the server and keep the feature.** Serving a visibility-gated `extends` is the same rule the browser runs today, evaluated where the data lives. Accepting the chip's loss would delete a shipped §13.10 surface for readers entitled to it, in the name of a leak the server closes anyway.
- **Answer an invisible `/v1/dependents` target exactly as a nonexistent one.** A nonexistent target and a target with no dependents already answer identically; a third answer for "invisible" would be the oracle.
- **Do not make the merged case verify differently from the unmerged case.** A rule that refuses the `noop` provider, or requires `PODIUM_SIGNATURE_VERIFY_KEY`, only for a merged response is itself an existence oracle: the caller learns from the refusal what the response no longer tells them. The unconditional recomputation applies to every response identically, and the signature policy stays the one §4.7.9 defines.
- **Narrow the §4.6 promise rather than leaving it false.** Welding existence to ID in one sentence made every closable leak read as a total failure of both, and it is what let the shipped documentation repeat a claim no build has ever satisfied.
- **Admit the requested row at the registry, at serve time, from the metadata store alone (OQ-6, option A as narrowed; OQ-7).** Stored-row admission checks that a row is consistent with its stored content hash. It does not defend against a store edit: a party with write access to the metadata store can make the registry serve any bytes by writing them together with the §4.7.6 digest over them, in every configuration, and no check over stored values alone tells that row from one ingest wrote. The check exists because the registry serves `content_hash` as the §6.5 cache key, the §7.5.3 lock value, and the `@sha256:` pin target, so a row whose stored hash does not name its stored bytes, such as a row still at the previous release's digest (§13.4), is refused. The §13.4 rewrite runs once, and a verdict it or ingest stored would be a value the same party can edit, so the check runs at serve time. The checks that a store edit does not pass lie outside admission: the consumer checks each body it fetches from object storage against its content hash (`cmd/podium-mcp/large_resources.go:95-101`), and SPEC-1 attests the delivery record in transit. SPEC-10 and CODE-17 state the rule, and four scope decisions set it.
  - *The requested row only.* A chain ancestor's `content_hash` is never served, because `mergeChain` keeps the child's (`pkg/registry/core/core.go:1747`), and the consumer's check today covers only the requested row's bytes (`cmd/podium-mcp/main.go:1775-1778`, `pkg/registry/core/core.go:1692`). Checking ancestors would add a refusal no release has made and a failure path whose outcome and timing concern a hidden parent.
  - *No object-storage read.* The §4.7.6 digest frames each resource body (`pkg/version/version.go:278-292`), so a row with a resource held in object storage cannot be recomputed without reading it. Reading it puts a read deadline, a per-process verdict cache, an outage failure, and object-key scrubbing on the load path, and the cache makes two processes answer one altered object differently. Such a row is served at its stored hash without the check. A `body_missing` row still fails at the consumer's fetch, a `body_unavailable` row is served at the previous release's digest once its object is readable and is rewritten by the next start, and an `unreproducible` or `signature_unverified` row is logged by the rewrite.
  - *No signature.* A stored-envelope test refuses only an editor who alters the hash and leaves the envelope, because clearing the envelope admits the row, and it needs a retired-key rule so that a key rotation does not refuse every older row. Admission reads no signature, so a rotation refuses no row, and nothing on the read path reads the stored envelope.   The check holds no state. It hashes bytes the load already holds, so it needs no cache, no wiring, and no configuration, and every node and deployment mode answers alike (§11). ## Spec amendment: §4.7.10 delivery attestation

**SPEC-1.** Anchor: `spec/04-artifact-model.md`, a new `### 4.7.10 Delivery Attestation` appended after §4.7.9, which ends with the signing subsection's last paragraph. SPEC-1 edits no existing subsection; SPEC-8 edits §4.7.9 separately.

> ### 4.7.10 Delivery Attestation
>
> The `content_hash` (§4.7.6) names the stored artifact. For a child declaring `extends:` the registry serves a merged re-serialization (§4.6) whose bytes do not reproduce that digest, so the record a consumer materializes is not the record the content hash names. The delivery attestation binds the served record instead.
>
> The **delivery record** is the artifact identity, type, and resolved version the response carries; the `content_hash` of the stored artifact the registry composed the response from; the served `sensitivity`; the served `ARTIFACT.md` document, which for a child declaring `extends:` is the merged document (§4.6), for every type including a skill; the served manifest body; the served `SKILL.md`, which for a skill is the child's own; and, for each bundled resource, its path and its content hash. Its canonical serialization uses the §4.7.6 framing: the framed ASCII tag `podium/delivery-record/1`, then the framed identity, version, type, content hash, and sensitivity in that order, then the framed `ARTIFACT.md` document, manifest body, and `SKILL.md`, then, for each bundled resource in ascending byte-wise order of its UTF-8 path, the framed path followed by the framed resource content hash. An absent `SKILL.md` frames a zero-length value. The `delivery_hash` is the SHA-256 digest of that serialization, served as `sha256:<hex>`.
>
> The serialization carries a resource's content hash rather than its body, so composing the delivery hash reads nothing from object storage, and a consumer checks each resource body it fetches or decodes against a content hash the verified record carries. The lifecycle fields (§4.7.4), the contributing layer, and the per-caller `extends` reference are excluded: the first change after ingest, and the last is served per requesting identity, so including either would make the digest depend on when or by whom the record was read.
>
> The registry computes the delivery hash per response and signs it with its registry-managed key (§4.7.9), serving the envelope as `delivery_signature`. The registry-managed key is the delivery signer whatever key model signed the artifact at ingest and whatever `SignatureProvider` (§9.1) the deployment configures. It does so for every `load_artifact` response and every batch entry, whether or not the artifact declares `extends:`. The uniformity is required: an attestation served only for a merged record would make its presence a disclosure of the merge, which §4.6 forbids. A registry that holds no registry-managed key serves `delivery_hash` with an empty `delivery_signature`, including a registry whose artifacts carry Sigstore-keyless or author-key signatures. Because the envelope is minted per response under the registry's current key, a rotation of that key takes effect on the next response: a consumer verifies against the rotated public key from then on, and a delivery signature it cached before the rotation does not verify under the new key.
>
> Sigstore-keyless and every other network-backed provider do not sign delivery records, because a per-response certificate request and transparency-log entry would put a network round trip inside every load. A consumer verifies `delivery_signature` with the registry-managed verifier against the registry's public key. The envelope carries no certificate chain, so a consumer whose verifier is Sigstore-keyless refuses a present delivery signature with `materialize.signature_invalid` whenever its §4.7.9 policy verifies the signature.
>
> On a `load_artifact` call the MCP server recomputes the delivery hash from the bytes it received and compares it to the served value before it reads any policy input out of the record, caches it, or writes any byte to disk (§6.6). A response that carries no `delivery_hash` fails the comparison. The MCP server then applies the §4.7.9 verification policy to `(delivery_hash, delivery_signature)`. Server-source `podium sync` (§7.5) and the language SDKs (§7.6.2) receive the delivery fields and neither recompute nor verify them, so they materialize the served record without a delivery check. A §6.4 workspace overlay load is served from the consumer's own filesystem, carries no delivery record, and is outside the comparison. A filesystem-source `podium sync` composes and materializes in one process, so it has no delivery to attest and computes no delivery hash. The materialized output is identical across these consumers and modes (§2.2); they differ in the attestation channel.
>
> The attestation states that the registry composed and served these bytes. It does not state that the merge is faithful. A consumer that cannot see a hidden parent cannot obtain it and therefore cannot check that the served manifest is the §4.6 fold of the child and its pinned ancestors, so a registry that folds the wrong parent, folds a parent the child never named, or fabricates the merged document produces a delivery record that verifies. Between the registry's response and the consumer's disk, the attestation binds the record against every party other than the one holding the registry's signing key. It carries no timestamp and no nonce, so a record captured from an earlier response verifies when it is replayed. It binds what the registry served, and the §13.4 stored-row admission check decides which stored rows the registry may compose a record from.

§4.7.10 is a new behavioral section and needs a citing test for `speccov-drift`; TEST-1 and TEST-3 carry the citation.

## Open questions

**OQ-1. Does this proposal ship in the same release as proposal 0026?** The consumer-cache action combines to a single `rm -rf` if it does and needs its own instruction if it does not. Nothing else in the design depends on the answer.

**OQ-2. Freshness.** The delivery record carries no timestamp and no nonce, so a captured record replays. Binding a timestamp is cheap to frame and expensive to use, because the consumer then needs a clock policy and a skew tolerance, and a wrong tolerance fails closed against a correct registry. The alternative is to treat the §7.5.3 lock, which already pins `(id, version, content_hash)`, as the place rollback is detected. This proposal leaves freshness out.

**OQ-3. The verification defaults.** Under `PODIUM_SIGNATURE_PROVIDER=noop`, an unset `PODIUM_SIGNATURE_VERIFY_KEY`, an unset `PODIUM_SIGN`, and `verify_signatures: medium-and-above`, the signature half of this attestation verifies nothing. This proposal deliberately does not fix that, because a strictness rule applied only to merged responses is itself an existence oracle and a strictness rule applied to every response is an availability break that belongs with the deployment posture rather than with the attestation. The sibling proposal that fixes the defaults and the check ordering owns it. Confirm that sequencing, and confirm whether standalone should default to `PODIUM_SIGN=registry-key`, which costs an operator nothing because the bootstrap already generates a keypair, and which would give the verification path its first non-fixture population.

**OQ-4. Does a search descriptor that fails the parent-ID test serve an empty frontmatter block or drop the result?** Closed: the descriptor is served without its frontmatter block. `FrontmatterHidingParent` returns the empty block today, `docs/reference/http-api.md:176` already documents a result with no `frontmatter` key for the other rewrite failures, and SPEC-2's descriptor sentence and CODE-8 state the same outcome for the parent-ID hit. The load path still fails the whole read, because it serves the merged record rather than a descriptor.

**OQ-5. Is `extends` the right wire name for a field carrying the resolved pin?** The authored reference may be a range and the served value is its resolution. Serving the pin is what the registry holds; serving the author's text would require storing it, which nothing does.

**OQ-6. Which party refuses a stored row whose bytes do not reproduce its stored hash, once the consumer stops recomputing §4.7.6?** Recommended by the review loop, not yet decided by the owner: option (A), the registry at serve time (CODE-17, SPEC-10, TEST-22). An earlier pass recorded it as the owner's decision; that was a misreading of an instruction about which proposal owns served-record verification. Redesign 2 narrows option (A) without reversing it, for the owner to confirm. The registry still refuses at serve time, fails closed, and returns a §6.10 code, and it checks the requested row only, from the bytes the metadata store holds, with no object-storage read, no signature, and no verdict cache. Every row that holds a bundled resource in object storage now loads at its stored hash, and the rows among them that the consumer's pre-change recomputation refuses are these: such a row whose other stored bytes, or whose stored content hash alone, were altered without recomputing the hash; such a row the rewrite left at the previous release's digest as `unreproducible` or `signature_unverified`, which no later start examines again; and a `body_unavailable` row whose object becomes readable, which loads at the previous release's digest until the next start rewrites it. Each object-held body stays bound at the MCP server by the per-resource content hash the delivery record frames, and the SDKs and server-source `podium sync` check no body (SPEC-1). The Decision "Admit the requested row at the registry" gives the reasons. Option (B) is rejected because a verdict recorded by the §13.4 rewrite or by ingest is written once and editable by the party it guards against, so it cannot refuse a row altered afterward, and it needs a store column. Option (C) is rejected because it removes a fail-closed refusal. The constraint stated before the decision still holds: no load materializes a row that fails the check, the refusal is fail-closed with a §6.10 code, and merged and unmerged artifacts are treated alike. SPEC-10, CODE-17 (including its comment updates at `internal/serverboot/rehash.go:109-111` and `:194-198`), DOC-1, and the `boot_rehash_test.go` and S64 bullet under "Tests removed or rewritten" dispose of the dependent sites.

**OQ-7. Does stored-row admission refuse a cleared or foreign-key stored signature on a signing registry, and does the registry bind the served body, sensitivity, and type to the admitted bytes?** Decided in Redesign 2, for the owner to confirm: neither. Admission reads no signature and binds no column (SPEC-10, CODE-17), because neither closes the store-edit path while the other stays open, and the Decision "Admit the requested row at the registry" states the threat model. The owner either accepts that this proposal ends the store-edit refusal a consumer with `PODIUM_SIGNATURE_VERIFY_KEY` and `PODIUM_VERIFY_SIGNATURES=always` makes today, or assigns its replacement to proposal 0028 or a follow-up: a signing registry that refuses an unsigned row, verifies an envelope naming another key against a retained key set with its own configuration surface, and serves each column from the admitted bytes, with a re-sign path for the rows those rules refuse.

**OQ-8. What does §7.6.2 say about the MCP server after the prefetch warm-up is removed?**

- Option (a), the default: delete the warm-up sentence (SPEC-5's §7.6.2 sub-edit). The spec then says nothing about MCP use of the endpoint, and no test is added.
- Option (b): replace the sentence with "The MCP server does not call this endpoint. It writes a §6.5 cache entry only from a `load_artifact` response whose §4.7.10 delivery record it has verified (§6.6), and it performs no startup warm-up." TEST-11 then gains an e2e arm, `TestMCPBridge_StartupNeverCallsBatchLoad` in `test/e2e/mcp_bridge_misc_test.go`, which starts the bridge with `PODIUM_PREFETCH` set and asserts zero `/v1/artifacts:batchLoad` requests, and the edge-case table gains a row for a leftover `prefetch` key. This option guards against the warm-up returning unverified. The cost is a spec sentence that states an absence and an e2e test that pins it.

## Relationship to proposal 0026

This proposal is written against the tree after 0026 lands and is implemented. It reuses 0026's `writeFramed` primitive and its ascending-path resource order, and SPEC-6 amends the §4.7.6 paragraph 0026 stages. It moves no stored hash, adds no store column, and invalidates no `@sha256:` pin, no ingest signature envelope, and no committed `sync.lock` entry, so it forces no second migration of stored values. 0026's migration is a rewrite the registry performs once, on the first start of the new version, before it ingests or serves, and nothing here adds to it or re-triggers it. This proposal moves the check that makes a row the rewrite did not rewrite fail closed (`spec/13-deployment.md:85`) from the consumer to the registry for rows whose bundled-resource bodies the metadata store holds, and serves a row with a bundled resource held in object storage at its stored hash (OQ-6, SPEC-10, CODE-17). DOC-1's changelog wording extends 0026's upgrade note, which states that start and the consumer cache-directory clear.

0026's OQ-3 is resolved: its CODE-5 moves the filesystem-source sync onto the authored bytes, and its TEST-7 gives the §11 equivalence fixture the `extends:` child that detects a divergence mechanically. Nothing here changes either. After `raw_frontmatter` is gone the server-source consumer stops recomputing §4.7.6 at all, so the parties to that agreement are ingest, the filesystem-source sync, the §6.4 overlay, and the registry's §13.4 recomputations of a stored row, at the first-start rewrite and, for a requested row that holds every bundled-resource body in the metadata store, at the stored-row admission check (CODE-17). 0026's fixture keeps ingest and the filesystem-source sync pinned, and TEST-23 pins the §6.4 overlay for an `extends:` package, which 0026's fixture does not reach: its overlay case overrides a package that declares no `extends:` (`test/integration/sync_equivalence_test.go:301-334`). The registry's recomputations call the `version.CanonicalContentHash` that ingest calls, and TEST-22's e2e arm pins the admission check's agreement with ingest by loading rows that ingest wrote.

It also answers 0026's OQ-4, which asks whether §4.6 permits serving the pre-merge `ARTIFACT.md` bytes to a requester who cannot see the parent's layer. The answer staged here is that it does not, and that the consumer does not need them.

## Non-goals

- **A Merkle tree over the artifact's parts with the parent's leaf redacted.** It collapses on the requirement it was built for. Hiding the parent's *existence* forces a uniformly-blinded slot that is never opened for any requester, so no sibling path is ever transmitted and the tree degenerates to a flat digest plus one blinded component, which is what SPEC-1 stages without the structure. It is recorded here so it is not re-derived.
- **Computing and storing the merged record at ingest as a separate artifact.** It collides on the `(tenant_id, artifact_id, version)` primary key, it makes re-ingest depend on yaml.v3's serialization staying byte-stable so an unrelated serializer or struct change bricks it, and it breaks §8.4 retention, which has no concept of a derived row to purge alongside its source. It is recorded here so it is not re-derived.
- **Re-basing the §4.7.6 content hash onto the merged bytes.** It would close the existence oracle, and it reverses proposal 0026's rule one proposal after it lands, costs a second migration on a hash 0026 has just moved, and leaves an author unable to compute their own artifact's hash from their own source in server mode.
- **Widening `pkg/sign.Provider`, or admitting a network-backed signer on the read path.** The SPI takes the delivery hash unchanged, and a Sigstore-keyless signature per response would be a Fulcio request and a Rekor upload inside every load.
- **Storing the countersignature, adding a store column, or backfilling one.** Serve-time minting covers every stored artifact from the moment the binary restarts.
- **Minting a §6.10 error code.** The consumer's remedy is identical for a delivery mismatch and a content mismatch, and the signature outcomes already have codes, axis entries, and matrix tests.
- **Verifying the delivery record in the SDKs or in `podium sync`.** Two more implementations of the serialization is the §2.2 drift problem in two languages with no shared library. Server-source `podium sync` could reuse the Go composer, and it is left out so the exemption stays one rule for every consumer outside the MCP server; SPEC-1's consumer paragraph states it in the spec. `podium sync` runs no signature or delivery check. The `defaults.verify_signatures` key in `sync.yaml` is an input to the MCP server's §4.7.9 policy (`cmd/podium-mcp/cliconfig.go:170-196`), and this proposal does not change how that policy is resolved.
- **Filtering `GET /v1/events` per subscriber identity.** `handleEvents` reads no identity and `PublishEvent` fans every payload, carrying an artifact's ID and layer, to every subscriber and webhook receiver in the tenant, so publishing a hidden parent discloses it with no `extends:` chain involved. It is a §4.7.2 defect on the event stream with its own design questions, and it is filed separately. SPEC-2's text is written so it stays true whether or not that is ever fixed.
- **An admin override on `/v1/dependents`.** There is none today, the `From` side has always been filtered without one, and adding one is a new capability with its own audit obligation.
- **Suppressing the `artifacts.dependents_of` audit emit on a filtered query.** `DependentsOf` emits the event with the queried ID before it evaluates visibility (`pkg/registry/core/dependents.go:27-31`), so a query against an artifact the caller cannot see still writes that ID into the tenant audit stream. The stream is read by a tenant admin, who is not the §4.6 adversary, and recording what was asked is the event's purpose.
- **Filtering the `DependencyInDegree` ranking signal per caller.** It is a per-request store scan on the search hot path for a weak statistical channel.
- **Closing the §4.7.9 sensitivity gate.** Under `medium-and-above` a registry that declares an artifact `low` is not verified, and reading the sensitivity out of the verified record does not change that, because a registry forging the record forges its `sensitivity:` too. Only `always` resists a hostile registry, and that is a policy question for the proposal that owns the defaults.
- **An author-signed envelope.** It needs its own field, its own trust-policy plumbing, and its own verification rules, including a `SigstoreKeyless.Verify` that inspects the signer's identity, which it does not today. Until such a field exists, SPEC-8's §4.7.9 edit records that a Sigstore-keyless or author-key signature stored alongside content is neither served nor verified on materialization. This build's ingest stores only registry-managed envelopes, so the statement removes no check that runs today.
- **Binding freshness, or detecting rollback within an artifact ID.** OQ-2 records both.

# Proposal 0027: Attest the served record and close the hidden-parent disclosures

- Issue: (to be filed)
- Status: Approved (2026-09-24). Verified 2026-09-23 after 16 adversarial review rounds (43 findings fixed). OQ-2 and OQ-5 resolved by the owner; the response field was renamed to extends_pin after verification.
- Date: 2026-09-15

This document stages the proposed spec, code, test, and documentation changes. It does not modify any spec, code, or doc file. Apply the changes in the staged sections after sign-off.

## Summary

**What changes.**

- A new §4.7.10 delivery attestation: the registry computes a framed digest over the record it serves (the identity, the merged frontmatter, the body, `SKILL.md`, and each bundled resource's path and content hash), signs it with the registry-managed key it already holds for ingest signing, and returns `delivery_hash` and `delivery_signature` on both `load_artifact` and `POST /v1/artifacts:batchLoad`. Nothing attests the merged bytes today, and the batch path carries no integrity value of any kind.
- The `load_artifact` response stops carrying `raw_frontmatter`, `manifest_merged`, and `signature`, and the merged-manifest exclusion from the presigned manifest-body channel goes with them. Each of the three is a §4.6 disclosure or an oracle for one, and each exists only to support a recomputation the delivery attestation replaces.
- The response gains `extends_pin`, the pinned `<id>@<version>` the child resolved at ingest, present only when the calling identity can see the parent record. The §13.10 web UI reads that field and deletes the client-side concealment gate it runs today, which decides in the browser what the server has already disclosed. The `load_artifact` entity tag folds in the served `extends_pin`, so a conditional request cannot revalidate one identity's cached body for another (SPEC-5, CODE-3, CODE-5).
- Further disclosure paths close: `GET /v1/dependents` filters on the queried target and on the pinned parent record rather than on the source artifact alone, the search descriptor of a pinned child is held to the parent-ID test the load path applies over the child's whole pinned chain, and the cross-layer collision rejection stops naming the contributing layer to a caller who cannot read it. The chain-error disclosure on `load_artifact` and `artifacts:batchLoad` is already closed by proposal 0028's `admitChain`, whose every client error names only the requested artifact; this proposal changes no chain-error code and pins that behavior (CODE-6, TEST-6).
- §4.6's hidden-parents paragraph is replaced. Its sentence promises that a hidden parent's "existence and ID are not surfaced to the requester", and the existence half is not deliverable: the served bytes of a merged child do not reproduce the served `content_hash`, which is a one-request boolean test for a parent that survives every change staged here. The replacement splits the guarantee into what is withheld, what the merge serves by design, and what is observable.
- §4.7.3 gains a visibility paragraph. Reverse-index edge queries have been filtered per caller since the endpoint shipped and `spec/` says nothing about it, so the rule being narrowed has no section a test can cite. The paragraph also states that the search ranking signal counts dependents across the tenant.
- The registry countersigns only rows proposal 0028's stored-row admission admitted, on every path it countersigns. 0028 lands before this proposal, so when this proposal removes the consumer's §4.7.6 recomputation, admission is already the check that refuses a row whose stored bytes, stored content hash, or stored signature disagree.
- The MCP server recomputes the delivery hash on every load in place of the §4.7.6 content hash, ahead of the signature policy. It writes its §6.5 resolution entry only after verification, and it keeps the cached delivery record per artifact ID, so two IDs that share a content-hash bucket do not read each other's merged document (SPEC-4, CODE-10).
- With the presigned-body exclusion gone, an above-cutoff merged manifest takes `manifest_body_url`. The §13.12 `/objects` route authorizes the served merged document and stops authorizing a pinned child's unserved pre-merge document (SPEC-9, CODE-16), and server-source `podium sync`, `podium artifact show`, and both SDKs follow the URL (CODE-14, CODE-15, CODE-18).
- The MCP server's §7.6.2 prefetch warm-up is removed, and §7.6.2's sentence describing it is replaced with a rule that the MCP server does not call the endpoint (OQ-8). The consumer cannot verify the batch envelope, so a prefetched entry could only be an unverified cache write or no write at all.
- Proposal 0028's consumer policy, which lands first and governs the served `signature`, is retargeted onto `delivery_signature` in the commit that removes the served field (CODE-19).

**Fixed decisions.**

- The countersignature is minted at serve time, on every response, for every artifact, whether or not it declares `extends:`. It is never stored and never backfilled (Decisions).
- The delivery digest is domain-separated from the §4.7.6 content hash by a framed leading tag and frames each bundled resource's content hash rather than its body (SPEC-1, CODE-1).
- `content_hash` stays on the wire with its §4.7.6 meaning, as the §6.5 cache key, the §7.5.3 lock value, and the `@sha256:` pin target. The MCP server verifies the delivery record in place of recomputing it (SPEC-4, CODE-10).
- The order on this branch is 0026, then proposal 0028, then this proposal, and all three ship in one release (OQ-1).
- The registry composes a delivery record only from rows proposal 0028's stored-row admission admitted (0028's SPEC-10 and CODE-14). This proposal stages no admission check of its own.
- Only the MCP server verifies the delivery record, on the `load_artifact` path. Server-source `podium sync`, the language SDKs, and a §6.4 workspace overlay load verify nothing (SPEC-1).
- The delivery signer is the registry-managed key, whatever key model signed the artifact at ingest and whatever `SignatureProvider` a deployment configures (SPEC-1, SPEC-8).
- `podium verify <artifact>` verifies the delivery pair (CODE-13).
- Every inline-only reader follows `manifest_body_url` (CODE-14, CODE-15), the `/objects` route serves the merged document the URL names (CODE-16), and every follower, the SDKs' included, sends the caller's token to a URL that is not SigV4 presigned (CODE-15, CODE-18).
- The delivery-hash recomputation runs unconditionally on every load, independent of `PODIUM_VERIFY_SIGNATURES` and of `sensitivity`, and fails closed. It runs before the signature policy inside `verifyServedArtifact`, which reverses the signature-first order proposal 0028's CODE-3 set there (CODE-10, TEST-10). The signature half is governed by the policy proposal 0028 lands first: the registry signs by default and the consumer requires a signature by default (OQ-3).
- `pkg/sign.Provider` is not widened (Decisions).
- An above-cutoff merged manifest is served through the manifest-body channel, and the design accepts that channel's object-store dependency rather than keep the structural oracle the `res.Merged` guard carries (Decisions, CODE-3).
- A search descriptor that fails the parent-ID test is served without its frontmatter block rather than dropped (OQ-4, CODE-8).
- The delivery record carries no timestamp and no nonce, so a captured record replays, and freshness is left out (OQ-2).
- The stored ingest signature stays, and the served `signature` field goes (Decisions, CODE-3).
- A failed delivery verification reuses `materialize.content_hash_mismatch` and amends its existing §6.9 row in place (SPEC-4b). A missing or invalid signature keeps the code the consumer serves today. No §6.10 code is minted.
- Proposal 0028 owns the order in `deliverLoadArtifact`, the local-sink read event's place below the §6.6 step-2 verification, the `materialize.signature_missing` code, and the verification on the §5.0 `resources/read` mirror, all through its `verifyServedArtifact`. This proposal replaces what that method verifies, reorders its two checks, and retargets 0028's policy onto the delivery pair (CODE-10, CODE-19). The mirror already follows `manifest_body_url` through that method, so it inherits the delivery verification and gains no code of its own.
- An invisible `/v1/dependents` target answers `200 {"edges":[]}`, byte-identical to a target that does not exist and to one nothing depends on (SPEC-3, Decisions).
- §4.6's existence guarantee is narrowed rather than restored, and the spec text says so (SPEC-2).

**Watch out for.**

- **Dropping `raw_frontmatter` alone blanks a shipped surface.** `declaredExtends` (`web/ui/src/surfaces/ArtifactViewer.tsx`) falls back to the served `frontmatter`, which the registry has already stripped for every requester, so the outbound extends rail reads "This artifact extends nothing" for every artifact including one whose parent the reader can see. CODE-5 and CODE-11 land together or a privacy fix ships as a feature regression.
- **`manifest_merged` and the presigned-body exclusion are the same oracle read two ways.** `omitempty` makes the flag's presence exactly the predicate "this artifact extends something", and `attachManifestBody` returns early on `res.Merged` (`pkg/registry/server/server.go`), so an above-cutoff merged manifest is served inline where an unmerged one is served by URL. Deleting the field and leaving the guard keeps the oracle in the response structure.
- **An ID-keyed `/v1/dependents` filter passes the case it is written for.** The §4.6 same-ID overlay makes a child extend its own canonical ID in a lower-precedence layer, so `edgesFor` records `{From: "team/overlay", To: "team/overlay"}` (`pkg/registry/ingest/ingest.go`). Both endpoints are "visible" by ID while the record the pin names is not, and the self-edge discloses that a layer the caller cannot read contributes that ID.
- **The delivery stream must not depend on the requesting identity.** `extends_pin` is served per caller and is therefore excluded from the stream. A per-requester digest cannot be compared across consumers and cannot be precomputed, and the single-load and batch paths would stop agreeing.
- **The per-caller `extends_pin` field breaks the content-hash ETag.** `handleLoadArtifact` answers a matching `If-None-Match` with 304 under a strong ETag equal to the content hash (`pkg/registry/server/server.go`), so a cache holding one identity's body, with its `extends_pin`, would be revalidated for an identity that cannot see the parent. CODE-3's `loadArtifactETag` folds the served `extends_pin` into the validator through `validatorFor`, which both the `Revalidate` predicate and the ETag branch read. A HEAD and a matching conditional GET are answered from `revalidationResult`, which `core.LoadArtifact` returns before `assembleResult` runs (`pkg/registry/core/core.go`), so CODE-5 sets the visibility-gated `ExtendsPin` on that result too. Setting it only in `assembleResult` leaves every HEAD and every 304 on the bare content-hash ETag.
- **Do not reuse `version.CanonicalContentHash` over the merged bytes.** Two digests with one definition, one hex encoding, one SPI, and one key means a signature over either is syntactically a signature over the other. It would also take `map[string][]byte`, which forces every large resource out of object storage on every load.
- **An ingest-stored countersignature depends on yaml.v3 and on struct field order.** `manifest.SerializeMerged` marshals a `manifest.Artifact` through `gopkg.in/yaml.v3` and splices the authored keys back, so its byte output is a function of the struct's field declaration order and of the serializer's quoting and wrapping. Adding a field to `Artifact` would invalidate every stored countersignature at once and require a re-sign migration on a release that intended no behavior change.
- **`test/e2e` skips parts of itself on macOS.** `test/e2e/artifact_extends_test.go` carries unconditional skips of its own, and the `oidc-jwt` arms skip on darwin. This proposal's central behavior is a visibility-boundary behavior, so a green local `go test ./test/e2e/...` is not evidence. Grep the run output for `SKIP`, and prefer `trusted-headers` for the new visibility arms.
- **Removing the consumer's §4.7.6 recomputation leaves the registry's admission as the only stored-row gate.** The registry frames whatever `content_hash` a row stores, so a row proposal 0028's admission did not refuse would verify at the consumer once `verifyContentHash` is gone. 0028 lands first, so admission is in place in every commit this proposal makes. A change here that composed a delivery record on a path that does not pass through `assembleResult` would countersign an unadmitted row.
- **The wire break and every reader of the removed fields land in one commit.** `raw_frontmatter`, `manifest_merged`, and `signature` have readers in `cmd/podium-mcp`, `cmd/podium`, `pkg/sync`, and `web/ui`, and the `res.Merged` guard's removal reaches every reader that decodes only the inline manifest fields, the SDK followers that fetch the URL without the caller's token, and the `/objects` route that serves the URL, so S7 carries CODE-10, CODE-11, CODE-13, CODE-14, CODE-15, CODE-16, CODE-18, and CODE-19 beside the server change, and the test rewrites with them.
- **The served `manifest_body` is covered only by the delivery record.** The consumer returns `resp.ManifestBody` to the agent (`cmd/podium-mcp/main.go`) and in the `resources/read` text (`cmd/podium-mcp/resources.go`), and `verifyContentHash` never hashed it. `verifyDeliveryHash` frames `resp.ManifestBody` itself, live and from the per-ID `body` file on a cache-served load, and never a body re-derived from the frontmatter. TEST-10's forged-body arms and TEST-11's per-ID `body` arm pin it.
- **The resolution index is a cache.** `cmd/podium-mcp` writes `(id, version) → content_hash` to its bbolt `index.db` before `deliverLoadArtifact` runs (`cmd/podium-mcp/main.go`), so leaving that write in place records an unverified response's values on disk. CODE-10 moves it behind the verification.
- **`web/bundle/` is committed build output.** `web/icons_test.go` fails with "rebuild web/ui and commit web/bundle", so the UI change is not complete without `npm run build` in `web/ui` and the rebuilt hashed assets committed.

## Current state and the gap

### Nothing attests the bytes an `extends:` child materializes

`assembleResult` (`pkg/registry/core/core.go`) returns, for a child declaring `extends:`, a `Frontmatter` that is `mergeChain`'s re-serialization with the parent stripped, a `ContentHash` that is the child's stored digest over its pre-merge `ARTIFACT.md`, and a `Signature` that is the child's stored envelope over that digest. The signed value therefore covers bytes the consumer never materializes, and the bytes that reach `adapter.Materialize` and then disk are covered by nothing. `verifyContentHash` (`cmd/podium-mcp/main.go`) hashes `RawFrontmatter` for exactly this reason, which checks the pre-merge document and leaves the merged document unchecked.

The batch path is worse. `BatchLoadEnvelope` (`pkg/registry/server/batch_load.go`) carries a merged `Frontmatter`, a pre-merge `ContentHash`, no pre-merge companion, and no signature, so an SDK consumer has never had an integrity gate on any artifact.

### The §4.6 guarantee is contradicted on several read surfaces

§4.6's hidden-parents paragraph (`spec/04-artifact-model.md`) states that a hidden parent's existence and ID are not surfaced to the requester. On the read path:

- `raw_frontmatter` carries the authored `extends: <parent>` line to every requester (`pkg/registry/core/core.go`, `pkg/registry/server/server.go`), and the consumer writes it to a side file on its own disk (`putExtras`, `cmd/podium-mcp/main.go`) and reads it back on a cache-served load (`cmd/podium-mcp/resolution_cache.go`).
- `manifest_merged` is an unconditional existence flag (`pkg/registry/server/server.go`), with a structural twin in `attachManifestBody`'s `res.Merged` early return.
- `GET /v1/dependents` filters `visibleIDs[e.From]` only (`pkg/registry/core/dependents.go`), so one GET against a guessed ID confirms the artifact exists and names its children. The web UI calls it.
- The chain errors no longer interpolate the parent. Before proposal 0028, `assembleResult` walked the chain through `resolveExtendsChain`, whose `"%w: parent %s: %v"` and `"%w: extends cycle at %s"` errors (`pkg/registry/core/core.go`) reached the client through `writeCoreError`. 0028's `assembleResult` walks through `admitChain` instead, which logs the failing member and returns `fmt.Errorf("%w: %s", sentinelOf(err), requestedID)` (`pkg/registry/core/admit.go`), and `revalidationRedactKeys`, the one remaining caller of `resolveExtendsChain` on the load path, scrubs its error the same way. No `load_artifact` or `artifacts:batchLoad` error names an ancestor today, and TEST-6 pins that.
- The search-descriptor strip removes the `extends:` key (`pkg/registry/core/core.go`), and `FrontmatterHidingParent` applies no parent-ID test (`pkg/manifest/merge_serialize.go`), whereas the load path refuses a merged block that names a chain parent in any key. When a pinned child's block also names its parent in another key, such as a `delegates_to` entry or an extension key, the descriptor serves that key. The pin itself is always present. `extends_pin` has been in both SQL stores' `CREATE TABLE` since v0.1.0, every released ingest sets it or rejects the child (`pkg/registry/ingest/ingest.go`), and `podium admin migrate-to-standard` copies each record unchanged (`cmd/podium/admin_migrate.go`). The `additiveColumns` entry (`pkg/store/schema_migrate.go`) makes a schema apply idempotent, and the only store created without the column was a SQLite file from a pre-release build, so no released build wrote an `extends:` row with an empty pin.
- The web UI receives the parent ID in the browser and decides client-side whether to draw it (`web/ui/src/surfaces/ArtifactViewer.tsx`). The concealment rule is correct and it is on the wrong side of the boundary.
- A cross-layer collision rejection names the contributing layer (`pkg/registry/ingest/ingest.go`) in a response body a non-admin layer owner can reach through `POST /v1/layers/reingest`.

### The existence half cannot be delivered

For an artifact with no parent, the consumer recomputes §4.7.6 from the served bytes and reproduces the served `content_hash`. For a merged child it cannot, because the stored digest is over pre-merge bytes. A requester who recomputes the digest and compares it learns that a parent exists. That signal survives dropping `raw_frontmatter` and `manifest_merged`, and the only closures are to withhold `content_hash` for merged artifacts, which moves the oracle to `/v1/sync/manifest` and breaks `@sha256:` pins, or to hash the merged bytes at ingest, which reverses proposal 0026's §4.7.6 rule one proposal after it lands.

## Decisions

- **Attest the served record rather than re-basing the stored one.** The defect is that the delivered bytes carry no attestation, which a second digest over the delivery closes without touching the identity every other subsystem is keyed on.
- **Mint at serve time.** The merged record is a pure function of stored state, so an ingest-time countersignature is possible and is still wrong. Its byte basis is `manifest.SerializeMerged`'s yaml.v3 output, which is a function of the `manifest.Artifact` struct's field declaration order and of the serializer's quoting and wrapping, so an unrelated struct edit would invalidate every stored countersignature and require a re-sign migration. It would also need a backfill on day one, a column on both store backends, and a rule for the §4.7.4 lifecycle fields that change after ingest. Serve-time minting has none of those and re-mints under the current key after a rotation. Its cost is a SHA-256 over the delivery record and an Ed25519 signature per load. Proposal 0028's stored-row admission, which runs before the record is composed, adds its own cost, which 0028 states. CODE-3's removal of the `res.Merged` guard adds an object-store dependency: every served manifest document above the inline cutoff, including a merged one that was served inline before, costs a `Stat` on every load and a consumer fetch, and fails during an object-store outage. The design accepts that, because keeping merged manifests inline keeps the structural oracle the guard's removal closes (Summary, "Watch out for"). Removing the `res.Merged` guard makes an above-cutoff merged manifest depend on object storage; the outage outcomes are in the edge-case table.
- **Domain-separate the digest.** Proposal 0026 declined a tag for §4.7.6 because that digest had no sibling. It has one now, and two digests with one definition under one key is a cross-protocol confusion by construction.
- **Frame resource content hashes rather than bodies.** Each resource already carries an authoritative `sha256:` digest in `store.ResourceRef.ContentHash`, in memory when the response is assembled, and the consumer already checks fetched bytes against it. Framing bodies would download every above-cutoff resource from object storage on every load.
- **Keep the SPI unchanged.** `pkg/audit/anchor.go` signs an audit chain head that has no delivery record, and `internal/serverboot/serverboot.go` takes `ingest.SignerFunc` from `signProvider.Sign` as a method value. Widening `Provider.Sign` breaks both for no gain, since the delivery hash is already the `alg:hex` string the providers accept.
- **Drop the served `signature`.** For a merged child it attests a digest the consumer can no longer reproduce, which is the inert-field pattern this repository already carries in `ExternalResource.Signature` (`pkg/manifest/types.go`). For every other artifact it attests a value the delivery stream frames, under the same key, from the same party. Keeping both would invite a consumer to verify whichever is present, which reintroduces the merged-versus-unmerged behavioral difference the uniformity invariant exists to remove. A future author-signed envelope needs its own field, its own trust policy, and its own verification rules, so reserving this one for it reserves the wrong field. The field has one reader outside the consumer, `podium verify <artifact>` (`cmd/podium/sign.go`), and it moves to the delivery pair (CODE-13) rather than gaining a separate surface that serves the stored envelope. The pair the consumer verifies is the pair an ad-hoc check should verify, and a second surface serving the stored envelope would restore the field this decision removes.
- **Move the concealment rule to the server and keep the feature.** Serving a visibility-gated `extends_pin` is the same rule the browser runs today, evaluated where the data lives. Accepting the chip's loss would delete a shipped §13.10 surface for readers entitled to it, in the name of a leak the server closes anyway.
- **Answer an invisible `/v1/dependents` target exactly as a nonexistent one.** A nonexistent target and a target with no dependents already answer identically; a third answer for "invisible" would be the oracle.
- **Do not make the merged case verify differently from the unmerged case.** A rule that refuses the `noop` provider, or requires `PODIUM_SIGNATURE_VERIFY_KEY`, only for a merged response is itself an existence oracle: the caller learns from the refusal what the response no longer tells them. The unconditional recomputation applies to every response identically, and the signature policy stays the one §4.7.9 defines.
- **Narrow the §4.6 promise rather than leaving it false.** Welding existence to ID in one sentence made every closable leak read as a total failure of both, and it is what let the shipped documentation repeat a claim no build has ever satisfied.
- **Countersign only admitted rows, and leave admission to 0028.** A serve-time countersignature attests whatever the registry serves, so a row altered in the metadata store would otherwise reach every consumer with a valid signature, where today a consumer under `always` holding the registry's key refuses it. Proposal 0028's stored-row admission, which lands first, recomputes each served row's hash over its stored bytes, object-held bodies included, verifies its stored signature on a signing registry, admits every row of an `extends:` chain, and serves the body, type, and sensitivity from the admitted bytes. The delivery record is composed from the rows admission returns, so it frames only admitted values, and this proposal adds no second check.
- **Remove the §7.6.2 prefetch warm-up rather than make it verify.** The batch envelope carries no `sensitivity` and no bytes for a resource held in object storage (`pkg/registry/server/batch_load.go`), so the consumer cannot rebuild the delivery record from it. A verifying prefetch would fetch each presigned resource, decode inline ones, recompute, run the §4.7.9 policy, and write the resolution entry, which is `deliverLoadArtifact`'s pipeline a second time over a second resource type. Kept as a no-op, it would still POST every configured ID at each bridge start under a 30-second timeout per batch (`cmd/podium-mcp/main.go`), and the registry would record an `artifact.loaded` event per ID (`pkg/registry/core/core.go`) for loads no agent made. No page under `docs/` documents `PODIUM_PREFETCH` or the `prefetch` key. After the removal, every write to the §6.5 content cache and resolution index happens in `deliverLoadArtifact` after verification. §7.6.2 then states that the MCP server does not call the endpoint, and a test pins that it does not (OQ-8), so a warm-up cannot return unverified.

## Spec amendment: §4.7.10 delivery attestation

**SPEC-1.** Anchor: `spec/04-artifact-model.md`, a new `### 4.7.10 Delivery Attestation` appended after §4.7.9, which ends with the signing subsection's last paragraph. SPEC-1 edits no existing subsection; SPEC-8 edits §4.7.9 separately.

> ### 4.7.10 Delivery Attestation
>
> The `content_hash` (§4.7.6) names the stored artifact. For a child declaring `extends:` the registry serves a merged re-serialization (§4.6) whose bytes do not reproduce that digest, so the record a consumer materializes is not the record the content hash names. The delivery attestation binds the served record instead.
>
> The **delivery record** is the artifact identity, type, and resolved version the response carries; the `content_hash` of the stored artifact the registry composed the response from; the served `sensitivity`; the served `ARTIFACT.md` document, which for a child declaring `extends:` is the merged document (§4.6), for every type including a skill; the served manifest body; the served `SKILL.md`, which for a skill is the child's own; and, for each bundled resource, its path and its content hash. Its canonical serialization uses the §4.7.6 framing: the framed ASCII tag `podium/delivery-record/1`, then the framed identity, version, type, content hash, and sensitivity in that order, then the framed `ARTIFACT.md` document, manifest body, and `SKILL.md`, then, for each bundled resource in ascending byte-wise order of its UTF-8 path, the framed path followed by the framed resource content hash. An absent `SKILL.md` frames a zero-length value. The `delivery_hash` is the SHA-256 digest of that serialization, served as `sha256:<hex>`.
>
> The serialization carries a resource's content hash rather than its body, so composing the delivery hash reads nothing from object storage, and a consumer checks each resource body it fetches or decodes against a content hash the verified record carries. The lifecycle fields (§4.7.4), the contributing layer, and the per-caller `extends_pin` reference are excluded: the first change after ingest, and the last is served per requesting identity, so including either would make the digest depend on when or by whom the record was read.
>
> The registry computes the delivery hash per response and signs it with its registry-managed key (§4.7.9), serving the envelope as `delivery_signature`. The registry-managed key is the delivery signer whatever key model signed the artifact at ingest and whatever `SignatureProvider` (§9.1) the deployment configures. It does so for every `load_artifact` response and every batch entry, whether or not the artifact declares `extends:`. The uniformity is required: an attestation served only for a merged record would make its presence a disclosure of the merge, which §4.6 forbids. A registry that holds no registry-managed key serves `delivery_hash` with an empty `delivery_signature`, including a registry whose artifacts carry Sigstore-keyless or author-key signatures. Because the envelope is minted per response under the registry's current key, a rotation of that key takes effect on the next response: a consumer verifies against the rotated public key from then on, and a delivery signature it cached before the rotation does not verify under the new key.
>
> Sigstore-keyless and every other network-backed provider do not sign delivery records, because a per-response certificate request and transparency-log entry would put a network round trip inside every load. A consumer verifies `delivery_signature` with the registry-managed verifier against the registry's public key. The envelope carries no certificate chain, so a consumer whose verifier is Sigstore-keyless refuses a present delivery signature with `materialize.signature_invalid` whenever its §4.7.9 policy verifies the signature.
>
> On a `load_artifact` call the MCP server recomputes the delivery hash from the bytes it received and compares it to the served value before it reads any policy input out of the record, caches it, or writes any byte to disk (§6.6). A response that carries no `delivery_hash` fails the comparison. The MCP server then applies the §4.7.9 verification policy to `(delivery_hash, delivery_signature)`. Server-source `podium sync` (§7.5) and the language SDKs (§7.6.2) receive the delivery fields and neither recompute nor verify them, so they materialize the served record without a delivery check. A §6.4 workspace overlay load is served from the consumer's own filesystem, carries no delivery record, and is outside the comparison. A filesystem-source `podium sync` composes and materializes in one process, so it has no delivery to attest and computes no delivery hash. The materialized output is identical across these consumers and modes (§2.2); they differ in the attestation channel.
>
> The attestation states that the registry composed and served these bytes. It does not state that the merge is faithful. A consumer that cannot see a hidden parent cannot obtain it and therefore cannot check that the served manifest is the §4.6 fold of the child and its pinned ancestors, so a registry that folds the wrong parent, folds a parent the child never named, or fabricates the merged document produces a delivery record that verifies. Between the registry's response and the consumer's disk, the attestation binds the record against every party other than the one holding the registry's signing key. It carries no timestamp and no nonce, so a record captured from an earlier response verifies when it is replayed. It binds what the registry served, and the §13.4 stored-row admission check decides which stored rows the registry may compose a record from.

§4.7.10 is a new behavioral section and needs a citing test for `speccov-drift`; TEST-1 and TEST-3 carry the citation.

A digest mismatch is not a `serverUnreachableError`, so the §7.4 offline-first no-op does not absorb it; a transport failure of the fetch is wrapped as one by `fetchBytes` (`pkg/sync/server.go`) and takes the existing unreachable handling. Server-source sync runs no §6.6 verification, which SPEC-1's consumer paragraph states, so this change adds a fetch and a digest check on the fetched document and no delivery verification.

**CODE-15 · `cmd/podium/main.go`, `cmd/podium/read_cli_json.go`.** `podium artifact show` reads `/v1/load_artifact`, decodes only the inline manifest fields, and never follows `manifest_body_url`. `podium artifact show` (`artifactShow`, `cmd/podium/main.go`) passes the raw body from its `mustGetJSON` call to `printArtifactHuman` and, under `--json`, to `emitArtifactShowJSON`, which decode only `frontmatter` and `manifest_body`. `attachManifestBody` clears those fields for a manifest above the cutoff, so the command already prints an empty document for a large unmerged manifest, and CODE-3's removal of the `res.Merged` guard extends that to a large merged one. A fetch or digest failure exits 1 with `artifact show <id>: manifest body: <error>` on stderr and prints nothing to stdout. **IMPLEMENTOR'S CHOICE:** whether the CLI's split and the sync path's split (CODE-14) share one helper with `fetchManifestBody`, and whether the CLI's credential test calls a single exported copy of `presignedSigV4` that replaces the two unexported ones or carries its own, subject to the constraints that every reader derives `manifest_body` from the fetched document with `manifest.ParseArtifact` or `manifest.ParseSkill`, so each yields the body the inline path serves, and that the CLI's credential test returns the same answer as `presignedSigV4` for every URL, which TEST-21's SigV4 arm asserts.

**CODE-16 · `pkg/registry/core/core.go`, `ResolveResourceOwner`.** On the filesystem object-store backend the `manifest_body_url` points at the registry's `/objects/{key}` route, which serves a key only when `ResolveResourceOwner` finds a visible owner (`pkg/registry/server/server.go`), and otherwise answers `404 registry.not_found` "no such object". The function authorizes a manifest-body key only when it equals `ManifestBodyKey(CanonicalManifestDoc(...))` of a visible **stored** record. For a merged child of a type other than skill, `attachManifestBody` uploads the document `mergeChain` re-serialized (`pkg/registry/server/server.go`, `core.go`), whose hash matches no stored record, so after CODE-3 every fetch of it would fail with `materialize.fetch_failed`. The stored-document pass is also too wide under SPEC-9. It authorizes the stored document of every visible record, including a pinned child of a type other than skill, whose stored document is the pre-merge `ARTIFACT.md` carrying `extends: <parent>`. That document is not served, so `attachManifestBody` did not upload it, and after CODE-3 it uploads only the served document, and the route answers such a key `404 registry.not_found "object not found"` from `writeObjectStoreError` where an unowned key gets "no such object". The difference is a guess oracle: a caller who reconstructs the child's authored `ARTIFACT.md` with a candidate `extends:` line learns from the message whether the guess hashes to the stored document, which confirms the hidden parent's ID. The stored-document pass therefore tests the key first and, on a match, skips the record when its type is not skill and its `ExtendsPin` is non-empty; the key then reaches no owner and answers "no such object". The skip lands with the rest of CODE-16 in S7. A skill's stored `SKILL.md` stays owned whatever its pin, because it is the document a pinned skill serves. `ResolveResourceOwner` gains a third pass, run only when the resource pass and the stored-document pass find no owner: for each visible record with a non-empty `ExtendsPin` and a type other than skill, it walks the record's chain with `resolveExtendsChain` and folds it with `mergeChain`, the unadmitted walk and the merge `revalidationRedactKeys` and `assembleResult` use (`pkg/registry/core/admit.go`, `core.go`), and authorizes the key when the merged record's `CanonicalManifestDoc` exceeds `objectstore.InlineCutoff` and its `ManifestBodyKey` equals the key. The pass does not call `assembleResult`, because `assembleResult` begins with proposal 0028's `admitChain`, which reads every object-held body in the chain and verifies stored signatures, and §13.4 states that the §13.12 object route serves no admitted content and is served without admission (`spec/13-deployment.md`). Admission serves a record's frontmatter from the stored bytes it admitted, so for a row admission passes, the unadmitted merge yields the document `attachManifestBody` uploaded; for a row it refuses, the pass authorizes only the document the stored rows fold to, which the route serves only when an earlier load uploaded it, and only to a caller who can see the child that served it. A merged skill needs no third pass, because its served document is the child's own stored `SKILL.md`, which the second pass already covers. A walk or merge error for a record (a missing or soft-deleted ancestor, a cycle, or a store error) skips that record and authorizes nothing, so every failure answers the same 404 as a key that does not exist, and the handler and its status codes do not change. The pass reads only the metadata store (the visible manifest records and each chain member through `GetManifest`), reads no object storage, verifies no signature, and writes nothing, so it holds no per-process state, behaves identically on every node and in every deployment mode, and answers the same during an object-store outage. Its cost is one `GetManifest` per ancestor and one merge per visible `extends:` record, paid only on an `/objects` request whose key the first two passes miss. SPEC-9 states the rule, and TEST-20 pins it. The S3 backend's presigned URLs do not reach this route and are unaffected.

## Non-goals

- **Replay protection for the delivery record in this release.** OQ-2 records why. A follow-up adds a monotonic check to the MCP server: it refuses a latest-version resolution older than one it has already resolved for the same artifact, which needs no clock and no protocol change.

- **A Merkle tree over the artifact's parts with the parent's leaf redacted.** It collapses on the requirement it was built for. Hiding the parent's *existence* forces a uniformly-blinded slot that is never opened for any requester, so no sibling path is ever transmitted and the tree degenerates to a flat digest plus one blinded component, which is what SPEC-1 stages without the structure. It is recorded here so it is not re-derived.
- **Computing and storing the merged record at ingest as a separate artifact.** It collides on the `(tenant_id, artifact_id, version)` primary key, it makes re-ingest depend on yaml.v3's serialization staying byte-stable so an unrelated serializer or struct change bricks it, and it breaks §8.4 retention, which has no concept of a derived row to purge alongside its source. It is recorded here so it is not re-derived.
- **Re-basing the §4.7.6 content hash onto the merged bytes.** It would close the existence oracle, and it reverses proposal 0026's rule one proposal after it lands, costs a second migration on a hash 0026 moves, and leaves an author unable to compute their own artifact's hash from their own source in server mode.
- **Widening `pkg/sign.Provider`, or admitting a network-backed signer on the read path.** The SPI takes the delivery hash unchanged, and a Sigstore-keyless signature per response would be a Fulcio request and a Rekor upload inside every load.
- **Storing the countersignature, adding a store column, or backfilling one.** Serve-time minting covers every stored artifact from the moment the binary restarts.
- **Minting a §6.10 error code.** The consumer's remedy is identical for a delivery mismatch and a content mismatch, and the signature outcomes already have codes, axis entries, and matrix tests.
- **Verifying the delivery record in the SDKs or in `podium sync`.** Two more implementations of the serialization is the §2.2 drift problem in two languages with no shared library. Server-source `podium sync` could reuse the Go composer, and it is left out so the exemption stays one rule for every consumer outside the MCP server; SPEC-1's consumer paragraph states it in the spec. `podium sync` runs no signature or delivery check. The `defaults.verify_signatures` key in `sync.yaml` is an input to the MCP server's §4.7.9 policy (`cmd/podium-mcp/cliconfig.go`), and this proposal does not change how that policy is resolved.
- **Filtering `GET /v1/events` per subscriber identity.** `handleEvents` reads no identity and `PublishEvent` fans every payload, carrying an artifact's ID and layer, to every subscriber and webhook receiver in the tenant, so publishing a hidden parent discloses it with no `extends:` chain involved. It is a §4.7.2 defect on the event stream with its own design questions, and it is filed separately. SPEC-2's text is written so it stays true whether or not that is ever fixed.
- **An admin override on `/v1/dependents`.** There is none today, the `From` side has always been filtered without one, and adding one is a new capability with its own audit obligation.
- **Suppressing the `artifacts.dependents_of` audit emit on a filtered query.** `DependentsOf` emits the event with the queried ID before it evaluates visibility (`pkg/registry/core/dependents.go`), so a query against an artifact the caller cannot see still writes that ID into the tenant audit stream. The stream is read by a tenant admin, who is not the §4.6 adversary, and recording what was asked is the event's purpose.
- **Filtering the `DependencyInDegree` ranking signal per caller.** It is a per-request store scan on the search hot path for a weak statistical channel.
- **Reintroducing a §4.7.9 sensitivity gate.** Proposal 0028 deletes `medium-and-above`, so no policy value reads `sensitivity`. The delivery record frames the served sensitivity, and reading it out of the verified record would still let the registry, which signs that record, choose the gate.
- **An author-signed envelope.** It needs its own field, its own trust-policy plumbing, and its own verification rules, including a `SigstoreKeyless.Verify` that inspects the signer's identity, which it does not today. Until such a field exists, SPEC-8's §4.7.9 edit records that a Sigstore-keyless or author-key signature stored alongside content is neither served nor verified on materialization. This build's ingest stores only registry-managed envelopes, so the statement removes no check that runs today.
- **Binding freshness, or detecting rollback within an artifact ID.** OQ-2 records both.

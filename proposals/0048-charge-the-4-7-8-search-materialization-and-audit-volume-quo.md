# Proposal 0048: Charge the §4.7.8 search, materialization, and audit-volume quotas to the request's tenant under that tenant's limits

- Issue: (to be filed)
- Status: Applied to spec (2026-10-03). The proposal was approved on 2026-10-03, decided on the user's behalf under the overnight authorization. Redesigned so routing carries the tenant record on the request context (no second store read), with bucket charge and rebuild made atomic. Signed off as staged. OQ-2 (max_user_layers precedence) and OQ-3 (charging the §7.6.2 bulk load) are recorded as follow-ups outside this proposal.
- Date: 2026-10-03

This document stages the proposed spec, code, test, and documentation changes. It does not modify any spec, code, or doc file. Apply the changes in the staged sections after sign-off.

## Summary

**What changes.**

- §4.7.8 states which tenant a search, a load, and an audit event are charged to, and how a request that resolves to no tenant is charged. It defines the precedence between a tenant's own value and a deployment default: a positive tenant value is enforced, zero selects the deployment default, and a negative value exempts the tenant. §13.12 gains a `### Quotas` table for the three `PODIUM_QUOTA_*` variables the binary already reads (SPEC-1, SPEC-2).
- `pkg/registry/server` gains `EffectiveLimits`, which resolves a tenant's search QPS, materialization rate, and audit volume from its store record and the deployment defaults. Routing already reads the tenant record. `WithTenantRouter`'s resolve function now returns that record, and `routeTenant`, which proposal 0047 adds and every routing wrapper calls, puts its ID and its `Quota` on the request context through one helper, `contextWithRoutedTenant`. `QuotaLimiter` charges against that carried record with no store read. When a tenant's limit changes, its existing bucket is retuned in place to the new rate on the next charge and keeps its unspent tokens up to the new capacity. `AuditVolumeMeter` becomes a per-tenant counter whose `Allow` takes the limit (CODE-1, CODE-2).
- The search, search-domains, and load handlers charge `s.core.TenantFor(r.Context())`, in place of the literal `"default"`, under the tenant record routing carried on the context. `GET /v1/quota` reports the search QPS, materialization rate, and audit-volume limits the limiter enforces for the same request, and the `store.Quota` and `QuotaEnvelope` doc comments state that it does (CODE-2).
- `internal/serverboot`'s `tenantResolver` returns the tenant record it already reads. Serverboot passes all three deployment defaults to the limiter, describes them as deployment defaults in its `Config` field comments, records each audit event under the emitting request's tenant, installs the meter unconditionally, and gates reingest on the stored layer's tenant. On a multi-tenant registry the reingest runner reads that tenant's record once and refuses the write on any read error, under the D6 table (CODE-3). `Server.tenant` and `WithTenant`, whose only reader after proposal 0046 is the limiter, are removed (CODE-4). The `podium admin tenant` flag help states the new zero and negative rule (CODE-5).
- Tests cover the change at the unit, in-process integration, serverboot, and end-to-end levels. The end-to-end level runs a multi-tenant binary on the standard stack, including the per-tenant audit-volume gate, and a standalone binary for the single-tenant quota report (TEST-1 to TEST-4).
- The HTTP API reference, the CLI reference, the clustered deployment page, the error-code reference, and the `[Unreleased]` changelog entry follow (DOC-1, CL-1).

**Fixed decisions.**

- The bucket key and the audit meter's recording key are `core.Registry.TenantFor` of the request. The reingest gate keys on the stored layer's tenant, `lc.TenantID`. `Server.tenant` no longer feeds the limiter (D1, D8).
- Precedence for search QPS, materialization rate, and audit volume per day is fixed as follows. A positive tenant value wins. Zero selects the deployment default. A negative value disables the budget for that tenant. When the tenant value and the deployment default are both zero, the budget is not enforced (D2).
- The limiter reads no tenant record, and `handleQuota` computes the three rate limits from the carried record with no further read. Both resolve against the record routing read for the same request and carried on the context. A request without a carried record is charged at the `PODIUM_QUOTA_*` deployment defaults (D5, D11). `GET /v1/quota` keeps its existing `core.Quota` read of the tenant record, which supplies `tenant_id`, `max_user_layers`, and the `storage_bytes` usage (`pkg/registry/core/quota.go:26-40`). The reingest audit-volume gate is the only quota path to which this proposal adds a store read. On a multi-tenant registry it refuses the reingest with `500 registry.unavailable` on any read error, a missing record included, and SPEC-1 and DOC-1 add no sentence for that refusal (OD-1, OD-3). The D6 table is the single statement of every quota path's store reads and fault outcomes.
- Unrouted multi-tenant requests are charged to `podium:unrouted` at the deployment defaults and are never refused on that account. These requests carry no tenant record (D4, D5). An unknown org under `oidc-jwt` is rejected with `auth.tenant_unknown` before any charge, as today.
- Only `search_domains`, `search_artifacts`, and `load_artifact` are charged, which are today's charge sites. The §7.6.2 bulk load (`POST /v1/artifacts:batchLoad`) stays uncharged, and OQ-3 records whether it should be (D15).
- A changed resolved rate retunes the tenant's existing bucket to the new rate in the same locked step as the charge, keeping its unspent tokens up to the new capacity. A bucket is never replaced or removed. A resolved rate of zero or less allows the charge and leaves the bucket untouched (D7).
- The audit meter is installed unconditionally (D9).
- CI gains no `-race` lane. `TestQuotaLimiter_ConcurrentRateChangeBoundsAdmissions` asserts an admission bound that holds without `-race`, and verification runs it under `-race` by hand (OD-2).
- `GET /v1/quota` reports the enforced values for the three budgets, and it reports `storage_bytes` and `max_user_layers` as stored. `GET /v1/admin/tenants` is unchanged (D10).
- `max_user_layers` precedence is not changed (D3, OQ-2).
- This proposal is implemented after proposals 0046 and 0047, in that order, and its code, test, and documentation text is written against that tree. It removes `Server.tenant`, `WithTenant`, and the last `WithTenant` call, with no shim (D12). Its `docs/deployment/clustered.md` Quotas bullet replaces the one proposal 0047 DOC-1(e) wrote (D13).
- No new §6.10 code, environment variable, flag, meta-tool, SPI, or SDK change is added. The 429 envelopes and `quota.audit_volume_exceeded` are reused unchanged (D14).

- **Spec line numbers are anchors at the time of writing.** Locate each edit by its quoted current text.
- **SPEC-1 and SPEC-2 land in one commit.** The SPEC-2 rows depend on the amended zero rule in §4.7.8. Either edit alone leaves §4.7.8 and §13.12 contradicting each other.
- **The signature changes do not compile in parts.** `WithTenantRouter`, `tenantResolver`, `rateBucket.allow`, `AllowSearch`, `AllowMaterialize`, `NewAuditVolumeMeter`, `AuditVolumeMeter.Allow`, `auditVolumeEmitter`, and `buildReingestRunner` all change. `NewQuotaLimiter` keeps its `QuotaLimits` parameter, and `QuotaLimits` gains `AuditVolumePerDay`. CODE-1, CODE-2, and CODE-3 therefore land in one commit (step S2), together with the mechanical call-site updates of existing tests that CODE-1 and CODE-3 list.
- **The existing cross-tenant integration test passes despite the defect.** `test/integration/auth_cross_tenant_quota_test.go` builds one server and one limiter per org, so each limiter's private `"default"` bucket looks isolated. Do not count it as the regression pin. TEST-2 and TEST-4 are the pins.
- **Do not read the tenant record in the limiter or in `handleQuota`'s limit computation.** Routing has already read it for this request (`internal/serverboot/orgid.go:29-36`). A second read adds a store transaction to every search and load (on Postgres, `pkg/store/postgres.go:517-528`) and reintroduces a fault path between two reads of one record. A single-tenant registry installs no router, so its requests carry no record and its limits come only from the `PODIUM_QUOTA_*` variables.
- **`envInt` and `envInt64` clamp a negative or non-integer value to the default of 0** (`internal/serverboot/serverboot.go:267-277`, `:317-327`). A deployment default is therefore never negative, and only a tenant record can carry the negative exemption.
- **This proposal depends on proposals 0046 and 0047.** Implement 0046, then 0047, then this proposal. After 0046, the limiter calls in `handleSearchDomains`, `handleSearchArtifacts`, and `handleLoadArtifact` are the only readers of `s.tenant`, and `options_test.go:29` is the only `WithTenant` call, so CODE-4 deletes the field outright. 0047 adds `routeTenant`, which `withTenantRouting`, `TenantRouted`, and `TenantRoutedNoReject` all call, so CODE-2 makes `routeTenant` return `contextWithRoutedTenant(r.Context(), t)`. The helper sets the tenant ID and the quota together, so no routing site can set one without the other. 0047 also refuses an unrouted reingest with `403 auth.forbidden` before the runner and serves the inbound webhook only for an active provisioned tenant, so `lc.TenantID` at the reingest gate is always a provisioned tenant. 0046 and 0047 each add a `WithTenantRouter` stub that CODE-3 updates. Code line numbers in this proposal are anchors in the tree before 0046; locate each edit by the symbol it names. If either sibling has not been implemented, stop: CODE-2, CODE-3, CODE-4, DOC-1(c), CL-1, and TEST-4 case (f) do not apply as written.
- **Do not read the tenant record at the reingest gate on a single-tenant registry** (D6 table). A stale bootstrap record is therefore ignored (D11), and the existing runner tests, which pass a nil store with `&Config{}` (`internal/serverboot/audit_volume_enforce_test.go:19`, `:30`), stay nil-safe. The gate never sees `podium:unrouted`: proposal 0047's `requireTenant` refuses an unrouted reingest before the runner, and its webhook handler reads a layer only under an active provisioned tenant.
- **Do not replace, delete, or refill a bucket on a rate change.** `newBucket` starts full (`pkg/registry/server/rate_limit.go:31-45`), and a charge uses a bucket pointer after it releases `q.mu` (`:103-104`). A replaced bucket would orphan any charge still in flight against the old pointer, and a deleted bucket would come back full. The retune happens in place inside `rateBucket.allow`, so a `PATCH` that raises, lowers, zeroes, or alternates a tenant's rate grants no fresh burst and loses no charge (D7).
- **TEST-4 case (f) uses a per-run tenant and an owner-arm layer with a network source.** dave holds no admin grant, and a host-path source calls the admin gate (`pkg/registry/server/layer_capabilities.go:92-101`). The per-run tenant keeps the case off the shared bootstrap tenant's quota, and the bootstrap tenant's unenforced deployment default makes a gate keyed on the boot tenant admit step 6 (D8).
- **Parts of `test/e2e` skip silently on macOS, and TEST-4's multi-tenant file `quota_tenant_isolation_test.go` skips without Postgres and S3.** Grep the run output for `SKIP` before claiming end-to-end verification.

## Current state and the gap

### Search and materialization share one bucket

§4.7.8 defines quotas as "Per-org limits, admin-configurable" and the audit-volume limit as "a per-tenant daily cap". On a multi-tenant registry, the binary enforces all three rate-like budgets deployment-wide.

`handleSearchDomains`, `handleSearchArtifacts`, and `handleLoadArtifact` call `s.quota.AllowSearch(s.tenant)` and `s.quota.AllowMaterialize(s.tenant)` (`pkg/registry/server/server.go:818`, `:843`, `:1018`). `Server.tenant` is the literal `"default"` (`server.go:284`). Only `WithTenant` sets it (`server.go:271-272`), and no production code calls `WithTenant`: serverboot installs the limiter at `internal/serverboot/serverboot.go:1303` without it. The limiter already keys buckets by its argument (`pkg/registry/server/rate_limit.go:93-120`). Because every call passes `"default"`, acme and globex draw on one search bucket and one materialization bucket. `withTenantRouting` puts the routed tenant on the context (`server.go:470-473`), and the quota calls never read it.

### The limits are global, so the per-tenant record has no effect

`QuotaLimiter` holds one `searchQPS` and one `matRate` (`rate_limit.go:69-86`), and it short-circuits the whole limiter when either is zero (`:94`, `:110`). Serverboot builds them once from `PODIUM_QUOTA_SEARCH_QPS` and `PODIUM_QUOTA_MATERIALIZE_RATE` (`serverboot.go:1295-1303`, `:2351-2352`). The per-tenant `store.Quota.SearchQPS` and `MaterializeRate` (`pkg/store/store.go:84-96`) can be set through `POST` and `PATCH /v1/admin/tenants` (`pkg/registry/server/tenants.go:21-79`), and no enforcement path reads them. `GET /v1/quota` reports those record values as the tenant's limits (`pkg/registry/core/quota.go:26-31`, `pkg/registry/server/quota.go:20-26`). A tenant can therefore read `search_qps: 20` while the registry enforces the environment value. It can also read `0` while the environment value is enforced.

### Audit volume is deployment-wide

`auditVolumeEmitter` calls `meter.Record(tenant)` with the boot tenant it captured (`internal/serverboot/audit_emitter.go:63-65`, `serverboot.go:1606`). The reingest runner checks `auditMeter.Allow(tenantID)` with the same boot tenant (`internal/serverboot/reingest.go:40`). The limit is the global `PODIUM_QUOTA_AUDIT_VOLUME_PER_DAY` (`serverboot.go:1603`, `:2353`), and nothing reads `store.Quota.AuditVolumePerDay`. The emitter is installed only when that variable is positive (`serverboot.go:1605`). One tenant's read traffic can spend the daily budget and block every tenant's reingest. Proposal 0047 (Approved) leaves `reingest.go` untouched and documents this as a known divergence: its DOC-1(e) adds a sentence to the `docs/deployment/clustered.md` Quotas bullet, and its CL-1 `### Documentation` entry names the deployment-wide budget.

### Unrouted requests reach the quota checks

Four kinds of multi-tenant request carry no context tenant:

- an unauthenticated caller, including an `oidc-jwt` caller during a JWKS outage (§6.3.3);
- an authenticated caller with an empty `OrgID`;
- an unknown org under `trusted-headers` (`server.go:470-482`, `serverboot.go:1454`); and
- every request on a `PODIUM_MULTI_TENANT` registry that has no verifier, which installs no router (`serverboot.go:1450`) yet binds `podium:unrouted` (`serverboot.go:1106-1108`).

For these requests `core.Registry.TenantFor` returns `"podium:unrouted"` (`pkg/registry/core/core.go:217-222`, `internal/serverboot/orgid.go:16`). Today they charge the shared `"default"` bucket.

### The existing regression test cannot catch the defect

`test/integration/auth_cross_tenant_quota_test.go:70-74` and `:166-167` build two servers, each with its own limiter, so each limiter's private `"default"` bucket looks independent.

### Single-tenant registries

Single-tenant routing installs no router (`server.go:453-455`), so `TenantFor` returns the bound tenant, the UUIDv5 of the `"default"` org (`serverboot.go:887`, `:1106`; `internal/serverboot/orgid.go:64-71`). Its store record carries a zero `Quota`, because `bootstrapDefaultTenant` creates it with none, and a single-tenant registry rejects `/v1/admin/tenants`. The `PODIUM_QUOTA_*` environment variables are therefore the only limit source a single-tenant operator has. None of them appears in `spec/` or `docs/`.

### What is already per tenant

`GET /v1/quota` already resolves the routed tenant through `TenantFor` (`core/quota.go:27`, `:32`), and it reports `storage_bytes` as its only usage. The defect there is the mismatch between the limits it reports and the limits enforced. The storage-bytes quota has no production enforcement path, because `ingest.Request.StorageQuotaBytes` is never set (`pkg/registry/ingest/ingest.go:186-193`, `:626-637`). Proposal 0047 moves the user-layer cap from the `LayerEndpoint`'s bound tenant to the request's routed tenant. Neither is a shared-bucket defect at the call sites this proposal changes.

## Decisions

- **D1. Bucket key.** Every search and materialization charge keys on `s.core.TenantFor(r.Context())`, the same tenant the request's store reads use. The pattern already exists at `pkg/registry/server/events.go:143`. `Server.tenant` no longer feeds the limiter.
- **D2. Limit source and precedence.** For search QPS, materialization rate, and audit volume per day, the limit enforced against tenant T follows T's `store.Quota` value:
  - A positive value is enforced.
  - Zero selects the deployment default from `PODIUM_QUOTA_SEARCH_QPS`, `PODIUM_QUOTA_MATERIALIZE_RATE`, or `PODIUM_QUOTA_AUDIT_VOLUME_PER_DAY`.
  - A negative value disables the budget for T, whatever the deployment default is.
  - When T's value and the deployment default are both zero, the budget is not enforced.

  This is the §4.7.8 user-layer-cap convention, where zero selects the deployment default and a negative value disables the cap (`pkg/store/store.go:93`). It keeps an operator's ability to exempt one tenant, which today's "zero disables" rule provides and a zero-means-default rule alone would remove. §4.7.8 currently says a zero tenant value disables the budget, so SPEC-1 amends that sentence. `PATCH /v1/admin/tenants` already accepts negative values (`tenants.go:72-79`), so §7.3.3 needs no change. The amendment adds no new environment variable. It specifies and documents the three that `serverboot.go:2351-2353` already reads.
- **D3. Precedence differs from `max_user_layers`.** `effectiveLayerCap` applies the deployment value ahead of the tenant record (`pkg/registry/server/layers.go:582-590`, documented in the `docs/reference/http-api.md` Quota section). Applying that order to the rate limits would make the per-tenant records inert whenever an operator sets a deployment value, which contradicts "per-org limits, admin-configurable". This proposal does not change the user-layer cap (Non-goals, OQ-2).
- **D4. Unrouted requests.** A multi-tenant request with no routed tenant is charged to the registry's no-data tenant ID, `podium:unrouted`, which `TenantFor` already returns. These requests carry no tenant record on the context (D5), so they are charged at the deployment defaults. An unknown org under `oidc-jwt` is outside this case, because `withTenantRouting` rejects it with `auth.tenant_unknown` before any handler or charge runs (`pkg/registry/server/server.go:474-480`, `internal/serverboot/serverboot.go:1454`). Unrouted traffic shares one set of buckets and never draws on a provisioned tenant's budget. It also stays throttled, so it cannot evade the deployment default. Refusing these requests would contradict §6.3.1, which treats an unknown org under `trusted-headers` as anonymous, and §6.3.3, which makes a request during a JWKS outage anonymous and does not reject it. No new error code and no new refusal path is added.
- **D5. The limit source is the record routing already read.** On a multi-tenant registry with a verifier, routing calls the tenant router for an authenticated caller with a non-empty `OrgID` (`pkg/registry/server/server.go:469-471`), and `tenantResolver` reads the tenant record with `store.GetTenant` (`internal/serverboot/orgid.go:29-34`). The router returns that record (`store.Tenant`). `routeTenant` (proposal 0047 CODE-1), which `withTenantRouting`, `TenantRouted`, and `TenantRoutedNoReject` call, passes it to `contextWithRoutedTenant(r.Context(), t)`, which puts `t.ID` on the context with `core.ContextWithTenant` and `t.Quota` under an unexported server key. The helper is the only setter of the carried quota and routing's only setter of the tenant ID. Nothing clears either value, because a context lives for one request. The readers are the three charge sites and `handleQuota`, which call `tenantQuotaFrom`. A request that routing did not resolve carries no record, and `tenantQuotaFrom` returns the zero `store.Quota`, which resolves to the deployment defaults (D2). That covers an anonymous caller, an empty `OrgID`, an unknown org under `trusted-headers`, a multi-tenant registry with no verifier, and every single-tenant request (D11). A routed record holding zeros resolves the same way, so no presence flag is carried. A `PATCH /v1/admin/tenants` change applies to the next request, because that request's routing reads the updated record. If a routing site set the tenant ID without the quota, the tenant would be charged under its own key at the deployment defaults. TEST-1's context-carrier case, TEST-2 case 3, and TEST-4 case (c) detect that. No cache and no TTL constant is added. The D6 table lists every store read and fault outcome.
- **D6. Store reads and faults.** This table is the single statement of which quota paths read the store and what a failed read does. Every other section cites it.

  | Path | Limit source | Store read this proposal adds | On a read error |
  |:--|:--|:--|:--|
  | Charge, routed request | Carried record, through `EffectiveLimits` | None | Not applicable |
  | Charge, unrouted multi-tenant request (anonymous, JWKS outage, empty `OrgID`, unknown org under `trusted-headers`, no verifier) | Deployment defaults, keyed on `podium:unrouted` | None | Not applicable |
  | Charge, single-tenant registry | Deployment defaults, keyed on the bound tenant | None | Not applicable |
  | `GET /v1/quota`, the three rate limits in the response | The carried record through `EffectiveLimits`, as for a charge on the same request | None | Not applicable |
  | `GET /v1/quota`, the existing `core.Quota` read (`tenant_id`, `max_user_layers`, and the `storage_bytes` usage) | Not a rate-limit source | None (existing `GetTenant` and `ListManifests` reads, `pkg/registry/core/quota.go:27`, `:32`) | Existing behavior, unchanged: any error answers `404 registry.not_found` (`pkg/registry/server/quota.go:15-18`). On a multi-tenant registry this includes every unrouted request, because core is bound to `podium:unrouted` (`internal/serverboot/serverboot.go:1106-1108`) and no tenant record exists under that ID, so the report never reaches the deployment defaults |
  | Reingest audit-volume gate, multi-tenant (`POST /v1/layers/reingest`, routed through `TenantRouted` by proposal 0047, and the inbound webhook, which carries no routed record) | `lc.TenantID`'s stored record, through `EffectiveLimits`. The manual trigger's carried record is not read. | One `GetTenant` per reingest, before source-provider resolution | Any error, including `store.ErrTenantNotFound` and a canceled context, refuses the reingest with `500 registry.unavailable` through `writeReingestError`'s default arm (`pkg/registry/server/layers.go:1817-1818`), and `notifyIngestFailure` fires (`:1694`) |
  | Reingest audit-volume gate, single-tenant | `cfg.auditVolumePerDay` | None | Not applicable |
  | Routing's own `GetTenant` in `tenantResolver` | Not a quota read | None (existing read) | Existing behavior, unchanged and unspecified: treated as no tenant, so under `trusted-headers` the request is charged to the unrouted budget, and under a verified provider it is rejected with `auth.tenant_unknown` (`pkg/registry/server/server.go:469-483`; Non-goals) |

  One runner serves both reingest triggers, and it reads the record from the store so both resolve the limit one way. On the manual trigger this is a second read of the record routing read, and a `PATCH` between the two reads applies to the gate. A miss at the gate is refused like any other fault. No store operation deletes a tenant (`pkg/store/store.go:359-378`), and deactivation keeps the record. Proposal 0047 refuses an unrouted layer write, the webhook reads a layer only under an active provisioned tenant, and rows written before 0047 carry the bootstrap tenant created at boot (`internal/serverboot/serverboot.go:887`). A missing record therefore means boot's tolerated `CreateTenant` fault left the store inconsistent. The reingest handler answers a fault on its preceding `GetLayerConfig` read the same way (`layers.go:1651-1657`), and `docs/reference/error-codes.md:166` defines the code, so SPEC-1 and DOC-1 add no sentence for the gate (OD-1).
- **D7. A limit change retunes the bucket in place.** `q.mu` guards only which buckets are in `searchBuckets` and `matBuckets`. A tenant's bucket is inserted once, on its first positive-rate charge, and is never replaced or deleted, so a pointer read under `q.mu` stays the tenant's live bucket after `q.mu` is released. `b.mu` guards the bucket's `capacity`, `tokens`, `rate`, and `last`. No code holds both locks at once. `rateBucket.allow(rate)` refills at the stored rate, retunes `rate` and `capacity` to the charge's rate if they differ, clamping `tokens` to the new capacity, and then charges, all under `b.mu`. A retune and a charge are therefore one atomic step, and concurrent charges carrying different rates serialize on `b.mu` with no charge lost. A raised limit grants no fresh burst, and a lowered limit takes effect on the charge that carries it. A charge that resolves a rate of zero or less is allowed without touching the map or the bucket, so a return to a positive rate continues from the bucket's balance rather than from a full bucket. The maps hold one bucket per key ever charged at a positive rate, as they do today.
- **D8. Audit volume per tenant.** The audit emitter records each `core.Registry` event under `registry.TenantFor(ctx)` of the emitting call, so `core.AuditEvent` needs no new field. The reingest runner checks `Allow(lc.TenantID, limit)`, keyed on the stored layer's tenant, which every store read fills, with the limit resolved under the D6 table. `Record` and `Allow` change together. Changing only the `Allow` key would leave every routed tenant's counter at zero. After proposal 0047, `lc.TenantID` is the request's routed tenant on the manual trigger and the tenant the URL names on the webhook trigger, and the emitter records that tenant's own meta-tool events under the same ID. TEST-3 case 2 pins the key in process, and TEST-4 case (f) pins it on the binary with a per-run tenant whose limit differs from the boot tenant's.
- **D9. Meter installation.** The volume-recording emitter is installed unconditionally, without the current `cfg.auditVolumePerDay > 0` guard, because a tenant record can carry a positive `audit_volume_per_day` while the deployment default is zero. - **D10. `GET /v1/quota` reports enforced limits.** `limits.search_qps`, `limits.materialize_rate`, and `limits.audit_volume_per_day` report the effective value under D2, where `0` means the budget is not enforced. `storage_bytes` and `max_user_layers` keep reporting the record value, because this limiter resolves neither (Non-goals). `GET /v1/admin/tenants` keeps reporting the stored record unchanged. `usage` still carries only `storage_bytes`, and no new response field is added.

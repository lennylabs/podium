# Proposal 0011: `mergeChain` builds the served record from the root parent's row

- Issue: (to be filed)

This document records a family of defects with one root cause, the evidence for each, and which of them needed a spec sentence rather than only a code fix. The spec edits it staged are applied, and the code changes have landed as recorded under "Deviations from the checklist".

## Summary

**What changes.**

- `mergeChain` in `pkg/registry/core/core.go` stops serving an extends child under the root parent's `Signature`, so the served signature covers the served content hash and `sign.EnforceVerification` succeeds on the served pair.
- `mergeChain` stops guarding the body carry-over, so a child with an empty body is served its own empty body rather than the root parent's prose. For a type whose prose lives in ARTIFACT.md the served `Body` and the body inside the same record's re-serialized frontmatter then carry the same prose, so the record stops disagreeing with itself. For `type: skill` the two sources are different by construction and stay so: ingest stores the SKILL.md body on `ManifestRecord.Body` and the ARTIFACT.md bytes as `ManifestRecord.Frontmatter` (`pkg/registry/ingest/ingest.go:1156-1160`, `:1190-1191`), so what the change gives a skill child is its own empty SKILL.md body in place of the parent's prose.
- The merged frontmatter the extends resolvers serve stops dropping frontmatter keys the `manifest.Artifact` struct does not declare, so `load_artifact` preserves the extension-type fields `search_artifacts` already preserves. Both resolvers change together: `mergeChain` in `pkg/registry/core/core.go:1751` and `resolveExtends` in `pkg/registry/filesystem/extends.go:60` call `manifest.SerializeArtifact` on the same closed struct, so repairing only the core load path would make the server mode and the filesystem-registry mode serve different bytes for the same extends child and break the §11 equivalence property. Which serialization route it takes is decision 3 and is open, under the fixed constraints recorded there.
- A child that inherits its parent's `audit_redact` directive emits a read event carrying the directive's fields as `[redacted]`, and a child that declares its own directive keeps using its own. Constrained by decision 4.
- The dead `Description`, `Tags`, and `SearchVisibility` assignments in `mergeChain` are deleted, and the in-function comment loses its search-descriptor clause, which has never held. The comment's sensitivity and deprecation clauses stay, because those assignments still have consumers. This one is conditional on decision 5.
- A merged frontmatter the §4.6 strip cannot rewrite fails the load instead of being served, so `mergeChain` returns an error to its single caller, `assembleResult` (`pkg/registry/core/core.go:1656`), which already returns `(*LoadArtifactResult, error)`. Constrained by decision 3.
- Tests assert each of the above on a consumer-visible surface at the level the change reaches, enumerated under "Testing". They include the fail-closed §4.6 strip case, the negative audit case, and an extends fixture added to the §11 filesystem ↔ server equivalence test.

**IMPLEMENTOR'S CHOICE:** the serialization route the merged frontmatter takes, subject to the served block preserving the undeclared keys §4.6 makes inheritable, resolving no `extends` under a literal key, an anchor, or a merge key, carrying the parent's ID under no other key either, and failing the load with `registry.invalid_argument` when it cannot be rewritten. The route is decision 3's.

## The root cause

`mergeChain` (`pkg/registry/core/core.go`) assembles the record `load_artifact` serves for an artifact that declares `extends:`. It starts from `chain[0]`, the root parent's stored row, and then repairs a hand-written list of fields from the child. Every field absent from that list ships the root parent's value.

The list is incomplete. What follows is each reachable consequence, established by tracing every assignment in the function to the consumer that reads it.

## Defect 1: an extends child is served under its parent's signature

`out.Signature` is never assigned from the child, so it stays the root parent's envelope, while `out.ContentHash` is assigned the child's. `resultFromRecord` copies `Signature` onto the served result, and it reaches the wire.

Ingest signs each record over its own content hash (`pkg/registry/ingest/ingest.go`), and `sign.EnforceVerification` verifies the served signature against the served content hash (`pkg/sign/sign.go`). The two no longer correspond for any extends child.

On a registry with a signer configured, every extends child is therefore served with a signature that cannot verify against its own content hash. §4.7.9 aborts materialization with `materialize.signature_invalid` on a verification failure, so this fails closed rather than open, and it propagates to every consumer that verifies: the MCP server on materialization (`cmd/podium-mcp/main.go:2018`) and `podium verify` (`cmd/podium/sign.go:124`). The `podium sync` path verifies nothing today. `sign.EnforceVerification` has no caller under `pkg/sync`, and the `verify_signatures` key in `sync.yaml` is read by the MCP server (`cmd/podium-mcp/cliconfig.go:195`) rather than by the sync command.

No test in the tree pairs signing with `extends:`, which is why it went unnoticed.

## Defect 2: a child with an empty body is served the parent's prose

The body carry-over is guarded: the child's body replaces the parent's only when it is non-empty (`pkg/registry/core/core.go:1726-1728`). `manifest.MergeExtends` has no such guard and assigns the child's body unconditionally (`pkg/manifest/merge.go:135`). The comment stating the rule the guard breaks sits directly above the guard itself, in core: "extends inherits structured fields, not the markdown body" (`pkg/registry/core/core.go:1723-1725`).

So a child whose body is empty is served the root parent's prose in the record's `Body`, while the body inside the same record's re-serialized frontmatter is the child's (`manifest.SerializeArtifact` writes `a.Body`, `pkg/manifest/merge.go:152-156`). For a type whose prose lives in ARTIFACT.md the returned record therefore disagrees with itself.

For `type: skill` the two sources hold different content by construction, before and after the change. Ingest stores the SKILL.md body on `ManifestRecord.Body` and the ARTIFACT.md bytes as `ManifestRecord.Frontmatter` (`pkg/registry/ingest/ingest.go:1156-1160`, `:1190-1191`), and `parsedArtifact` reads the frontmatter (`pkg/registry/core/core.go:1761`), so the re-serialized body is the child's ARTIFACT.md prose while the record's `Body` is a SKILL.md prose. Removing the guard changes a skill child by serving its own empty SKILL.md body rather than the root parent's SKILL.md prose, and it does not make the two sources equal.

The defect is that disagreement, together with the divergence of core from every other implementation of the same rule. `manifest.MergeExtends` assigns the child's body unconditionally (`pkg/manifest/merge.go:135`), the filesystem resolver folds through that same function and therefore already serves the child's body (`pkg/registry/filesystem/extends.go:121`), and `docs/authoring/extends.md:28` states that the child's prose body replaces the parent's and that bodies are never concatenated. Core is the outlier.

Serving parent-derived content to a requester who cannot see the parent's layer is not a §4.6 "Hidden parents" violation. That paragraph mandates exactly this: the registry resolves and merges the parent server-side and serves the merged manifest to that requester, and its guarantee is scoped to the parent's existence and ID (`spec/04-artifact-model.md:681`). The merged frontmatter already ships the parent's inherited description, tags, and sensitivity to the same requester, and a prose body carries neither the parent's ID nor evidence of its existence. The §4.6 rule about inheritance is "Omitted fields", which is scoped to frontmatter fields (`spec/04-artifact-model.md:700`), and the markdown body is not one (`Body string \`yaml:"-"\``, `pkg/manifest/types.go:161-163`).

## Defect 3: the served merged frontmatter drops every undeclared key

The merged frontmatter is produced by `manifest.SerializeArtifact`, which marshals the closed `manifest.Artifact` struct (`pkg/manifest/merge.go:143-144`). Every frontmatter key the struct does not declare is dropped, which covers the extension-type fields §4.6 names as inheritable (`spec/04-artifact-model.md:700`) and the §9 `TypeProvider` SPI registers.

Proposal 0009 refused a typed round-trip on the search path for this precise reason and landed a node-level strip instead, recording it as a fixed decision. The load path still does the thing 0009 rejected, so `search_artifacts` now preserves an extension key that `load_artifact` destroys for the same artifact. The search path and the load path disagree.

Both extends resolvers do this. `mergeChain` re-serializes through `manifest.SerializeArtifact` (`pkg/registry/core/core.go:1751`), and the filesystem-source resolver re-serializes the merged manifest through the same call (`pkg/registry/filesystem/extends.go:60`), with a doc comment stating that it uses the shared merge so a filesystem-source materialization matches the registry's load-time assembly (`pkg/registry/filesystem/extends.go:10-12`). Today both modes drop the same keys, so they agree while both being wrong. `pkg/sync` carries whichever mode's bytes into the harness adapters, taking the served `Frontmatter` from a server (`pkg/sync/server.go:133`) and the resolver's `ArtifactBytes` from a filesystem registry in `filesystemRecords` (`pkg/sync/sync.go:559`), whose walk is the one that sets `ResolveExtends: true` and so is the only `pkg/sync` conversion the extends resolver reaches (`pkg/sync/sync.go:545-548`), so repairing one resolver alone would make the two modes materialize different bytes for the same extends child. §11 requires byte-identical output across the two (`spec/11-verification.md:33`), and §13.11.3 states that the filesystem consumer runs the same module functions the registry runs behind its HTTP API (`spec/13-deployment.md:305`). The existing equivalence test carries no extends fixture, so nothing in the suite would catch the divergence.

The §4.6 hidden-parent strip currently rides on this same typed round-trip: `mergeChain` sets `merged.Extends = ""` and the closed struct guarantees that no `extends` key, anchor, or merge key survives (`pkg/registry/core/core.go:1747-1752`). Removing the closed round-trip removes that guarantee, which is why the strip is a fixed constraint on decision 3 rather than part of it.

## Defect 4: an inherited `audit_redact` never reaches the read event

§4.6's omitted-field rule makes `audit_redact` inheritable and `MergeExtends` implements it child-wins (`pkg/manifest/merge.go:119-121`), but the §8.2 read-audit emitter derives its redaction keys from the pre-merge leaf record, falling back to parsing that record's own frontmatter (`pkg/registry/core/core.go:1537-1542`). A child that omits `audit_redact` and inherits its parent's directive reaches the emitter with an empty key set.

The observable effect is a §8.2 fidelity gap rather than a disclosure. The emitter surfaces a sensitive frontmatter value into the event context only because `audit_redact` named it, and `manifest.FrontmatterFields` returns nil for an empty name set (`pkg/manifest/parse.go:58-61`), so the loop at `pkg/registry/core/core.go:1547-1551` adds nothing and `ev.RedactKeys` stays empty. The audit adapter masks only the keys the directive itself pulled in (`internal/serverboot/audit_emitter.go:32-33`). The author-named fields are therefore absent from the read event instead of appearing as `[redacted]`, and no value reaches a sink unmasked.

The emitter's value source has the same defect independently of the key set. It calls `manifest.FrontmatterFields(rec.Frontmatter, redactKeys)` (`pkg/registry/core/core.go:1547`), and `rec` is the leaf child's pre-merge stored row: `assembleResult` takes `rec` and computes `merged := mergeChain(chain)` only inside itself (`pkg/registry/core/core.go:1648`, `:1656`), and the comment on `RawFrontmatter` records that `rec` is the leaf of the chain (`pkg/registry/core/core.go:1662`). `FrontmatterFields` decodes only the source it is handed (`pkg/manifest/parse.go:59-71`). In the case the defect is about, the parent declares both the sensitive field and the `audit_redact` directive and the child omits both, so §4.6's omitted-field rule serves that field to the requester in the merged frontmatter (`spec/04-artifact-model.md:700`) while the child's own bytes contain neither. A fix that resolves the key set alone would emit `ev.RedactKeys` naming fields that the context loop (`pkg/registry/core/core.go:1547-1551`) never adds, so the event would omit the fields rather than carry them as `[redacted]`.

The two audit streams disagree as a result. The MCP-side sink parses the served merged frontmatter and so already honours the inherited directive (`cmd/podium-mcp/main.go:712`), while the registry read event does not.

Three changes are required together, and any one alone is a regression or a no-op.

1. `mergeChain` carries the merged directive onto the record it returns. `out := chain[0]` starts from the root parent's stored row (`pkg/registry/core/core.go:1710`), and `AuditRedact` appears in neither the per-iteration identity block nor the post-loop surfacing block (`pkg/registry/core/core.go:1740-1746`), so the returned record carries the root parent's value while `merged` carries the resolved one.
2. The resolved key set reaches the emitter, which today holds only `rec` and the `*LoadArtifactResult`, and `LoadArtifactResult` declares no `AuditRedact` field (`pkg/registry/core/core.go:1378-1425`). Without change 1 this serves the root parent's key list to a child that declares its own directive.
3. The emitter's value source moves from `rec.Frontmatter` to the served merged frontmatter, in scope at the emitter as `res.Frontmatter` (`pkg/registry/core/core.go:1518`, `:1805`). A non-extends read is unaffected, because `assembleResult` returns `resultFromRecord(rec)` for a record with no pin (`pkg/registry/core/core.go:1649-1650`) and `resultFromRecord` sets `Frontmatter: rec.Frontmatter` (`pkg/registry/core/core.go:1805`).

**IMPLEMENTOR'S CHOICE:** how change 2 is plumbed, subject to the emitter's keys being the set `manifest.MergeExtends` resolved, its values coming from the served merged frontmatter, and a non-extends read staying byte-unchanged. Whether that arrives on the merged record or on a new `LoadArtifactResult` field is decision 4.

## Dead assignments

`Description`, `Tags`, and `SearchVisibility` are assigned onto the merged record and read by nothing: `LoadArtifactResult` declares no such fields. `Name` and `WhenToUse` are never assigned and are likewise unread. The in-function comment claims the assignments exist so search descriptors, sensitivity gating, and deprecation reporting agree with the served frontmatter (`pkg/registry/core/core.go:1737-1739`). The search-descriptor clause has never held. `mergeChain` has had one caller in every revision that touched it, `assembleResult` on the load path (`pkg/registry/core/core.go:1656`, `:1648`), and `SearchArtifacts` builds each descriptor from the stored record through `descriptorOf` (`pkg/registry/core/core.go:1278`, `:2001`). Proposal 0009 removed a different mechanism, `mergedSensitivity`, which walked the chain through `resolveExtendsChain` and folded `c.Sensitivity` for the search path without reading `mergeChain`'s output (`git show 316b5f6 -- pkg/registry/core/core.go`); the search path now reads the stored column directly (`pkg/registry/core/core.go:1284`). The assignments were therefore dead before 0009 as well.

These are not defects today. They are why the function's remaining defects are hard to see: a reader cannot tell which assignments matter without tracing each to its consumer, and half of them have none. An earlier draft of this proposal reported one of these dead assignments as the headline defect, on a reproduction that observed the function's return value rather than any served surface. That is the failure mode this proposal is written to avoid.

## The structural fix

Each defect above is an omission from the hand-written carry-over list, so repairing them one at a time reproduces the structure that caused them. `Signature` and `AuditRedact` are the omissions this proposal establishes; the list gives no reason to believe they are the last. The alternative is to build the served record from the leaf and copy down only what §4.6 says is inherited, which makes the inherited set explicit and the default correct.

That is a larger change than repairing the individual assignments, and it touches the function every extends read passes through. Which of the two to take is the proposal's central decision.

## Decisions taken

The five decisions below were left to the reviewer while the document was drafted, and were taken at sign-off on 2026-08-20. Each is reversible by amending this section and re-running the implementation. The original question is kept with each answer, because the alternative each one rejects is the part a later reader would otherwise re-derive.

**1. The missing carry-overs are added to the existing list.** `mergeChain` is not restructured to build from the leaf. The document argues that repairing defects one at a time reproduces the structure that produced them, and that argument is sound about recurrence. Two things outweigh it. The checklist records that this decision "selects how each carry-over step is written rather than which steps exist", so the same steps land either way. And the run's own introspection recorded that this decision drew no findings across four rounds because no reviewer lens maps to it, which makes it the least-examined choice in the document; a restructure of the function every `extends:` read passes through is not the change to make on the least-examined decision. The structural repair still lands where it matters, because the shared serialization helper in S4 replaces the duplicated round-trip in both resolvers rather than adding another entry to a list.

**2. Neither the signature rule nor the body rule gains a spec sentence.** Both are code defects against the spec as written, so no spec step enters the sequence. §4.7.9 does not state in as many words that a served signature covers the served content hash, but the code is incoherent under every reading of it: ingest signs over each record's own content hash, and the served pair cannot verify. The body case is thinner, and the original question below records why: no spec section says which body an extends child serves, so the body test cites `manifest.MergeExtends` and `docs/authoring/extends.md` rather than a section. If a reviewer later wants that test to cite §4.6, the sentence is a separate one-line proposal.

**3. The merged frontmatter is serialized at the YAML node level.** Proposal 0009 refused the typed round-trip on the search path for this same defect and landed a node-level strip, and taking the same route here keeps one answer across both paths. The alternative changes a type every package uses in order to repair two call sites. The four constraints recorded under the original question stand, including the fail-closed abort with `registry.invalid_argument` and the accepted regression for a child whose `extends` arrives through a YAML merge key or an anchor.

**4. The resolved key set is plumbed internally**, by returning the merged record from the assemble path. `LoadArtifactResult` is a client-facing type and the key set is an input to the §8.2 emitter rather than something a client reads, so widening the wire contract for an internal need is the wrong trade.

**5. The dead assignments are deleted** in the same change. The deletion is behavior-preserving, and the ambiguity it removes is what produced this proposal's own earlier misdiagnosis: an assignment was read as consequential without tracing it to a consumer that does not exist.

### The questions as they were put

1. Whether to restructure `mergeChain` to build from the leaf, or to add the missing carry-overs to the existing list.
2.    **IMPLEMENTOR'S CHOICE:** the serialization route, subject to four constraints. (a) The undeclared parent keys §4.6's omitted-field rule makes inheritable survive the merge.

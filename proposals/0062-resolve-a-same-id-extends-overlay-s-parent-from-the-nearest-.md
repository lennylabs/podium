# Proposal 0062: Resolve a same-ID extends: overlay's parent from the nearest lower-precedence layer that holds the ID

- Issue: (to be filed)

This document stages spec, code, test, and documentation changes. It does not modify any spec, code, test, or doc file. Apply the changes in the staged sections after sign-off. The change is backward-incompatible: ingest rejects some same-ID overlays it accepts today, and it pins others to a different parent. It lands in the 0.6.0 MINOR release.

## Summary

- `internal/serverboot` writes every bootstrap layer config before it ingests any layer, in one `bootstrapLayers` function that `run()` calls once, and `server.NewFromFilesystem` registers each layer before ingesting it (CODE-4, CODE-5).

## Current state and the gap

### What the spec says

§4.6 sanctions a same-ID collision only when the higher-precedence artifact declares `extends: <lower-precedence-id>`. §4.7.3 describes the case as "a child that overlays a lower-precedence layer's artifact under the same canonical ID". Neither section says which lower layer the parent comes from or which versions are candidates. §4.7.6 runs selection over "the parent's candidate versions" without defining the set.

Proposal 0057 added a sentence to §4.6 that sanctions an own-layer selection: "When the reference selects an earlier version of the overlay stored from the overlay's own layer, the edge lies within that layer." That sentence contradicts the §4.6 collision rule, §4.7.3, and §2.2. §13.11.3 holds no own-layer clause. It states generally that the filesystem parent "can differ from the parent version a server pins (§4.7.6)". 0057 D-5 recorded that restricting a same-ID pin to lower-layer rows "needs its own spec edit" and listed the alignment as a non-goal. The own-layer statement also appears in `docs/authoring/extends.md` ("Which edges the rule tests"), `docs/reference/cli.md`, the Unreleased `CHANGELOG.md` bullet for 0057, scenario S93 (its Goal, its Why-by-hand text, and step 6), and the S39 step 7 note in `test/manual-validation.md`.

### What the two modes do

The filesystem resolver follows the §4.6 reading. For a same-ID reference it takes `layered[rec.ID][layerIdx-1]` (`pkg/registry/filesystem/extends.go:318-326`), which is the one record of the nearest lower layer that contributes the ID, and it ignores the pin (`:314`).

The server works differently. `resolveExtendsPin` (`pkg/registry/ingest/ingest.go:1604`, called only at `:677`) lists every manifest of the tenant with the referenced ID. It drops exactly one row: the row matching the child's ID, version, and layer (`:1642`). It has no layer-precedence input, because `ingest.Request` carries only `LayerID` and the ingest package never reads layer configs. Every other row of the ID stays a candidate, in every layer. The exact, range, content-hash, and `latest` arms then select over that set (`:1662-1724`). `latest` takes the most recently ingested non-deprecated row and breaks ties by semver (`pkg/version/version.go:160-180`). A range takes the highest matching semver.

### Failure modes

- **Own earlier version.** An overlay bumped from 1.1.0 to 1.2.0 in its own layer pins its own 1.1.0 row. `TestIngest_ExecutableInheritanceSameLayerOverlayPinAccepted` (`pkg/registry/ingest/executable_inheritance_test.go:533-559`) asserts `ExtendsPin == "x@1.1.0"`, and S93 step 6 expects the same result.
- **Higher-precedence row.** A newer row from a higher-precedence layer becomes the parent of a lower layer's overlay. This includes a row from a user-defined layer, which §4.6 composes only into its owner's view, becoming the parent of an admin-defined overlay that every caller reads. The collision check sanctions such a user row whenever any stored cross-layer row overlays the ID (`pkg/registry/ingest/ingest.go:766-776`).
- **Farther lower layer.** On a single fresh boot with layers A (x@1.5.0), B (x@1.2.0, `extends: x`), and C (x@2.0.0, `extends: x@1.x`), the server pins C to A's 1.5.0 and skips B. The filesystem merges C over B. This needs no stored history, because both `server.NewFromFilesystem` (`pkg/registry/server/server.go:353-371`) and `bootstrapLayerPath` (`internal/serverboot/serverboot.go:474-545`) ingest the lowest layer first, so every lower layer's rows are candidates.

### Why it reaches served bytes

The wrong pin reaches the served document in two ways. `core.ExtendsChain` follows stored pins (`pkg/registry/core/core.go:1836`), and `MergeExtends` unions tags and keeps the most restrictive sensitivity (`pkg/manifest/merge.go:47`, `:57`). Ingest also folds the pinned parent into the child's indexed columns (`pkg/registry/ingest/ingest.go:721-742`). A tag the author removed, or a sensitivity the author lowered, keeps being served and indexed, and the server and filesystem modes materialize different output. That contradicts §2.2 and the §13.11.3 equivalence claim.

The bootstrap path hits the bug on restart. The default SQLite store persists between boots, and `bootstrapLayerPath` re-ingests every layer on each boot. Each layer's `LayerConfig` is written only after that layer's ingest (`internal/serverboot/serverboot.go:489` against `:544`), and `NewFromFilesystem` writes no config at all.

### What stays divergent after the fix

D-11 states what stays divergent, and SPEC-3 states it in §13.11.3. Two cases in the code ground that statement. For a different-ID reference, the filesystem takes the effective highest-precedence record (`pkg/registry/filesystem/extends.go:327-334`), while `resolveExtendsPin` keeps every stored row of the ID (`pkg/registry/ingest/ingest.go:1630-1646`), and `TestWalk_ExecutableInheritanceDivergentParentKeepsChild` (`pkg/registry/filesystem/extends_executable_test.go:440`) pins the filesystem outcome. The second case is the reason SPEC-3 states the same-ID condition over the copies sync keeps after its drops rather than over the layer subdirectories. L2 holds an `mcp-server` p 1.0.0 that sets `server_identifier` and an `mcp-server` x 1.0.0 with `extends: p` that omits it, and L3 holds an overlay of p and an overlay x 2.0.0 with `extends: x`, both restating it. A server ingests L2's p before x in canonical-ID order (`pkg/registry/ingest/ingest.go:1052`), pins x to L2's p, and accepts both copies of x. Sync resolves L2's x to L3's p, a cross-layer edge, drops L2's x, and then drops L3's x because no copy of x remains below it (§13.11.3). The stored rows match the layer subdirectories, yet the server serves L3's x merged over L2's x and sync materializes no x.

## Decisions

- **D-1 (maintainer, closed). Candidate set.** For a reference that names the child's own canonical ID, the candidates are the rows of the nearest lower-precedence layer that holds a non-deleted row of that ID. Rows of the child's own layer and of every higher-precedence layer are never candidates. The existing content-hash, exact, range, and `latest` arms, and the deprecation filter, run over those candidates unchanged (`pkg/registry/ingest/ingest.go:1662-1724`). A reference to a different ID keeps today's candidate set.
- **D-2. Precedence source.** The resolver reads `store.ListLayerConfigs` and composes it in §4.6 order. Every admin-defined layer comes first, ordered by `Order`. Every user-defined layer ranks above every admin-defined layer whatever its `Order` (§4.6 composition order). That split is the one `core.layerConfigs` applies (`pkg/registry/core/core.go:429-460`). The raw `Order`-ascending listing (`pkg/store/memory.go:501-519`, `pkg/store/sqlite.go:881-889`, `pkg/store/postgres.go:1348-1361`) is not §4.6 precedence on its own. The ordering is extracted into one exported core function that both callers use (CODE-1).
- **D-3. User-defined layers of different owners.** A user-defined layer is composed only into its owner's view (§4.6; §7.3.1 *User-defined layers*). The lower layers of a user-defined child are every admin-defined layer plus the same owner's user-defined layers below the child. A user-defined layer of another owner is never a candidate. For an admin-defined child, the lower layers are the admin-defined layers below it, because every user-defined layer ranks above it. The rule follows the §4.6 composition order for the child layer's owner, so no per-caller ambiguity remains. The rule holds whatever the registration state, because a child whose layer is absent from the listing has no lower layer (D-5).
- **D-4. Registration before ingest.** Every server ingest path registers its layers before it ingests any of them. The orchestrator and API paths and `registryharness.NewLayered` already do. `bootstrapDeclaredLayers` writes each declared config immediately before ingesting that layer, and no earlier (`internal/serverboot/serverboot.go:645` before `:650`), which leaves the layers it has not reached at their previous `Order`. `bootstrapLayerPath` writes each config after the layer's ingest (`:489` before `:544`), and `server.NewFromFilesystem` (`pkg/registry/server/server.go:353-371`) persists nothing. CODE-4 writes every declared and every `--layer-path` config before the first bootstrap ingest, and CODE-5 registers each `NewFromFilesystem` layer before ingesting it. Without these changes, a first boot of the §11 three-layer fixture rejects both overlays under D-5, through the compiled binary and through `NewFromFilesystem`.
- **D-5. Unlisted child layer.** The resolver locates the child's layer in the composed listing (D-2). When the listing does not hold it, including when the tenant holds no layer config, the child has no lower-precedence layer, so a same-ID reference finds no lower holder and is rejected under D-6. Without a position in the composed order, ingest cannot tell a lower layer from a higher-precedence layer or from another owner's user-defined layer, which SPEC-1 edit 1 and D-3 exclude, so it keeps no row, as `code-best-practices.md` requires of a check that cannot evaluate. Every server ingest path registers its layers before it ingests them (D-4). A server therefore reaches this case only when the child's layer, or every layer of the tenant, is deleted while its reingest fetches the source. The handler passes the loaded config to the runner (`pkg/registry/server/layers.go:1929`), `SourceIngestWithOptions` snapshots the source (`pkg/registry/ingest/orchestrator.go:117`) before it calls `Ingest` (`:148`), and `ListLayerConfigs` omits a tombstoned config (`pkg/store/memory.go:508`, `pkg/store/sqlite.go:888`). A library caller that drives `ingest.Ingest` without registering a layer, such as a unit test, gets the same rejection for every same-ID overlay, and registers its layers to exercise the selection (TEST-2). A row whose layer is not in the composed list is never a candidate.
- **D-6. No lower holder.** When no lower-precedence layer holds the ID, ingest rejects the child with `ingest.invalid_artifact` and today's reason, `extends: self-extends cycle: "<ref>"` (`pkg/registry/ingest/ingest.go:1652-1654`). This now covers two further cases: the lowest holder whose reference used to select its own earlier version, and a lower layer whose reference used to select a higher layer's row. A middle-layer child that used to select a higher row now re-points to the nearest lower holder, and the §4.6 sandbox-profile and executable-field checks apply to it against that holder's version.
- **D-7. No fall-through.** When every version in the nearest lower holder is deprecated, a range or unpinned reference is refused with the deprecation message. It never falls through to a farther layer. An exact or content-hash pin that names a version stored only in a farther layer is refused as unsatisfied. Both outcomes follow from D-1, because the arms run unchanged over the restricted set. The deprecation message changes from "every stored version of parent %q is deprecated" to "every candidate version of parent %q is deprecated", which matches the unchanged §4.7.6 text "reports that the parent's candidate versions are deprecated" and stays true when a farther layer holds live versions.
- **D-8. An unchanged stored version is not re-resolved.** Today `resolveExtendsPin` runs before the idempotency switch (`pkg/registry/ingest/ingest.go:672-680` against `:778-786`), so a resolution error rejects an unchanged stored row on every reingest of its layer. That contradicts §4.7.6 ("a re-ingest of the child's unchanged bytes is idempotent") and the §4.6 statement that a cycle presenting a stored version unchanged classifies it unchanged. D-6 would turn every stored own-layer-only overlay into such a recurring rejection. CODE-3 skips resolution for a row that this layer already stores at the same version with the same content hash, and the switch then classifies the row idempotent. The same guard stops an unchanged child from being rejected after its pinned parent's layer was unregistered, because `DeleteLayerConfig` tombstones the parent rows and `ListManifests` omits them.
- **D-9. Stored rows keep their pins (§4.7, §4.7.6).** Ingest is the only code that writes `ExtendsPin` (`pkg/registry/ingest/ingest.go:711`), and the fix adds no repair, re-pin, or migration. A stored overlay that pinned its own earlier row or a higher row keeps serving that merged document until the author publishes a new version. Pre-1.0, the fix is backward-incompatible: some overlays accepted today are rejected, under D-6 or under the §4.6 sandbox-profile or executable-field rule applied to the re-pointed parent. It lands in the 0.6.0 MINOR release with no flag or shim.
- **D-10. Insert-path rules.** Under D-1, every same-ID edge ingested under the new rule points to a lower-precedence layer. Proposal 0063 renames `executableInheritance` to `extendsEdgeRejection` (`pkg/registry/ingest/ingest.go:1538`) and keeps its one call after the idempotency switch (`:807-808`). The function applies the §4.6 sandbox-profile rule to every edge, and it returns before the executable-field rule only when the parent shares the child's layer (`:1542`, `:1568`). Every same-ID edge that CODE-2 pins therefore gets both rules, the sandbox-profile rule first, with no further code change. The same-layer arms stay reachable through a different-ID reference, which `TestIngest_SandboxConflictRejectsOnEveryEdge` drives, so CODE-2 leaves no dead branch. The filesystem resolver applies both rules in the same order in `mergeRecord` (`pkg/registry/filesystem/extends.go:357`, `:361`), and this proposal changes no filesystem code. §4.6 drops the own-layer sentence 0057 added (SPEC-1 edit 2), and the stored-version sentence gains a different-ID qualifier (SPEC-1 edit 3).
- **D-11. Remaining divergence.** The parent-selection divergence between a server and `podium sync` against a filesystem registry that remains after D-1 is accepted. SPEC-3's replacement sentence in §13.11.3 is its single normative statement. DOC-2 mirrors it in `docs/reference/cli.md`, and every other section of this proposal cites D-11 without restating the cases. Each case follows from a difference this proposal keeps. A different-ID reference keeps today's candidate set (D-1, Q-1). The filesystem holds one record per layer and reads no pin, so it has no versions to select among within a layer. A server's stored versions are the outcome of its ingest history and its ingest-time checks, while sync keeps no ingest state and reads the directory on each run (§13.11.3). A correction to the cases edits SPEC-3 and DOC-2, and it edits D-11 only when it adds a cause outside these three. §13.11.3 and `docs/reference/cli.md` are narrowed to the statement rather than deleted.
- **D-12. No new surface.** The fix adds no §6.10 error code, environment variable, `ingest.Request` field, store method, or SPI. Precedence comes from the existing `ListLayerConfigs` read. The resolver reads it at most once per `Ingest` call, and only when a same-ID reference appears. A listing error aborts the call as a store fault, as the parent read does at `pkg/registry/ingest/ingest.go:724-728`.
- **D-13. Spec first.** SPEC-1 to SPEC-4 land in one commit before any code. The narrowed §13.11.3 sentence cites the §4.6 rule SPEC-1 adds, SPEC-2 cites the same rule, and SPEC-4 names a fixture whose expected output follows from it, so none of them reads correctly alone.
- **D-14. User decisions.** This proposal applies the relayed user decisions as the user stated them. Items 6 and 7 of the release plan, of which this fix is item 7, and the sandbox_profile fix, proposal 0063, join 0.6.0. F1's "leave the spec as is" refers to the unrelated break-glass approver finding in `tmp/research/implementation-plan.md`, so it does not constrain this item.
- **D-15. Disclosure of a same-ID resolution.** §4.6 bounds what an author learns from resolving an `extends:` reference, and it caps disclosure about the parent's layer at what the executable-field rule reveals (`spec/04-artifact-model.md:691`). Under D-1, D-6, and D-7, the accept or reject outcome of a same-ID reference also reveals whether a layer below the author's own holds the ID (resolved against `self-extends cycle`), which versions the nearest such layer stores (an exact or content-hash pin succeeds or is refused as unsatisfied), and whether those versions are all deprecated. This disclosure is inherent to the D-1 candidate set, so it is accepted and stated in the spec rather than suppressed. ### CODE-2. `pkg/registry/ingest/ingest.go`: restrict a same-ID reference's candidates to the nearest lower holder

This implements D-1, D-3, D-5, D-6, D-7, and D-12.

- **Signature.** `resolveExtendsPin(ctx context.Context, st store.Store, tenantID, ref, childID, childLayer string, sameIDLower []string) (pin, parentType, parentLicense string, err error)`. The `childVersion` parameter is removed. The resolver reads `sameIDLower` only when the reference names `childID`, and a different-ID caller passes `nil` without reading the listing. - **Precedence lookup in `Ingest`.** Before calling the resolver, compute `refID, _ := splitRef(rec.Artifact.Extends)`. When `refID == rec.ID`, evaluate a per-call memo the first time it is needed, and reuse it for the rest of the record loop.

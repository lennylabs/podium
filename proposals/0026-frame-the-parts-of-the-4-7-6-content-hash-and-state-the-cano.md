# Proposal 0026: Frame the parts of the §4.7.6 content hash and state the canonicalization normatively

- Issue: (to be filed)
- Status: Implemented (2026-09-19). Verified 2026-09-18 after 15 adversarial review rounds (26 findings fixed). On 2026-09-18 the rehash moved from an off-server command into the registry's own start, by decision.
- Date: 2026-09-09

This document stages the proposed spec, code, test, and documentation changes. It does not modify any spec, code, or doc file. Apply the changes in the staged sections after sign-off.

## Summary

**What changes.**

- §4.7.6 states the canonical serialization normatively and closes its inputs: each part is framed with its length; the slot order is the manifest, then `SKILL.md`, then each bundled resource's path and body in ascending path order; an absent `SKILL.md` is a zero-length slot; the resource set is every file under the package root, dot-prefixed names included, other than the package root's `ARTIFACT.md` and, for a skill, the package root's `SKILL.md`, and other than the files of a nested package; every framed value is the bytes as ingested with no normalization; and a resource stored in object storage is hashed over its full bytes. §4.4's membership sentence gains the nested-package exclusion so the two sections agree. The section says only "the SHA-256 of the canonicalized manifest + bundled resources" today, and the word "canonicalized" is defined nowhere in `spec/`.
- §11's "Versioning and ingest tests" bullet gains a clause requiring a pinned canonicalization vector and a repartitioning case, and its equivalence bullet requires the fixture to carry an `extends:` child. §13.4's no-downtime clause is qualified to a schema-only upgrade, and the section gains a paragraph stating that the additive schema guarantee does not cover the values stored under the schema, and that the registry rewrites the stored content hashes on the first start of the new version that binds its listen address, before it ingests or serves; the same paragraph states that `podium admin migrate-to-standard` clears the target store's record of the rewrite, so the target's next start rewrites the rows it copied, and states the rule for the target registry around the command, and §13.12's object-storage table gains `PODIUM_MIGRATION_OBJECT_READ_TIMEOUT`, the deadline on each object-storage read that rewrite makes. §6.9's failure-mode table gains the row for `materialize.content_hash_mismatch`, a refusal the consumer returns today that no spec section defines and that this proposal's own text is the first to name.
- Every composer moves onto one framed function over the authored bytes. `pkg/version/version.go` length-frames every part inside `CanonicalContentHash` and deletes the exported variadic `version.ContentHash`, so no caller can produce an unframed digest. `cmd/podium-mcp/main.go` computes the §6.4 workspace-overlay response's `content_hash` through the same function over the whole overlay package and stops writing the §6.5 content cache. `pkg/registry/filesystem`'s walk record gains `AuthoredBytes`, the `ARTIFACT.md` as read from disk, set by the filesystem walk and by ingest's own loader alike and left in place when the `extends:` resolver overwrites `ArtifactBytes` with the merged re-serialization, so a filesystem-source `podium sync` records the same `content_hash` for an `extends:` child that ingest stores and a server-source sync records. Ingest's resource walk moves onto the filesystem walk's rule for a skill's `SKILL.md`, excluding the package root's copy and keeping one in a subdirectory, so the two walks produce one resource set for every package. The Python and TypeScript SDK overlay loaders, which compute no digest, move onto the amended §4.4 nested-package exclusion and the Go walks' dot-directory discovery skip (CODE-7), so an overlay loaded through an SDK carries the resource set and the artifacts the MCP server's overlay carries.
- The migration is a boot step inside the registry rather than a store rebuild or a separate command. `pkg/store` gains `RehashManifest`, a compare-and-swap rewrite of one stored row's `content_hash` and `signature`, `ListManifestsIncludingDeleted`, and a named data-migration marker, all on the `store.Store` interface and implemented on sqlite, postgres, and memory. `internal/serverboot` gains the rehash pass, which the first start of the new binary runs with the serving process's own store, object store, signer, and audit sink, before the bootstrap ingest and before any request is served, and `podium admin migrate-to-standard` clears the target store's marker before it copies the first manifest row, so the target's next start rewrites the copied rows; no registry process runs on the target store while the command runs, the target registry is started, or restarted when it was already running, only after a run of the command succeeds, and the target store is recreated empty before the command runs again when a run fails at a copied row with the immutability error, or when a registry started on the target store, or the source registry started on the new version, after the command's first run against it began. Before the signing-key loader runs, a start configured to sign whose key file is absent is refused while the rewrite has not completed and any stored row carries a signature, so a refused start generates and writes no key; a start whose listener could not bind does not run the pass; and the pass waits no longer than a deadline on each object-store read, whether or not the object-store provider honors its context. SPEC-3 states the pass's contract, CODE-4 is the single statement of how the pass meets it, DOC-1 item 2 states the operator order, and CODE-8 gives the Helm chart the startup budget the first start needs.
- The tests and the documentation follow. `pkg/version/version_test.go` pins the serialization to vectors built from the spec text and its injectivity across every part boundary, and the call sites of the removed helper migrate onto `CanonicalContentHash`; the §11 equivalence fixture under `testdata/registries/reference` gains an `extends:` child; and `cmd/podium-mcp`, `cmd/podium`, `pkg/sync`, `pkg/registry/filesystem`, `pkg/registry/ingest`, `pkg/store/storetest`, `internal/serverboot`, `test/e2e`, `test/chart`, `sdks/podium-py`, and `sdks/podium-ts` gain the tests the Testing section names. `CHANGELOG.md` records the break in persisted data, the upgrade order around the first start, and the cache-directory clearing on each consumer, records the two hashing disagreements CODE-5 and CODE-6 repair, and amends the unreleased entries from proposal 0025 that this change falsifies; `docs/deployment/operator-guide.md` qualifies its canary, coexistence, and rollback claims; `docs/deployment/single-node.md`'s upgrade note names the backup a stored-value migration needs; `docs/reference/cli.md`'s `podium admin migrate-to-standard` section names the marker clear CODE-4 adds, the rule that no registry runs on the target store while the command runs and that the target registry starts or restarts only after a successful run, and the recreation of the target store after an immutability failure or a start of either registry between runs, and its environment-variable table gains `PODIUM_MIGRATION_OBJECT_READ_TIMEOUT`; `docs/authoring/bundled-resources.md` states the resource-set membership for authors and the dot-directory discovery skip that the spec leaves unstated; and `test/manual-validation.md` gains scenario S64 and its index row, and its S20 migration scenario recreates the target store before the command runs, as the staged §13.4 rule requires of a target registries have started on.

**Fixed decisions.**

- The spec lands and is verified before the code. The canonicalization is a specification gap, and it is stated in §4.7.6 before `pkg/version` implements it.
- The framing is an 8-byte big-endian unsigned length prefix on every part. It uses no delimiter, no escaping, no per-part sub-digest, no Merkle structure, and no leading tag.
- The slot order and the ascending-path resource order are exactly what the code has today. Only the framing is added.
- An absent `SKILL.md` is a zero-length slot. There is no presence tag, so an absent and an empty `SKILL.md` hash alike.
- Slot one carries the artifact's own pre-merge `ARTIFACT.md` bytes, and any party that recomputes the digest for an `extends:` child recomputes over those bytes. SPEC-1 states nothing about how a consumer obtains them, because the response element the code uses is undefined in `spec/` and serving it to a requester who cannot see the parent's layer is a §4.6 question that proposal 0027 resolves without moving any hash; OQ-4 records the split between the answers that move hashes and the ones that do not. A filesystem-source `podium sync` hashes the merged re-serialization for an `extends:` child today; CODE-5 moves it onto the authored bytes, so every computing party agrees for every package and SPEC-2's agreement clause carries no `extends:` qualifier. Hashing the merged form instead was rejected, and the Decisions section records why. The accepted cost, a filesystem-source lock entry that does not move on a parent-only change, is recorded in the edge-case table and repaired by no part of this proposal.
- The exported variadic `version.ContentHash` is deleted rather than kept alongside the framed function.
- The §6.4 overlay path moves onto `version.CanonicalContentHash` in the same change, and the overlay's §6.5 content-cache write is deleted rather than completed, so the registry-served path is the single writer of the canonical key.
- Podium is pre-1.0, so the change takes a clean break. It adds no algorithm identifier, no negotiation, no dual computation, and no stored algorithm label, and it leaves no compatibility path for the old digest.
- The consumer's existing `materialize.content_hash_mismatch` refusal gains its §6.9 row and its §6.10 axis entry here, because this proposal's spec text is the first to name it. Proposal 0027 stages the same row; this proposal lands first and carries it, so 0027 drops its copy. No code that does not exist today is minted.
- The break lands in persisted data, and the migration runs inside the registry on the first start of the new binary, as CODE-4 specifies. It is not a separate command: an off-server command has to reconstruct the server's configuration, and Non-goals records why that was dropped. The pass touches no dependency row and no object, runs once per store behind a data-migration marker, which `podium admin migrate-to-standard` clears on its target, and emits the existing `artifact.signed` event, with ingest's §8.2 manifest-declared redaction, for each row it re-signs. Each consumer's cache directory, including the resolution index, is still cleared by hand.
- The rehash is the one event that re-signs every stored row, so proposal 0028 ships in the same release, and DOC-1's changelog entry is written as the release's single upgrade note so that the entries proposals 0027 and 0028 add extend it without naming a second store-wide step. Those proposals are Drafts and are cited for sequencing only. The Relationship section states what 0028 owns once it changes the signing default.
- The §4.7.6 input pins state existing behavior and change no code, with one exception: a dot-prefixed file is a bundled resource, a nested package's files are not, no ignore file or size threshold or name pattern removes a file from the set, no line-ending or Unicode or case or byte-order-mark normalization applies to any part, and a resource above the inline cutoff is hashed over its full bytes. The exception is the `SKILL.md` rule, where the two resource walks disagree today: the pinned rule excludes the package root's copy only, and CODE-6 moves ingest onto it. Outside the digest, the SDK overlay loaders move onto §4.4's nested-package exclusion and the Go walks' dot-directory discovery skip under CODE-7, because §6.4 gives an overlay the registry-side layers' format. An ignore mechanism, if one is ever wanted, filters at authoring time so that stored hashes do not move.

**Watch out for.**

- **Deleting `version.ContentHash` stops 13 test files compiling rather than two.** `grep -rn "version\.ContentHash(" --include="*.go" .` returns 34 call sites, plus 4 unqualified in-package calls in `pkg/version/version_test.go`. The framing, the new vector, and the caller migration must land in one commit or the tree does not build.
- **Some of those call sites are not mechanical renames.** A site that folds a resource path and body in variadically must become a resources map. A flattened rewrite compiles and then fails at run time as `materialize.content_hash_mismatch`, because the fixture hash is what the §6.6 step-2 gate recomputes through the shared function.
- **The gate does not defend an unsigned artifact against the party that supplies the hash.** That party sends both the bytes and `content_hash` and can send a matching digest. Injectivity buys integrity where the digest is independently attested: the §4.7.9 signature envelope, an `@sha256:` pin, and the §7.5.3 lock. Do not write the sub-threshold "only integrity gate" claim into a permanent code comment.
- **`podium layer reingest` is never the migration for the stored hashes, and it repairs no row this change moves.** The walk yields one record per artifact directory (`pkg/registry/filesystem/walk.go`, `loadArtifactRecord`), so a reingest reaches only the version each directory currently declares, while the store keys a row per `(tenant_id, artifact_id, version)` and hard-deletes one only in the §8.4 retention purges (`PurgeDeprecatedManifests`, `PurgeExpiredLayerDeletions`). Every earlier version, and every row of a soft-deleted layer, keeps its pre-upgrade hash through any number of reingests, and the head version is refused before the store is reached: ingest's own switch reports a differing hash for an existing `(artifact_id, version)` as a conflict, with `PutManifest`'s `ErrImmutableViolation` as the backstop. The same refusal reaches a pre-CODE-6 row for a skill holding a `SKILL.md` below its root, which CODE-6's closing paragraph states.
- **The pass has to reach soft-deleted rows.** `GetManifest` and `ListManifests` filter `deleted_at IS NULL` on every backend (`pkg/store/sqlite.go`, `pkg/store/postgres.go`, `pkg/store/memory.go`), and `RestoreLayerConfig` clears the tombstone within the §8.4 window. A rehash built on `ListManifests` leaves a restored layer serving pre-upgrade hashes; CODE-3's deleted-inclusive enumeration exists for this.
- **The rehash pass's contract is in SPEC-3, its mechanism in CODE-4, and its operator order in DOC-1 item 2.** SPEC-3 states the contract: the rewrite on the first start that binds its listen address, the refusal to start rather than strand a stored signature, and the per-read deadline. CODE-4 alone states the mechanism: the order of the checks in `run`, the check that refuses a start that would generate a signing key, and how the registry stops waiting on a read the provider does not abandon. The pass runs before the bootstrap ingest, because an ingest that meets a row still at the previous digest reports a conflict for it. Nothing answers `/healthz` until the pass finishes, so a Kubernetes liveness probe can restart the pod mid-pass, and CODE-8 adds the startup probe that prevents it. Implement from CODE-4 rather than from this bullet.
- **The `podium admin migrate-to-standard` target lifecycle is an operator rule, and it adds no code.** The command keeps its order of `pumpStore`, `pumpObjects`, and the audit-log copy, and its only change is the marker clear. The rule that no registry runs on the target store while the command runs, that the target starts only after a run that exits 0, and that the target store is recreated empty after an immutability failure or a start of either registry between runs is stated in SPEC-3, CODE-4's migration paragraph, DOC-1 item 2, and the `docs/reference/cli.md` sentences, and those statements use the same predicates. An implementor who reorders the pumps or adds an in-place reconciliation of the two stores reintroduces the mechanism Redesign 2 deleted.
- **The consumer cache does not self-heal.** An upgraded consumer that still holds pre-upgrade buckets fails the load with `materialize.content_hash_mismatch`, a consumer reverted to the previous binary fails the same way on the buckets the new binary wrote, and `podium cache prune` is not the remedy. DOC-1 item 4 states which cache modes the refusal reaches and the cache-directory clearing the changelog names.
- **The existing composition test states that the spec fixes nothing.** `pkg/version/version_test.go` says "§4.7.6 fixes neither the order of those slots nor the order in which resources are folded in", and expresses its expectation by calling the helper this change deletes. It is rewritten rather than extended.
- **Do not derive a pinned vector from the implementation.** A constant computed once from `CanonicalContentHash` records an endianness or width choice rather than checking it. Each vector is built from a literal framed stream written out of the spec text, and one of them frames an absent `SKILL.md` beside a bundled resource, which is the only assertion that catches an implementation that omits the empty slot.
- **The overlay path returns before the §6.6 pipeline.** Nothing re-derives its `content_hash`, so the divergence CODE-2 fixes is invisible to the suite today and returns unnoticed without TEST-3.
- **The walk record carries the authored and the merged bytes at once.** Materialization reads the merged form through `adapter.Source.ArtifactBytes`, which is the §13.11.3 parity with the server, and the digest reads the authored form, so the filesystem-source sync cannot be repaired by walking without `ResolveExtends` or by re-merging inside `pkg/sync`. `applyOverlay` in `pkg/sync/sync.go` builds its own `materialRecord` and must copy `AuthoredBytes` too, or every overlay record's filesystem-mode lock hash becomes the digest of an empty manifest; no existing test pins an overlay record's lock hash, so TEST-7 adds one.
- **Adding an `extends:` child to the reference fixture changes what every existing equivalence assertion compares.** `assertTreesEqual`, `artifactKeys`, and `assertLockArtifactsEqual` in `test/integration/sync_equivalence_test.go` all take the child in, and the lock comparison is the one that fails against today's code. Other test files read the same fixture; TEST-7 item 4 names them and reconciles them in the same commit. A tree divergence the child surfaces under `assertTreesEqual` is a §13.11.3 defect; the assertion stays as written.
- **Dotfiles are hashed today, and an ignore feature added later moves every stored hash it filters.** The hidden-directory skip runs in artifact discovery only (`walkLayer` in `pkg/registry/filesystem/walk.go` and in `pkg/registry/ingest/ingest.go`); `captureResources` and ingest's resource walk have no hidden check, so `.DS_Store`, an editor swap file, and a `.claude/` directory inside a package are bundled resources and are in the digest. Any future ignore mechanism filters at authoring time, before the bytes reach a registry, or it is a second §4.7.6 migration.
- **The SDK overlay loaders are a third implementation of the resource set and of discovery, and they compute no digest.** `sdks/podium-py/podium/_overlay.py` and `sdks/podium-ts/src/overlay.ts` walk a §6.4 overlay with their own code, which neither stops at a nested package nor skips a dot-directory in discovery; CODE-7 aligns them and TEST-9 pins them. They are outside TEST-8's two-walk comparison because they produce no `content_hash`.
- **The digest's resource set has two independent implementations, they already disagree on one file, and SPEC-4's membership sentence is what both conform to.** `captureResources` in `pkg/registry/filesystem/walk.go` (a `filepath.WalkDir` with `filepath.Rel` and `filepath.ToSlash`) and the `fs.WalkDir` in ingest's `loadOne` (`strings.TrimPrefix(p, dir+"/")`) agree on path form and on every membership rule but one: ingest drops a file named `SKILL.md` at any depth inside a skill package, while the filesystem walk drops only the package root's, so a skill carrying `references/SKILL.md` gets two different digests today. CODE-6 moves ingest onto the root rule, and nothing pins that the two walks agree until TEST-8 does. TEST-8 compares the two maps over one tree; a change to one walk without the other is a §4.7.6 disagreement between a filesystem-source consumer and the registry. Under CODE-5 the same two loaders are the two writers of `AuthoredBytes`, and TEST-8's digest comparison is what catches either one leaving it unset.
- **A non-ASCII filename can arrive as different bytes from different filesystems, and the pin makes those two distinct resources by definition.** Paths are framed and ordered as raw UTF-8 bytes with no normal-form conversion, so `café.md` in NFC and in NFD are two resources with two digests. That is the existing behavior and the one SPEC-4 states; a report that two authors' identical packages hash differently is answered by the authoring filesystem rather than by a normalization step in the composer, because a normalization step moves every stored hash that carries such a path.
- **A leading domain-separation tag added later is itself a full migration and labels nothing.** A tag sits inside the SHA-256 input, so it changes every stored value without making any stored `sha256:<hex>` say which scheme produced it; the Decisions section records why the serialization opens with none. Do not add one as a cheap forward-compatibility measure during implementation.

## Current state and the gap

### The digest is a function of the concatenation of the parts

`version.CanonicalContentHash` (`pkg/version/version.go`) composes the artifact's `ARTIFACT.md` bytes, its `SKILL.md` bytes, and each bundled resource's path and body as adjacent parts, and `version.ContentHash` (`pkg/version/version.go`) writes every part into one SHA-256 stream with no delimiter and no length prefix. Any re-partition of the same byte sequence therefore collides. A resource named `ab` with body `c` hashes the same as one named `a` with body `bc`, and a manifest and `SKILL.md` split at a different offset hash the same: `CanonicalContentHash("AB", "C", nil)` and `CanonicalContentHash("A", "BC", nil)` are both `sha256("ABC")`, `b5d4045c3f466fa91fe2cc6abe79232a1a57cdf104f7a26e716e0a1e2789df78`.

### Many paths depend on the value

It keys ingest immutability (`pkg/registry/ingest/ingest.go`, `pkg/store/sqlite.go`, §7), it is the §7.5.3 lock's recorded hash (`pkg/sync/sync.go`), it resolves `@sha256:` pins (`pkg/registry/core/core.go`, `pkg/registry/ingest/ingest.go`), it keys the §6.5 content cache (`cmd/podium-mcp/main.go`), and it is the §6.6 step-2 delivery gate (`cmd/podium-mcp/main.go`).

The exposure is not confined to an author colliding with their own artifact. Signing does not contain it: the envelope is produced over the ingest-time hash (`pkg/registry/ingest/ingest.go`) and verified over the served hash (`cmd/podium-mcp/main.go`), so a delivery that moves a boundary between `SKILL.md` and the first resource, or between a resource path and its body, arrives under an unchanged digest carrying a valid signature from the legitimate signer. The same holds for an `@sha256:` pin and for a committed lock entry: each of those is an independent attestation over a value that does not bind the bytes it names.

The §6.6 step-2 gate is a weaker case than its own doc comment claims. Against a tampering registry response on an unsigned sub-threshold artifact the gate gives nothing either way, because the same party supplies both the bytes and `resp.ContentHash` and can send a matching digest with no collision required. Injectivity is what the independently attested sites need; the gate is where the recomputation happens.

### The spec constrains none of it

§4.7.6 says only that `content_hash` is the SHA-256 of the canonicalized manifest plus bundled resources. `grep -rn "canonicaliz" spec/` returns that one line, and the word is never defined. §6.6 step 2 mandates a content-hash match without saying what is recomputed. The composition is pinned only by a unit test that says the spec fixes neither the slot order nor the resource order (`pkg/version/version_test.go`), which inverts the rule that a test encodes a spec requirement. §8 shows the spec states a composition when it means to, in the audit chain's `event_hash = sha256(event_body || prev_event_hash)`.

Proposal 0025 deliberately deferred this as a §4.7.6 question with its own migration cost and recorded the ambiguity in its edge-case table.

### One site diverges from the canonical composition

The §6.4 workspace-overlay load path computes the served `content_hash` as the SHA-256 of the artifact bytes alone (`cmd/podium-mcp/main.go`) while the same record carries `SkillBytes` and `Resources` (`pkg/registry/filesystem/walk.go`) and the overlay materializes from both. The overlay response returns before the §6.6 pipeline, so nothing re-derives it, and the hash it caches under does not move when an overlay skill's `SKILL.md` or a bundled resource changes.

## Decisions

- **State the canonicalization normatively in §4.7.6 rather than leaving it to a unit test.** Every party that computes the value has to agree byte for byte, which is a spec obligation rather than an implementation preference.
- **Frame every part with an 8-byte big-endian length prefix, and keep the existing slot and resource order.** Length framing makes the serialization injective in one pass over the same inputs, it is stateable in one paragraph of spec text, and it needs no second digest pass and no delimiter that would have to be escaped out of resource paths and bodies.
- **Define the absent `SKILL.md` as a zero-length slot, with no presence tag.** An absent and an empty `SKILL.md` therefore hash alike, and no artifact loses a load over the distinction. The reasoning is stated once, in the `CanonicalContentHash` doc comment staged under CODE-1.
- **Open the serialization with no domain-separation tag.** A tag sits inside the SHA-256 input, so it changes the digest value without labelling it: a stored `sha256:<64 hex>` is opaque under either scheme, and telling a tagged digest from an untagged one takes a recomputation from the bytes or a stored label, neither of which a tag supplies. The substantive reason to decline it is that there is one composer and one comparison. `version.CanonicalContentHash`'s non-test callers are `contentHashOf` (`pkg/registry/ingest/ingest.go`), `contentHashFor` (`pkg/sync/sync.go`), and `verifyContentHash` (`cmd/podium-mcp/main.go`), and every one of them computes the artifact content hash for the same comparison. Every other SHA-256 in the tree hashes a different thing and is never compared against an artifact content hash: `resourceRefsFor` (`ingest.go`) digests one raw resource body, which `cmd/podium-mcp/large_resources.go` checks against the body it fetched; `ManifestBodyKey` (`pkg/registry/core/core.go`) digests the raw canonical manifest document; the audit chain (`pkg/audit/audit.go`, `file.go`, `endpoint.go`) digests a canonical body plus the previous hash; `digest` in `pkg/sync/render.go` digests one rendered file; and the PKCE and HMAC uses are not content digests at all. The one shared index, `ResolveResourceOwner` (`core.go`), matches an `/objects/{key}` key against resource hashes and manifest-body keys, both raw-blob digests, and never against a row's `ContentHash`. The one preimage overlap that exists today is that the unframed `CanonicalContentHash(artifactBytes, nil, nil)` degenerates to `sha256(artifactBytes)`, and `CanonicalManifestDoc` returns exactly those bytes for a non-skill artifact, so `ManifestBodyKey` of an oversized non-skill manifest with no bundled resources equals its content hash; the framing removes that coincidence on its own, because it prefixes every part with its length. The "add it now, it is the last cheap moment" argument is circular, because the moment is a cost only if the tag has a use. For a future partial change to the canonicalization a tag makes the rewrite larger rather than smaller: the rewrite is store-wide, no code path or operator inspects an individual digest to decide what to rewrite, and a tag added later is itself a full migration that still labels nothing. The signing layer is a separate concern: `sign.Provider.Sign` takes an opaque `alg:hex` string and signs the decoded bytes with no purpose context, both the artifact content hash (ingest's `req.Signer` branch) and the audit chain head (`pkg/audit/anchor.go`) feed it, and a tag inside `CanonicalContentHash` would not reach the chain head; that cross-purpose gap is out of scope here and belongs to a separate proposal that binds a purpose into the signed message across every provider, since both the artifact content hash and the audit chain head reach `sign.Provider.Sign` as bare digests. The keyed encoding considered as the alternative to positional framing is recorded as rejected in Non-goals.
- **Delete the exported variadic `version.ContentHash`.** A helper whose contract is "concatenate these parts and hash them" is the defect itself, and it has no non-test caller outside `CanonicalContentHash` after proposal 0025 moved the §6.6 gate onto the shared function. Removing it means no caller can produce an unframed digest. Pre-1.0, a library-surface removal lands in a MINOR bump with every caller updated.
- **Move the §6.4 overlay path onto `version.CanonicalContentHash` in the same change, and stop the overlay writing the content cache.** §2.2 gives one behavioral surface across deployment modes, and a second composer would both contradict §4.7.6 and silently keep the old algorithm after the fix. The canonical key is one a registry-served load of the same package produces, and §6.5 maps a content hash to the bytes it names, so that bucket takes one writer. The overlay's write has no reader on the overlay's own path, so removing it costs nothing there.
- **Hash the authored `ARTIFACT.md` bytes in every mode, and repair the filesystem-source sync rather than redefine slot one as the merged form.** Ingest (`contentHashOf`, `pkg/registry/ingest/ingest.go`) and the §6.6 check (`verifyContentHash`, `cmd/podium-mcp/main.go`) already hash the bytes the author wrote, which are also the bytes git stores. The filesystem-source sync is the one party that does not: `filesystemRecords` (`pkg/sync/sync.go`) walks with `ResolveExtends: true`, `resolveExtends` (`pkg/registry/filesystem/extends.go`) overwrites the record's `ArtifactBytes` with `manifest.SerializeMerged` output, and `contentHashFor` hashes that. CODE-5 keeps the merged form where materialization needs it and gives the digest the authored form. Defining the digest over the merged re-serialization instead was considered and rejected on two grounds. First, the merged form is not a property of the artifact alone: an unpinned `extends:` resolves to the parent's latest non-deprecated version at the child's ingest (`resolveExtendsPin`, `pkg/registry/ingest/ingest.go`), so a parent version bump changes the merged bytes of a byte-identical child, and the next routine reingest of that child would arrive under a new hash for the same `(artifact_id, version)` and fail `ingest.immutable_violation` at the switch where a same-hash reingest is idempotent and a differing one is a conflict. Second, the merged bytes are `yaml.Marshal` output over the `manifest.Artifact` struct (`SerializeArtifact` in `pkg/manifest/merge.go`, called by `SerializeMerged` in `pkg/manifest/merge_serialize.go`), so adding one frontmatter field to the struct, reordering its fields, or bumping `gopkg.in/yaml.v3` moves every inheriting artifact's identity in every registry with no artifact having changed, and nothing in the suite would see it. The authored bytes carry neither dependency. The cost is that a filesystem-source lock entry for a child no longer moves when only its parent changed; CODE-5's closing paragraph states the mechanism and the edge-case table records where it is observable. For the same reason §4.7.6 is not future-proofed against the answers to the hidden-parent question that would move hashes: defining slot one as the authored bytes with the parent reference removed turns the canonical form from bytes into a YAML round-trip and would force §4.7.6 to specify a YAML canonicalization, which is the dependency the merged form was rejected for. Slot one stays the authored bytes as staged, and OQ-4 records which answers to that question are hash-neutral.
- **Pin the digest's inputs in §4.7.6 as well as its framing: the resource set, the byte-exactness of every part, and the full-bytes body of a resource held in object storage.** The framing paragraph fixes how the parts are combined and says nothing about which files are parts or which bytes each part carries, and that is where the next recomputation most plausibly comes from. Most future changes to the digest arrive as answers to an ambiguity the spec leaves open: an ignore rule for `.DS_Store` after a report that a stray file changed an artifact's hash, NFC normalization of paths after a report that a non-ASCII filename hashes differently on two machines, CRLF normalization after a Windows checkout, a hash that skips a resource above the inline cutoff because the row no longer carries its bytes. Each of those answers is a one-line tidy-up in the code and moves every stored hash it touches, which is this proposal's migration over again. Stating the current behavior converts each such tidy-up into a visible spec break that needs a proposal and a stored-value migration of its own. The sentences cost no implementation beyond CODE-6, which aligns ingest's walk to the subdirectory-`SKILL.md` clause, and SPEC-4's rationale carries the code citations for each. An ignore mechanism, if one is ever wanted, filters at authoring time, before the bytes reach a registry or a lock, because a filter applied at ingest or at recomputation changes the digest of every stored artifact that carries a filtered file.
- **Take the clean break.** Pre-1.0 policy forbids the shim, and the wire carries no place to negotiate, since the §6.6 gate recomputes and compares with no opt-out.
- **Migrate the stored rows inside the registry, on the first start of the new binary, rather than by a documented deletion and re-ingest or by a separate command.** The break is in persisted data rather than in an interface: every stored `(artifact_id, semver, content_hash)` triple, every `@sha256:` pin recorded against one, every signature envelope, and every committed `sync.lock` entry carries a value nothing recomputes. The registry retains every input the digest covers, since `ManifestRecord.Frontmatter` is the verbatim `ARTIFACT.md`, `SkillRaw` the verbatim `SKILL.md`, and each resource body is inline below the cutoff or in object storage above it at a key this change does not move (`pkg/store/store.go`, `ManifestRecord` and `ResourceRef`), so the pass recomputes from stored bytes and re-ingests nothing, and it rehashes an `extends:` child over the pre-merge bytes SPEC-1 names because those are the bytes the row holds. The rebuild it replaces had to delete the tenant's `dependencies` rows as well, because nothing removes a §4.7.3 edge when a manifest row is deleted and the table carries no unique constraint (`pkg/store/sqlite.go`, `pkg/store/postgres.go`, the `dependencies` DDL), so a skipped step silently duplicated every edge; and `podium layer reingest` reaches only the version each artifact directory currently declares, so the rebuild could not restore any earlier version at all. The pass runs in the serving process because that process already holds the store, the object store, the signing key, the audit sink, the image, and the mounted volumes; an earlier draft staged an off-server `podium admin rehash`, and Non-goals records why it was dropped. Schema migration on startup (`applySchema` on each backend) is the precedent for a start that changes the store. The pass is migration code that a later release deletes once no deployment holds a pre-upgrade row, which is what distinguishes it from the dual code path pre-1.0 policy forbids: it computes the new digest only, and its one use of the old composition is a check that a row is unmigrated.
- **Leave the object store alone.** It is keyed per blob: each bundled resource by the SHA-256 of its body and each oversized manifest body by its own key, and `/objects/{content_hash}` resolves those two families. No object is re-keyed or re-uploaded.
- **Name the consumer-side cache action alongside the migration.** The §6.5 pair is a resolution index keyed by `(id, version)` plus a content cache keyed by the hash that index returns, so a consumer never looks a bucket up by a hash it recomputed and the caches do not self-heal on an upgrade. DOC-1 item 4 is the single statement of which cache modes the resulting `materialize.content_hash_mismatch` reaches and what the operator clears.

## Proposed solution

### CODE-1: frame the parts, and delete the unframed variadic helper

In `pkg/version/version.go`, `CanonicalContentHash` computes the digest itself over framed parts, and `ContentHash` is removed:

```go
// CanonicalContentHash returns the §4.7.6 content hash of one artifact: the
// SHA-256 digest over the framed manifest bytes, the framed SKILL.md bytes, and
// each bundled resource's framed path and framed body in ascending path order.
// A framed value is its length as an unsigned 64-bit big-endian integer
// followed by its bytes. The digest carries no "sha256:" prefix; a caller that
// stores or serves the value adds one.
//
// The framing is what makes the serialization injective. Without it the digest
// is a function of the concatenation of the parts, so a byte moved across a
// part boundary leaves it unchanged and a resource named "ab" with body "c"
// hashes the same as one named "a" with body "bc". Every place the digest
// stands in for the artifact under an independent attestation then stops
// binding the bytes: the §4.7.9 signature envelope is produced over the hash at
// ingest and verified over the served hash, so a re-partitioned delivery would
// carry a valid signature from the legitimate signer; an @sha256: pin resolves
// against the stored value; and the §7.5.3 lock records it. The §6.6 step-2
// gate is where a consumer recomputes this value from the served bytes.
//
// It also exists so the registry and the filesystem consumer cannot compute the
// hash differently. They did: the filesystem path hashed SKILL.md instead of
// the manifest for a skill, so a frontmatter-only edit left the lock's
// content_hash unmoved while the materialized output changed.
//
// An absent SKILL.md frames a zero-length value, so an absent and an empty
// SKILL.md hash alike. That is deliberate: ingest passes a nil SKILL.md slot
// while the consumer passes the wire's omitempty skill_raw as a non-nil empty
// slice for the same artifact, and manifest parsing refuses input with no
// frontmatter, so no stored artifact carries a zero-byte SKILL.md.
func CanonicalContentHash(artifactBytes, skillBytes []byte, resources map[string][]byte) string {
	h := sha256.New()
	writeFramed(h, artifactBytes)
	writeFramed(h, skillBytes)
	keys := make([]string, 0, len(resources))
	for k := range resources {
		keys = append(keys, k)
	}
	sort.Strings(keys)
	for _, k := range keys {
		writeFramed(h, []byte(k))
		writeFramed(h, resources[k])
	}
	return hex.EncodeToString(h.Sum(nil))
}

// writeFramed writes v's length as an unsigned 64-bit big-endian integer
// followed by v itself (§4.7.6). A hash never fails a write.
func writeFramed(w io.Writer, v []byte) {
	var n [8]byte
	binary.BigEndian.PutUint64(n[:], uint64(len(v)))
	_, _ = w.Write(n[:])
	_, _ = w.Write(v)
}
```

`sort.Strings` gives byte-wise lexicographic order over the UTF-8 path bytes, which is the order SPEC-1 states. The file's imports gain `encoding/binary` and `io`; `crypto/sha256` and `encoding/hex` are already present and stay.

Deleting the exported `ContentHash` is the point of the change rather than a tidy-up: an exported "concatenate these parts and hash them" helper lets any caller reconstruct the unframed digest. Every remaining caller is a test, enumerated in TEST-2, and every one of them builds an expected `content_hash` that the framing changes, so those sites are owed a rewrite with or without the deletion.

### CODE-3: a compare-and-swap rewrite of one stored content hash, and a data-migration marker

The change lands on the `store.Store` interface in `pkg/store/store.go`, which is the §9.1 `RegistryStore` SPI. `RehashManifest`, `ListManifestsIncludingDeleted`, `DataMigrationApplied`, and `SetDataMigrationApplied` are added beside `PutManifest`, `GetManifest`, and `ListManifests`, and each backend implements them: `pkg/store/sqlite.go`, `pkg/store/postgres.go`, and `pkg/store/memory.go`. `storetest.FaultStore` embeds `store.Store` (`pkg/store/storetest/faultstore.go`) and inherits them without an edit.

```go
// RehashManifest replaces the content_hash and signature of one manifest
// row, including a soft-deleted one, only when the stored content_hash
// equals oldHash and, when oldHash equals newHash, only when the stored
// signature is empty. It returns ErrNotFound when no row exists for the
// key and ErrImmutableViolation when either condition fails. The second
// condition makes a call that only attaches a first signature a
// compare-and-swap as well, so two replicas cannot both sign one row. It is the
// only write to a stored content_hash after PutManifest, and it exists for
// the §4.7.6 migration: PutManifest is the immutability anchor and refuses
// a differing hash for an existing key, so no ingest path can repair a
// stored value. The compare-and-swap keeps a concurrent ingest, or the
// same pass on a peer replica, from overwriting a hash it did not read.
RehashManifest(ctx context.Context, tenantID, artifactID, version, oldHash, newHash, signature string) error
// ListManifestsIncludingDeleted is ListManifests without the deleted_at
// filter, so a migration reaches the rows a restored layer would serve.
ListManifestsIncludingDeleted(ctx context.Context, tenantID string) ([]ManifestRecord, error)
// DataMigrationApplied reports whether the named one-time rewrite of
// stored values has completed against this store. The marker is global
// to the store rather than per tenant.
DataMigrationApplied(ctx context.Context, name string) (bool, error)
// SetDataMigrationApplied records (applied true) or removes (applied
// false) the named marker. Both directions are idempotent, so replicas
// that finish the same pass together both succeed. The pass sets it.
// podium admin migrate-to-standard, which copies rows another store
// computed, removes it on the target so the target's next start
// rewrites what it copied.
SetDataMigrationApplied(ctx context.Context, name string, applied bool) error
```

`PutManifest` is the immutability anchor on every backend: an `INSERT ... ON CONFLICT DO NOTHING` followed by a read-back that returns `ErrImmutableViolation` on a differing hash (`pkg/store/sqlite.go` and `pkg/store/postgres.go`, `PutManifest`; `pkg/store/memory.go`, `PutManifest`). `RehashManifest` is one `UPDATE manifests SET content_hash = ?, signature = ? WHERE tenant_id = ? AND artifact_id = ? AND version = ? AND content_hash = ?` on the SQL backends, with the row count distinguishing a miss from a conflict through a read-back of the stored hash, and a guarded map write on memory. When `oldHash` equals `newHash` the statement gains `AND signature = ''`, and memory applies the same guard, which is what keeps CODE-4's replicas paragraph true for a row that needs only its first envelope. It carries no `deleted_at` condition. The CAS miss reuses `ErrImmutableViolation` rather than a new sentinel, because the refusal is the same invariant the anchor enforces and a new sentinel would carry a new `spi.Error` code. `ListManifestsIncludingDeleted` reuses each backend's `ListManifests` row scan with the `deleted_at IS NULL` clause dropped.

The marker is one additive table, `data_migrations(name TEXT PRIMARY KEY, applied_at <timestamp>)`, created by the same `CREATE TABLE IF NOT EXISTS` path every other table takes (`applySchema` in `pkg/store/sqlite.go`; on postgres it joins `sharedTableStmts` as `public.data_migrations`, beside `public.operator_grants`, because the per-org schemas hold tenant data and the marker is store-wide). `SetDataMigrationApplied` with `true` is an insert that does nothing on conflict, and with `false` it is a delete that succeeds when no row matches. `DataMigrationApplied` is an existence read, and memory keeps a guarded set. The table is additive under §13.4, so a previous binary ignores it. The one name this proposal writes is `content-hash-framing`, exported from `pkg/store/store.go` as `DataMigrationContentHashFraming` so that `internal/serverboot` and `cmd/podium` read one constant. `ResetForTest` in `pkg/store/postgres.go` truncates `public.tenants` and `public.vector_pending` today and gains `public.data_migrations`, because a marker that survived the test fixture's reset would make TEST-5's marker case fail on its second run against one database.

### CODE-4: the registry rehashes its stored rows on the first start

This section is the single statement of the pass: its gate, its classification, its writes, its failure policy, and its behavior across replicas. Every other section points here.

The pass is `rehashStoredHashes` in a new file, `internal/serverboot/rehash.go`, called from `run` in `internal/serverboot/serverboot.go`, which is the path both `podium serve` and `podium-server` take (`cmd/podium/serve.go`, `cmd/podium-server/main.go`). It runs in the serving process, so it uses that process's configuration, store, object store, signer, image, and mounted volumes, and nothing is reconstructed.

**Placement in `run`.** The call sits after `registrySignerFor` (`internal/serverboot/serverboot.go:891`) and before `bootstrapDeclaredLayers` (`internal/serverboot/serverboot.go:941`). When the early `net.Listen` failed, `run` does not call the pass: the call is guarded by `bindErr == nil` and by nothing else. `run` carries the bind failure in `bindErr` and returns it only at its end (`internal/serverboot/serverboot.go:806-821` and `:1630-1631`), so a rewrite in that start would let a second process, started while another still holds the port, rewrite and re-sign the store the first process is serving and then exit on the bind error. The rest of that start is today's `run`: the loader, the bootstrap ingest, whose hash conflicts are reported in `res.Conflicts` and fail nothing (`pkg/registry/ingest/ingest.go:767`, `:813`), and the bind error at the end. Step 6's check runs ahead of the loader whatever the bind outcome, so a start it refuses writes no key whether or not it bound, and a start it passes loads or generates a key under which no stored row was signed. A peer on the new version that binds while another runs the pass is the replicas case below, and a process on the previous version holding the port is the stop DOC-1 item 2 orders, which the pass does not detect. Removing the guard was considered and rejected: the guard costs one condition, and it is the one detector of a single-node upgrade started beside the previous process. The startup refusals that sit later in `run` than the pass (the webhook URL policy, the runtime keys, the identity guards, the OIDC prime, and tracing) are not brought forward: a start one of them refuses has already completed the pass, the rewritten store is the correct store for the new version, and DOC-1 item 2's stop of every previous-version process is what protects a consumer of the previous version. It precedes the bootstrap ingest because an ingest that meets a stored row still at the previous digest reports a conflict for that `(artifact_id, version)` (`pkg/registry/ingest/ingest.go`, the switch on `existing.ContentHash`), and it precedes the serve call, so no request reads a row mid-pass. **Gate.** The pass first calls `DataMigrationApplied(ctx, "content-hash-framing")`. When the marker is set it returns without reading a row. When the call errors, the start fails. A store with no rows runs an empty pass and sets the marker, so a registry created on this release never pays for a second look.

**Plan.** The pass enumerates every tenant `ListTenants` returns, and each tenant's rows through `ListManifestsIncludingDeleted`, and classifies every row before it writes any:

1. The resource bodies are assembled from `rec.Resources`: `ref.Inline` when it is non-nil, otherwise `Get` on the object store under `strings.TrimPrefix(ref.ContentHash, "sha256:")`, which is the key `persistResources` wrote it under (`pkg/registry/ingest/ingest.go`). The fetch is required because the digest covers a resource's full bytes, which SPEC-4's full-bytes sentence states and TEST-8 pins. A `Get` whose error satisfies `errors.Is(err, objectstore.ErrNotFound)`, which is how the memory, filesystem, and S3 providers report an absent key (`pkg/objectstore/objectstore.go`, `ErrNotFound`), classifies the row as `body_missing`: the store opened and answered, and the object is not there. A nil `Inline` with no object store, or a `Get` that fails with any other error, classifies the row as `body_unavailable`. `run` opens the object store through `openObjectStoreOrNil`, which logs and continues on an open failure, so an object store that cannot be opened surfaces here as `body_unavailable` rows rather than as a refusal to start. Each `Get` runs under a context derived from `run`'s with the deadline `cfg.migrationObjectReadTimeout` carries, which `LoadConfig` reads from `PODIUM_MIGRATION_OBJECT_READ_TIMEOUT` through `envPositiveDuration` with a 30-second default (`internal/serverboot/serverboot.go:295-301`), and from no `registry.yaml` key, as the §13.12 row SPEC-3 stages states, because `run`'s context is a `signal.NotifyContext` over `context.Background()` with no deadline (`internal/serverboot/serverboot.go:773`) and `S3.Get` sets none of its own (`pkg/objectstore/s3.go:129-150`). The pass does not rely on the provider to honor that context: the `Get` contract is silent on cancellation (`pkg/objectstore/objectstore.go:107-110`), `Filesystem.Get` discards its context and calls `os.ReadFile` (`pkg/objectstore/filesystem.go:88-96`), filesystem is the default object store (`internal/serverboot/serverboot.go:2114`), and the chart's filesystem volume is a claim every replica mounts, which a multi-node cluster with more than one replica mounts as ReadWriteMany (`deploy/helm/podium/values.yaml:144-147`), where a hung mount blocks a read indefinitely. The pass therefore calls every `Get` through `getWithDeadline`, an unexported helper in `internal/serverboot/rehash.go` whose only caller is the pass. It starts the provider's `Get` in a goroutine that sends the result on a channel buffered to one, and selects on that channel and on the deadline context's `Done`. When the result arrives first it returns the result unchanged, so `objectstore.ErrNotFound` still classifies as `body_missing`. When `Done` fires first it returns the context's error, which the pass treats as a failure other than `ErrNotFound`, and it abandons the goroutine, which sends into the buffer and exits whenever the provider returns and whose result nothing reads. The helper holds no state, so nothing sets or clears any. After the first `Get` whose deadline expires, which `getWithDeadline` reports as an error satisfying `errors.Is(err, context.DeadlineExceeded)`, the pass calls `Get` no more in that run and classifies every remaining row that needs an object-store read as `body_unavailable` without reading it, and the summary line counts those rows. An object store that stops answering therefore costs the plan one deadline rather than one per row. Because the pass calls `Get` no more after an expired deadline, at most one goroutine outlives a pass, and a read that never returns keeps that one goroutine and its file descriptor or connection for the life of the process, which the summary line's `body_unavailable` count and the logged row make visible to the operator. A `Get` that returns before its deadline with an error other than `objectstore.ErrNotFound`, such as an S3 `AccessDenied` or `InvalidObjectState`, which `S3.Get` returns as-is (`pkg/objectstore/s3.go:137-148`), or an `EACCES` or `EIO` that `Filesystem.Get` returns from `os.ReadFile` (`pkg/objectstore/filesystem.go:92-96`), classifies only the row whose object it read as `body_unavailable`, and the pass reads the next row's objects. The stop is confined to the expired deadline because that is the one failure that costs the deadline, and so the one the stall bound needs; stopping on a prompt error would make one unreadable object leave every externally backed row enumerated after it at the previous digest on every start, because `ListTenants` and `ListManifests` enumerate in a fixed order (`pkg/store/sqlite.go:233`, `:527`). The log line for a `body_unavailable` row names the object key and the error `Get` returned, so the operator can find the object.
2. The new value is `"sha256:" + version.CanonicalContentHash(rec.Frontmatter, rec.SkillRaw, resources)`, which is what `contentHashOf` computes at ingest for the same bytes.
3. Where a signer is configured and the row's stored signature is non-empty, the pass calls `provider.Verify(ctx, storedHash, storedSignature)` before any other classification. A row whose envelope does not verify is `signature_unverified` and is left untouched, whatever its stored hash. The envelope is the only evidence that the stored bytes are the bytes the registry signed: an actor with write access to the store can alter a row's bytes and recompute either digest over them, and cannot mint an envelope, so a rehash that re-signed such a row would turn a consumer's `materialize.signature_invalid` into an accepted load. `sign.RegistryManagedKey.Verify` rejects a differing non-empty `key_id` (`pkg/sign/registry_managed.go`), so an envelope minted under another key is refused by the same predicate; the pass cannot tell a rotated key from a forged envelope, and it rewrites neither.
4. A row whose stored hash equals the new value is `migrated` when its signature is non-empty or no signer is configured, and `unmigrated` when its signature is empty and a signer is configured, with the new value as both hashes, so the apply step mints its first envelope. Otherwise the stored hash is compared against the pre-framing digest of the same bytes, the SHA-256 over the unframed concatenation in the same slot order, computed by an unexported helper in `internal/serverboot/rehash.go`. A row that reproduces it is `unmigrated`. A row that reproduces neither value is `unreproducible` and is left untouched, because the bytes the registry holds do not produce the hash it serves. The helper is the tree's only use of the old composition, it lives outside `pkg/version` so TEST-2's check still holds, and it is deleted with the pass.
5. When no signer is configured and any `unmigrated` row carries a signature, the pass returns an error naming `PODIUM_SIGN` and those rows, and `run` returns it, so the registry refuses to start. The plan completes before any write, so the refusal leaves the store as it was and the marker unset. Rewriting such a row would strand its envelope over a hash the row no longer stores. The error also names `PODIUM_SIGN_KEY_PATH`, because an operator who turns signing on without pointing it at the key that signed those rows reaches step 6 next.
6. A signing key generated at this start is refused before it exists, and the pass itself carries no step-6 logic. The check is `refuseGeneratedSigningKey(ctx, st, signMode)`, an unexported function in `internal/serverboot/rehash.go` that `run` calls after `openStore` (`internal/serverboot/serverboot.go:832`) and immediately before `registrySignerFor` (`:891`), whatever the bind outcome. It returns an error naming `PODIUM_SIGN_KEY_PATH`, the resolved key path, and the first signed row it met by `(tenant, artifact_id, version)` when four conditions hold. They are evaluated in this order, so each read runs only when the earlier conditions hold: `registrySigningEnabled(signMode)` returns true, the helper `registrySignerFor` also calls; `os.Stat` on `registrySigningKeyPath(os.Getenv("PODIUM_SIGN_KEY_PATH"))` returns an error satisfying `errors.Is(err, fs.ErrNotExist)`, which is the condition under which `readOrCreateEd25519` generates (`internal/serverboot/audit_anchor.go:168-174`), and a symbolic link to an absent target counts as absent because both calls follow it; `DataMigrationApplied(ctx, store.DataMigrationContentHashFraming)` is false; and a row returned by `ListManifestsIncludingDeleted`, for a tenant `ListTenants` returns, carries a non-empty `Signature`, the enumeration stopping at the first such row. `run` returns the error unchanged, so no key is generated or written, no row is written, and the marker stays unset. A stat error other than absence makes the check return nil, and the loader then fails the start with the read error it returns today. An error from the path resolution, the marker read, or the enumeration fails the start, wrapped as `registry signing key: %w`. The check sets no state. The key file is written only by `readOrCreateEd25519` and by the operator, and nothing in the tree removes it. The marker is set only by the pass and removed only by `podium admin migrate-to-standard` on its target, as the migration paragraph below states. A row's `Signature` is set by ingest's `req.Signer` branch (`pkg/registry/ingest/ingest.go:785-786`), by the pass through `RehashManifest`, and by `pumpStore`'s copy (`cmd/podium/admin_migrate.go:358`), and it is removed only with its row, by the §8.4 purges. The predicate is the whole condition because a key generated at this start signed no stored row and `sign.RegistryManagedKey.Verify` rejects a differing `key_id` (`pkg/sign/registry_managed.go:97-110`). Every signed row would therefore classify `signature_unverified`, and the pass would set the marker and leave those rows at the previous digest even after the operator restored the key that signed them. The check reads no resource body and verifies no envelope. When the check does not fire and the key file is absent, the loader generates and writes a key as it does today, and no stored row carries a signature that the key could strand. When the marker is set, the check does not fire, and a lost key file is generated again as it is today; the pass does not run, so it strands nothing. Because a refused start writes no key, an operator retry, a supervisor restart, or a peer replica on a shared volume that starts with the same configuration is refused the same way, and a start whose listener could not bind reports this error ahead of the bind error. TEST-6 case 10, `TestRun_BindFailureStillRefusesAGeneratedKey`, and the generated-key arm of `test/e2e/boot_rehash_test.go` pin the check. The deployments that reach this step generate a key at start into a location that does not persist: a container run from either image with a writable home and no volume at the key path (`Dockerfile:62-71`, a distroless `nonroot` image; `deploy/Dockerfile`, whose `WORKDIR /home/podium` is writable), or a host whose key file was removed. The Helm chart does not reach it by setting `PODIUM_SIGN` alone: its container runs with `readOnlyRootFilesystem: true` (`deploy/helm/podium/values.yaml:123-125`, applied at `deploy/helm/podium/templates/deployment.yaml:37-38`) and mounts only the `objects` claim and the `runtimeKeys` secret (`deploy/helm/podium/templates/deployment.yaml:176-199`), so the default key path is not writable. Such a start against a store holding signed rows is refused here, and one against a store holding none fails at the loader's write, with `registry signing key:` and the write error, as `registrySignerFor` fails such a start today. Where the key that signed the rows exists, the operator points `PODIUM_SIGN_KEY_PATH` at it and starts again. Where it does not, because each container generated its own key into a home that was discarded, no key file verifies the rows and no start configuration clears both refusals: with `PODIUM_SIGN` unset step 5 refuses, and with no key file this step refuses. The route is a persistent key file that the loader reads rather than generates, which a start of the new binary with `PODIUM_SIGN=registry-key` against a store holding no signed row, such as `podium serve --standalone` with `PODIUM_REGISTRY_STORE=sqlite` and `PODIUM_SQLITE_PATH` naming a new database file outside the deployment's store directory, writes at `PODIUM_SIGN_KEY_PATH`. Both variables are required. `--standalone` only sets `PODIUM_STANDALONE` (`cmd/podium/serve.go:94-99`) and does not select the backend: `openStore` switches on the store type and reads `PODIUM_SQLITE_PATH` only in its `sqlite` arm (`internal/serverboot/serverboot.go:2449-2462`), and the store type is `PODIUM_REGISTRY_STORE` (`:2111`) or, when that variable is unset, a `registry.yaml` `store.type` (`internal/serverboot/yaml_config.go:363-365`). A start that inherits a deployment's `PODIUM_REGISTRY_STORE=postgres`, which is how the Helm chart and a `podium-server` container deployment select their store (`deploy/helm/podium/templates/deployment.yaml:85`), or that leaves the variable unset beside a `registry.yaml` declaring `store.type: postgres`, opens the store holding the rows signed under the lost key, is refused by this step, and writes no key file. A set `PODIUM_REGISTRY_STORE=sqlite` overrides both. The path variable must name that new file: `LoadConfig` reads it from the environment (`internal/serverboot/serverboot.go:2112`), a set value takes precedence over a `registry.yaml` `store.sqlite_path` because the file key fills only an empty value (`internal/serverboot/yaml_config.go:366-367`), and an empty value resolves to that file key or to `~/.podium/standalone/podium.db` (`internal/serverboot/serverboot.go:2304-2307`), which on a standalone host whose key file was removed is the store holding the rows signed under the lost key, so that start is refused by this step and writes no key file. A start against the real store with that file then leaves every row signed under a lost key as `signature_unverified`, rewrites the others, sets the marker, and serves; those rows fail closed at the consumer and are repaired as the paragraph on untouched rows states. A key file that exists and holds a different key is not this step's case: the loader generated nothing, the rows stay `signature_unverified`, and the paragraph on untouched rows states the route.

The pass cannot distinguish an envelope an actor with store write access removed from a row that was never signed, because the store records no history of a row's signature. That limit is accepted, and the edge-case table records it.

**Apply.** For each `unmigrated` row: when a signer is configured the row is signed over the new value exactly as ingest does at its `req.Signer != nil` branch, and the row is written through `RehashManifest(ctx, tenant, id, version, rec.ContentHash, newHash, signature)`. After a write that returns nil for a row the pass signed, it appends `artifact.signed` to the audit sink: an `audit.Event` with the `system` caller, an empty trace id, the artifact id as the target, and `version` and the new `content_hash` as the base context, passed through the redaction below and through `scrubber.ScrubEvent`, which is the event `ingestAuditEmitter` builds. A nil sink makes the call a no-op, and no event is appended for a row that was not signed or not written. When `Append` returns an error the pass stops appending for the rest of the run, keeps rewriting, and logs the number of events it did not append. It stops rather than retrying per row because an `http(s)` audit destination is an `EndpointSink`, whose `Append` is a synchronous POST with a ten-second timeout (`pkg/audit/endpoint.go`), so an unreachable endpoint would otherwise cost that timeout for every re-signed row while nothing answers the health probes. The pass touches no `dependencies` row and no object, and it re-ingests nothing.

The redaction is `ArtifactEventRedactor(mr store.ManifestRecord) func(base map[string]string) map[string]string`, a new exported function in `pkg/registry/ingest` extracted from the `redacted` closure in ingest's emit block. It derives the row's redaction key set once, collects `manifest.FrontmatterFields(mr.Frontmatter, keys)` once, and returns a function that merges those fields into a base context without overwriting a structural key and returns `audit.RedactFields(base, keys)`. The key set is `mr.AuditRedact` when it is non-empty, and otherwise the `AuditRedact` of `manifest.ParseArtifact(mr.Frontmatter)` when that parses, because the SQL backends store no `audit_redact` column and a row read back from them carries an empty `AuditRedact`. A frontmatter that does not parse yields no key set and no added field. Ingest's closure is replaced by one call to the function per artifact, so its `artifact.published`, `artifact.deprecated`, and `artifact.signed` emits keep their contexts, and the function's callers are `pkg/registry/ingest/ingest.go` and `internal/serverboot/rehash.go`. Neither applies a directive an `extends:` child inherits, which predates this change.

**Failure policy.** The table is the single statement of what each outcome does to the start and to the marker. "Retry" means the marker stays unset and the next start runs the pass again, which skips every row already `migrated`.

| Outcome | Start | Row | Marker |
|:--|:--|:--|:--|
| `DataMigrationApplied`, `ListTenants`, or `ListManifestsIncludingDeleted` returns an error | Fails | No write | Unset |
| The early listener could not bind | `run` does not call the pass. Step 6's check still runs ahead of the loader and fails the start when it fires; otherwise `run` fails at its end with the bind error, as it does today | No write by the pass | As it was |
| A signed `unmigrated` row and no signer (step 5) | Fails, naming `PODIUM_SIGN` and `PODIUM_SIGN_KEY_PATH` | No write | Unset |
| Signing on, no key file, marker unset, and any stored row signed (step 6) | Fails before the loader, naming `PODIUM_SIGN_KEY_PATH`; no key is generated or written, so the next start with the same configuration fails the same way, whether or not it binds | No write | Unset |
| `body_unavailable` (step 1): a row whose `Get` failed before its deadline with an error other than `ErrNotFound`, a row with a nil `Inline` and no object store, and every remaining row that needs an object-store read after the first `Get` that exceeds `PODIUM_MIGRATION_OBJECT_READ_TIMEOUT` | Proceeds | Untouched, logged with the object key and the error | Unset: retry |
| `body_missing` (step 1) | Proceeds | Untouched, logged | Set, unless the wrong-root guard below holds it back |
| The signer returns an error for a row, or `RehashManifest` returns an error other than the two below | Proceeds | Untouched, logged | Unset: retry |
| `RehashManifest` returns `ErrImmutableViolation` or `ErrNotFound` | Proceeds | As the peer replica or the retention purge left it | Set |
| `signature_unverified` or `unreproducible` | Proceeds | Untouched, logged | Set |
| `SetDataMigrationApplied` returns an error | Proceeds, logged | Rewritten rows stand | Unset: retry |
| The audit sink's `Append` returns an error | Proceeds | Rewritten and re-signed; no further event is appended in this run, and the count is logged | Unaffected |

The pass logs one summary line with the counts of rows rewritten, already migrated, `signature_unverified`, `unreproducible`, `body_missing`, `body_unavailable`, classified `body_unavailable` without a read, in conflict, and in error, and of events not appended, and one line per untouched row naming its `(tenant, artifact_id, version)` and its class, through the standard `log` package `run` already uses. A `signature_unverified`, `unreproducible`, or `body_missing` row does not hold the marker back, because no later pass could clear it and an unset marker would make every later start re-read every resource body in the store. The one exception is the wrong-root guard below, which treats every `body_missing` row as `body_unavailable` when no object-store read in the pass returned a body; SPEC-3 states the same predicate.

**Rows the pass leaves untouched.** A row still at the pre-framing hash fails every load on an upgraded consumer. The observable code depends on the row. An unsigned or validly signed row, and an `unreproducible` row, fail the §6.6 step-2 check with `materialize.content_hash_mismatch`. A `body_missing` or `body_unavailable` row fails before step 2, as it did on the previous binary: when its object is missing the consumer's resource fetch fails with `materialize.fetch_failed` (`cmd/podium-mcp/large_resources.go`, `cmd/podium-mcp/main.go`), and when the row's `Inline` is nil and the registry has no object store the registry answers `registry.unavailable` (`pkg/registry/server/server.go`, `inlineBytes`). For a `signature_unverified` row the consumer's §4.7.9 policy decides, because the load path runs `enforceSignaturePolicy` before `verifyContentHash` (`cmd/podium-mcp/main.go`): where the policy covers the artifact's sensitivity the load fails with `materialize.signature_invalid` at either stored hash, and below that threshold or with verification off a row at the pre-framing hash fails with `materialize.content_hash_mismatch` while a row already at the new hash loads. That is the exposure the row carries on the previous binary, and the pass neither widens nor narrows it. The repairs are these. For `body_unavailable`, the operator makes the object the logged line names readable and restarts, and the pass runs again because the marker is unset: a store-wide failure is repaired by restoring the object-store configuration, and a failure confined to one object by correcting its permission, ACL, or key grant, by restoring it from an archive storage class, or, for a read that exceeds the deadline, by raising `PODIUM_MIGRATION_OBJECT_READ_TIMEOUT`. An object that cannot be made readable is deleted from the object store by the operator, after which its `Get` reports `objectstore.ErrNotFound`, the row classifies as `body_missing`, and, while another read in the pass returns a body, it no longer holds the marker back; the row is then repaired as a `body_missing` row. Until one of those repairs, every start re-reads the bodies the plan needs and the marker stays unset, which the summary line's `body_unavailable` count shows on each start. Publishing a new version does not clear the state, because the unreadable row is still enumerated. For `body_missing`, `unreproducible`, and `signature_unverified`, the author publishes a new version; restoring a missing object makes the row loadable on a consumer of the previous version only, because the row stays at the previous digest. The store-wide states have the backup DOC-1 item 2 takes as their route, because it holds no marker and a start against the restored store runs the pass again: a key file that holds a key other than the one that signed the rows, which leaves every signed row `signature_unverified`. The summary line is where an operator sees it.

**Wrong-root guard.** An object store opened at the wrong root or bucket answers every `Get` with not-found, which no single row can tell from one lost object. The pass therefore counts the object-store reads that returned a body. When the plan holds a `body_missing` row and no object-store read in the pass returned a body, every `body_missing` row is treated as `body_unavailable`: the marker stays unset, the log line names the object store's configured root or bucket, and the next start retries. A store whose externally held bodies are all lost takes the same path, and its exit is restoring an object or the §8.4 purge of the affected rows. A lost key file is not among them: step 6 refuses that start with no row, no marker, and no key file written, every later start with the same configuration is refused the same way, and step 6 states the route. Apart from the marker clear `podium admin migrate-to-standard` performs on its target, which the migration paragraph below states, nothing else re-triggers the pass, and Non-goals records that.

**Replicas.** Replicas that start together each find the marker unset and each run the pass. The compare-and-swap makes the writes safe for every class, including the row that needs only its first envelope, because CODE-3's statement also requires an empty stored signature when the two hashes are equal: one replica's write succeeds, the other's returns `ErrImmutableViolation` and is counted as a conflict, and only the replica whose write succeeded appends the event. Both set the marker, which is idempotent. No advisory lock is added. The pass has no reach over a registry process on the previous binary: a row such a process ingests after the pass enumerated its tenant, or after the marker is set, stays at the previous digest and fails closed as the paragraph above states, which is why DOC-1 item 2 stops every such process first. The pass does not detect one.

**Start time.** `run` opens its listener early and serves late, so nothing answers `/healthz` or `/readyz` until the pass and the bootstrap ingest finish, and the plan reads every resource body in the store once. The Helm chart's liveness probe starts after five seconds with the kubelet's default period and threshold (`deploy/helm/podium/templates/deployment.yaml`), so without a startup probe a pass that outlasts that budget is killed, and because the plan writes nothing a killed plan makes no progress. CODE-8 adds the startup probe. An object store that stops answering costs the plan one `PODIUM_MIGRATION_OBJECT_READ_TIMEOUT` rather than one per row, including a filesystem object store on a hung mount whose provider ignores the deadline, as step 1 states, so a stalled endpoint does not by itself exhaust that budget. A pass killed during the apply step resumes on the next start, because every row already written classifies as `migrated`.

**IMPLEMENTOR'S CHOICE:** the wording of the log lines and of the step-5 and step-6 errors, subject to the summary carrying every count the failure-policy paragraph names, each untouched row being named with its `(tenant, artifact_id, version)` and class, a `body_unavailable` row read through `Get` also naming the object key and the error `Get` returned, the step-5 error naming `PODIUM_SIGN` and `PODIUM_SIGN_KEY_PATH`, and the step-6 error naming `PODIUM_SIGN_KEY_PATH`. How `rehashStoredHashes` receives its dependencies is also open, subject to it taking the store, the object store or nil, the per-read deadline, the `sign.Provider` or nil, the `audit.Sink` or nil, and the scrubber as values, and to `refuseGeneratedSigningKey` taking the store and the sign mode as values, so TEST-6 can pass a `store.Memory`, a wrapper embedding `store.Store`, an in-process object store, a provider whose `Sign` fails for one row, and a recording or failing sink without touching the environment.

**The standalone-to-standard migration.** `podium admin migrate-to-standard` is the tree's other writer of manifest rows: `pumpStore` copies each source row into the target through `PutManifest` with its `content_hash` and `signature` unchanged (`cmd/podium/admin_migrate.go:351-378`). A target whose marker is set, which a completed pass sets even over an empty store, would never rewrite rows copied in afterwards at the previous digest. When the plan holds at least one manifest row, `pumpStore` therefore calls `SetDataMigrationApplied(ctx, store.DataMigrationContentHashFraming, false)` on the target before its first `PutManifest`, and it fails the command with `clear data-migration marker: %w` when that call errors. It clears before writing, so a pump that fails partway leaves the target unmarked, and a re-run clears again. The clear is the command's only change: the order of `pumpStore`, `pumpObjects`, and the audit-log copy in `adminMigrateToStandard` (`cmd/podium/admin_migrate.go:169-216`) is unchanged, `--dry-run` returns before `pumpStore` (`cmd/podium/admin_migrate.go:157-160`) and changes nothing, and the source's marker is not read. A target whose store never started carries no marker, and the clear is a no-op there. A target that a registry started once before the command's first run, such as a Helm release installed ahead of the migration, carries the marker even when that start ingested nothing, and the clear lets the registry's next start rewrite the copied rows. The pass runs only at a start of `run`, so a registry that keeps running through the command never rewrites them.

The target's lifecycle follows one rule. No registry process runs on the target store while the command runs, so a target registry started before the command's first run and still running, such as a pre-installed Helm release, is stopped before that run. The target registry is started, or restarted when it was running before the command, only after a run of the command that exits 0. The target store is recreated empty before the command runs again when a run exits 1 with `put manifest <tenant>/<artifact_id>: ` wrapping `ErrImmutableViolation`, or when, at any point after the command's first run against it began, including while a run was in progress, a registry started on the target store or the source registry started on the new version. A re-run is idempotent only while the target holds each copied row at the hash the source holds, because `PutManifest` refuses a differing hash at a stored key with `ErrImmutableViolation` (`pkg/store/sqlite.go:355-356`), which the command reports as `put manifest <tenant>/<artifact_id>: ` and exit 1 (`cmd/podium/admin_migrate.go:359`, `:169-172`). A target that a registry of the new binary started before the first run can fail that condition on the first run: that start's ingest wrote rows at the framed digest, and the source, which has not started on the new version, holds the same keys at the previous digest. No start follows the first run in that case, so every re-run into that store exits 1 at the same row, and the immutability trigger recreates it. Any start of either registry between two runs can break the same condition, because the target's pass rewrites or leaves each copied row according to the target's objects and signing key, and the source's pass rewrites the source's rows independently. Reconciling the two in place needs a different sequence of starts for each way they diverge. A recreated target is a target that never started, so the next run is a first run: it copies every row as the source holds it, and the target's first start rewrites the rows the source holds at the previous digest and classifies the rows the source already rewrote as steps 3 and 4 state. The target's object store is not recreated. Every object is keyed by the SHA-256 of its body (`pkg/registry/ingest/ingest.go:1257-1282`), so a body already present at a key is the body the run copies there, and the filesystem provider's `Put` accepts the same body at an existing key (`pkg/objectstore/filesystem.go:64-69`). A run that fails with any error other than the immutability error while neither registry has started since the command's first run against the target began is re-run as it is. A run that fails after `pumpStore` copied some rows, followed by a start of the source on the new version, is not: the source's pass rewrites its rows to the new digest while the target holds the copies at the previous one, so the target store is recreated first. When the rule is not followed, a re-run fails at the first copied row the two stores hold at different hashes, and no layer config and no admin grant are copied, because `pumpStore` copies manifests first (`cmd/podium/admin_migrate.go:356-376`). A target started without a further run leaves the rows copied after its pass enumerated at the previous digest, and a target registry left running through the command serves every copied row at the previous digest until its next start; in both cases a consumer's load of those rows fails closed with `materialize.content_hash_mismatch`. The copied signed rows meet steps 3, 5, and 6 at the target's start, so the target reads the signing key that signed the source's rows; without that key, a consumer verifying those envelopes refuses them whether or not the pass runs. SPEC-3's staged §13.4 paragraph states the clear, the stop and start rule, and the recreation. The rule adds no code. A recreated target is the never-started target the existing migrate tests drive, and the store conformance suite pins the `ErrImmutableViolation` refusal (`pkg/store/storetest/storetest.go:212-220`). The existing tests that seed a source store directly need no edit, and the legacy DDL in `test/e2e/schema_forward_migration_test.go` gains no `data_migrations` table.

### CODE-5: the filesystem-source sync hashes the authored manifest

In `pkg/registry/filesystem/walk.go`, `ArtifactRecord` gains one field beside `ArtifactBytes`:

```go
// AuthoredBytes is ARTIFACT.md as read from disk. It equals ArtifactBytes
// until the extends: resolver overwrites ArtifactBytes with the merged,
// parent-hidden re-serialization (§4.6), after which the two differ for a
// child. Materialization reads ArtifactBytes; the §4.7.6 digest reads
// AuthoredBytes, because the digest is defined over the bytes as ingested
// and a merged serialization does not reproduce it. The store's
// ManifestRecord.Frontmatter and the wire's raw_frontmatter carry the same
// bytes on the registry side.
AuthoredBytes []byte
```

`loadArtifactRecord` sets `AuthoredBytes` and `ArtifactBytes` to the same slice for every record, and `resolveExtends` (`pkg/registry/filesystem/extends.go`) keeps its single assignment to `out.ArtifactBytes` and does not touch `AuthoredBytes`. Populating the field at load rather than capturing it in the resolver means it is non-nil for every record, so a composer reads it with no fallback to `ArtifactBytes` for a record that declared no `extends:`. Ingest does not go through `loadArtifactRecord`: `loadOne` in `pkg/registry/ingest/ingest.go` builds a `filesystem.ArtifactRecord` directly from an `fs.FS`, so it sets `AuthoredBytes` to the same bytes it assigns to `ArtifactBytes`. The field therefore has two writers, one per loader, and a composer that reads it is wrong the moment either loader is changed without the other, which is what TEST-8 item 2's digest comparison guards. The resolver's doc comment, which says it "rewrites the record's ArtifactBytes", gains the sentence that `AuthoredBytes` is left as loaded and why.

In `pkg/sync/sync.go`, `materialRecord` gains `AuthoredBytes []byte` with a comment naming it as the filesystem source's hashing input. `filesystemRecords` and `applyOverlay` copy `rec.AuthoredBytes` into it; the overlay walk (`pkg/overlay/overlay.go`) does not resolve `extends:`, so there the two fields are equal, and the copy exists so the overlay record's lock hash is a digest over its manifest rather than over nothing. The server-source record builder in `pkg/sync/server.go` copies the served frontmatter into `AuthoredBytes`, so `lockContentHash`'s fallback to `contentHashFor` keeps its current meaning for a server-source record: the registry's value is used verbatim when the response carries one, which §5 requires, and a response without one hashes the served bytes as it does today rather than a nil manifest. `contentHashFor` becomes

```go
// contentHashFor computes the §7.5.3 content_hash for a filesystem-source
// record over the authored ARTIFACT.md bytes rather than the merged form the
// extends: resolver writes into ArtifactBytes, so this consumer, ingest, and
// the §6.6 check hash the same bytes for an extends: child (§4.7.6). The
// record supplies the other slots as before: the SKILL.md bytes when the
// artifact carries one, and every bundled resource, inline and large alike.
// The result carries the spec's "sha256:<hex>" prefix, which
// CanonicalContentHash omits. spec: §4.7.6, §7.5.3, §14.11.
func contentHashFor(rec materialRecord) string {
	return "sha256:" + version.CanonicalContentHash(rec.AuthoredBytes, rec.SkillBytes, rec.Resources)
}
```

`lockContentHash`'s doc comment, which says a filesystem source's value "is computed from the served bytes", is reworded to say it is computed from the authored bytes. `version.CanonicalContentHash` stays the single composer; nothing in `pkg/sync` merges, re-serializes, or reads the walk's merged form for the digest.

The other composers that read a walk record move onto the same field in this step, so that `ArtifactBytes` feeds materialization only: `contentHashOf` in `pkg/registry/ingest/ingest.go`, whose records come from `loadOne`, which sets the field, and whose walk does not resolve `extends:`, so it hashes the same bytes before and after the change, and the CODE-2 overlay line in `cmd/podium-mcp/main.go`, whose overlay walk does not resolve `extends:` either; CODE-2's staged block is written against the record as it exists before this change and is rewritten here rather than there. The test records that feed these composers move onto `AuthoredBytes` in this deliverable's commit: the `contentHashFor` records in `pkg/sync/lock_content_hash_test.go`, the fixture guard in `TestRun_ServerSourceLockPinsRegistryContentHash`, and the overlay record TEST-3 builds in `cmd/podium-mcp/overlay_load_test.go`. After the change, `grep -rn "CanonicalContentHash(rec.ArtifactBytes" --include='*.go' .` returns nothing.

**IMPLEMENTOR'S CHOICE:** the test records the field addition touches beyond the ones named above. Every test record that feeds `contentHashFor`, `contentHashOf`, or the overlay composer sets `AuthoredBytes` in the commit that adds the field; a record that sets only `ArtifactBytes` hashes an empty manifest and is a defect.

The change carries one accepted cost. `Result.Changed` is `lockChanged(priorLock, lock)` (`pkg/sync/sync.go`), which compares the content hash recorded per `(artifact id, materialized path)` entry, and `cmd/podium/main.go` publishes it to a `kind: workspace` target's `publish` phase as `$PODIUM_CHANGED` (§7.5.2). With the lock hash over the authored bytes, a filesystem sync whose `extends:` child is byte-identical while its parent changed rewrites the child's materialized file and reports the child's entry unchanged. The edge-case table states where that is observable. It is reporting only: the materialized bytes are correct, and the repair would be a separate digest over the materialized output, which no proposal stages: proposal 0027's delivery hash is computed at serve time and is not written to the §7.5.3 lock, so it does not reach this case.

### CODE-6: ingest excludes only the package root's `SKILL.md`

The two resource walks disagree on one file today. `captureResources` in `pkg/registry/filesystem/walk.go:230-235` compares against `filepath.Join(dir, "SKILL.md")`, so it excludes the package root's `SKILL.md` and captures a `SKILL.md` in any subdirectory. The walk inside `loadOne` in `pkg/registry/ingest/ingest.go:1174-1175` compares `d.Name()`, so it excludes every file named `SKILL.md` at any depth. For a skill carrying `references/SKILL.md` the two maps differ, ingest's stored hash and a filesystem-source lock hash differ for the same package, and SPEC-2's clause that the parties agree on the digest for every package does not hold.

The change is in the ingest walk's file predicate: the skill arm compares the walk path against the package root's `SKILL.md`, in the form `p == joinPath(dir, "SKILL.md")`, the way the `ARTIFACT.md` arm above it already reaches only the root through `fsHasArtifactManifest`'s package boundary. `joinPath` is the file's own slash-path helper (`pkg/registry/ingest/ingest.go:1598`), and it is the expression the skill branch of `loadOne` already evaluates to read the file, so the predicate names the same path the read does and the file gains no import; hoisting that value into one variable both sites read is open to the implementor. The `ARTIFACT.md` arm keeps its base-name comparison, because a nested `ARTIFACT.md` is a package boundary the directory arm has already skipped.

The change moves the stored hash of a skill package carrying a `SKILL.md` below its root, because that file enters the resource set. It moves no other package's hash, and every hash moves in this release anyway. One consequence does not follow the rehash: a row ingested before this change holds no bytes for that file at all, so the CODE-4 pass recomputes over what the row holds and produces a hash that a filesystem-source consumer still disagrees with. Nothing in this proposal repairs that row in place, and a reingest does not either. Reingesting the same package recomputes over the widened resource set, so the new hash differs from the stored one at the same `(artifact_id, version)`, and ingest's `GetManifest` switch reports that as a conflict and writes nothing (`pkg/registry/ingest/ingest.go`, the switch on `existing.ContentHash`), which `spec/07-external-integration.md` states normatively as "Same version, different content_hash | Rejected as `ingest.immutable_violation`. The author bumps the version." An unregister followed by a re-register does not open a path either, because the tombstoned row still satisfies the insert and the read-back returns the old hash. The author bumps the artifact's `version:`, and the next ingest stores a row over the CODE-6 resource set; the pre-upgrade row keeps its stale resource set and stale hash for as long as it is retained, and a filesystem-source consumer of that earlier version disagrees with it. The edge-case table, TEST-8 item 5, and DOC-1's `Fixed` entry state it.

The CODE-4 pass is deliberately not widened to cover this case. Recomputing a row's resource set from the layer source rather than from the bytes the registry holds would make the pass a partial re-ingest, which CODE-4 excludes, and it would give the pass a second source of truth for a row's contents. The narrower cost is one artifact version an author republishes under a new version.

### CODE-7: the SDK overlay loaders stop at a nested package and skip dot-directories in discovery

The language SDKs load a §6.4 workspace overlay with their own walks, and §6.4 requires them to honor the same lookup and the same format as the registry-side layers (`spec/06-mcp-server.md:196`, `:205`). The Go overlay reaches the filesystem walk (`pkg/overlay/overlay.go:57-61`), so the MCP server and `podium sync` apply the nested-package exclusion and the dot-directory discovery skip to an overlay, and the SDKs apply neither today. `LocalOverlay._read_package` in `sdks/podium-py/podium/_overlay.py:311-321` walks every directory below the package with `os.walk` and captures every file other than the root `ARTIFACT.md` and a skill's root `SKILL.md`, and `LocalOverlay._load` (`:268-285`) discovers every directory holding an `ARTIFACT.md` with no hidden-name check. `readPackage` in `sdks/podium-ts/src/overlay.ts:387-406` recurses into every subdirectory the same way, and the discovery `walk` (`:339-361`) recurses into every directory entry. After SPEC-4 amends §4.4, an SDK overlay package that contains a nested package carries the nested package's files as its own resources, and an `ARTIFACT.md` below a dot-directory is an SDK overlay artifact that the MCP server's overlay does not surface.

The change is confined to the two walks in each SDK, and it adds no field, option, or type:

- The resource walk stops at a subdirectory of the package that directly contains a file named `ARTIFACT.md`, together with everything below it, which is the predicate `hasArtifactManifest` applies in `pkg/registry/filesystem/walk.go:225-227` and `:270-273`. In Python, `_read_package` removes each such name from the `os.walk` directory list in place; in TypeScript, `collect` does not recurse into such a directory.
- The discovery walk does not descend into a directory below the overlay root whose name begins with a dot, together with everything below it, which is the predicate `walkLayer` applies in `pkg/registry/filesystem/walk.go:144-146`. The overlay root itself is exempt, as the layer root is in `walkLayer`, because the default overlay path is `<CWD>/.podium/overlay/` (`spec/06-mcp-server.md:200`). In Python, `_load` removes dot-prefixed names from the `os.walk` directory list in place; in TypeScript, `walk` does not recurse into a dot-prefixed entry.

Every other membership rule already matches: both SDKs compare the root-relative path against `SKILL.md`, so a `SKILL.md` in a subdirectory is captured, and neither applies a hidden check inside a package, so a dotfile or dot-directory inside a package is captured. The SDKs compute no §4.7.6 digest (`grep -rn "sha256" sdks/podium-py/podium sdks/podium-ts/src` returns no composer; the SDKs read `content_hash` from the wire), so SPEC-4's byte-exactness and full-bytes sentences do not reach them, and the Python loader's text-mode read of a resource body is outside this change. The change moves no stored hash. TEST-9 pins it.

### CODE-8: the Helm chart gives the first start a startup budget

`deploy/helm/podium/templates/deployment.yaml` renders a liveness probe and a readiness probe with `initialDelaySeconds: 5` and no startup probe, and `run` answers neither path until the CODE-4 pass and the bootstrap ingest finish. The registry container gains a `startupProbe` on `/healthz` at the `http` port whose `periodSeconds` and `failureThreshold` come from a new `startupProbe` block in `deploy/helm/podium/values.yaml`. A startup probe holds the liveness and readiness probes off until it succeeds, so the kubelet does not restart a pod that is still migrating. The liveness and readiness probes are unchanged.

**IMPLEMENTOR'S CHOICE:** the default budget, subject to `periodSeconds` times `failureThreshold` being at least ten minutes, to both keys being overridable from `values.yaml`, and to a comment in `values.yaml` stating that a store-wide stored-value migration runs before the first probe succeeds and that an operator with a large store raises the threshold for that upgrade.

The chart's default `strategy` is `RollingUpdate` (`deploy/helm/podium/values.yaml`), which starts a replica on the new version beside replicas on the previous one. CODE-8 does not change that default, because a rolling update is right for every release that migrates no stored value; DOC-1 item 2 states the scale-to-zero the operator performs for this one.

1. The pinned vector, built from the spec text rather than from the implementation:

```go
// Spec: §4.7.6 — the canonical serialization is the framed manifest, the framed
// SKILL.md, then each resource's framed path and framed body in ascending path
// order. A framed value is its length as an unsigned 64-bit big-endian integer

//
```

It hashes the literal framed stream for a manifest `artifact`, a `SKILL.md` `skill`, and resources `{"ref.md": "R", "a.md": "A"}` supplied in reverse insertion order, and asserts `CanonicalContentHash` returns that hex. The same test carries a second literal vector for a package that declares no `SKILL.md` and carries one bundled resource: the stream is `frame(manifest) || frame("") || frame(path) || frame(body)`, written out of SPEC-1's text, and it is compared against `CanonicalContentHash(manifest, nil, map[string][]byte{path: body})`. **OQ-3.** The filesystem-source sync's digest for an `extends:` child is resolved: CODE-5 moves it onto the authored bytes in this proposal, TEST-7 gives the §11 equivalence fixture the `extends:` child that pins it, and the Decisions section records why hashing the merged form was rejected.

**OQ-4.** Whether §4.6 permits serving the pre-merge `ARTIFACT.md` bytes to a requester who cannot see the parent's layer is resolved outside this proposal, and the resolution moves no hash. SPEC-1's rationale carries the conflict and its citations. The candidate answers split by what they change. An answer that changes what the consumer must verify leaves every stored hash where it is. An answer that changes what the consumer is given to hash, such as redacting the parent reference and hashing the redacted form, hashing the merged form, or an opaque parent-free token, moves every `extends:` child's hash and carries the same store-wide rewrite this release runs. Proposal 0027 stages an answer of the first kind: a serve-time delivery attestation over the merged record, with `raw_frontmatter` removed from the wire and `content_hash` keeping its §4.7.6 meaning, so SPEC-1's pre-merge slot-one rule and this proposal's digest are unchanged by it, and the Decisions section records why §4.7.6 is not redefined to accommodate the answers of the second kind. This proposal does not wait on 0027; the Relationship section states the sequencing.

**OQ-5.** Whether recreating the target store after an immutability failure or a start between runs also recreates the target object store is open, and this proposal keeps the object store by default. Every object is keyed by the SHA-256 of its body (`pkg/registry/ingest/ingest.go:1257-1282`) and the filesystem provider's `Put` accepts the same body at an existing key (`pkg/objectstore/filesystem.go:64-69`), so a re-run's `pumpObjects` writes nothing that differs. Recreating both stores gives an instruction that does not depend on a provider's `Put` semantics, at the cost of copying every object again and a second thing for the operator to delete.

**OQ-6.** Whether the Summary's "Watch out for" bullet on the rehash pass restates CODE-4 step 6's refusal of a start that would generate a signing key is open, and this proposal deletes the restatement by default. The bullet directs the implementor to CODE-4, and each restatement is one more copy to update when step 6 changes. Keeping it lets a reader of the Summary see that the refusal does not depend on the listener binding without opening CODE-4.

## Relationship to proposals 0027 and 0028

Proposal 0028 (make signature verification verify) ships in this proposal's release, because the first start on this release is the one event that re-signs every stored row, and that event does not recur for a store except when `podium admin migrate-to-standard` copies rows into it: the data-migration marker makes every later start skip the pass. Proposal 0027 (attest the served record and close the hidden-parent disclosures) targets the same release, because it shares this proposal's consumer cache clear and moves no stored hash; it also carries the hash-neutral resolution of OQ-4. 0027 also stages the §6.9 row for `materialize.content_hash_mismatch`; this proposal lands first and carries that row as SPEC-5, so 0027 drops its copy. DOC-1's changelog entry is therefore written as the release's single upgrade note, and the entries those two proposals add extend it without naming a second store-wide step or a second cache clear; DOC-1 item 2's blank fixes that wording. Both proposals are Drafts, and this document cites them for sequencing only, never as evidence for a claim made here.

This proposal lands and is implemented first, and CODE-4 is written against the signing surface as it stands then, where an unset `PODIUM_SIGN` means no signer. 0028 makes an unset `PODIUM_SIGN` resolve to `registry-key` and accepts `none`. The pass takes whatever provider the boot path's one loader returns, and step 5's refusal is keyed on that provider being nil, so 0028's change to the loader reaches the pass with no edit to CODE-4's code. Step 6's check and `registrySignerFor` both call `registrySigningEnabled`, the helper CODE-4's placement bullet adds, so 0028's change to the mode reading, made in that helper, reaches both callers. 0028 also owns TEST-6 case 10's "mode empty" arm, which asserts the pre-0028 reading and under 0028 passes `none`. Because the check runs before the loader and leaves the loader's write in place, a `<path>.pub` that 0028 writes beside a generated key is written only by a start the check passed and never by a refused one. What 0028 owns, in its own change set and after this proposal is implemented, is the fixtures that rely on the old reading: the TEST-6 boot test that starts `run` with `PODIUM_SIGN` unset to reach the refusal, which under 0028 sets `none`, and the wording of the refusal's error and of DOC-1 item 2 where they name the variable. Under 0028's default every row the first start rewrites is signed, including rows stored unsigned, which is what lets 0028 flip the consumer default in the same release. A registry that turns signing on after its marker is set gets no second pass from this proposal. 0028 owns that case: it states that such a start signs no stored row and that the repair is the rebuild by deletion and re-ingest. Nothing here is written against 0028's surface, so this proposal does not depend on 0028.

## Non-goals

- **Changing the slot order or the ascending-path resource order.** Both stay exactly as proposal 0025 left them; only the framing is added.
- **Adding an algorithm identifier, a version byte, or any negotiation of the hash algorithm on the wire or in the store.** Pre-1.0 policy forbids the dual path, and the §6.6 gate has no negotiation point.
- **Minting a new error code.** The pass's failures are a refusal to start and log lines, and its store methods reuse `ErrNotFound` and `ErrImmutableViolation`, so nothing new reaches a client from the migration. The one client-facing code this change makes normative, `materialize.content_hash_mismatch`, is a code the consumer already returns; SPEC-5 gives it the §6.9 row and TEST-4 the §6.10 axis entry and annotation it shipped without.
- **An off-server migration command.** An earlier draft staged `podium admin rehash`, a command run beside a stopped registry. It was dropped because it had to reconstruct the server's configuration: the store, the object store, the signing mode and key, and the audit destination, from an environment that is not the server's. `podium serve` sets some of those from flags inside its own process only, the published registry image carries only `podium-server`, and a host that does not mount the registry's object volume resolves an empty one, so every review round found another way the reconstruction could be silently wrong, and each guard added a surface the next round audited. The serving process holds all of those inputs already.
- **Exposing the rehash over HTTP, or an operator re-trigger other than the target clear `podium admin migrate-to-standard` performs.** `/v1/admin/reembed` is a precedent for an HTTP admin pass, and the rehash does not take it: the pass has to finish before the registry ingests or serves, which is before an endpoint exists. No flag, variable, or endpoint runs the pass again once the marker is set, because the states that would want one each have another answer: a row written by a previous-binary process after the pass, which DOC-1 item 2's stop prevents; rows copied in by `podium admin migrate-to-standard`, which the command itself reaches by clearing its target's marker before it copies them; a store whose signing key or object-store root was wrong, for which the route is the backup DOC-1 item 2 takes; and a registry that turns signing on after its marker is set, which 0028 owns. A row left at the previous digest fails closed at the consumer.
- **Minting a new §8 audit event type for the rehash.** The pass emits the existing `artifact.signed` event for each row it re-signs, through the registry's own sink, and nothing else: no `artifact.rehashed` or run-level event is added, because the hash rewrite alone changes a derived value and no artifact's bytes, and the row's existing `artifact.published` and `layer.ingested` events stand. The events carry the `system` caller and an empty trace id, which is the attribution the reembed pass records off any request (`pkg/registry/core/reembed.go`). Giving the bootstrap ingest an audit emitter, which it lacks today, is a separate change.
- **Re-keying object storage.** Bundled resources and oversized manifest bodies are keyed per blob, and no key moves.
- **Adding code that detects or evicts a pre-upgrade consumer cache.** The remedy is the documented clearing of the cache directory stated in DOC-1 item 4. Podium is pre-1.0 and adds no migration shim for it.
- **Changing `@sha256:` pin resolution.** Both comparison sites match the pin against the stored value rather than recomputing, so no code there changes; only the stored values move.
- **Plumbing `skill_raw` into the §6.4 overlay *response*, correcting the overlay response's `manifest_body` for a skill, or routing the overlay path through the §6.6 step-2 gate.** CODE-2 corrects the hash the overlay serves and removes the cache write, so no incomplete bucket reaches a later reader. The response fields and the overlay's bypass of the pipeline are a separate question. The overlay's response carries `rec.Artifact.Body` for a skill, which is empty, while the registry serves the `SKILL.md` prose there; that divergence predates this change and is untouched by it.
- **Introducing per-part sub-digests or a Merkle structure.** Length framing gives injectivity in one pass; a tree would add a structure the spec would then have to define.
- **A keyed (tagged-part) encoding in place of the positional framing.** It was considered as forward compatibility for additive parts and rejected. It protects only a part type no existing artifact carries: an author who adds a file bumps the version through ordinary publishing, and the most plausible new part, a prose companion for a non-skill type, already exists as a bundled resource, so promoting it to a named part moves the hash under a keyed encoding too. It protects nothing against a normalization, membership, ordering, or digest-function change, and because the rewrite is store-wide a migration is avoided only when zero hashes move. It also carries disciplines of its own: a required `resource:` namespace prefix, because a resource at path `skill` would otherwise collide with the `SKILL.md` key; key reservation; and a `len() > 0` presence predicate, because `skill_raw` is `omitempty` on the wire (`pkg/registry/server/server.go`), so `contentHashOf` passes a nil `SKILL.md` slot while `verifyContentHash` passes `[]byte(resp.SkillRaw)`, a non-nil empty slice, for the same artifact. The positional framing is therefore not forward-compatible for additive parts, and that is accepted: a new part is a §4.7.6 amendment that moves every hash, and no optional trailing part is ever added to the stream, because an artifact with one resource and no trailing parts would serialize identically to one with no resources and both trailing parts, which is the collision class this proposal removes.
- **An ignore mechanism for bundled resources, whether an ignore file, a built-in name pattern, or a size filter.** Any filter applied at ingest or at recomputation moves the stored hash of every artifact carrying a filtered file. SPEC-4 states that no such filter exists, and the Decisions bullet on the input pins records why one, if ever wanted, belongs at authoring time.
- **Unicode, line-ending, whitespace, case, or byte-order-mark normalization of any part.** Each conversion changes the bytes the digest covers for every stored artifact that carries the converted form, so each is a stored-value migration. SPEC-4 states that no normalization applies, and TEST-8 pins the composer against one being added.
- **Routing the migration through ingest.** `podium layer reingest`, alone or after an unregister and re-register, reaches only the head version, as the Summary's "Watch out for" states; the CODE-4 pass is the repair path, and no ingest path is widened to become one. A reingest is not the repair for the pre-CODE-6 subdirectory-`SKILL.md` row either; CODE-6's closing paragraph states why.
- **An end-to-end test that the computing parties agree** (dropped alternative). An earlier draft carried a fourth test standing up a registry, an MCP load, and a sync in one body to assert that ingest, the §6.6 gate, and the sync lock produce one digest for one artifact. It is dropped. There is a single implementation: `pkg/registry/ingest/ingest.go`, `pkg/sync/sync.go`, and `cmd/podium-mcp/main.go` all call the same `version.CanonicalContentHash`, which is the §2.2 property the project already enforces, so they cannot drift in serialization and only in the inputs they feed. Input agreement is already pinned on fixtures carrying an `ARTIFACT.md`, a `SKILL.md`, and bundled resources: `test/integration/sync_equivalence_test.go` compares whole lock entries including `ContentHash` across both registry sources, `test/integration/sync_server_content_hash_test.go` and `test/e2e/sync_content_hash_test.go` pin the lock against the registry-served value, and `test/e2e/bundled_resources_test.go` loads a bundled-resource skill through the real `podium-mcp` binary, where the gate runs unconditionally and a disagreement fails the load. All of those re-run unchanged against the framed serialization. The one input divergence they did not cover was an `extends:` child, because the reference fixture carried none; under TEST-7 the fixture carries one, so `assertLockArtifactsEqual` compares a lock entry for an `extends:` child across both sources, which is the comparison CODE-5 makes pass. Adding the test would otherwise assert, at the most expensive level in the suite, that the call sites of one function return the same value.

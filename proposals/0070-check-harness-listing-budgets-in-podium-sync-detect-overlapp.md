# Proposal 0070: Check harness listing budgets in podium sync, detect overlapping descriptions and near-duplicate content in lint, make the lint thresholds configurable, and define the podium lint output for CI

- Issue: (to be filed)
- Status: Implemented (2026-11-16). Verified after 15 adversarial review rounds (54 findings fixed). The open questions are resolved as recommended.
- Date: 2026-11-16

This document stages spec, code, test, manual-validation, and documentation changes. It does not modify any spec, code, test, or doc file. Apply the changes in the staged sections after sign-off. The change is backward-incompatible: `podium lint` reports warnings it did not report before, `lint.colliding_descriptions` reports overlapping descriptions where it reported equal ones, and the `pkg/lint` Go API changes (D-13). It ships in a MINOR release.

## Summary

**What changes.**

- **Spec §3.3, §12, §4.3, §4.3.4, and §7.3.1 (SPEC-1, SPEC-3).** §7.3.1 defines the catalog advisories: `lint.thin_description`, `lint.colliding_descriptions` (word-set Jaccard similarity of 0.7 or higher between descriptions), and the new `lint.near_duplicate_content` (five-word shingle Jaccard similarity of 0.8 or higher between prose bodies or text resources of different artifacts). Registry ingest runs them over the ingested layer, and `podium lint` runs them over every layer it walks. §7.3.1 also defines the `podium lint` contract for CI: `--fail-on`, `--json`, the envelope, and the exit codes. §4.3 and §4.3.4 name the `lint_suppress` key. §3.3 and §12 point at §7.3.1, and §12 gains rows for duplicated content and listing overflow.
- **Spec §4.1, §4.3.4, §4.5.5, and §13.12 (SPEC-2, SPEC-6).** §4.1 defines the estimated token count. The size thresholds become configurable defaults. A new §13.12 Lint subsection lists every `PODIUM_LINT_*` variable, which the registry and `podium lint` both read. Registry ingest does not apply the §4.5.5 `DOMAIN.md` body-size warning, so only `podium lint` applies its threshold. §7.3.1 names the `DOMAIN.md` checks `podium lint` runs and does not claim which ones ingest runs, so it stays consistent with §4.5.2 and §12, which assign `DOMAIN.md` checks to ingest.
- **Spec §7.5, §7.5.2, §7.5.8, and §11 (SPEC-4, SPEC-5, SPEC-7).** A new top-level `listing_budgets:` map in `sync.yaml` configures a per-adapter listing budget. A new §7.5.8 defines the estimate that `podium sync` computes for each `kind: workspace` target, its defaults, the `listing` member of the `--json` envelope, and the effect of `check: off | warning | error` on the exit status. §11 gains verification bullets.
- **`pkg/lint`, ingest, and `podium lint` (CODE-1, CODE-2, CODE-3, CODE-4).** A `lint.Thresholds` value replaces the hard-coded constants and the soft-cap fields. One exact similarity-join helper serves the refined colliding rule and the new near-duplicate rule. Ingest runs the advisories with the configured thresholds. `podium lint` runs the advisories and gains `--json` and `--fail-on`, and `layer.Drop` gains `Details` for the envelope's `rejected` member.
- **`pkg/sync` and `podium sync` (CODE-5, CODE-6).** `pkg/sync` holds `listing_budgets` as an undecoded node that `podium sync save-as` writes back, type-checks, merges, and validates it in `LoadMergedConfig` and `ListingBudgetFor`, and computes the listing report as a pure function of a run's `Result`. `sync.Check` takes an adapter registry and reports every invalid entry. `podium sync` prints the report, adds it to the `--json` envelope, and maps `check: error` to the exit status on every path.
- **Tests, manual validation, and docs (TEST-1, TEST-2, MV-1, DOC-1).** Unit, integration, and end-to-end tests pin each behavior. `test/manual-validation.md` gains S108, and CODE-4 rewrites the S01, S02, S23, and S51 descriptions that the new advisories would flag. The CLI reference, the configuration reference, the authoring pages, the harness configuration page, the upgrade notes, and the CHANGELOG follow.

**Fixed decisions.**

- D-1: the listing check runs in `podium sync`, for each `kind: workspace` target, over the set the run materializes. `podium lint` gains no `--harness`, `--profile`, or identity flag.
- D-2: `listing_budgets` keys are `max_chars` (default 8000), `entry_overhead_chars` (5), `max_entry_chars` (unset by default), `types` (`[skill]`), and `check` (`warning`). The defaults are the same for every adapter. An entry for `none` is invalid.
- D-3: listing cost is the sum over entries of the code points of the name, the code points of the description, and `entry_overhead_chars`.
- D-4: the listing check changes no written file. `check: error` fails the run as a §13.11.3 drop does. An invalid entry for the run's harness, including an entry for `none` or for an adapter this binary does not register, exits 2, `podium sync --preview` included. A `listing_budgets` value of the wrong YAML type is a load error in the commands that call `sync.LoadMergedConfig`, so `podium sync` exits 1 and `podium sync override` ignores the file as it does today. The readers that do not decode the block, which include `podium config show` and `podium sync save-as`, never fail on a value of the wrong type. `podium sync save-as` writes each alias in the block as a copy of the value it names, and fails without writing on an alias to a node that encloses it. `podium sync override` validates the entry only when it re-materializes.
- D-5: the lint thresholds are `PODIUM_LINT_*` environment variables only, read by registry ingest and by `podium lint`. A value that does not parse or falls outside its range keeps the default and logs a warning naming the variable. Ingest does not apply the `DOMAIN.md` body-size warning, so `PODIUM_LINT_DOMAIN_BODY_WARN_TOKENS` takes effect in `podium lint` only.
- D-6: `lint.colliding_descriptions` keeps its code and reports every pair whose normalized word sets have Jaccard similarity of 0.7 or higher.
- D-7: `lint.near_duplicate_content` is a new warning over five-word shingle sets at 0.8, found by an exact prefix-filtered similarity join over interned tokens, after identical units are grouped so a file bundled in many artifacts costs time linear in their number. MinHash and LSH are out.
- D-8: the catalog advisories stay out of `AllRules()`. Ingest runs them over the ingested layer as non-blocking advisories, and `podium lint` runs them over every walked artifact.
- D-9: `lint_suppress` is `ARTIFACT.md`-only and one-sided for the pairwise codes.
- D-10: the `podium lint --json` envelope is `{registry, diagnostics, rejected, counts}`, and `--fail-on` defaults to `error`. An `info` diagnostic never fails the run, and an open or walk failure or an interrupt writes no envelope and exits 1.
- D-11: an embedding-based overlap report is deferred.
- D-12: the similarity code lives in `pkg/lint/similarity.go`, the listing in `pkg/sync/listing.go`, and the CLI helpers in `cmd/podium/lint_json.go` and `cmd/podium/sync_listing.go`. No package and no dependency is added.
- D-13: the change is backward-incompatible and ships in a MINOR release, with no compatibility shim.
- D-14: the spec lands first in one commit, then thresholds, similarity, ingest, the lint CLI, the sync library, the sync CLI, tests, manual validation, and docs, with the CHANGELOG last.

**Watch out for.**

- **The lint output of existing fixtures changes.** `lintCmd` prints `lint: no issues.` only when it finds no diagnostic (`cmd/podium/main.go:1107-1110`), and a dozen end-to-end files assert that line over fixtures with descriptions such as `from-overlay`, `A skill`, or `Tagged`. CODE-4 lengthens those descriptions in its own commit. A fixture that a documentation page's commands produce changes on the page too, because the page's D-<slug> end-to-end test executes it. Lengthen each description into a distinct sentence: five artifacts described as "a skill that ...", "a command that ...", and so on cross the 0.7 overlap threshold together.
- **Zero and partial `Thresholds` values keep the defaults.** `&lint.Linter{}` and `Thresholds{PerFileSoftCapBytes: 1024}` must keep every other default. Resolve field by field. A whole-struct zero check turns off the thin-description check and makes every description pair collide.
- **`NewIngestLinter` runs per ingest.** `internal/serverboot/reingest.go:60` and `internal/serverboot/serverboot.go:507`, `:662` build a linter for every ingest, so the environment is re-read and an invalid value logs its warning on every ingest. This is accepted (D-5).
- **`Rule.Check` returns no error.** A cancelled near-duplicate pass returns no diagnostics, and `Linter.Lint` returns what it has. `podium lint` checks `ctx.Err()` after `Lint` and exits 1 without an envelope; otherwise an interrupted run would report a clean catalog. `runLint` takes the context as a parameter so `TestRunLint_InterruptedWritesNoEnvelope` can pin this guard (CODE-4).
- **`layer.Drop` stops being comparable.** Its new `Details map[string]any` field breaks the `!=` comparisons in `pkg/layer/invalid_test.go:11`, `pkg/layer/collision_test.go:36`, and `assertOneCollision` at `pkg/sync/sync_collision_test.go:71`, which CODE-4 rewrites in the same commit. S5 runs `go test ./pkg/sync/` so the break surfaces in the step that owns it.
- **Diagnostics can tie in the sort order.** `Linter.Lint` sorts by artifact ID and code (`pkg/lint/lint.go:213-218`). Several near-duplicate units of one artifact share both, so CODE-2 adds the message as the third key.
- **A threshold of 1.0 must still report identical units.** Identical token sets are grouped before the join, and two distinct groups never reach similarity 1, so at t = 1.0 the join returns no pair and identical units are reported from their group alone. `TestNearDuplicate_ThresholdOne` pins that two byte-identical bodies are reported at `PODIUM_LINT_CONTENT_SIMILARITY=1.0`. A test that sets 1.0 on a pair that differs by a paragraph proves only that a below-threshold pair is silent.
- **The join's filter bounds are computed in `float64`.** `0.55*100` is `55.00000000000001`, so an unslackened bound drops a pair at exactly 0.55. CODE-2 computes every filter bound with a slack threshold and decides each pair with one exact test.
- **The listing reads `Result`; it never enters `Run`.** `sync.Run` adapts every record before its `DryRun` return (`pkg/sync/sync.go:302-334`), so `Result.Artifacts[].Files` is populated under `--dry-run` too. Keeping the budget out of `Options` keeps the §11 byte-identical equivalence true by construction.
- **`--config` reads one file.** `runMultiTargetSync` reads only the named file (`cmd/podium/main.go:513`). The listing budgets for a `--config` run come from `sync.LoadMergedConfig` at the configuration file's workspace, the walk `defaults.verify_signatures` already uses (`cmd/podium/main.go:550-552`).
- **yaml.v3 coerces `listing_budgets` scalars silently, and readers that do not decode the block must not fail on it.** A bare `Decode` loads `max_chars: 1.5` as 1 and `check: 1` as `"1"` without an error, so the merged load has to check each value's YAML type. The MCP server, the bridge, and the §4.7.9 policy resolution decode the whole file into `SyncConfig` and skip a file that fails, and `podium sync save-as` re-encodes all of it, so a typed field would let a mistyped budget drop a version pin or a `verify_signatures: always`, or would rewrite the block. CODE-5 holds the block as an undecoded `yaml.Node` and type-checks it in `LoadMergedConfig` alone. `podium config show` reads the scopes through `ReadConfigFile` and never calls `LoadMergedConfig`, so it is one of the readers that do not decode the block. `ListingBudget.Check` is a `*string`, because a quoted `check: ""` is a string that SPEC-4 Edit 3 makes invalid, and a `string` field would read it as unset (CODE-5).
- **The undecoded node can hold an alias to an anchor outside the block.** `SaveAs` keeps only the `SyncConfig` keys, so an anchor defined under another top-level key is gone when `marshalConfig` encodes, and `Node.Encode` fails with `yaml: unknown anchor 'ok' referenced`. CODE-5 has `marshalConfig` encode a detached copy of the block (`detachNode`), and `TestSaveAs_PreservesListingBudgets` pins the merge-key and block-alias forms.
- **A `--config` listing failure returns after the publish phase.** Under `check: error`, `runWorkspaceTarget` returns `errListingOverBudget` where it returns `droppedErr(dropped)` today, after the target's workflow publishes (`cmd/podium/main.go:642-648`). Returning it beside the `reportListing` call skips the publish phase that §13.11.3 runs before a drop fails the target (CODE-6 item 6).
- **`podium sync --check` without `--config` returns before resolution** (`cmd/podium/main.go:268-270`). Its listing warnings come from `sync.Check`.
- **`none` is a registered adapter** (`pkg/adapter/none.go:19`). Validation rejects an entry for it explicitly.
- **Removing `DescriptionAdvisoryRules` breaks two tests and one caller.** `pkg/lint/description_rules_test.go:23`, `:164`, and `pkg/registry/ingest/ingest.go:551` reference it. CODE-3 removes it and rewrites them in the same commit.
- **Shared bundled files draw the near-duplicate warning in every artifact that bundles them.** The reference registries under `testdata/registries/` can hold such files. CODE-4 re-checks every linted fixture against all three advisories.
- **Parts of `test/e2e` skip silently on macOS.** Run the end-to-end steps with `-v` and grep the output for `SKIP` before claiming a pass.
- **Line numbers drift.** Anchor each edit by the quoted text, and treat cited line numbers as hints.

## Current state and the gap

Teams that share skills at scale report context budget, overlap between skills, and duplication as their main quality problems. A harness loads the name and description of every installed skill into a listing whose size limit derives from the model's context window and the user's settings. Claude Code uses 1% of the window by default and caps each entry at 1,536 characters. Codex uses about 2%, or 8,000 characters when the window is unknown. Above the limit the harness shortens descriptions or omits entries without an error. Podium covers part of this today.

### No check models a harness listing

A search of `spec/`, `pkg/`, `cmd/`, and `internal/` finds no listing budget, context-window model, or per-harness description cap. §6.7 defers per-harness specifics to each harness's documentation, and `pkg/adapter` has no listing logic. The only per-description cap is the agentskills.io `SKILL.md` `description` limit of 1024 characters (§4.3.4), which `lint.skill_ref_validate` enforces as a warning (`pkg/lint/skill_rules.go:335-358`).

The set of artifacts that reaches a harness listing is resolved in `podium sync`. `sync.Run` reads the effective view and applies scope, toggles, the workspace overlay, and the §4.3 `target_harnesses` skip before it adapts each record (`pkg/sync/sync.go:212-334`, §7.5), so sync is the only path that knows what a consumer receives. Against a server source that set is the caller's own visibility-filtered view. Against a filesystem source visibility short-circuits to true (§13.11.3). `podium lint` composes no consumer view: it takes `--registry` and `--offline` and lints the union of all layers (`cmd/podium/main.go:1060-1117`). Ingest lints one layer's records (`pkg/registry/ingest/ingest.go:528-551`). MCP discovery never puts the catalog into a harness listing (§3.2), and `load_artifact` adds materialized skills one at a time (§6.6), so no pre-delivery check can bound that growth.

### The thresholds are constants

The size and description thresholds are Go constants with no override: `SkillBodyWarnTokens` 5000, `SkillBodyWarnLines` 500, `ManifestErrTokens` 20000, and `DomainBodyWarnTokens` 2000 (`pkg/lint/size_rules.go:13-33`), and `MinDescriptionChars` 15 and `MinDescriptionWords` 3 (`pkg/lint/description_rules.go:20-28`). The spec fixes the four size values in §4.1, §4.3.4, and §4.5.5, so making them tunable is a spec change. The §4.1 soft caps are the precedent: §4.1 states their values, §12 declares them configurable, and `PODIUM_LINT_PER_FILE_SOFT_CAP_BYTES` and `PODIUM_LINT_PER_PACKAGE_SOFT_CAP_BYTES` implement that (`pkg/lint/lint.go:78-86`, `:147-177`). Those two variables appear in `docs/reference/configuration.md:226-227` and nowhere in `spec/`. The spec fixes no description threshold, so those two already fall under the overridable-default rule of `.claude/rules/code-best-practices.md`.

The spec never defines a token. The code estimates one as the byte length divided by four, rounded up (`pkg/lint/size_rules.go:36-45`).

### Duplication and overlap

No rule compares bodies or bundled resources across artifacts, and `pkg`, `cmd`, and `internal` contain no shingling, MinHash, Jaccard, or LSH code. `ruleCollidingDescriptions` groups descriptions that are equal after lowercasing and collapsing non-alphanumeric runs (`pkg/lint/description_rules.go:98-164`). §3.3 and §12 require flagging "clusters of artifacts whose summaries collide" and do not define a collision. Both description advisories stay out of `AllRules()` (`description_rules.go:30-47`) and run only as non-blocking ingest advisories over one layer (`ingest.go:546-551`), so the CLI that CI runs (§7.3.1) never produces them, as `docs/authoring/your-first-skill.md:51` says. The spec assigns the checks to the registry, so the CLI gap matches the spec and is a design choice.

### `podium lint` has no machine-readable output

`podium lint` prints `Diagnostic.String()` lines (`[severity] id: message (code)`, `pkg/lint/lint.go:52-57`) and exits 0, 1 (an error diagnostic, a refused artifact, or an open or walk failure), or 2 (usage) (`cmd/podium/main.go:1060-1117`, `:132-137`). The spec defines `--json` only for the read CLI (§7.6.1) and for `podium sync` (§7.5). It names one lint code by itself, `lint.invalid_version` (§4.3.4). `lint_suppress` is honored per rule, by `lint.thin_description`, `lint.colliding_descriptions`, and `lint.skill_ref_validate` only (`description_rules.go:80`, `:123`; `skill_rules.go:345`). The colliding rule already suppresses one-sidedly: the suppressing artifact draws no warning, and its peers still name it (`description_rules.go:108-145`). The spec never names the `lint_suppress` key; §4.3.4 says only "lint suppression flag available".

### Embeddings cannot gate CI

An embedding-based overlap check cannot be a reproducible CI gate. The embedding provider is optional server-side configuration that the SPI can replace or `--no-embeddings` can disable, and a model switch re-embeds (§13.12, §4.7). Filesystem-source lint and sync have no embedding path (§13.11.3).

## Decisions

- **D-1. The listing check runs in `podium sync`.** It runs for each `kind: workspace` target: on a one-shot run, `--dry-run`, each `--watch` cycle, each `--config` target including under `--check`, and the re-materialization of `podium sync override`. It covers the set the run materializes, after scope, toggles, the workspace overlay, and the §4.3 `target_harnesses` skip. Sync is the only surface that resolves what a harness receives, and against a server source it resolves the caller's own visibility-filtered view (§7.5). Three alternatives were dropped. `--harness`, `--profile`, and `--target` flags on `podium lint` would duplicate sync's view resolution and still lack identity-based visibility. Ingest sees one layer and no consumer. A whole-catalog check measures a listing that no consumer receives.
- **D-2. Budgets are absolute characters per adapter value.** A new top-level `listing_budgets:` map in `sync.yaml` (§7.5.2) is keyed by adapter value, with the keys `max_chars`, `entry_overhead_chars`, `max_entry_chars`, `types`, and `check`. The built-in defaults are 8000, 5, unset, `[skill]`, and `warning`, the same for every adapter. The `none` adapter feeds no harness listing, gets no check, and an entry for it is invalid. Harness budgets are fractions of a context window that Podium cannot observe, users can configure them, and they change between harness versions, so the spec fixes only Podium's defaults and names no harness-internal value. 8000 characters equals Codex's unknown-window fallback and approximately Claude Code's 1% of a 200K-token window at four characters per token. `max_entry_chars` has no default: at 1024 it would repeat the `lint.skill_ref_validate` warning on a `SKILL.md` description over 1024 code points (§4.3.4). The `sync.yaml` key satisfies the overridable-default rule of `.claude/rules/code-best-practices.md` through the client configuration §7.5.2 defines. No environment variable or flag is added.
- **D-3. Listing cost.** The cost is the sum over entries of the code points in the name, the code points in the description, and `entry_overhead_chars`. The name is the last segment of the canonical ID, which for a skill equals the `SKILL.md` `name` (§4.3.4). The description is the `SKILL.md` `description` for a skill and the `ARTIFACT.md` `description` for any other type. The report estimates whether the target's contribution overflows. It does not predict which entries a harness shortens or drops: Claude Code, for one, drops descriptions by per-user invocation frequency, which Podium cannot see.
- **D-4. Effect on output and exit status.** The listing check never changes what sync writes, so the §11 byte-identical equivalence holds. `check: warning` reports on standard error and leaves the exit status unchanged, `check: error` writes the target and then fails the run as a §13.11.3 drop does, and `check: off` computes nothing. An invalid entry for the run's harness exits 2 before the view is resolved, following the `sync.Resolve` precedent. That includes an entry for `none`, which is the run's harness when nothing sets one, an entry for an adapter this binary does not register, and `podium sync --preview`, which computes no listing. A `listing_budgets` value of the wrong YAML type fails the load of the file that holds it in the commands that call `sync.LoadMergedConfig`: `podium sync`, `podium status`, `podium login`, `podium logout`, and the `podium layer register`, `podium layer reingest`, and `podium layer watch` commands. The readers that do not decode the block, which are the MCP server, the bridge, the §4.7.9 signature-policy resolution, `podium config show`, and `podium sync save-as`, never fail on a value of the wrong type, so a mistyped budget cannot remove a file's registry, version pin, or `verify_signatures: always`, and `podium config show` displays the file's other keys as before (CODE-5). `podium sync save-as` writes the block back with each alias replaced by a copy of the value it names, so the written file needs no anchor that save-as drops; a block holding an alias to a node that encloses it makes save-as fail without writing (CODE-5). `podium sync override` validates the entry only when it re-materializes, keeps today's tolerance of a `sync.yaml` that does not load, and then uses the §7.5.8 defaults. SPEC-4 Edit 3 and SPEC-5 state the outcome on each path, and the edge-case table lists them.
- **D-5. Thresholds are configurable defaults read from the environment.** The spec-fixed size thresholds (5000 tokens, 500 lines, 20000 tokens, 2000 tokens) become spec-stated defaults that are configurable, following the §4.1 soft-cap and §12 precedent. They, the description thresholds, and the two similarity thresholds are set through `PODIUM_LINT_*` environment variables. Registry ingest and `podium lint` both read them, so a CI run and the registry apply one value when both set it. Registry ingest lints artifact records with a nil registry (`pkg/registry/ingest/ingest.go:541`), and every `DOMAIN.md` lint rule returns nothing without a registry (`pkg/lint/size_rules.go:140-143`, `pkg/lint/domain_imports.go:25`, `:70`, `:116`, `:190`), so `PODIUM_LINT_DOMAIN_BODY_WARN_TOKENS` takes effect in `podium lint` only, and the spec says so. They have no `registry.yaml` key, because `podium lint` does not read `registry.yaml`, and the new §13.12 Lint subsection states this exception to the rule that every variable is also a config-file key. An unset or empty variable keeps the default silently. A value that does not parse or falls outside its range keeps the default and logs a warning naming the variable. `NewIngestLinter` reads the variables, and the registry builds a linter per ingest, so the warning repeats on each ingest. The two existing soft-cap variables move into the same subsection.
- **D-6. Description overlap refines `lint.colliding_descriptions`.** Two descriptions overlap when the Jaccard similarity of their normalized word sets is 0.7 or higher (configurable, 0.5 to 1.0). The normalization is the current `normalizeDescription`. Identical normalized descriptions have similarity 1, so every pair the current rule reports is still reported. The rule reports pairs rather than clusters, because similarity is not transitive. Each artifact draws one warning naming its peers in order of descending similarity and then by identifier.
- **D-7. Near-duplicate content is a new code.** `lint.near_duplicate_content` is a warning. A unit is the prose body (the `SKILL.md` body for a skill and the `ARTIFACT.md` body otherwise) or a bundled resource that is valid UTF-8 and contains no NUL byte. A unit is normalized like a description and split into five-word shingles. A unit under 50 words is not compared, and two units of one artifact are not compared. Two units are near-duplicates when the Jaccard similarity of their shingle sets is 0.8 or higher (configurable, 0.5 to 1.0). Candidates come from an exact similarity join with prefix and length filtering, shared with D-6, and each candidate is verified exactly. Words and shingles are interned to dense integer IDs rather than hashed, so two distinct tokens never merge and the computed similarity equals the defined one. Identical token sets are grouped before the join, so a file bundled in N artifacts forms one group and costs time and memory linear in N; the join's remaining cost grows with the number of distinct-set candidate pairs its filters admit. The output depends only on the input bytes and the threshold. Byte-identical binary resources are out of scope. MinHash with LSH banding was weighed and rejected: with fixed seeds a given pair is either always found or always missed, so its probabilistic recall cannot be tested, its band count is undefined at t = 1.0, and it would be a second similarity mechanism beside the description join.
- **D-8. Where the advisories run.** `lint.thin_description`, `lint.colliding_descriptions`, and `lint.near_duplicate_content` are warnings. Registry ingest runs them as non-blocking advisories over the layer it ingests, with the thresholds of `req.Linter`. `podium lint` runs them by default over every artifact it walks. They stay out of `AllRules()`, so ingest does not run them twice and they never gate ingest.
- **D-9. Suppression.** Each artifact applies `lint_suppress` for itself, and the pairwise codes keep the existing one-sided behavior: an artifact that lists the code draws no diagnostic of that code, and its peers still name it. §4.3 and §4.3.4 name `lint_suppress` as an `ARTIFACT.md` field, so a skill without an `ARTIFACT.md` cannot suppress. The listing check has no per-artifact suppression; the consumer's `sync.yaml` governs it.
- **D-10. `podium lint` output.** `podium lint` gains `--json` and `--fail-on <error|warning>` (default `error`). The envelope is `{registry, diagnostics: [{artifact_id, code, severity, message}], rejected: [{artifact_id, code, reason, details}], counts: {error, warning, info}}`. The diagnostic members match the reingest response's advisory objects, and the `rejected` members match its rejection objects, with `details` present when the refusing rule defines one (`pkg/registry/server/layers.go:2234-2242`, `:2287-2298`). Under `--json`, standard output carries only the envelope, and refused artifacts appear in `rejected` and not on standard error. Exit codes keep their meanings: 0 clean, 1 when a diagnostic reaches the failure severity or an artifact was refused, and 2 for usage, including an unrecognized `--fail-on` value. An `info` diagnostic never fails the run. An open or walk failure, including a §4.6 collision, and an interrupt write no envelope and exit 1. The spec does not enumerate every lint code.
- **D-11. Embedding-based overlap is deferred.** The embedding provider is optional, replaceable, versioned by model, and absent from filesystem-source lint and sync, so it cannot give a reproducible result.
- **D-12. Placement.** The similarity code lives in `pkg/lint` as unexported helpers next to the rules it serves (`pkg/lint/similarity.go`). `pkg/sync` computes the listing in `pkg/sync/listing.go`. The CLI helpers go in `cmd/podium/lint_json.go` and `cmd/podium/sync_listing.go`. The change adds no package and no dependency.
- **D-13. Compatibility.** The change is backward-incompatible and ships in a MINOR release. `podium lint` reports warnings it did not report before, which leaves its exit status at 0 unless `--fail-on warning` is set. `lint.colliding_descriptions` reports overlapping descriptions. `lint.Linter`'s `PerFileSoftCapBytes` and `PerPackageSoftCapBytes` fields are replaced by `Thresholds`, `DescriptionAdvisoryRules()` is replaced by `(*Linter).AdvisoryRules()`, `sync.Check` takes an adapter registry, and `layer.Drop` gains `Details`. Every caller is updated, and no shim is added.
- **D-14. Order.** The spec lands first in one commit. The code follows: thresholds, similarity and rules, ingest wiring, the lint CLI with fixture updates, the sync library, and the sync CLI. Tests, manual validation, and docs come next, and the CHANGELOG lands last.

A harness can shorten descriptions or omit entries without reporting an error.
>

A rule builds one interner per `Check` call and drops it when the call returns. Two distinct words or shingles never share an ID, so the similarity of two ID sets equals the similarity of the word or shingle sets they stand for. The interner replaces hashing: the document-frequency map that prefix filtering needs holds one entry per distinct token either way, so interning adds no asymptotic memory.

  - `type setGroup struct { tokens []uint32; members []int }` and `func groupIdentical(sets []tokenSet) []setGroup` group the sets whose token slices are equal, compared element by element; no hash decides equality. An empty set joins no group and never pairs. `members` holds ascending indexes into `sets`, and groups are ordered by their first member. Every two members of one group have similarity 1.
  - `type scoredPair struct { i, j, inter, union int }` with `i < j` as indexes into the groups. `func similarPairs(ctx context.Context, groups []setGroup, t float64) ([]scoredPair, error)` is an exact all-pairs Jaccard join over the groups' token sets with prefix and length filtering. It orders tokens globally by ascending document frequency and then by ID. Every filter bound uses the slack threshold `tf = t − 1e-9`, so floating-point rounding can only admit extra candidates and never excludes a qualifying one: it indexes each set's prefix of `|x| − ⌈tf·|x|⌉ + 1` tokens in that order and keeps a candidate `y` only when `tf·|x| ≤ |y|` and `tf·|y| ≤ |x|`. It verifies each candidate by a merge over the sorted slices and keeps the pair when `float64(inter)/float64(union) >= t`. A pair whose similarity equals `t` exactly passes that test, because both sides are the correctly rounded `float64` of the same rational. It returns the pairs sorted by `(i, j)`. Two distinct groups never have similarity 1, so at `t = 1.0` it returns no pair and identical sets are reported through their group alone. The loop checks `ctx.Err()` between groups and returns it on cancellation.
  - `func newPeerIndex(sets []tokenSet, groups []setGroup, pairs []scoredPair, ident func(set int) string) *peerIndex` builds the index once per `Check` call, and `func (p *peerIndex) summary(s int) (first []int, total int)`, called `peerSummary` below, returns, for set `s`, the indexes of its first 10 peers and the total number of its peers. Its peers are the other members of its group, at similarity 1, and the members of every group that `similarPairs` paired with its group, at that pair's similarity, excluding every set whose `owner` equals `s`'s owner. Peers are ordered by descending similarity, compared exactly as `inter·union′` against `inter′·union`, and then by the identifier the calling rule supplies for each set. It reads each group's members presorted by that identifier and a per-group count of members per owner, so the cost for one set is proportional to the number of groups paired with its group plus 10 for each distinct similarity among them, and a group of N identical sets costs O(N) in all. `<pct>` in every message is `100·inter/union` rounded down in integer arithmetic, and 100 for a member of the same group.
  - **Cost bound.** Each rule's time is proportional to the total number of words in its units plus the posting entries the prefix filter probes and the candidate group pairs it verifies, and its memory to the total number of words plus the number of group pairs at or above the threshold. A file bundled in N artifacts, identical after normalization, forms one group and costs O(N). ## Non-goals

- An embedding-based semantic overlap report. The embedding provider is optional, replaceable through the SPI, can be disabled, and is versioned by model, and filesystem-source lint and sync have no embedding path (§13.11.3, §13.12, §4.7). A registry-side advisory report can be proposed separately.
- A registry-side duplicate or overlap report across layers over stored rows. Ingest sees one layer (`pkg/registry/ingest/ingest.go:528-551`), and a cross-layer pass over stored bodies is a separate design. `podium lint` covers the union of a filesystem registry's layers.
- Bounding the listing growth that MCP `load_artifact` materialization causes. Skills accumulate one load at a time into native directories (§6.6), and no pre-delivery check can bound that.
- A listing check for `kind: marketplace` targets. Marketplace consumers install a subset of plugins, and the listing reflects the publisher's view rather than the consumer's (§7.8). A per-plugin estimate can follow.
- Predicting which entries a harness shortens or drops. That depends on the harness version and on per-user state such as invocation frequency.
- Built-in per-harness budgets, or a context-window-fraction setting. Podium cannot observe the model's context window or the user's harness settings, so budgets are absolute characters with one default.
- Duplicate detection for binary bundled resources.
- Running the `DOMAIN.md` lint rules at registry ingest. §4.5.2 calls the unresolved-import warning an ingest-time warning, and §4.5.5 has lint warn on `DOMAIN.md` `discovery:` blocks under `discovery.allow_per_domain_overrides: false`, but ingest lints with a nil registry (`pkg/registry/ingest/ingest.go:541`) and reports neither. This proposal leaves that divergence as it is and states only the `DOMAIN.md` checks `podium lint` runs (SPEC-3 Edit 2). A separate proposal can give ingest a registry view to lint `DOMAIN.md` against.
- Extending `lint_suppress` to the size warnings or to `lint.skill_metadata_field_ignored`. The size thresholds become tunable through §13.12 instead.
- `--harness`, `--profile`, or identity flags on `podium lint` (D-1).
- A `registry.yaml` key for the lint thresholds, or an environment variable or flag for the listing budget.
- SARIF or other output formats beyond the `--json` envelope, and exit-code values that distinguish a tool failure from a lint failure.
- A spec catalog of every lint code. The spec names only the codes its text defines.
- Printing the resolved `listing_budgets` in `podium config show` (§7.7).
- MinHash or LSH candidate selection (D-7).

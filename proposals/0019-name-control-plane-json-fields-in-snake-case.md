## Summary

**What changes.**

- §7.2 gains a first subsection, §7.2.1, fixing the control-plane JSON convention: lower snake_case field names, one name for one value across a request and its response, a credential returned once by the operation that mints it, RFC 3339 timestamps, and a duration written in the string form the matching request field accepts. The SCIM 2.0 receiver is exempted by name.
- §7.3.1 gains the layer object and §7.3.2 gains the receiver object, each fixing its field list.
- Five response types stop reaching the wire under Go field names, across twelve endpoints. `store.LayerConfig`, `store.Quota`, `core.EffectiveLayer`, and `core.ReembedResult` with its `core.ReembedFailure` entries take snake_case JSON tags. `webhook.Receiver` takes a projection in `pkg/registry/server` instead, because tagging it would rewrite an on-disk format.
- The tenant identifier leaves the layer object, closing a disclosure on a read that is not admin-gated, and it leaves the receiver object with it, because SPEC-3's projected field list carries none. `GET /v1/quota`'s top-level `tenant_id` stays, and so does the `id` of each element of §7.3.3's tenant object, because §7.2.1 permits a field whose subject is the tenant itself.
- `git_provider` gains the setters §7.3.1 already promises, so a layer can name the provider whose signature scheme verifies its inbound deliveries. A layer registered over HTTP is set through the request body. A layer declared in the `registry.yaml` `layers:` block is set through a new `source.git.git_provider` key beside the existing `force_push_policy`, because `bootstrapDeclaredLayers` re-seeds every declared entry from the YAML on each boot and would otherwise revert an HTTP-set value. No CLI flag is added.
- The receiver's `debounce` is reported as the duration string the request accepts, so a client can feed a read back into an update. The receiver object's three timestamps are emitted in UTC by the same projection, because the worker records `last_delivery` and `last_failure` from an unnormalized clock and §7.2.1 requires UTC.
- The layer object's `created_at` is normalized to UTC where the Postgres backend scans it, because `lib/pq` returns a `timestamptz` in the connection's session time zone and the nullable stamps beside it are already normalized on that read. Without it §7.2.1 would state a rule the standard deployment contradicts, and the standard and standalone deployments would emit the same field in two forms.
- The in-repo web UI reads the layer object's new member names, and the committed `web/bundle` is rebuilt, in the same commit as the server change. The quota client and the bundle are paired the same way with the `store.Quota` tags.
- The Go suite's Go-name assertions, the layer-record paragraph of the web UI design brief `web/DESIGN.md`, `docs/reference/http-api.md`, `docs/deployment/layers.md`, `test/manual-validation.md`, and `CHANGELOG.md` follow.

**Fixed decisions.**

- The convention is stated for the whole control plane and every endpoint that violates it is converted here. Stating a rule in §7.2.1 and leaving the untagged records in violation would land a specification the shipped code contradicts.
- §7.2.1's tenant rule bars a record from restating a tenant that is not its own subject. `GET /v1/quota`'s top-level `tenant_id` and the `id` of each §7.3.3 tenant object are permitted and unchanged. The layer object and the receiver object each drop theirs; the layer object's removal is DEFECT-2, and the receiver object's follows from SPEC-3's field list. TEST-2 and TEST-5 pin both halves.
- The mechanism is a JSON tag where the type is not JSON-persisted, and a projection where it is. `webhook.Receiver` is persisted verbatim by `FileStore` to the operator's `PODIUM_WEBHOOK_STORE_PATH` file, whose format is documented in-code as "a flat array of Receiver structs" (`pkg/webhook/file_store.go:14-19`), so a tag there would rewrite an on-disk format and orphan every existing operator file. `store.LayerConfig`, `store.Quota`, `core.EffectiveLayer`, `core.ReembedResult`, and `core.ReembedFailure` are not JSON-persisted, so a tag is the smaller change for them.
- Every field emitted today is emitted after the change under its snake_case name, with the same presence semantics, except the tenant identifier, which the layer object and the receiver object both stop carrying. No `omitempty` is added or removed. `created_at` stays, `deleted_at` stays and keeps marshalling as `null` on a live layer, and `groups` and `users` keep marshalling as `null` when unset. Beyond the key names the change alters value forms in the receiver object and in the layer object, in every case because §7.2.1 requires it. In the receiver object `debounce` becomes the request's duration string, and `created_at`, `last_delivery`, and `last_failure` are emitted in UTC. In the layer object `created_at` is emitted in UTC on the Postgres backend, which reads it back today in the connection's session time zone. It closes the three named defects and makes no other alteration.
- The receiver object's timestamps are normalized in the projection rather than at the store write. `Worker.recordResult` assigns `cur.LastFailure = now()` and `cur.LastDelivery = now()` (`pkg/webhook/webhook.go:348`, `:354`) from a clock that defaults to bare `time.Now` (`:301-304`), so on a registry process whose local zone is not UTC those two members reach the wire with a zone offset, which is RFC 3339 but is not what §7.2.1 requires. Normalizing at the write site would still leave every receiver already stored in an operator's `PODIUM_WEBHOOK_STORE_PATH` file emitting its stored offset, because neither `MemoryStore` nor `FileStore` converts on the round trip. `receiverToWire` is the one place that governs the emitted form for every stored and newly written receiver alike.
- `tenant_id` leaves the layer object. `LayerEndpoint` carries one `tenantID` fixed at construction (`pkg/registry/server/layers.go:45`, `:187-189`, wired at `internal/serverboot/serverboot.go:1249`) and every handler scopes its store calls to it, so the value is constant across the response and is a server-side boot constant the caller never supplied. On a multi-tenant registry it republishes the registry's stored org ID on a read that is not admin-gated.
- The layer's webhook HMAC secret stays absent from the layer object. `store.LayerConfig.WebhookSecret` keeps `json:"-"`.
- The receiver's `secret` keeps the imperative `***` masking on the list, read, and update paths and keeps returning the unmasked secret on create. That is documented behaviour and a different rule, because the receiver secret is operator-supplied.
- Podium is pre-1.0. No flag, environment variable, `registry.yaml` key, content negotiation, or dual serialization preserves the Go-cased keys.
- No §6.10 error code is added and no matrix cell changes.

## Current state and the gap

### The casing defect

`POST /v1/layers` decodes `LayerRegisterRequest` (`pkg/registry/server/layers.go:466-489`), which carries a complete snake_case tag set, and answers `LayerRegisterResponse` (`:533`), whose `Layer store.LayerConfig \`json:"layer"\`` member is the store record marshalled as it stands. `store.LayerConfig` (`pkg/store/store.go:258`) carries a tag on three of its fields and nothing on the other eighteen, so one endpoint accepts `source_type` and answers `SourceType`, and one object carries `TenantID` beside `force_push_policy`.

`docs/reference/http-api.md:356` documents the request's spelling for both, so a client written from the reference cannot read the response.

### The boundary

Every response type declared inside `pkg/registry/server/` is fully tagged and fully snake_case: `HealthResponse`, `ReadyResponse`, `LoadDomainResponse`, `DomainDescriptor`, `ArtifactDescriptor`, `SearchResponse`, `CatalogResponse`, `CatalogEntry`, `LoadArtifactResponse`, `LargeResourceLink`, `ErrorResponse`, `BatchLoadEnvelope`, `BatchResource`, `registryEvent`, `LayerCapabilities`, `tenantOut`, and `tenantQuotaOut`. Every ad-hoc `map[string]any` body uses snake_case literal keys.

Every defect is a record from another package handed to `writeJSON` with no conversion:

|:--|:--|:--|
| `store.LayerConfig` | `pkg/store/store.go:258` | `POST /v1/layers`; `POST\|PUT /v1/layers/update`; `GET /v1/layers`; `GET /v1/layers?deleted=true`; `POST /v1/layers/reorder` |

### The three contract defects the survey found

**DEFECT-1: `git_provider` cannot be set.** §7.3.1's trigger table states that the git provider webhook is "Configured at layer-creation time". `store.LayerConfig.GitProvider` is never assigned in non-test code: the only references are a read at `pkg/registry/server/webhook_ingest.go:59`, the SQL column bind and scan in both backends, and the field declaration. `webhook_ingest.go:60-62` therefore falls back to `"github"` for every layer, so a GitLab or Bitbucket source is verified against GitHub's signature scheme and its deliveries fail with no configuration that fixes them.

**DEFECT-2: the tenant identifier is published on a read that is not admin-gated.** `GET /v1/layers` returns `TenantID` on every record. `LayerEndpoint` holds a single `tenantID` field fixed when the endpoint is constructed (`pkg/registry/server/layers.go:45`, `:187-189`), wired once at boot from the deployment's tenant (`internal/serverboot/serverboot.go:1249`), and every layer handler scopes its store calls to `e.tenantID` (`layers.go:349`, `:617`, `:901`, `:1055`, `:1188`). The layer routes are mounted on the outer mux (`internal/serverboot/serverboot.go:1271-1272`) outside `Server.withTenantRouting` (`pkg/registry/server/server.go:441-472`), so no per-request resolution runs on them. The emitted value is therefore constant across the response and is a server-side boot constant the caller never supplied. On a multi-tenant registry the stored value is the internal org ID, which need not be the organization name the caller knows. The layer read is deliberately not admin-gated, which is why the webhook secret carries its own defensive redaction.

**DEFECT-3: `debounce` cannot be round-tripped.** The create and update bodies accept a duration string (`pkg/registry/server/webhooks.go:57`, `:145`, parsed by `parseDebounce`), and the stored field is a `time.Duration` (`pkg/webhook/webhook.go:64`), which marshals as an integer. A client sends `{"debounce": "30s"}` and reads back `30000000000`, so it cannot send a receiver it has read back to `PUT /v1/webhooks/{id}` without converting.

## Spec amendment: §7.2.1 control-plane JSON conventions

**SPEC-1.** Anchor: `spec/07-external-integration.md`, §7.2. Append a new subsection at the end of §7.2, after the paragraph beginning "Below the inline cutoff" and immediately before the `## 7.3 Host Integration` heading. §7.2 has no subsections today, so §7.2.1 is the next ordinal at that level and no sibling is renumbered.

> ### 7.2.1 Control-Plane JSON Conventions
>
> Every control-plane request body and response body is JSON, and every field name in it is lower snake_case: `source_type`, `last_ingested_at`, `webhook_url`. A field name is part of the API contract and is chosen for the client, so it is independent of the name the registry uses for the same value internally, and where a request and a response carry the same value they name it identically.
>
> A credential is returned once, by the operation that mints or rotates it, and no other response carries it (§7.3.1, §7.3.2). A record inside a response omits a field that restates the tenant the response is confined to, where that tenant is not the record's own subject. A field whose subject is the tenant itself is a different thing and is permitted: the §4.7.8 quota read reports the tenant whose limits it returns in a top-level `tenant_id`, and the §7.3.3 tenant object names the tenant each element describes in its `id`, on the one read that crosses orgs. A timestamp is RFC 3339 in UTC. A duration is written in the same string form the matching request field accepts, so a client returns a value it read without converting it.
>
> The convention binds every control-plane endpoint. The §6.10 error envelope, the §5 meta-tool results, the §7.6.2 bulk-fetch envelopes, and the §7.3.2 outbound event bodies are already stated in these terms and are unchanged by it. A response body whose field names are fixed by a protocol outside this specification keeps that protocol's names; the SCIM 2.0 receiver (§6.3.1) is the one such surface, and it is outside this rule.

## Spec amendment: §7.3.1 the layer object and the git provider

**SPEC-2.** Anchor: `spec/07-external-integration.md`, §7.3.1. Two paragraphs land after the paragraph beginning "`podium layer register` returns the webhook URL and HMAC secret" and before the paragraph beginning `**User-defined layers.**`.

> **The layer object.** The layer-management endpoints that return a layer return it as the object `{id, source_type, repo, ref, root, local_path, order, user_defined, owner, public, organization, groups, users, git_provider, force_push_policy, last_ingested_at, last_ingested_ref, created_at, deleted_at}`, under §7.2.1. `force_push_policy` is carried by a layer that sets one and is omitted by a layer that does not, and `last_ingested_at` is carried once the layer has completed an ingest and is omitted before that. Every other member is carried on every layer. `POST /v1/layers` and `POST|PUT /v1/layers/update` return it under `layer`; a `git` registration and an update that requests a secret rotation carry `webhook_url` and `webhook_secret` beside it, and a `local` registration and an update that requests no rotation carry neither. `GET /v1/layers` and `POST /v1/layers/reorder` return an array of it under `layers`. `created_at` is the layer's registration time. `deleted_at` reports the §8.4 soft-delete tombstone and is null on a layer that carries none, so a reader computes the remaining recovery window from it.
>
> The layer object never carries the layer's inbound webhook HMAC secret under any name. That credential is returned once, in the `webhook_secret` field of the registration response and of an update that requests a rotation; the layer read is not admin-gated, and the visibility rule narrows which layers it returns rather than which fields each layer carries. The layer object also carries no tenant identifier, under §7.2.1: the layer-management endpoints serve one tenant, so the value would be constant across every record and would republish the registry's stored tenant identifier on a read that is not admin-gated.

A further block lands after the paragraph beginning `**Admin-only registration fields.**` and before `**Errors.**`, closing DEFECT-1:

> **Git provider selection.** A `git` layer names the §9.1 `GitProvider` whose signature scheme verifies its inbound webhook deliveries, through the `git_provider` field of the registration and update bodies. The value is one the registry has registered; a value it does not carry is refused with `400 registry.invalid_argument` naming the field. A registration that omits it, and a layer stored before this field existed, resolve to `github`, which is the default the registry applied to every layer before the field was accepted. The field applies to a `git` source alone, and a registration that sets it on a `local` source is refused on the same code.
>
> A layer declared in the registry config, which §4.6 defines as the admin-defined layer list, names its provider in the declaration's git source block instead, because the registry re-applies every declared entry at each start and the declaration is authoritative for the fields it carries. A declared provider the registry has not registered aborts startup with an error naming the layer and the value, on the same terms as an invalid declared force-push policy.

## Spec amendment: §7.3.2 the receiver object

**SPEC-3.** Anchor: `spec/07-external-integration.md`, §7.3.2, after "Receivers are configured per org (URL + HMAC secret)."

> **The receiver object.** The receiver CRUD endpoints return a receiver as the object `{id, url, secret, event_filter, disabled, failure_count, last_delivery, last_failure, created_at, debounce}`, under §7.2.1. `debounce` is the trailing window written in the same duration string the request body accepts, so a client returns a receiver it read without converting the value, and it is omitted on a receiver that sets none. `secret` carries the receiver's HMAC secret on the creating response alone, so the operator records it once; the list, the single read, and the update return it masked. The object carries no tenant identifier, under §7.2.1.

The write sites need no change and no stored row moves. Every non-test writer stamps UTC (`pkg/registry/server/layers.go:910`, `internal/serverboot/serverboot.go:503`, `:696`), both backends persist the column in UTC (`pkg/store/postgres.go:1220`, `pkg/store/sqlite.go:760`), and the SQLite backend already parses it back as `Z` (`pkg/store/sqlite.go:931-932`), so the conversion closes a divergence between the standard and standalone deployments on one observable value, which §2.2 does not permit. `store.Memory` holds the value it is handed and is an undocumented test backend (`internal/serverboot/serverboot.go:2339-2344`), so it needs no conversion.

### CODE-4: `git_provider` becomes settable

`LayerRegisterRequest` (`pkg/registry/server/layers.go:466-489`) gains `GitProvider string \`json:"git_provider,omitempty"\``. `register` (`:900`) assigns it onto the stored config, and `update` patches it on the same terms as the other patchable fields.

The `update` handler's doc comment enumerates the patchable set as a closed list: "Allowed mutations: visibility (Public, Organization, Groups, Users), Ref, Root, LocalPath, Owner, ForcePushPolicy, and a webhook-secret rotation (rotate_webhook_secret)" (`pkg/registry/server/layers.go:673-677`). Making the field patchable falsifies that sentence, so `GitProvider` is added to it beside `ForcePushPolicy` in the same commit. The following sentence, which names `TenantID`, `ID`, `SourceType`, and `CreatedAt` as immutable, stays correct and is unchanged.

The value is validated against the providers the registry has registered, through the same registry `webhook_ingest.go` resolves against, and an unregistered value is refused with `400 registry.invalid_argument` naming the field. A value set on a `local` source is refused on the same code, because the field governs inbound webhook signature verification and a `local` source receives none.

An empty value resolves to `github` at the point of use, which is the fallback `webhook_ingest.go:60-62` already applies, so a layer stored before this change keeps verifying exactly as it does today and no migration is required.

The HTTP request body is the setter for a layer registered at runtime. It is not a sufficient setter for a layer declared in the `registry.yaml` `layers:` block, because that path re-seeds the stored record from the YAML on every start. `bootstrapDeclaredLayers` calls `PutLayerConfig` for every declared entry on each boot with no already-stored guard (`internal/serverboot/serverboot.go:603-610`), `layerConfigFromEntry` builds the record without assigning `GitProvider` (`:670-721`, whose `case hasGit:` arm sets `SourceType`, `Repo`, `Ref`, `Root`, and `ForcePushPolicy` alone), and both backends implement `PutLayerConfig` as a full upsert that assigns the column from the passed struct (`pkg/store/postgres.go:1194-1219`, `pkg/store/sqlite.go:749-760`). An HTTP-set provider on a declared layer is therefore overwritten with the empty string at the next restart and `webhook_ingest.go:59-62` falls back to `github` again, which is the condition DEFECT-1 states. That reconcile is authoritative for every field a declared entry carries, and this proposal does not change it.

The declared path therefore gains the field on its own surface. `yamlGitSource` (`internal/serverboot/yaml_config.go:231-238`, which already carries `force_push_policy`) gains `GitProvider string \`yaml:"git_provider,omitempty"\``, and `layerConfigFromEntry`'s `case hasGit:` arm assigns `lc.GitProvider = entry.Source.Git.GitProvider` beside its `lc.ForcePushPolicy` assignment. The key is declarable on a git source alone, because `yamlGitSource` is reachable only under `source.git`, so the local-source refusal the HTTP path needs has no counterpart here. A declared value the provider registry does not carry aborts startup with an error naming the layer and the value, in the style of the `validForcePushPolicyYAML` refusal in `internal/serverboot/serverboot.go`, whose error return aborts the boot before any listener binds. An entry that omits the key re-seeds the empty string, which resolves to `github` at the point of use, so an existing `registry.yaml` keeps its present behaviour with no edit.

The same reconcile also governs the declared layer's inbound webhook secret, which the provider selection only matters for. `layerConfigFromEntry` assigns no `WebhookSecret` (`internal/serverboot/serverboot.go:670-721`, and a grep for `WebhookSecret` under `internal/` returns nothing), and the only non-test assignments are the register path and the rotation patch (`pkg/registry/server/layers.go:1017`, `:753`), so a declared layer holds an empty secret until an operator rotates one, and the reconcile erases a rotated secret at the next start along with any HTTP-set provider. Every provider refuses an empty secret outright (`pkg/layer/webhook/webhook.go:85-87` for GitLab), so a delivery to a declared layer verifies only after a rotation performed since the last start. This proposal does not change that, and TEST-9's declared-path arm rotates after its final restart for exactly this reason.

Both validations read the same process-global registry the delivery path resolves against, `webhook.Default` (`pkg/layer/webhook/registry.go:35`, seeded by `newDefault` at `:37-43`, read through `Get` at `:65`), which is seeded with `github`, `gitlab`, and `bitbucket` and extended by a deployment's imported provider modules.

`podium layer register` and `podium layer update` gain no `--git-provider` flag (`cmd/podium/layer.go:83`, `:191` show the analogous `--force-push-policy`). The setter for a layer registered at runtime is therefore the request body of `POST /v1/layers` and `POST|PUT /v1/layers/update`, sent with an HTTP client such as `curl`, which is how S58 exercises it. Neither CLI command can carry the field: `layerRegister` builds a closed body from its own flags (`cmd/podium/layer.go:208-241`) and so does `layerUpdate` (`:96-126`), and neither has a passthrough for an arbitrary key. A flag would be a third configuration surface for one field that §7.3.1 does not require. `docs/deployment/layers.md` documents registration through the CLI and through `registry.yaml`, so it gains prose naming both setters, naming the HTTP request as the runtime setter, and stating that no flag exists. The Documentation changes section carries the constraint that prose satisfies. `docs/reference/cli.md` is unchanged, because no flag is added.

**IMPLEMENTOR'S CHOICE:** whether the HTTP validation reads the provider registry at request time or a snapshot taken at boot. The constraint is that a provider the registry cannot resolve at delivery time must be refused at registration time, so the two readings cannot disagree. The declared-layer validation runs during boot and reads the registry directly.

## Testing

Every case carries `// Spec: §7.2.1` and its object's section. Every new pin decodes into `map[string]json.RawMessage` rather than into a typed struct, because a typed decode reads through the same tags the handler encoded with and cannot observe the emitted names.

**TEST-1: the layer object's key set, per endpoint.** A table over `POST /v1/layers` (git and local), `PUT /v1/layers/update` (with and without rotation), `GET /v1/layers`, `GET /v1/layers?deleted=true`, and `POST /v1/layers/reorder` asserts **set equality** against a per-arm expected set. The expected set is the §7.3.1 list minus the two members §7.3.1 states are conditional, plus `force_push_policy` on an arm whose fixture sets a policy and plus `last_ingested_at` on an arm whose layer has completed an ingest. Set equality rather than containment is what makes a field added later without a spec decision fail, which is how the tenant identifier reached the wire unnoticed. Separate arms assert the empty-list body is exactly `{"layers":[]}`, that `deleted_at` is present and null on a live layer and carries the stamp on the deleted arm, that `groups` and `users` are null when unset, and that `force_push_policy` and `last_ingested_at` are both absent on a layer that sets no policy and has never ingested.

A further arm pins §7.2.1's UTC rule on the layer object, at the store level and in the Postgres lane, because that is the one backend on which the offset is reachable. It appends a `timezone` runtime parameter naming a fixed non-UTC zone to `PODIUM_POSTGRES_DSN`, which `lib/pq` forwards as a startup parameter (`github.com/lib/pq@v1.12.3/connector.go:433-435`), opens a second handle over that DSN, and writes two layer configs. The first is live and carries a `CreatedAt` and a `LastIngestedAt`, and the arm reads it back through `GetLayerConfig` and `ListLayerConfigs`, both of which filter `deleted_at IS NULL` (`pkg/store/postgres.go:1236`, `:1255`). The second additionally carries a `DeletedAt`, so those two reads exclude it and the arm reads it back through `ListDeletedLayerConfigs` (`pkg/store/postgres.go:1335`), which is the query the `?deleted=true` list arm runs (`pkg/registry/server/layers.go:1052-1053`). On each read the arm asserts that every returned stamp reports `time.UTC` as its location and the same instant it wrote, which covers `created_at`, `last_ingested_at`, and `deleted_at`. The arm skips cleanly when `PODIUM_POSTGRES_DSN` is unset, on the footing of `TestPostgres_ConformanceSuite` (`pkg/store/postgres_test.go:27-38`) and of the live-infrastructure escape hatch in `.claude/rules/test-coverage.md`. No server-level arm covers this, because the handler marshals whatever the store returns and every write site already stamps UTC, so a memory-backed or SQLite-backed arm would pass whether or not the conversion lands.

**TEST-2: the withheld fields, structurally.** Registers a git layer, captures the one-time `webhook_secret`, then drives all five routes and asserts for each that the literal secret value appears in the envelope's `webhook_secret` alone and in no record, under any key and any casing, and that no key named `tenant_id` or `TenantID` appears on any body. Asserting against the raw bytes rather than a decoded key name is what survives a future refactor that reintroduces either under a new name.

**TEST-3: request and response agree.** Reflects over `LayerRegisterRequest` and `store.LayerConfig` and asserts every JSON tag the request declares appears on the response under the same name, naming and explaining the exceptions. This is the mechanical pin on §7.2.1's one-name-one-value rule.

**TEST-4: the receiver.** Asserts set equality of the key set against a per-arm expected set on create, on the list, on the single read, and on the update, so the dropped `TenantID` is pinned as absent under any spelling. The expected set is SPEC-3's member list minus `debounce` on an arm whose receiver sets none, and the full list on the arm that sets `"60s"`, because SPEC-3 states `debounce` is omitted on a receiver that sets none. The same case also asserts `debounce` reported as `"1m0s"` for a `"60s"` request and **round-tripped** verbatim into a `PUT` that answers 200, which is DEFECT-3's regression test; `secret` unmasked on create and `***` on the list, read, and update paths; and an operator store file written before the change loading unchanged.

**Implementation note (S5, 2026-09-04): the round trip is asserted without the `secret` member.** The staged wording says the read is round-tripped verbatim into the `PUT`. A byte-for-byte replay of the read object sends `"secret": "***"` back, and the update path assigns whatever secret the body names (`pkg/registry/server/webhooks.go:227-229`), so the replay would answer 200 while overwriting the receiver's HMAC key with the mask sentinel. Treating the mask as a no-op on input is a rule §7.2.1 does not state and CODE-2 does not stage, and adding it would widen S5 beyond the projection. The landed arm therefore drops the `secret` member from the replayed body, which leaves `debounce` and the remaining members carried verbatim, and it reads the receiver back out of the store after the `PUT` and asserts the minted secret survives and the failure count is what the update wrote. That read-back also records the second effect of the replay: the read-back body carries `"disabled": false`, which the unchanged update path treats as a re-enable and which clears `failure_count` (`webhooks.go:234-240`). The mask-as-input rule and the unconditional failure-count clear are both deferred to their own proposal.

A further arm pins §7.2.1's UTC rule on the receiver object. It seeds the store with a receiver whose `CreatedAt`, `LastDelivery`, and `LastFailure` all carry a fixed non-UTC offset, reads the receiver through the list and the single read, and asserts each timestamp member of the emitted object ends in `Z`. Seeding through the store rather than through the worker is what keeps the arm at the level the projection lives on, and it is the state a registry in a non-UTC zone reaches, because `MemoryStore.Put` writes the two delivery stamps verbatim and defaults `CreatedAt` only when it is zero (`pkg/webhook/webhook.go:493-509`). A companion unit arm drives the worker itself with `Worker.Now` returning a fixed-offset time, the injection point `pkg/webhook/debounce_test.go:68` already uses, and asserts the receiver the worker persists is emitted in UTC through the same projection.

## Open questions

**OQ-1. Should the sweep be bounded to the layer endpoints?** This proposal converts every endpoint in the table above, because §7.2.1 is stated for the whole control plane and a spec rule the registry contradicts on the endpoints it leaves alone is the divergence the pipeline exists to prevent. The layer surface carries most of the work, because it is the only one with a CLI reading and hand-run scenarios. The quota conversion also has a browser client and so carries a client edit and a bundle rebuild of its own (UI-3), and the `core.EffectiveLayer` conversion reaches four end-to-end decoders (CODE-3). The receiver and re-embed conversions are mechanical with test-only in-repo consumers.

**OQ-2. Should DEFECT-1's setter land here or separately?** It is bundled because `git_provider` is a field of the object §7.3.1 defines in SPEC-2, so the spec sentence that names the field and the code that makes it settable are the same edit. Splitting it would mean SPEC-2 names a field the registry accepts on no request.

**OQ-3. Does the HTTP `git_provider` validation read the provider registry at request time or at boot?** Recorded as an implementor's choice in CODE-4, bounded by the requirement that registration-time and delivery-time resolution cannot disagree. The declared-layer validation is fixed: it runs inside `layerConfigFromEntry` during boot and reads `webhook.Default` directly.

## Non-goals

- Adding or removing `omitempty` beyond what is emitted today. `deleted_at` keeps marshalling as `null` on a live layer, and `groups` and `users` keep marshalling as `null` when unset.
- Withholding `created_at`. It is renamed and kept, on the same terms as every other field the response carries today.
- Any change to a request body other than the `git_provider` field CODE-4 adds. Every request type in the server package is already snake_case.
- A null-versus-omitted rule for the whole control plane. Several shipped responses emit `null` for an empty list, and settling that would change endpoints this proposal does not touch.
- Tagging `webhook.Receiver`, which would rewrite an on-disk format.
- The SCIM 2.0 receiver, which §7.2.1 exempts by name.
- Removing `GET /v1/quota`'s top-level `tenant_id`, or the `id` of each element of §7.3.3's tenant object. §7.2.1 permits both and the endpoints keep them.
- A `--git-provider` CLI flag. A layer registered at runtime is set through the `POST /v1/layers` and `POST|PUT /v1/layers/update` request body, sent with an HTTP client such as `curl`; `podium layer register` and `podium layer update` each build a closed body from their own flags (`cmd/podium/layer.go:208-241`, `:96-126`) and cannot carry the field. A declared layer sets it in the `registry.yaml` `source.git.git_provider` key CODE-4 adds.
- Changing what the boot reconcile of a declared layer overwrites. `bootstrapDeclaredLayers` keeps re-seeding every declared entry from the YAML on each start, for `git_provider` as for every other declared field.
- A compatibility shim, dual emission, or content negotiation.
- Restructuring the layer record into nested source or visibility objects.
- Any change to which layers a caller reads. The §7.3.1 read visibility rule and `readableBy` are untouched.

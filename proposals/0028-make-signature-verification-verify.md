# Proposal 0028: Make signature verification verify

- Issue: (to be filed)
- Status: Draft
- Date: 2026-09-15

This document stages the proposed spec, code, test, and documentation changes. It does not modify any spec, code, or doc file. Apply the changes in the staged sections after sign-off.

## Summary

**What changes.**

- `pkg/sign` splits the §4.7.9 policy into two axes. A signature the response carries is verified under any policy other than `never`, with no sensitivity consulted. Above `never`, `PODIUM_VERIFY_SIGNATURES` governs whether a *missing* signature aborts the load; `never` checks nothing, including a signature the response carries. The policy takes `never` or `always`, and `medium-and-above` is deleted, because after the split its only behavior is to waive the missing-signature requirement on a label the registry supplies (CODE-13). `sign.EnforceVerification` today returns `nil` before touching the provider whenever `needsVerification` is false, so a response declaring `sensitivity: low` skips the cryptographic path entirely.
- `pkg/sign` makes `Noop.Verify` refuse every signature. `Sign` is unchanged. The value `Sign` produces is `"noop:" + contentHash`, and `content_hash` is served in the clear on every `load_artifact` response, so accepting it lets any party mint a passing envelope for any artifact.
- `cmd/podium-mcp` reorders `deliverLoadArtifact`: the signature check runs first, the content-hash recomputation second, and the §8.2 read event, the §4.4.1 sandbox gate, and the §4.4.1 runtime gate move below both, because each reads manifest bytes that nothing has bound to the served digest at the point it runs today. The same function also maps a missing signature onto `materialize.signature_missing`, a §6.10 cell no served error currently carries. The verification prefix of that order becomes one method that the §5.0 `resources/read` mirror also calls, so the mirror stops returning a registry-served manifest with no signature or content-hash check (CODE-12).
- The registry signs at ingest by default. `PODIUM_SIGN` resolves to `registry-key` when unset and accepts `none` to turn signing off. The keypair is already generated on first run under the process's home, so a standalone deployment whose home persists needs no operator action and an unenforcing consumer ignores the envelope. A registry with signing on and no `PODIUM_SIGN_KEY_PATH` refuses to start unless its store is the SQLite store in the directory the default key resolves to, so a Postgres deployment, or a SQLite file moved off that directory, sets `PODIUM_SIGN_KEY_PATH` on the store's persistent storage or sets `PODIUM_SIGN=none`, and a key never sits on storage with a different fate from the store it signs (CODE-4). The Helm chart cannot generate a key, because its root filesystem is read-only and every replica has to sign under one key, so it mounts an operator-supplied Secret at `PODIUM_SIGN_KEY_PATH` and refuses to render without one unless signing is set to `none`. The documented start that generates that key runs under `env -i` with a scratch `HOME`, because the first start of this release runs the one-shot §13.4 rewrite on whatever store it opens and would otherwise sign the operator's own standalone store under the cluster key (CODE-8).
- The consumer defaults become `registry-managed` for `PODIUM_SIGNATURE_PROVIDER` and `always` for `PODIUM_VERIFY_SIGNATURES`, and `podium-mcp` resolves its verification material once in `loadConfig` and refuses to start when a policy above `never` resolves none. The standalone bootstrap stops writing `defaults.verify_signatures: never` and writes no key material in its place. `pkg/sign` gains one resolver for the registry-managed key file, `KeyFilePath`, which `internal/serverboot`'s existing `registrySigningKeyPath` becomes a delegate of, plus the readers for that file's `public:` and `private:` lines. A set `PODIUM_SIGNATURE_VERIFY_KEY` is authoritative, and a malformed one refuses the start rather than falling through to the key file. A consumer with no `PODIUM_SIGNATURE_VERIFY_KEY` resolves the same file the registry writes, so on a standalone machine the producer and the consumer cannot resolve different keys, and no configuration file carries key material.
- The §7.6.2 bulk-fetch envelope carries `signature`, so the §6.6 step-2 signature check runs on a bucket the prefetch warmed exactly as it does on a live fetch, and the prefetch warms a bucket only when the bytes it would hold reproduce the served `content_hash`. An artifact carrying bundled resources, or an `extends:` child, fails that recomputation, because the batch envelope delivers resources by reference and the merged frontmatter rather than the child's pre-merge bytes, so the prefetch skips it: `offline-only` then reports `network.offline_cache_miss` for it rather than a refusal the consumer cannot repair, and the other cache modes fetch it live (CODE-9).
- §4.7.9 is rewritten. It states what a signature attests, states that the identity and log properties keyless verification does not check are not checked, drops the claim that the registry key is rotated quarterly, and states that a rotation invalidates every prior envelope. §6.6 step 2 states the verification order normatively, §6.2 gains the consumer-side signing rows, §6.9 gains the failure rows, §6.11's host-configuration recipes gain the consumer-side signing variables, §7.5.2 gains the policy key the §13.10 deletion removes from the spec, §7.6.2's envelope gains `signature` and states which items the MCP server warms, §7's ingest-error table gains `ingest.sign_failed`, §9.1's `SignatureProvider` built-in becomes the registry-managed key, §13.10's signing row flips and its verification relaxation is deleted, §13.12 gains a `### Signing` subsection, and the §14 scenarios stop offering Sigstore-keyless as a registry signing mode and stop enumerating an MCP consumer's variables without the verification key.

**Fixed decisions.**

- The whole of this proposal ships in the release that carries proposal 0026. 0026 rewrites every stored content hash in a pass the registry runs once, on the first start of the new version, before it ingests or serves; where a signer is configured that pass re-signs every row it rewrites and mints a first envelope for a stored row already at the framed digest that carries none. Flipping the producer default in the same release means that one pass signs every row it writes. A row the pass leaves untouched keeps whatever envelope it had, so an unsigned row classified `unreproducible`, `body_missing`, or `body_unavailable` stays unsigned and an upgraded consumer refuses it with `materialize.signature_missing`. A row classified `signature_unverified` carries a signature by construction, keeps the envelope that failed to verify, and an upgraded consumer refuses it with `materialize.signature_invalid` under any policy other than `never`. The constraint is hard: a marker records that the pass completed and nothing runs it again, so a default flipped in a later release signs no stored row.
- 0026 lands and is implemented first. Its pass takes the boot path's own signer, and the start is refused in two cases while the rewrite has not completed: a row the pass would rewrite is signed and no signer is configured, and signing is on, the key file is absent, and a stored row carries a signature. The signing-mode test behind both lives in one function, `registrySigningEnabled`, so CODE-4's change there reaches the loader and both refusals together, and no logic in the pass changes here. CODE-4 and TEST-4 own the fixtures in 0026's tests that read an unset `PODIUM_SIGN` as no signer, and the no-signer refusal's error wording. The Relationship section states the handoff.
- The policy has two axes. Verification of a present signature is unconditional under any policy other than `never`; the policy governs only a missing signature. `needsVerification` is deleted rather than kept beside the new predicate.
- The verification order is signature, then content hash, then every gate that reads the manifest. Neither direction may be relaxed, and the cache-served path takes the same order because `deliverLoadArtifact` is shared. The §5.0 `resources/read` mirror runs the same two checks through the same method before it returns an artifact's text (CODE-12).
- The policy reads no `sensitivity`, and `PODIUM_VERIFY_SIGNATURES` takes `never` or `always`. `medium-and-above` is deleted rather than kept as a rollout posture (CODE-13): after the split its only behavior waives the missing-signature requirement on a label the registry supplies, and for a child declaring `extends:` the merge takes the most-restrictive value while the hash covers the child's pre-merge bytes, so no attested source for that label exists.
- `Noop.Sign` stays. The audit anchor and the ingest tests depend on it. `Noop.Verify` refuses unconditionally, and "this deployment does not verify" is stated with `PODIUM_VERIFY_SIGNATURES=never`.
- Verification material is resolved once, in `loadConfig`, by one resolver, into one `config` field. There is no second resolution and no capability predicate stated beside the resolver: a failed resolution under a policy above `never` is the startup refusal, and under `never` no material is resolved at all.
- Consumer key distribution stays out of band for every deployment other than standalone, where the key is on the same filesystem. This proposal adds no key-publication route and no trust-on-first-use pin.
- The consumer resolves the registry's key file by the same path resolution the registry uses, `sign.KeyFilePath`, rather than through a `sync.yaml` key. No configuration file carries key material, and the resolution order is stated once, in §4.7.9.
- The statements this proposal falsifies are enumerated once, as AUDIT-1's claim inventory. Each claim carries its finder: a token sweep over the identifiers the claim names, a prose finder for a file that asserts the claim without naming an identifier, or both. No deliverable carries an edit-site list that is not a record of what a named finder returns, and no deliverable carries its own exception to the sweep. The lists that are not such a record name sites a deliverable breaks through behavior rather than through a claim in prose, so no finder returns them, and the deliverable that names each owns it and S9.5 assigns them to no step: CODE-8's and TEST-8's enumeration of the `render` and `renderErr` call sites in `test/chart/render_test.go`, TEST-4's standard-stack e2e boots that the generated-key refusal reaches after a migration, and MAN-1's S64 disposition, whose **Expect** blocks hold only for an unsigned row. The assignment of files to steps is made at S9.5 and both axes are re-run at S17. A list in this document records what the finders return on one tree; the finders are what the implementor runs.
- Sigstore verification correctness is a separate proposal. `SigstoreKeyless.Sign` is implemented and `podium sign --provider sigstore-keyless` mints a keyless envelope (`pkg/sign/sigstore.go:99-146`, `cmd/podium/sign.go:168-175`), but no registry signing mode does, so nothing puts a keyless envelope into the store at ingest and every verification defect there is latent for served artifacts. What lands here is the §4.7.9 text that stops claiming otherwise.
- No path attaches an envelope to a stored row, or replaces one, once the §13.4 first-start rewrite has completed. A row stored unsigned keeps that state and gains an envelope only when a new version of the artifact is ingested, and every earlier version stays as it is. A row signed under a key the registry no longer holds keeps its envelope, and the sentences below name its repair. The proposal states no delete-and-re-ingest rebuild as a repair, because no command hard-deletes a stored row, deleting manifest rows leaves every §4.7.3 dependency edge in place to be duplicated by the re-ingest, and the re-ingest restores only the version each directory currently declares. Restoring the key that signed the rows is the repair for a row whose stored hash is already the framed digest, which covers a key lost or rotated after the §13.4 rewrite and a migrated row the source had already framed, and it requires that key to still exist. A row the rewrite classified `signature_unverified` while it held the pre-framing hash stays at that hash and is not repaired by restoring the key alone. Two existing routes make the rewrite run again over such a row with the right key, and the docs keep both: on an upgraded store, restoring the backup the upgrade order takes, which carries no rewrite marker, and starting with the key that signed the rows (`CHANGELOG.md:87-91`), at the cost of every write made since that backup; and on a migration target, recreating the target store empty and re-running `podium admin migrate-to-standard` with the source's key at the target's `PODIUM_SIGN_KEY_PATH`, because the command clears the target's rewrite marker (`docs/reference/cli.md:627-629`, `CHANGELOG.md:96-108`). A new version of the artifact is the repair only where neither route is available, or where the key that signed the row no longer exists. OQ-5 carries a re-triggerable signing pass.
- Podium is pre-1.0. There is no grace policy value, no "artifacts ingested before the upgrade" exemption, and no compatibility path for an unsigned row.

**Watch out for.**

- **Enabling signing on an existing registry signs no stored row.** `ingest.Ingest` short-circuits on `existing.ContentHash == mr.ContentHash` with `res.Idempotent++; continue` before the signing block, and no ingest path writes a signature onto an existing row. 0026's first-start rewrite signs stored rows once and does not run again after its marker is set, so a registry that enables signing after that start keeps every row stored before it unsigned, and an artifact gains an envelope only when a new version of it is ingested. No command hard-deletes a stored row so that the same version can be re-ingested (`podium layer unregister` soft-deletes), and a delete-and-re-ingest done against the store directly duplicates every dependency edge and restores only the currently declared versions, so the proposal does not offer it as a repair. That is why the release window is a constraint rather than a preference.
- **The standalone relaxation fails open and no code change removes it from an existing machine.** `writeFileIfAbsent` never rewrites `~/.podium/sync.yaml`, so a machine that ran `podium serve` once keeps `defaults.verify_signatures: never` indefinitely, including when it is later pointed at a production registry through `PODIUM_REGISTRY`. The remedy is an operator editing one line, and the proposal says so rather than implying self-healing.
- **The relaxation also fires on the explicit-server-config branch.** `standaloneStartup` bootstraps on both branches, so a SQLite-backed server with an OIDC identity provider on a non-loopback bind writes the relaxation too. Deleting the line removes that leak; do not attempt to rescope the bootstrap itself, which also writes the registry pointer, `registry.yaml`, and the artifacts directory.
- **Do not reintroduce a sensitivity threshold.** `sensitivity` has no attested source for a child declaring `extends:`, so reading it from the hash-covered bytes lowers the gate on exactly the artifacts §4.6 protects, and reading it off the envelope lets the registry opt an artifact out of the requirement. Do not implement the relocation an earlier review asked for.
- **The signature check needs no manifest bytes.** `Provider.Verify(ctx, contentHash, signature)` consumes two scalars off the envelope, which is what makes it runnable before any fetch. Running it first is what turns `verifyContentHash` from a self-consistency check over two registry-supplied values into an integrity check.
- **The cache replays old envelopes through the new gate.** `putExtras` persists the served `sensitivity` and `signature` on the live-fetch path, and `deliverLoadArtifact` is the shared path, so a warmed `offline-only` consumer refuses those artifacts with no in-product recovery. 0026's mandated cache-directory clear repairs it in the same release, which is another reason the two ship together.
- **The prefetch writes buckets with no signature at all.** The §7.6.2 warm-up records `cacheExtras{SkillRaw: e.SkillRaw}` (`cmd/podium-mcp/main.go:2493`) because the batch envelope carries neither `sensitivity` nor `signature`, and all three cache branches return `deliverLoadArtifact` directly rather than falling through to a full fetch (`cmd/podium-mcp/main.go:1341`, `:1361`, `:1385`), so the comment above `putExtras` claiming a re-fetch is wrong. Clearing the cache does not repair it, because the next prefetch rewrites the same buckets. CODE-9 carries `signature` on the envelope so the signature half of the §6.6 step-2 check runs on a warmed bucket; that comment is rewritten in the same change. The content-hash half cannot be satisfied by a warmed bucket for every artifact. The prefetch calls `cache.put` with a nil resources map (`cmd/podium-mcp/main.go:2487`) and `BatchLoadEnvelope` carries no `raw_frontmatter` or `manifest_merged` (`pkg/registry/server/batch_load.go:30-56`, against `pkg/registry/server/server.go:606` and `:611`), while `verifyContentHash` hashes the resource map and, for a merged manifest, `RawFrontmatter` (`cmd/podium-mcp/main.go:1776-1785`). A warmed bucket for a resource-bearing artifact or an `extends:` child therefore recomputes a different digest today, which is a 0026 residue. CODE-9 closes it by not warming: the prefetch runs `verifyContentHash` over the bytes it would write and skips an item that fails.
- **The standalone server and the bridge do not share a home in the e2e harness.** `startServer` pins the server to `HOME=t.TempDir()` (`test/e2e/helpers_test.go:436`) while `mcpExec` reaches `runBin`, which pins the bridge to `cmdharness.IsolatedHome(t)` (`test/e2e/helpers_test.go:134`). `cmdharness.Run` also sets `PODIUM_NO_AUTOSTANDALONE=1` (`internal/testharness/cmdharness/cmdharness.go:52`), which suppresses `bootstrapStandaloneFiles` entirely. No existing test inherits the bootstrapped `sync.yaml`, so a test that exercises the standalone journey wires the two homes together deliberately (TEST-6).
- **Two separate breakages hit the existing suites, one step apart.** The first is a per-artifact refusal that arrives at S12: CODE-1 verifies any present signature under any policy above `never`, `Noop.Verify` refuses everything from CODE-2, and CODE-4 makes a zero-flag `startServer` registry sign every bootstrapped fixture, so from S12 every load through `podium-mcp` of a `startServer`-served artifact is refused whatever the fixture's sensitivity is, while the consumer defaults are still `noop` and `medium-and-above`. The second is the startup refusal CODE-5 adds at S14, under which any `podium-mcp` process with no verification material refuses to start. The audit therefore runs before S12 and covers every process that starts the bridge and every in-process `loadConfig` caller, rather than medium and high fixtures.
- **A standalone server signs at ingest from the step that flips the producer default.** `startServer` passes no `--sign` (`test/e2e/helpers_test.go:431-437`) and the boot path hands the resolved signer to the filesystem bootstrap ingest (`internal/serverboot/serverboot.go:903-910`, `:1002`, `:510`), so every fixture a zero-flag server ingests carries an envelope from S12 onward. A case whose subject is an unsigned artifact starts its server with `PODIUM_SIGN=none`; one that does not stays in the suite asserting a different code. `test/manual-validation.md` inherits the same change, and its isolation block has to keep the generated key and the bootstrapped `~/.podium/sync.yaml` inside the scenario's throwaway directory.
- **The default key lives in the registry process's home.** `registrySigningKeyPath` falls back to `~/.podium/standalone/registry-signing.key` (`internal/serverboot/signing.go:22-31`), and the published image, which `.github/workflows/release.yml:448-454` builds from the repository-root `Dockerfile`, runs as `nonroot` on `gcr.io/distroless/base-debian12:nonroot` (`Dockerfile:62`, `:69`), so its home is `/home/nonroot`, with no volume over it. Where the store outlives that home, a recreated container would generate a fresh key: once the §13.4 rewrite has completed, every row the lost key signed would be refused at the consumer with `materialize.signature_invalid`, and while the rewrite is held back, as a `body_unavailable` row holds it (`internal/serverboot/rehash.go:356-361`, the marker decision at `:407-411`), no key that still exists would repair the rows the pass already signed (`internal/serverboot/rehash.go:365-375`). The Helm chart (CODE-8) and the compose stack (CODE-11) are handled by configuration, and every other deployment by CODE-4's persistence refusal: a start with signing on, no `PODIUM_SIGN_KEY_PATH`, and a store outside the directory the default key lives in is refused before any key is generated. The published image run with its default SQLite store keeps the key and the store in the same directory, so a recreate loses both together and strands no signature.
- **A key file outlives the signing mode that generated it.** `sign.KeyFilePath` resolves the same path whatever `PODIUM_SIGN` says, and nothing in the product deletes the file, so a home whose earlier start generated a key resolves it under `PODIUM_SIGN=none` and under a later remote registry. The consumer then starts and refuses each load, with `materialize.signature_missing` for an unsigned row and `materialize.signature_invalid` for a row another key signed. Both arms are fail-closed, and TEST-5 and TEST-6 pin one each.
- **`materialize.signature_missing` is a matrix cell and a documented code that no served error carries.** `deliverLoadArtifact` prefixes every policy failure with `materialize.signature_invalid`, so the missing-signature case surfaces under the wrong code. Existing tests do not all pass either way: `assertUnsignedHighRefused` (`test/e2e/governance_adoption_test.go:959`) and `TestArtifactResponse_SignatureInvalid` (`test/e2e/artifact_response_test.go:749`) match the literal `signature_invalid` on a load whose signature is absent, and `spi.Error.Error()` returns the Message alone (`pkg/spi/errors.go:33`), so `materialize.signature_missing: signature_missing: …` contains no `signature_invalid` and both go red at S11. TEST-2 carries their disposition.
- **`podium sync` and both SDKs verify nothing at any setting.** `EnforceVerification` has one production caller. Every claim this proposal makes about what a consumer verifies is a claim about `podium-mcp`.

## Current state and the gap

### The policy skips the cryptography on a value the registry supplies

`sign.EnforceVerification` (`pkg/sign/sign.go`) returns `nil` before reaching the provider whenever `needsVerification(policy, sensitivity)` is false, which under the documented `medium-and-above` default (`spec/06-mcp-server.md:34`) is every artifact the response does not report at `medium` or `high`. The sensitivity it reads is `resp.Sensitivity`, the JSON envelope field, served from the `manifests` column and carried across a restart by the cache's side files. A registry that sets `"sensitivity":"low"` on a response therefore skips the entire cryptographic path with no forgery, no key, and no collision.

Cross-checking the wire field against the frontmatter closes nothing, because a registry forging an artifact writes the same value into the frontmatter and recomputes the hash over its own bytes. Relocating the read to the hash-covered bytes is worse than neutral. `pkg/manifest/merge.go` merges sensitivity most-restrictive and `foldExtendsParent` folds the merged value into the stored column, so for a child declaring `extends:` the served value can be `high` while the pre-merge `ARTIFACT.md` the hash covers declares `low` or declares nothing. A consumer reading the trigger from the attested bytes would skip verification on an artifact the registry itself classified `high`. There is no attested source for a child's effective sensitivity, which makes the conditional trigger a control with no sound input.

### The order gives the content-hash check nothing to defend against

`deliverLoadArtifact` (`cmd/podium-mcp/main.go`) emits the §8.2 read event, enforces the signature policy, enforces the §4.4.1 sandbox gate, and enforces the §4.4.1 runtime gate, and only then recomputes the digest in `verifyContentHash`. Each of the three gates reads `resp.Frontmatter` at a point where nothing has bound those bytes to the served digest, and the read event applies the manifest's `audit_redact` directive from the same unverified bytes.

`verifyContentHash` compares a value recomputed from registry-supplied bytes against a registry-supplied digest, which detects a tampering intermediary and nothing else. It becomes a check against the registry only once the digest has been attested. `Provider.Verify(ctx, contentHash, signature)` consumes no manifest bytes, so the signature check can run before any fetch, and running it first is what gives the recomputation a party to defend against. The spec fixes neither order: §6.6 step 2 is one undivided sentence (`spec/06-mcp-server.md:239`).

### No default verifies anything

`registrySignerFor` (`internal/serverboot/signing.go`) returns `(nil, nil)` unless the mode is `registry-key`, and `registry-key` is the only accepted non-empty value, so `ingest.Request.Signer` stays nil and `mr.Signature` is never assigned. `buildSignatureProvider` maps both `""` and `"noop"` to `sign.Noop{}`, whose `Verify` accepts `"noop:" + contentHash`, a value any party holding the response can compute. The standalone bootstrap writes `defaults.verify_signatures: never` into `~/.podium/sync.yaml`, honored by `loadConfig` whenever `PODIUM_VERIFY_SIGNATURES` is unset.

The one verifying configuration needs a registry started with `--sign registry-key`, a consumer provider of `registry-managed`, a consumer key in `PODIUM_SIGNATURE_VERIFY_KEY`, and a policy above `never`, coordinated across two processes with no in-band key distribution. `test/e2e/signed_artifact_helpers_test.go` is the only place in the repository where all of them are set.

### Enabling signing later signs no stored row

`ingest.Ingest` short-circuits the idempotent branch before the signing block, `PutManifest` enforces the §4.7 immutability invariant, and `podium layer unregister` soft-deletes without removing the row. A `podium layer reingest` after enabling signing therefore reports every artifact idempotent and leaves every stored `Signature` empty. 0026's first-start rewrite is the one path that attaches an envelope to a stored row: where a signer is configured it re-signs every row it rewrites and mints a first envelope for a stored row already at the framed digest that carries none (`internal/serverboot/rehash.go:207-215` classifies that row `classUnmigrated`, and the apply step signs it at `:365-375`). It runs once, on the first start of the new version, and a marker keeps it from running again. Flipping the producer default in the same release therefore signs every row the pass writes, in the start every deployment already performs. The pass writes no row it classified `signature_unverified`, `unreproducible`, `body_missing`, or `body_unavailable`, because the apply loop `continue`s past each of those classes before the signing block (`internal/serverboot/rehash.go:343-362`), so an unsigned row classified `unreproducible`, `body_missing`, or `body_unavailable` leaves the upgrade unsigned and an upgraded consumer refuses it with `materialize.signature_missing`. `classSignatureUnverified` is set only for a row that carries a signature (`internal/serverboot/rehash.go:199-205`), so such a row leaves the upgrade carrying the envelope that failed to verify and an upgraded consumer refuses it with `materialize.signature_invalid` under any policy other than `never`. A registry that enables signing after that start gets no second pass, and an artifact whose stored rows are unsigned gains an envelope only when a new version of it is ingested, because ingest signs a row it inserts (`pkg/registry/ingest/ingest.go:780-796`) and short-circuits on every row it already holds at the same content hash (`:759-766`).

### The bootstrap relaxation is sticky and out of scope

`verifySignaturesFromSyncYAML` resolves `defaults.verify_signatures` from the workspace `.podium/sync.yaml` and then the home-global file with no association to the registry in use, and `writeFileIfAbsent` never rewrites an existing file. A developer who runs `podium serve` once and is later pointed at a production registry through `PODIUM_REGISTRY` keeps the relaxation. `standaloneStartup` also bootstraps on the `hasExplicitServerConfig` branch, so a multi-user SQLite deployment with an OIDC provider writes it too.

### Codes this surface returns are unregistered

`materialize.content_hash_mismatch` gained its §6.9 row, its §6.10 axis cell, and its annotated test from proposal 0026, so it needs nothing here. `config.signature_provider_unavailable` and `ingest.sign_failed` are returned by `pkg/sign` and `pkg/registry/ingest` and appear in neither. `materialize.signature_missing` is on the matrix axis and in the docs but nowhere in `spec/`, and no served error carries it as its leading code, because `deliverLoadArtifact` prefixes every policy failure with `materialize.signature_invalid`.

### §4.7.9 describes a model the code does not implement

The section calls Sigstore-keyless preferred and names a transparency-log entry. `SigstoreKeyless.Verify` never reads the certificate's subject or issuer, validates the chain at wall-clock time against a certificate that lives minutes, and treats an HTTP 200 from Rekor as sufficient while discarding the body and the attested time. The log check is also skipped when the envelope itself declares `log_index: -1`. None of this has a product effect: `registrySignerFor` accepts only `registry-key`, and no code path anywhere outside tests mints a Sigstore envelope into the store. The section also states that the registry-managed key is rotated quarterly, while `RegistryManagedKey` holds one keypair and no path re-signs a stored row, so a rotation invalidates every prior envelope permanently.

## Decisions

- **Split the policy into two axes, and delete the sensitivity condition.** The conflation of "check the signature I was given" with "require a signature" is the defect. Unconditional verification of a present signature costs nothing operationally and closes the free bypass for every signed artifact. After the split, `medium-and-above`'s only behavior is to waive the missing-signature requirement for an artifact the registry reports below `medium`, and the registry is the party that requirement defends against, so the value is deleted (CODE-13) and the policy takes `never` or `always`. A deployment whose signing does not yet cover every artifact runs `never` until it does. `docs/deployment/progressive-adoption.md`, which was built on the value, is restated around the two (DOC-1). The deletion lands with the fallback flip to `always` rather than with the split, so no commit defaults to a value that no longer exists.
- **Verify the signature before the content hash.** The signature consumes no manifest bytes, so the order is available, and it is the order under which the recomputation means something.
- **Move the read event and the manifest gates below the content-hash check.** Each is a fail-closed control reading unattested input, which is the same defect class as the sensitivity read. The read event moves below the content-hash check and stays above the two manifest gates. That puts both verification checks above it, and it also puts the resource fetch above it, because the fetch already ran above the content-hash check. A load either verification check refuses, and a load whose inline-resource decode or large-resource fetch fails, therefore record no local `artifact.loaded` event, while a load the §4.4.1 gates refuse still records one. The widening to the fetch classes is a cost the reorder carries rather than a goal: today a `materialize.fetch_failed` load records the event, and after the reorder it records nothing locally. The registry's own audit stream records the call in every case.
- **Make `Noop.Verify` refuse.** A provider that accepts a value derived from a public field is an acceptance predicate rather than a placeholder, and it satisfies `always`. `Sign` is a legitimate placeholder and is unchanged.
- **Resolve the verifier once rather than per load.** `buildSignatureProvider` runs on every `load_artifact` today (`cmd/podium-mcp/main.go:2008`), reading the environment at call time, so adding the key-file fallback to it would put a file read on every delivery. Moving the call into `loadConfig` and storing the result makes the refusal a consequence of the resolution rather than a predicate beside it, so nothing states twice what "can verify" means, and it removes the per-load I/O. The cost is that a key file replaced under a running bridge takes effect at restart, which matches every other `config` field.
- **Flip the producer default before the consumer defaults, in that order, in one release.** Signing is producer-side and breaks nothing on its own. The consumer defaults are what break a deployment, and they are safe only once 0026's first-start rewrite has attached envelopes.
- **Resolve the consumer's key from the same path the registry resolves, rather than through a `sync.yaml` key.** `readOrCreateEd25519` writes one file carrying a `private:` line and a `public:` line, at mode `0o600` in a `0o700` directory, and `registrySigningKeyPath` already resolves its location from `PODIUM_SIGN_KEY_PATH` or the `~/.podium/standalone/registry-signing.key` default. That resolver moves into `pkg/sign` as `KeyFilePath`, and the consumer falls back to it when `PODIUM_SIGNATURE_VERIFY_KEY` is unset, so the handover is the file mode rather than a configuration value. A config key would have to be written into a file the bootstrap does not rewrite, which means a line-inserting mutator over the operator's own YAML, and it would be scope-resolved workspace-first, which puts trust material on a path a checked-in `.podium/sync.yaml` controls. Neither cost buys anything the shared resolver does not already give.
- **Carry `signature` on the §7.6.2 envelope, and warm only a bucket that passes both step-2 checks.** A bucket warmed by the prefetch records no signature today, so under an enforcing policy every prefetched artifact is refused, and in `offline-only` there is no fall-through to repair it. Treating every prefetched bucket as a miss would disable prefetch for `offline-only`, which is the mode prefetch exists to serve, and extending the existing envelope keeps one delivery contract. The content-hash half is closed by not warming. The batch endpoint delivers resources by reference and an `extends:` child's merged frontmatter without its pre-merge bytes, so the prefetch cannot make such a bucket reproduce its digest, and it skips the item. Carrying the resource bytes and the pre-merge frontmatter on the batch envelope was rejected, because it enlarges a response the endpoint keeps small by design. A later load of a skipped artifact fetches it and caches it whole. The envelope does not carry `sensitivity`, because after CODE-13 no consumer check reads it.
- **Keep consumer key distribution out of band, except in standalone.** In standalone the registry's key file sits on the same filesystem, under the same user account, as the consumer, so the consumer reads it directly. Elsewhere the operator copies the public half into each consumer's `PODIUM_SIGNATURE_VERIFY_KEY`, which is a documented step rather than a new protocol: DOC-1 stages the extraction command on `docs/deployment/clustered.md`, and TEST-12's D-clustered case executes it. A published-key route with a first-use pin is a mechanism with its own security semantics and belongs in its own proposal.
- **Carry the §4.7.9 correction now and defer the Sigstore work.** A spec that claims verification properties the code does not deliver is the defect this proposal exists to remove, and correcting text costs nothing. Building certificate-identity policy and transparency-log verification carries a dependency decision and has no product effect until the registry gains a keyless signing mode.
- **Do not repair key rotation.** A key set is a provider redesign that belongs with the Sigstore work. 0026's first-start rewrite leaves untouched a row whose stored envelope does not verify under the configured key, because it cannot tell a rotated key from a forged envelope, and it runs once, so it is not a rotation repair. §4.7.9 states the accepted behavior instead, and OQ-2 carries the question.

Every registry process serving one store resolves `PODIUM_SIGN_KEY_PATH` to the same key file. The default resolves per process, under that process's home, so a registry with signing on and `PODIUM_SIGN_KEY_PATH` unset refuses to start, naming `PODIUM_SIGN_KEY_PATH` and `PODIUM_SIGN=none`, unless its store is the SQLite store in the directory the default path resolves to or the non-durable memory store. The refusal runs before the registry generates a key or rewrites a row. A deployment running more than one replica, or whose store is not the default SQLite store, therefore supplies the path explicitly on the store's persistent storage and mounts one key, or sets `PODIUM_SIGN=none`. A registry that loses a generated key signs under a fresh one on its next start once the §13.4 rewrite has completed, and a consumer refuses every row the lost key signed with `materialize.signature_invalid`. While the rewrite has not completed, that start is refused by the §13.4 generated-key rule, and because the rewrite signs the rows it writes before it decides whether to record completion, no key that still exists makes those rows verify again. A consumer holds one verification key, so replicas signing under different keys serve envelopes that consumer refuses with `materialize.signature_invalid` on some fraction of its loads and accepts on the rest.

Signing is producer-side: it determines whether an artifact ingested from now on carries a §4.7.9 envelope. Ingest does not attach one to an already-stored artifact, because a stored signature is written once, at ingest. The §13.4 first-start rewrite signs each row it rewrites, including a stored row whose hash already equals the new value and that carries no signature. It leaves every other row untouched, and an untouched row keeps whatever envelope it had, so a row whose stored bytes reproduce neither digest and a row whose bundled-resource bytes could not be read stay unsigned when they were unsigned, and a consumer under a policy that requires a signature refuses each of them with `materialize.signature_missing`. A row whose stored signature does not verify keeps that signature, and a consumer under any policy other than `never` refuses it with `materialize.signature_invalid`. The rewrite does not run again once it has completed. Turning signing on afterwards leaves every row stored before it unsigned: no path attaches an envelope to a stored row after the rewrite has completed, and an artifact gains one only when a new version of it is ingested.

The consumer-side settings that decide whether a signature is checked are client configuration and live in §6.2 and §7.5.2. `PODIUM_SIGN_KEY_PATH` is the one setting both process kinds read. The registry process writes the file it names, and a consumer running under the same user account on the same machine reads the `public:` line from it when `PODIUM_SIGNATURE_VERIFY_KEY` is unset (§4.7.9).

```go
// EnforceVerification applies policy to one served artifact.
//
// Two axes, deliberately separated. A signature that is present is always
// verified under any policy other than never, because the sensitivity the
// policy would otherwise gate on is reported by the same party that supplies
// the signature, and for a child declaring extends: (§4.6) no attested source
// for it exists: the merge takes the most-restrictive value
// (pkg/manifest/merge.go) while the content hash covers only the child's
// pre-merge bytes. Whether a missing signature aborts the load is the axis the
// policy governs, and only `always` resists a registry that serves an unsigned
// forgery.
//
// spec: §4.7.9, §6.6 step 2.
func EnforceVerification(ctx context.Context, policy VerificationPolicy, provider Provider, sensitivity manifest.Sensitivity, contentHash, signature string) error {
	if policy == PolicyNever {
		return nil
	}
	if signature == "" {
		if !requiresSignature(policy, sensitivity) {
			return nil
		}
		return fmt.Errorf("%w: sensitivity %q requires a signature", ErrSignatureMissing, sensitivity)
	}
	return provider.Verify(ctx, contentHash, signature)
}

// requiresSignature reports whether a missing signature is a refusal. An
// unrecognized policy fails closed; loadConfig refuses such a value at startup
// (§6.2), so this is defense in depth for a direct constructor.
func requiresSignature(policy VerificationPolicy, s manifest.Sensitivity) bool {
	switch policy {
	case PolicyAlways:
		return true
	case PolicyMediumAndAbove:
		return s == manifest.SensitivityMedium || s == manifest.SensitivityHigh
	case PolicyNever:
		return false
	default:
		return true
	}
}
```

When it is `none` the template renders `PODIUM_SIGN=none` and neither the variable for the path, the mount, nor the volume. Any other value fails the render. The `volumeMounts` and `volumes` guards, which today test `objects.enabled` and `runtimeKeys.enabled`, also test the signing mode.

The Secret holds the key file in the format `readOrCreateEd25519` writes, carrying both the `private:` and the `public:` line. The loader reads an existing file and writes nothing, so the read-only mount is sufficient, and no companion file is needed, because a consumer of this deployment is handed the base64 public value out of band rather than a path, extracted from the same file by the command DOC-1 states. The operator produces the file by starting a standalone registry once, and creates the Secret from it; DOC-1 states the commands. That start is isolated from every store the operator uses: it runs under `env -i` carrying `PATH`, `HOME` set to a fresh scratch directory, and `PODIUM_SIGN_KEY_PATH` naming a file in that directory, and nothing else. The first start of this release runs the one-shot §13.4 rewrite against whatever store it opens, with the configured key as its signer (`internal/serverboot/serverboot.go:895`, `:903`, `:934-944`), and a standalone start with no store configuration opens `~/.podium/standalone/podium.db` and `~/.podium/standalone/objects` under the invoking home (`internal/serverboot/serverboot.go:2346-2354`). Run against the operator's own home, the key-generation start would sign every unsigned personal row under the key destined for the cluster and record the rewrite's completion marker (`internal/serverboot/rehash.go:407-408`), so the operator's next ordinary `podium serve` generates a different key at the default path, the local bridge resolves that key, and every personal row is refused with `materialize.signature_invalid` with no second pass to repair it; on a home whose store already carries signed rows the start is refused by the generated-key rule instead. It would also bootstrap `~/.podium/registry.yaml`, `~/.podium/sync.yaml`, and the artifacts directory into that home. Clearing the environment as well as `HOME` keeps an inherited `PODIUM_SQLITE_PATH`, `PODIUM_FILESYSTEM_ROOT`, `PODIUM_CONFIG_FILE`, or `PODIUM_REGISTRY_STORE` (`internal/serverboot/serverboot.go:789`, `:2152-2156`) from pointing the start back at a store the operator uses. The chart's default now requires a value it did not before, so every site that renders or installs the chart without setting a signing value follows, whether or not it passes other overrides: every `render` and `renderErr` call site in `test/chart/render_test.go` that sets no signing value, which TEST-8 enumerates, the `helm install` command in `docs/deployment/clustered.md`, and the chart-install manual scenario in `test/manual-validation.md`.

## Open questions

**OQ-1. Does the consumer-facing default flip ship in the same release as the producer default?** The checklist orders S12 before S14 and this document assumes one release, because splitting them across releases leaves an interval in which the store is signed and no consumer checks, which is the status quo, and because 0026's first-start rewrite runs once. A reviewer who wants the consumer flip held to the following MINOR gets a safer rollout and a second coordinated upgrade for operators. S14 is severable without touching S10 through S13.

**OQ-2. Is the rotation limitation acceptable as documented behavior?** §4.7.9 currently claims quarterly rotation and SPEC-1 replaces that with the truth: a rotation invalidates every prior envelope and an artifact verifies again only once a new version of it is ingested, because 0026's first-start rewrite leaves untouched a row whose envelope does not verify under the configured key and does not run again. The alternatives are a verification key set, which is a provider redesign, and a re-triggerable signing pass that trusts a retired key, which is a key set by another name. Neither is staged here.

**OQ-3. Should the standalone bootstrap hand the consumer a pointer to key material?** Resolved: no. The consumer resolves the registry's key file by the same `sign.KeyFilePath` the registry resolves, so the handover is the file's `0600` mode under one user account rather than a configuration value. Nothing in the tree writes a `.pub`, and no `sync.yaml` key is added, so there is no second place for the path to be stated, no insertion into an operator's file, and no scope-resolved key path a checked-in `.podium/sync.yaml` could redirect. A deployment where the registry is not the same user on the same filesystem supplies `PODIUM_SIGNATURE_VERIFY_KEY`, which every deployment other than standalone already does.

**OQ-4. Which release carries the follow-up Sigstore proposal?** It is latent today, and it stops being latent the moment a registry signing mode mints a keyless envelope. The two should be scheduled together.

**OQ-5. Should a later proposal add a re-triggerable signing pass?** 0026's `RehashManifest` can write a fresh envelope onto a stored row, and only 0026's marker-gated first-start rewrite drives it. A registry that enables signing after that start has no in-place repair: each artifact gains an envelope only when a new version of it is ingested, and every earlier version stays unsigned. A pass an operator can trigger again would remove that, at the cost of a trigger surface and of the marker semantics 0026 declined.

**OQ-6. How does the Helm chart hold the signing key under the new default?** Resolved: the chart mounts an operator-supplied Secret at `PODIUM_SIGN_KEY_PATH` and refuses to render without one unless `signing.mode` is `none` (CODE-8). A chart default of `none` was rejected because it would leave clustered deployments, which most need verification, unsigned by default.

**OQ-7. Should a prefetched bucket be made to pass the §6.6 step-2 content-hash check, or be left unwarmed?** Resolved: left unwarmed. The prefetch runs the step-2 recomputation over the bytes it would write and skips an item that does not reproduce its digest (CODE-9).

**OQ-8. Should `medium-and-above` be deleted rather than kept as a rollout posture?** Resolved: deleted. The policy takes `never` or `always`, and a consumer configured with the old value refuses to start (CODE-13).

**OQ-9. Should the registry refuse to generate a signing key where its home may not persist?** Resolved: yes. A start with signing on, no `PODIUM_SIGN_KEY_PATH`, and a store other than the SQLite store in the default key's directory or the memory store is refused before any key is generated (CODE-4).

## Relationship to proposal 0026

0026 length-frames the §4.7.6 content hash, which moves every stored digest and therefore invalidates every stored envelope, since each envelope is over the digest string. Its migration is a rewrite the registry performs once, on the first start of the new version, before it ingests or serves. The pass recomputes each stored row from the bytes the registry holds and, where a signer is configured, re-signs every row it rewrites and mints a first envelope for a stored row already at the framed digest that carries none. It leaves untouched a row whose stored envelope does not verify under the configured key, a row whose stored bytes reproduce neither digest, and a row whose bundled-resource bytes it could not read, and an untouched row keeps whatever envelope it had. It refuses the start, writing nothing, when a row it would rewrite is signed and no signer is configured, or when the signing key was generated at that start while signed rows fail verification. A marker records completion and nothing runs the pass again. This proposal ships in the same release because that start is the one event that signs stored rows: with the producer default flipped beside it every row the pass writes leaves the upgrade signed, while a row the pass leaves untouched keeps the envelope it had, and a default flipped later would sign nothing already stored. 0026's mandated consumer cache clearing is also what removes the stale envelopes a warmed cache would otherwise replay through the stricter gate. 0026's OQ-1 is resolved in favour of the first-start rewrite.

## Non-goals

- **Generating the signing key inside the cluster.** A pre-install hook Job that mints the key and writes the Secret would remove one operator step, and it would need cluster RBAC to create Secrets and would mint a fresh key on a reinstall over a store whose rows an earlier key signed. The operator supplies the Secret.
- **Sigstore verification correctness.** The certificate-identity policy, verification at the transparency log's attested time rather than at wall-clock time, entry binding, inclusion-proof and signed-entry-timestamp verification, refusing an envelope that declares `log_index: -1`, refusing a digest algorithm other than `sha256`, and a versioned self-describing envelope are a separate proposal. No registry signing mode mints a Sigstore envelope into the store, so every one of those defects is latent for served artifacts, although `podium sign --provider sigstore-keyless` can already produce such an envelope outside the ingest flow, and the fix carries a dependency decision about adopting an upstream Sigstore library that must be taken on its own terms. What lands here is the §4.7.9 text that stops describing the model as working.
- **A registry key-publication route with a first-use pin.** It would make `always` the default with no operator action on a non-standalone deployment. It is also a trust-on-first-use mechanism with its own security semantics, its own `sync.yaml` state, and its own re-pinning flow, and adding it here would land it unreviewed inside a rollout proposal.
- **A verification key set and non-destructive rotation.** See OQ-2.
- **A re-triggerable pass that signs already-stored rows.** 0026's `RehashManifest` writes a fresh envelope onto a stored row, and only 0026's marker-gated first-start rewrite drives it. This proposal adds no second driver, no second store method, and no trigger. The same-release constraint makes one unnecessary for the upgrade, and OQ-5 carries the question for a registry that enables signing later.
- **Signature verification in `podium sync` or the SDKs.** `EnforceVerification` has one production caller, and that bound is unchanged. The operator guide states it for `podium sync` today, and DOC-1 stages the matching sentence for the SDKs in the operator guide and in `docs/consuming/custom-via-sdk.md`.
- **A grace policy value, a legacy provider alias, or an exemption for artifacts ingested before the upgrade.** Podium is pre-1.0 and each is a second behavior retained beside the first, which `.claude/rules/code-best-practices.md` forbids.
- **Rescoping `bootstrapStandaloneFiles` away from the explicit-server-config branch.** Deleting the relaxation line removes the leak this proposal cares about, and the bootstrap's other writes are benign.

# Proposal 0071: Fold the command and context types into skills: add a skill invocation field and remove both types

- Issue: (to be filed)
- Status: Implemented (2026-11-17). Verified after a redesign and 12 adversarial review rounds (22 findings fixed), following 8 earlier rounds (36 findings fixed).
- Date: 2026-11-16

This document stages spec, code, test, manual-validation, and documentation changes. It does not modify any spec, code, test, or doc file. Apply the changes in the staged sections after sign-off. The change is backward-incompatible: ingest refuses an `ARTIFACT.md` that declares `type: command` or `type: context`, stored rows of those types stop serving, and `claude-cowork` loses its only project-scope output. It ships in 0.7.0 as a MINOR bump.

## Summary

**What changes.**

- **Spec §4.1, §4.2, §4.3, and §4.3.4 (SPEC-1).** `command` and `context` leave the type system. A new §4.1 **Removed types** paragraph refuses an `ARTIFACT.md` of either type with `ingest.invalid_artifact` and `details.constraint: "type_removed"`, and retires stored rows of either type under the mechanism §4.6 uses for `extends:`. A skill gains the Podium field `invocation` (`any` or `user`), carried at the top level of `ARTIFACT.md` or as `SKILL.md` `metadata.invocation`, and only the value `user` makes a skill user-invoked: an absent value and every other value resolve to `any`.
- **Spec §5.1, §5.2, §6.4, §6.7, §6.7.1, §7.3.1, §7.5, §7.5.8, §7.6, §7.8, §13.11.3, the retired-row sentences, and the type lists in §1, §3.5, §10, §11, and the glossary (SPEC-2 to SPEC-6).** §5.2 becomes "User-Invoked Skills". §6.7 maps a user-invoked skill per harness: a user-only control on claude-code, cursor, codex, and pi, the native command file on opencode and gemini, and nothing on claude-desktop, claude-cowork, and hermes. §6.7.1 drops both type rows and gains the `invocation: user` row. §7.3.1 states the ingest refusal and adds the removed-type rule to the `podium lint` refusals that proposal 0070 states, whose `--json` `rejected` entry carries `details.constraint`. §7.5.8, which proposal 0070 adds, stops counting a user-invoked skill as a listing entry. §7.8 states the emitter outputs, and §13.11.3 drops the refused artifacts in a filesystem-source sync.
- **`pkg/manifest`, ingest, the walk, the read path, and the scaffolder (CODE-1, CODE-2).** The 0068 metadata codec gains `invocation`, so the unchanged resolvers give it the existing key-presence precedence. One classifier in `pkg/layer` refuses `extends:` and a removed type in both deployment modes, the walk's drop carries the classifier's constraint in the `layer.Drop.Details` field that proposal 0070 adds, and one stored-row predicate retires rows of a removed type on every read path. The same step drops both names from the type list and makes `podium artifact scaffold` refuse them, so no step registers or scaffolds a type that ingest refuses.
- **Adapters, emitters, and lint (CODE-3, CODE-4).** A bytes-level SKILL.md writer applies the compatibility derivation and the harness control for every SKILL.md writer. The codex adapter and emitter write `agents/openai.yaml`. The opencode and gemini adapters write command-file fallbacks. `claude-cowork` emits nothing. `capabilityMatrix` drops both type rows and gains the `invocation: user` row, and the §6.9 guard resolves the skill at the `podium-mcp` and registry-backed `podium sync` call sites. The `pkg/sync` listing estimate that proposal 0070 adds skips a user-invoked skill. Lint gains `lint.skill_invocation`.
- **CLI, web UI, fixtures, tests, manual validation, and docs (CODE-5, CODE-6, FIX-1, FIX-2, TEST-1, TEST-2, MV-1, DOC-1).** `podium artifact scaffold` gains `--invocation`, and the `podium-mcp` `search_artifacts` descriptions drop both type names. The upgrade notes describe converting a `command` or `context` package to a skill by hand. The web UI type dropdown drops both names. Fixtures, golden files, tests, `test/manual-validation.md` (new S108), the docs, and the CHANGELOG follow. Each code step leaves the suite green and dispositions the existing tests it turns red.

**Fixed decisions.**

## Current state and the gap

### The two types in the spec and the code

Podium defines `context` and `command` as first-class artifact types. They appear in the §4.1 type list, the §4.3 `type:` enum, the §4.2 layout fallback, the §5.1 `search_artifacts` type filter (mirrored in `cmd/podium-mcp/descriptions.go:17` and `:80`), §5.2 Command Materialization, the §6.7 context paragraph and command target row, and the §6.7.1 type rows (mirrored at `pkg/adapter/capability.go:86-87`).

### The harnesses no longer model them

Claude Code merged custom commands into skills, and a skill becomes user-invoked through `disable-model-invocation: true`. Cursor converts commands into skills with the same key. Codex has no project-scope commands (§6.7; `pkg/adapter/codex.go:34`), but it accepts explicit `$skill` invocation, and `agents/openai.yaml` `policy.allow_implicit_invocation: false` disables implicit invocation. No harness has a `context` concept. Every adapter, `claude-cowork` and `hermes` included, writes `type: context` only to the harness-neutral `.podium/context/<id>/` directory (`pkg/adapter/layout.go:39-50`). No harness loads that directory by itself, yet the matrix grades it native everywhere except claude-desktop (`pkg/adapter/capability.go:86`).

### Today's command outputs

A command is a native file per harness: `.claude/commands/<n>.md` (`pkg/adapter/claudecode.go:87-92`), `.cursor/commands/<n>.md` (`pkg/adapter/builtins.go:68-69`), `.opencode/commands/<n>.md` (`:183-184`), `.gemini/commands/<n>.toml` through `geminiCommandTOML` (`:154-155`; `pkg/adapter/layout.go:95-105`), and `.pi/prompts/<n>.md` (`:209-210`). It is `✗` for codex, hermes, claude-desktop, and claude-cowork. The Claude plugin emitter writes `commands/<n>.md` (`pkg/adapter/emitter.go:142-143`), and the Gemini extension writes `commands/<n>.toml` (`emitter.go:319-320`). Every command arm writes the body verbatim, and §5.2 forbids an argument layer, so each harness's placeholder convention applies to the bytes it receives.

### SKILL.md has no place for a per-harness control

SKILL.md stays within the Agent Skills specification (§4.3.4). Podium reads `metadata` keys only from a closed list, and compatibility is the precedent for an adapter adding a key at materialization (`pkg/adapter/compatibility.go:23-40`). That precedent does not fit a per-harness control as written:

- `injectFrontmatterLine` always double-quotes its value (`pkg/adapter/compatibility.go:77-98`).
- The Claude Code adapter (`pkg/adapter/claudecode.go:41-56`) and the Claude plugin emitter (`claudePluginSkill`, `pkg/adapter/emitter.go:167-188`) write SKILL.md outside `skillOut` (`pkg/adapter/layout.go:52-65`).
- No adapter writes `agents/openai.yaml`.
- Lint does not stop an author from writing a harness-native key such as `disable-model-invocation` at the top of SKILL.md (`pkg/lint/skill_rules.go:24-56`, `pkg/manifest/skill_fields.go:33-63`), so that key passes through today.

### Other surfaces that name the types

- `claude-cowork` loses its only project-scope output (`pkg/adapter/builtins.go:40-51`; §6.7). Hermes keeps only `rule` (`builtins.go:220-241`).
- §4.1 tells authors to factor large reference content into `type: context` and exempts context from skill-tier review.
- The effort_hint lint names command (`pkg/lint/lint.go:412-424`).
- The scaffolder offers both types (`cmd/podium/artifact_scaffold.go:29-31`, `:576-582`).
- The web UI type dropdown lists both (`web/ui/src/surfaces/SearchSurface.tsx:47-55`).
- Four reference fixtures declare them: `personal/notes/journal`, `personal/notes/glossary-notes`, `team-finance/commands/quick-variance`, and `org-defaults/company-glossary`.
- The golden seeds use both types (`test/materialization/golden_test.go:75`, `:79`), and many Go test files use them, mostly `type: context` as a stand-in type.

### What removal needs that does not exist

Dropping the names from `firstClassTypes` (`pkg/manifest/parse.go:365`) does not refuse such an artifact, because an unregistered type only warns `lint.unknown_type` (`pkg/lint/lint.go:242-249`). Stored rows need their own rule: the §13.4 admission fallback serves rows it cannot parse, ingest of identical bytes is a no-op, and same-version different bytes is a conflict (`pkg/registry/ingest/ingest.go:852-864`). No conversion path exists: `podium import` reads a flat directory of skills, has no `--type` flag, and refuses any `ARTIFACT.md` (`cmd/podium/import.go:18-42`, `:172-180`).

The 0.6.0 removal of `extends:` (proposal 0064) built the mechanism this change needs. Ingest refuses a removed feature with `ingest.invalid_artifact` and a `details.constraint` (`pkg/layer/invalid.go`; `pkg/registry/ingest/ingest.go:1500-1530`; `pkg/registry/filesystem/walk.go:120-145`). Stored rows it covers are retired through one predicate on the listing choke points (`pkg/registry/core/servable.go`; `pkg/registry/ingest/autoversion.go:57`). The maintainer decided to fold both types into skills in 0.7.0 as a backward-incompatible MINOR change.

## Decisions

- **D-1. Scope and release.** `command` and `context` are removed from the type system across `spec/`, `pkg/`, `cmd/`, `internal/`, `web/ui` (with `web/bundle` rebuilt), `docs/`, `testdata/`, the tests, and `test/manual-validation.md`. No compatibility flag, shim, or dual code path is added. The change ships in 0.7.0 as a MINOR bump (maintainer decision; user request to include it in 0.7.0).
- **D-2. Field name and location.** A skill gains the Podium field `invocation`, which takes one of two values. `any`, the default when the field is absent or holds any value other than `user`, lets the agent load the skill by itself and lets a human invoke it. `user` means the skill is meant for a human to invoke. The field applies to `type: skill` only. It lives at the top level of `ARTIFACT.md` and as the `SKILL.md` `metadata.invocation` string, and it joins the §4.3.4 **Podium fields in `metadata`** list through the `manifest.ResolveSkillFields` and `manifest.ResolveStoredSkill` resolvers that proposal 0068 added. A converted command is therefore a single SKILL.md. An enum leaves room for a later model-only value (Claude's `user-invocable: false`) without a second field. The maintainer kept this name and these values on 2026-11-16 (Q-3). Three alternatives were rejected. A boolean such as `user_invoked: false` misreads as "the user cannot invoke it". A harness key name such as `disable-model-invocation` puts a vendor key into the Podium vocabulary. An `ARTIFACT.md`-only field forces a second file on every converted command.
- **D-3. Resolution and output (maintainer decision on Q-3, 2026-11-16).** A skill is user-invoked exactly when its resolved `invocation` is `user`. `any` is the default when the field is absent and when it holds any other value, in either file: empty, null, a value in another case such as `User`, or an unknown word such as `yes`. `invocation` resolves under the 0068 key-presence precedence with no exception. When `ARTIFACT.md` states the key, its value decides, whatever `metadata` holds. An unstated key takes a `metadata` value that follows the `any or user` encoding. Every reader resolves the field this way whether or not lint runs, so the §6.4 overlay, a filesystem-source `podium sync`, ingest, and a §13.4 admitted row agree. Lint reports an invalid value as a warning, matching the 0068 codec, which ignores a malformed `metadata` value with a warning and lets the field take its default. A `metadata` value is reported through the existing `lint.skill_metadata_field_ignored` warning, and an `ARTIFACT.md` value through a `lint.skill_invocation` warning. A stated `ARTIFACT.md` value that differs from a valid `metadata` value is the existing `lint.skill_artifact_field_mismatch` error. A skill whose resolved `invocation` is `user` is never emitted where the harness would invoke it by itself. On a harness with a documented user-only skill control, the adapter writes that control. On a harness without one, the adapter writes the harness's native command file, graded `⚠`. Where neither exists, the cell is `✗` and nothing is emitted.
- **D-4. Per-harness mapping, project-files mode.**
  - claude-code writes `.claude/skills/<n>/SKILL.md` with `disable-model-invocation: true` (`✓`).
  - cursor writes `.cursor/skills/<n>/SKILL.md` with the same key (`✓`).
  - codex writes `.agents/skills/<n>/SKILL.md` and `.agents/skills/<n>/agents/openai.yaml` carrying `policy.allow_implicit_invocation: false` (`✓`, new output for Codex).
  - pi writes `.pi/skills/<n>/SKILL.md` with `disable-model-invocation: true` (`✓`, per Pi's skills documentation).
  - opencode writes `.opencode/commands/<n>.md`, a fallback graded `⚠`, because the repository documents no OpenCode user-only skill control.
  - gemini writes `.gemini/commands/<n>.toml` through `geminiCommandTOML`, also a `⚠` fallback.
  - Both fallbacks put bundled resources in `.podium/resources/<id>/`, as commands do today.
  - claude-desktop, claude-cowork, and hermes are `✗`, matching their skill row.
  - The spec names each key as adapter output and leaves runtime semantics to the vendor documentation (§6.7).
- **D-5. Per-emitter mapping, marketplace mode (§7.8).** The Claude plugin writes `skills/<n>/SKILL.md` with `disable-model-invocation: true` and no longer writes `commands/`. The Codex plugin writes `skills/<n>/SKILL.md` plus `skills/<n>/agents/openai.yaml`. The Cursor plugin writes the skill with the key. The Gemini extension writes `commands/<n>.toml` for a user-invoked skill and omits its bundled resources, as it omits a command's today; a model-invocable skill still has no Gemini extension component. The Pi package writes the skill with the key. The Hermes tap omits a user-invoked skill, because no Hermes control is documented and the tap's skills are model-invocable.
- **D-6. Authored harness-native controls.** Lint reads no harness-native key, because §4.3.4 keeps SKILL.md within the Agent Skills standard and D-2 keeps vendor keys out of the Podium vocabulary. The adapter decides by the control's value. For a user-invoked skill, an authored top-level `disable-model-invocation: true` is kept, and any other authored value is replaced with `true`. In an authored bundled `agents/openai.yaml`, `policy.allow_implicit_invocation` is set to the YAML boolean `false` whatever the authored value's type or quoting, and every other key is kept. ## Non-goals

- Hiding user-invoked skills from `search_artifacts`, `load_artifact`, or any MCP surface. A user-invoked skill stays discoverable and loadable through the meta-tools, as a `type: command` artifact is today.
- A Podium argument layer or placeholder translation between harness conventions such as `$ARGUMENTS` and `{{args}}`.
- A cross-artifact reference field that lets several skills share one reference bundle. `delegates_to` stays agent-only.
- A model-only invocation value (Claude's `user-invocable: false`). The enum leaves room for it later.
- Rewriting, deleting, or re-signing stored rows, or a release-time migration. Stored rows of a removed type are retired, and no release step migrates them.
- A conversion or migration command for `command` and `context` packages, matching proposal 0064, which shipped none for `extends:`. The 0.7.0 upgrade notes describe the hand conversion (D-13).
- SDK changes. The SDKs embed no harness adapter (§7.6), and their overlays read no `invocation` value.
- Applying ingest rules in the workspace local overlay (§6.4).
- Granting skills to claude-desktop, claude-cowork, or hermes at project scope, or removing the claude-cowork adapter value.
- Adding a model-invocable skill component to the Gemini extension emitter.
- Guarding against a harness that also reads another harness's skill directory and ignores that directory's control. The adapter writes only the target harness's control. A control for another harness that the author bundled as a resource or wrote in `SKILL.md` passes through unchanged.
- A `TypeProvider` registration refusal for the removed names. Lint is the only `TypeProvider` reader, and the refusal runs before lint whatever provider is registered.
- Lint checks on harness-native keys in `SKILL.md` or on bundled `agents/openai.yaml` files (D-6).

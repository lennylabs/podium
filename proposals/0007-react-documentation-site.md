# Proposal 0007: React Documentation Site and Content Generator

- Issue: (to be filed)
- Status: Draft (2026-08-15)
- Date: 2026-08-15
- Spec amendment: none. This proposal changes documentation delivery and repository tooling. It does not change Podium's product surface, and `spec/` is untouched.

## Summary

Podium's documentation is published by GitHub Pages from `docs/` using Jekyll with the remote `just-the-docs` theme (`docs/_config.yml`, `.github/workflows/docs.yml`). The theme sets the visual design, the navigation, and the search. There is no landing page: `docs/index.md` serves both as the project's front door and as the first documentation page, rendered in the same sidebar layout as every other page. Extending the site means extending a Ruby theme, and adding an interactive element to a page means embedding raw HTML and script tags in a markdown file.

This proposal replaces the Jekyll build with a static site generated by a project-owned generator written in TypeScript, rendered by React at build time, and deployed to the same GitHub Pages target. Markdown files under `docs/` remain the single source of documentation content. The generator reads those files, produces a serializable page model per page, and renders each model to static HTML through React server rendering. The output is HTML and CSS with a small client bundle for search, navigation, and selectively hydrated components. A hand-authored landing page is added at the site root, styled from the palette the project already uses in its SVG diagrams (`.claude/rules/doc-diagram-style.md`).

The generator covers a bounded feature set: frontmatter parsing, navigation derived from the directory tree, internal link resolution, build-time syntax highlighting, callouts, section call-to-action links, a client-side search index, and a component island mechanism. It is not a general-purpose site generator. Versioned documentation, localization, a blog, a theme system, and a plugin API are out of scope and are recorded as such.

The proposal is designed around the follow-on work the requester described: animated explanations where a static diagram falls short, and interactive components that demonstrate a concept. Those need a content model that can carry a component reference through the pipeline and a client runtime that can hydrate one region of a page without shipping the rest of the page as JavaScript. The island mechanism and the directive syntax are specified here and land with an empty component registry, so the follow-on work adds components rather than restructuring the pipeline.

## Current state and the gap

### What the site is today

`.github/workflows/docs.yml` builds `docs/` with `actions/jekyll-build-pages@v1` and deploys the result to GitHub Pages. The workflow runs on a `v*` tag push and on `workflow_dispatch`, so documentation is republished per release rather than per commit. `docs/_config.yml` pulls `just-the-docs` through `jekyll-remote-theme` and configures the theme's search, navigation, edit links, and footer. `docs/Gemfile` pins the Ruby dependencies for local preview through `bundle exec jekyll serve`.

Jekyll writes each page to its source path with an `.html` extension: `docs/getting-started/quickstart.md` becomes `/getting-started/quickstart.html`. The site is served from `https://lennylabs.github.io/podium/`.

### What the markdown actually uses

The content is portable. A scan of the 53 markdown files under `docs/` (52 carry frontmatter; `docs/rfc/README.md` does not) shows a small theme-specific surface:

| Feature | Usage | Notes |
| --- | --- | --- |
| Frontmatter keys | `title`, `nav_order`, `layout`, `description` on all 52 pages; `parent` on 44; `has_children` on 8; `grand_parent` on 5; `permalink` on 1 | `layout`, `parent`, `grand_parent`, and `has_children` restate what the directory tree already encodes |
| Kramdown inline attributes | `{: .btn .btn-outline }` (7), `{: .btn .btn-purple }` (6), `{: .note }` (2) | The only theme-coupled markup in the corpus |
| Mermaid | none | Diagrams are checked-in SVG files |
| Fenced code languages | `yaml` (73), `bash` (65), `json` (21), `markdown` (13), `python` (10), `powershell` (1), `javascript` (1) | A fixed, small language set |
| Images | 16 SVG diagrams under `docs/assets/diagrams/`, each with descriptive alt text and an adjacent HTML-comment ASCII fallback | Governed by `.claude/rules/doc-diagram-style.md` |
| Internal links | Extensionless relative paths (`../consuming/publishing`, `oidc/`), 11 links written with an explicit `.md` suffix | Resolution rules must handle both |

Total prose is roughly 63,000 words. Nothing in the corpus depends on Liquid templating, Jekyll collections, includes, or data files.

### Coupling to the repository's test and coverage tooling

Two mechanisms read `docs/` directly and constrain any change:

- `tools/doccov` scans every markdown file under `docs/` plus `README.md`, classifies pages that contain a runnable command example, and requires each such page to map to a feature-named end-to-end test by `D-<slug>` or to a written waiver (`tools/doccov/manifest.yaml`).
- The end-to-end suite under `test/e2e/` carries feature-named files whose header comments name the documentation page they cover, and those tests execute the commands the pages document.

Both read markdown from `docs/`. Neither reads generated HTML. Keeping markdown as the source of content preserves both without modification, and the generator must not require a markdown syntax that changes how `doccov` classifies a page.

### The gap

1. **No landing page.** The project's front door is a documentation page in a documentation sidebar. A visitor evaluating Podium reads the same layout as a reader looking up a frontmatter field.
2. **Presentation is delegated to an external theme.** Typography, color, spacing, code presentation, and navigation come from `just-the-docs`. The project already owns a defined visual language in its diagrams (a warm palette, Helvetica, flat geometry) and the site does not reflect it.
3. **No path to interactive explanation.** Adding an animation or an interactive component to a Jekyll page means inline HTML and script tags inside a markdown file. That markdown is also read by `doccov`, rendered on GitHub, and edited by contributors, so inline script is the wrong carrier.
4. **Two toolchains.** The repository builds Go and TypeScript. Documentation adds Ruby and Bundler for local preview only.
5. **No link validation.** Nothing checks that internal links resolve. Two links in `README.md` are live 404s today: `https://lennylabs.github.io/podium/consuming/publishing/` and `https://lennylabs.github.io/podium/consuming/configure-your-harness/` both return 404 because the trailing-slash form does not match Jekyll's `<page>.html` output, while the extensionless forms return 200. A build-time link check catches this class of error.

## Decisions

These were settled during design and form the basis of the specification below.

1. **Markdown under `docs/` stays the source of content.** The generator reads it and never writes to it. `doccov`, the end-to-end suite, and GitHub's own rendering of `docs/` keep working unchanged.
2. **The generator is a project-owned TypeScript program, and its scope is fixed.** It covers the feature set listed in "Proposed solution" and nothing else. Versioned documentation, localization, a blog, a theme system, a plugin API, and a content management integration are out of scope, and the proposal records them so scope growth is a deliberate decision rather than an accretion.
3. **React renders at build time; the client bundle is small and optional.** Every page is fully rendered HTML with no client JavaScript required to read it. JavaScript is loaded for search, the mobile navigation, the theme toggle, and any component islands a page declares.
4. **Existing URLs are preserved exactly.** The generator emits `<source path>.html` at the same paths Jekyll produced, so every published link and search-engine result keeps working. The landing page takes the site root, and the current `docs/index.md` content moves to a documentation overview page with a redirect from its old location.
5. **Callouts use GitHub's alert syntax.** `> [!NOTE]`, `> [!TIP]`, `> [!IMPORTANT]`, `> [!WARNING]`, and `> [!CAUTION]` render natively on GitHub and parse cleanly, so a page reads correctly in both places. This replaces the 2 uses of the kramdown `{: .note }` attribute.
6. **Section call-to-action links move to frontmatter.** The 13 `{: .btn ... }` attributes appear on section index pages. An `actions:` list in frontmatter carries them as structured data, which validates at build time and stays invisible in GitHub's rendering.
7. **Component markup uses directive syntax, reserved now and populated later.** A leaf directive (`::demo{...}`) and a container directive (`:::tabs`) mark regions the generator turns into islands. Every island directive names a fallback that renders when the component is absent, when JavaScript is unavailable, or when the reader has requested reduced motion. The registry ships empty in this proposal.
8. **Navigation is derived from the directory tree.** A directory is a section, its `index.md` is the section page, and `nav_order` in frontmatter orders siblings. The `layout`, `parent`, `grand_parent`, and `has_children` keys are removed by a one-time codemod, because the tree already carries that information and title-matched parent references break silently when a title changes.
9. **Syntax highlighting runs at build time.** Shiki produces highlighted markup during the build for the languages the corpus uses plus Go and TypeScript. No highlighter ships to the browser.
10. **Search is a prebuilt index served as a static file.** The generator writes a serialized MiniSearch index; the client fetches it on first interaction with the search field.
11. **Ruby is removed from the repository.** `docs/Gemfile`, `docs/Gemfile.lock`, `docs/_config.yml`, and the Jekyll entries in `docs/.gitignore` are deleted at cutover. Local preview becomes an npm script.

## Proposed solution

### Repository layout

The generator and the site application live in a new top-level `site/` directory as one npm package. `docs/` keeps only markdown and assets. The existing `web/` directory is the Go-embedded web interface and is unrelated.

```
site/
  package.json
  tsconfig.json
  vite.config.ts
  src/
    build/
      main.ts              # CLI entry: build, dev, check
      content/
        frontmatter.ts     # parse and validate frontmatter
        pipeline.ts        # unified/remark/rehype pipeline
        alerts.ts          # > [!NOTE] blockquotes to Callout nodes
        directives.ts      # ::demo and :::tabs to island nodes
        highlight.ts       # Shiki, build time
        links.ts           # internal link resolution and validation
        headings.ts        # slugs, anchors, on-page table of contents
      nav.ts               # directory tree to navigation model
      search.ts            # index construction
      render.ts            # React server rendering to HTML
      assets.ts            # copy docs/assets, hash static files
      check.ts             # validation gate
    components/
      layout/              # Shell, Sidebar, TableOfContents, Header, Footer
      content/             # Callout, CodeBlock, Figure, Tabs, ActionLinks
      islands/registry.ts  # component id to lazy import; empty at first
    pages/
      Landing.tsx
      Doc.tsx
      NotFound.tsx
    content/landing.ts     # landing page copy as data
    client/entry.ts        # island hydration, search, navigation
    styles/                # tokens.css and component styles
  test/
    fixtures/              # small markdown corpus
    *.test.ts
  dist/                    # build output, gitignored
```

### Content pipeline

The build runs in two stages. The first stage is pure Node with no React involved. It reads each markdown file and produces a page model:

```ts
type PageModel = {
  route: string;            // "/getting-started/quickstart.html"
  sourcePath: string;       // "docs/getting-started/quickstart.md"
  title: string;
  description: string;
  navOrder: number;
  sectionRoute: string | null;
  headings: Array<{ depth: number; id: string; text: string }>;
  actions: Array<{ label: string; href: string; variant: "primary" | "outline" }>;
  body: HastRoot;           // hast, with element nodes for callouts and islands
  islands: Array<{ id: string; component: string; props: unknown }>;
  editUrl: string;
  updatedAt: string;        // last commit date for the source file
};
```

The markdown transform is a `unified` pipeline: `remark-parse`, `remark-gfm`, `remark-directive`, the project's alert and directive transforms, `remark-rehype`, `rehype-slug`, `rehype-autolink-headings`, then the link resolver and the Shiki highlighter over the resulting tree. The output is a hast tree, which is JSON-serializable, so the page model can be cached, inspected in tests, and reused by the search indexer without re-parsing.

The second stage renders each page model with React. `hast-util-to-jsx-runtime` maps hast nodes to React elements with a component table, so `<pre>` becomes the project's `CodeBlock`, a callout node becomes `Callout`, and an island node becomes a hydration placeholder. Rendering uses `renderToStaticMarkup` for pages with no islands and `renderToString` for pages that have them. Vite builds the client bundle with one chunk per island component, so a page loads only the components it declares.

Direct dependencies are held to a short list: `react`, `react-dom`, `unified`, `remark-parse`, `remark-gfm`, `remark-directive`, `remark-rehype`, `rehype-slug`, `rehype-autolink-headings`, `hast-util-to-jsx-runtime`, `shiki`, `minisearch`, `yaml`, and `vite`. Each is a well-maintained package with a narrow purpose.

### Frontmatter

The generator accepts and validates these keys. Any other key is a build error, so a typo fails the build rather than being ignored.

| Key | Required | Purpose |
| --- | --- | --- |
| `title` | yes | Page title, navigation label, and `<title>` element |
| `description` | yes | Meta description, search result summary, and section listing summary |
| `nav_order` | no | Order among siblings. Pages without it sort after ordered pages, alphabetically by title |
| `nav_title` | no | Navigation label when it should differ from the page title |
| `permalink` | no | Explicit route, used by the overview page |
| `actions` | no | Section call-to-action links, first entry rendered as primary |
| `hidden` | no | Excludes the page from navigation and search while still publishing it |

`layout`, `parent`, `grand_parent`, and `has_children` are removed by a codemod (`site/scripts/codemod-frontmatter.ts`), which runs once and is then deleted.

### Navigation and URLs

Navigation is built from the directory tree. `docs/deployment/` is a section whose page is `docs/deployment/index.md`; `docs/deployment/oidc/` is a subsection. Sibling order comes from `nav_order`. The current tree produces the same navigation the theme produces today.

Route mapping preserves the published URLs:

| Source | Route |
| --- | --- |
| `docs/getting-started/quickstart.md` | `/getting-started/quickstart.html` |
| `docs/deployment/index.md` | `/deployment/index.html`, also served at `/deployment/` |
| `docs/index.md` (moved to `docs/overview.md`) | `/overview.html`, with `/index.html` redirecting readers who land on the old home |
| new landing page | `/` (`/index.html`) |

The link resolver rewrites internal markdown links to routes. It accepts the extensionless relative form the corpus uses today, the explicit `.md` form, and directory links ending in `/`. An unresolvable link, a link to a missing anchor, or a link to a page excluded from the build fails `site check`.

Inbound links to `https://lennylabs.github.io/podium/` continue to resolve, and they land on the landing page instead of the current home page. The landing page links into the documentation from its hero and its footer, so no redirect is required. Every deeper route is byte-identical to the route Jekyll publishes today.

### Callouts

A GitHub alert blockquote becomes a `Callout`:

```markdown
> [!NOTE]
> Podium is at 0.1.x, an early release. See [Implementation status](../about/status).
```

The transform reads the first paragraph of a blockquote, matches the `[!TYPE]` marker, strips it, and emits a callout node with the type. Unmarked blockquotes stay blockquotes. This renders correctly on GitHub, in any markdown editor, and in the generated site.

### Section call-to-action links

```yaml
---
title: Home
description: ...
actions:
  - label: Quickstart
    href: getting-started/quickstart
  - label: Concepts
    href: getting-started/concepts
---
```

The first entry renders as the primary action and the rest as outlined actions. `href` goes through the same link resolver as body links, so a broken action link fails the build.

### Code blocks

Shiki highlights each fenced block at build time with a light theme and a dark theme, emitting CSS-variable-based markup so the theme switch is a CSS change with no re-highlighting. The `CodeBlock` component adds a language label, a copy button, and optional line highlighting through fence metadata (```` ```bash {2-3} ````). Blocks tagged `text` or left untagged render without highlighting.

The highlighter loads only the languages the corpus uses plus Go and TypeScript. An unknown language tag fails the build with the file and line, which prevents a silent fall back to plain text.

### Search

The generator walks each page model, extracts headings and prose text, and builds a MiniSearch index keyed by page and heading. The serialized index is written to `dist/search-index.json` and fetched on the reader's first interaction with the search field. At roughly 63,000 words the index is a few hundred kilobytes before compression, which is acceptable for a lazy fetch. If it grows past a threshold the index splits per top-level section and the client fetches the sections it needs; the threshold check is part of `site check`.

### The landing page

The landing page is a hand-authored React page. Its copy lives in `site/src/content/landing.ts` as data so it is reviewable without reading JSX, and the documentation style rules in `.claude/rules/doc-style.md` apply to that copy in full.

The visual design derives from the palette the project's diagrams already use, so the landing page, the documentation pages, and the 16 embedded SVG diagrams read as one design:

| Role | Value |
| --- | --- |
| Page background | `#ffffff` |
| Primary text | `#1f2933` |
| Secondary text | `#54616e` |
| Cream surface | `#fffaf0` |
| Mustard accent | `#ffe9c7` |
| Sage accent | `#d6e9d2` |
| Coral accent | `#c84a1d` |
| Muted foot text | `#8a7755` |

Typography is the Helvetica stack used in the diagrams, with a monospace stack for code. Composition is flat and geometric with straight rules and no gradients or drop shadows, matching `.claude/rules/doc-diagram-style.md`.

Page composition:

1. A hero with the one-sentence statement of what Podium is, the install command with a copy button, and two actions (Quickstart, Concepts).
2. A short statement of what the catalog holds and what the tooling does with it, drawn from `docs/index.md`.
3. The two deployment modes (filesystem catalog and registry server) as two cards, each linking to its documentation.
4. A worked example panel that steps through authoring an artifact, running `podium sync`, and using the result in a harness. The panel is the first candidate for an island in the follow-on work; it ships as a static tabbed code panel.
5. The capability list from `docs/index.md`, each item linking to the page that documents it.
6. The current release status, using the same callout treatment as the documentation.
7. A footer with the license, the repository, and the documentation entry points.

### Component islands and the follow-on work

An island is a region of a page rendered by a React component and hydrated in the browser. The mechanism is specified now so the follow-on work adds components without changing the pipeline.

A leaf directive names a component and its props:

```markdown
::demo{component="sync-playground" fallback="../assets/diagrams/sync-watch.svg"}
```

A container directive wraps markdown content the component arranges:

```markdown
:::tabs
::tab{label="Claude Code"}
...markdown...
::tab{label="Cursor"}
...markdown...
:::
```

Rules that make this safe for the rest of the repository:

- **Every island names a fallback.** The fallback is a diagram path, a code block, or the container's own markdown content. It renders in the static HTML, so a reader on GitHub, a reader without JavaScript, and a crawler all see the content. Hydration replaces it.
- **Runnable commands stay in markdown.** An island never removes the commands a page documents from the markdown source, because `tools/doccov` classifies pages by their fenced blocks and the end-to-end suite executes them. An interactive demonstration accompanies the commands.
- **`prefers-reduced-motion: reduce` suppresses hydration of animated components** and leaves the static fallback in place.
- **An unknown component id fails the build.** The registry in `site/src/components/islands/registry.ts` maps ids to lazy imports, and `site check` verifies every directive in the corpus resolves.
- **Animated diagram variants sit beside the static SVG.** `::diagram{name="sync-watch"}` renders `site/src/components/diagrams/sync-watch.tsx` when it exists and `docs/assets/diagrams/sync-watch.svg` when it does not. The static SVG stays checked in, keeps its alt text, and keeps its ASCII fallback, so `.claude/rules/doc-diagram-style.md` continues to apply.

The registry is empty in this proposal. `remark-directive` is in the pipeline, the transforms exist, the client hydration path exists, and the tests cover them with fixture components.

### Accessibility and theming

The site supports a light theme and a dark theme with a toggle that persists in `localStorage` and defaults to the system preference. Diagrams are white-background SVG files, so in the dark theme each diagram renders on a white card with padding rather than being inverted. Dark variants of the diagrams are a separate piece of work and are not required here.

Baseline requirements the build checks where it can and the review checks otherwise: a skip-to-content link, visible focus states, keyboard-operable navigation and search, text contrast at WCAG AA in both themes, alt text on every image, and heading levels that descend without gaps.

### Build, preview, and CI

Commands:

| Command | Behavior |
| --- | --- |
| `npm run build` (in `site/`) | Full build to `site/dist/` |
| `npm run dev` | Watches `docs/` and `site/src/`, serves with hot reload |
| `npm run check` | Validation gate: frontmatter, links, anchors, directives, duplicate routes, orphan pages, missing alt text, search index size |
| `npm test` | Vitest unit and snapshot tests |

Makefile targets `docs-build`, `docs-dev`, and `docs-check` wrap these so the repository keeps one entry point.

`.github/workflows/docs.yml` changes its build job from `actions/jekyll-build-pages` to a Node build (`actions/setup-node`, `npm ci`, `npm run build` in `site/`) and uploads `site/dist/`. The trigger stays a `v*` tag push plus `workflow_dispatch`, and the deploy job is unchanged.

A new job in the pull-request test workflow runs `npm run check` and `npm run build` when a pull request touches `docs/`, `site/`, or `README.md`. This catches broken links before a release rather than after, which is the failure mode described in "The gap".

### Tests

The generator is held to the same bar as the rest of the repository (`.claude/rules/test-coverage.md`: at least 85% line coverage on new code, tested at the highest level the behavior reaches). Vitest with V8 coverage reports it.

- **Unit**: frontmatter parsing and validation errors, navigation ordering from a fixture tree, link resolution across the three link forms, anchor validation, alert transform, directive transform including the unknown-component error, action-link resolution, heading slug collisions, and search index construction.
- **Integration**: a fixture corpus under `site/test/fixtures/` builds end to end and asserts route mapping, emitted files, and page content.
- **Regression on the real corpus**: a test builds the actual `docs/` tree and asserts that every route Jekyll published still exists in the output. The route list is a checked-in fixture generated once at cutover, so a later refactor that changes a URL fails the build.
- **Rendering**: snapshot tests for `Callout`, `CodeBlock`, `Tabs`, `ActionLinks`, and the documentation page template.
- **Islands**: a fixture component registered in a test registry hydrates in a jsdom environment, and the fallback renders when hydration is skipped.

## Migration plan

Each phase is a pull request. The Jekyll site keeps serving until phase 4.

**Phase 1: generator and content pipeline.** Add `site/` with the build stage, the page model, the navigation model, the link resolver, and the documentation page template. Output every page with URL parity. Add unit and integration tests. Add the build to the pull-request workflow without deploying. The site is buildable and reviewable locally; nothing published changes.

**Phase 2: presentation.** Landing page, layout components, code blocks with Shiki, callouts, action links, search, dark theme, and accessibility work. Migrate the 2 `{: .note }` attributes to GitHub alerts and the 13 `{: .btn }` attributes to frontmatter `actions:`. Run the frontmatter codemod.

**Phase 3: validation gate.** `site check` with the full rule set, the checked-in route fixture, and the pull-request job that runs on documentation changes. Fix the two broken `README.md` links the check reports.

**Phase 4: cutover.** Point `.github/workflows/docs.yml` at the Node build. Move `docs/index.md` to `docs/overview.md`. Delete `docs/_config.yml`, `docs/Gemfile`, `docs/Gemfile.lock`, and the Jekyll entries in `docs/.gitignore`. Update `docs/about/contributing.md` and `CONTRIBUTING.md` with the new preview commands. Verify the deployed site against the route fixture.

**Phase 5 (follow-on, separate proposal or issue): interactive content.** Populate the island registry, add animated diagram variants where a static diagram falls short, and add interactive components where they explain a concept better than prose. The pipeline does not change.

An untracked `docs/Gemfile.lock` exists in the working tree today and is removed with the rest of the Ruby files at phase 4.

## Documentation changes

- `docs/index.md` moves to `docs/overview.md`; the site root becomes the landing page.
- `docs/about/contributing.md` and `CONTRIBUTING.md` replace the Jekyll preview instructions with `make docs-dev`.
- `README.md` fixes the two trailing-slash links that 404 today.
- A new `site/README.md` documents the generator: the page model, the frontmatter keys, the callout and directive syntax, how to add an island component, and how to run the checks.
- `.claude/rules/doc-style.md` gains a short section covering the callout syntax, the `actions:` frontmatter key, and the directive syntax, so authors have one place to look.

## Risks

| Risk | Mitigation |
| --- | --- |
| A project-owned generator is a maintenance obligation | The dependency list is short, the scope boundary is written down, and the test suite covers each transform. The generator is roughly 1,500 to 2,500 lines of TypeScript, most of it thin adapters over `unified` and React |
| Search quality regresses against the theme's search | MiniSearch indexes headings and prose with the same granularity `just-the-docs` uses. Phase 2 compares result quality on a set of representative queries before cutover |
| A URL changes silently and breaks inbound links | The checked-in route fixture is asserted by a test, so any route change is an explicit fixture edit |
| Dark theme degrades the white-background diagrams | Diagrams render on a white card in the dark theme. Dark diagram variants are separate work |
| The landing page drifts toward marketing copy | `.claude/rules/doc-style.md` applies to landing copy, and the copy lives in one data file that a reviewer can read in isolation |
| Node becomes a build requirement for documentation | The repository already builds TypeScript for `sdks/podium-ts` with Node 20 or later. Ruby is removed at the same time, so the toolchain count goes down |

## Alternatives considered

**Keep Jekyll and restyle the theme.** `just-the-docs` supports color scheme overrides and custom includes. This addresses the visual concern and none of the others. It leaves Ruby in the toolchain, leaves no path to component islands other than inline script, and leaves link validation unsolved.

**Astro Starlight, Docusaurus, Nextra, or VitePress.** Each of these delivers most of this proposal's feature set without a project-owned generator, and each has an established component story (MDX for Docusaurus and Nextra, islands for Starlight). Choosing one would trade the generator's maintenance cost for the framework's upgrade cost and its conventions about content location and frontmatter. The requester asked for a project-owned generator over `docs/` markdown, and the measured coupling supports that choice: the corpus uses no theme features beyond three inline-attribute patterns, `doccov` and the end-to-end suite require markdown to stay where it is and stay plain, and the interactive work planned next wants a content model the project controls. The proposal proceeds with the custom generator, and this paragraph records what it costs.

**MDX for the documentation pages.** MDX would make components trivial to place. It also makes `docs/` files stop being plain markdown, which breaks GitHub rendering of the source tree, complicates `doccov` classification, and raises the barrier for a contributor editing a page. The directive syntax reaches the same outcome while leaving the files readable everywhere.

## Open questions

1. **Directory name.** `site/` is proposed. `docs-site/` and `www/` are alternatives. `web/` is taken by the Go-embedded interface.
2. **Dark theme in the first release.** Proposed as in scope for the site chrome and code blocks, with diagrams on a white card. Deferring it to the follow-on phase is reasonable if phase 2 runs long.
3. **Custom domain.** The site is at `lennylabs.github.io/podium`, which forces a `/podium` base path into every absolute reference. A custom domain would remove the base path handling. The generator supports both through one configuration value, so this can be decided later.
4. **Landing page at the root versus a separate marketing route.** Proposed at the root with the current home content at `/overview.html`. The alternative keeps the documentation home at the root and puts the landing page elsewhere, which weakens its purpose.
5. **Search index granularity.** Proposed as page plus heading. Section-level snippets would improve result previews at the cost of index size, which phase 2 can measure.
6. **Adversarial validation.** This proposal has not been through the repository's adversarial review passes, which the existing proposals record. It can go through them before implementation begins if the change warrants that treatment.

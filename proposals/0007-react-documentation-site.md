## Summary

Podium's documentation is published by GitHub Pages from `docs/` using Jekyll with the remote `just-the-docs` theme (`docs/_config.yml`, `.github/workflows/docs.yml`). The theme sets the visual design, the navigation, and the search. There is no landing page: `docs/index.md` serves both as the project's front door and as the first documentation page, rendered in the same sidebar layout as every other page. Extending the site means extending a Ruby theme, and adding an interactive element to a page means embedding raw HTML and script tags in a markdown file.

This proposal replaces the Jekyll build with a static site generated by a project-owned generator written in TypeScript, rendered by React at build time, and deployed to the same GitHub Pages target. Markdown files under `docs/` remain the single source of documentation content. The generator reads those files, produces a serializable page model per page, and renders each model to static HTML through React server rendering. The output is HTML and CSS with a small client bundle for search, navigation, and selectively hydrated components. A hand-authored landing page is added at the site root. The landing page and the documentation page template both follow the design handoff in `proposals/0007-design/`, which supplies the tokens, the screen compositions, and the interaction states for a light and a dark theme.

The generator covers a bounded feature set: frontmatter parsing, navigation derived from the directory tree, internal link resolution, build-time syntax highlighting, callouts, section call-to-action links, a client-side search index, and a component island mechanism. It is not a general-purpose site generator. Versioned documentation, localization, a blog, a theme system, and a plugin API are out of scope and are recorded as such.

The proposal is designed around the follow-on work the requester described: animated explanations where a static diagram falls short, and interactive components that demonstrate a concept. Those need a content model that can carry a component reference through the pipeline and a client runtime that can hydrate one region of a page without shipping the rest of the page as JavaScript. The island mechanism and the directive syntax are specified here and land with structural registry entries and no interactive component, so the follow-on work adds components rather than restructuring the pipeline.

## Current state and the gap

### What the site is today

`.github/workflows/docs.yml` builds `docs/` with `actions/jekyll-build-pages@v1` and deploys the result to GitHub Pages. The workflow runs on a `v*` tag push and on `workflow_dispatch`, so documentation is republished per release rather than per commit. `docs/_config.yml` pulls `just-the-docs` through `jekyll-remote-theme` and configures the theme's search, navigation, edit links, and footer. `docs/Gemfile` pins the Ruby dependencies for local preview through `bundle exec jekyll serve`.

Jekyll writes each page to its source path with an `.html` extension: `docs/getting-started/quickstart.md` becomes `/getting-started/quickstart.html`. The site is served from `https://lennylabs.github.io/podium/`.

### What the markdown uses

The content is portable. A scan of the 53 markdown files under `docs/` (52 carry frontmatter; `docs/rfc/README.md` does not) shows a small theme-specific surface:

| Feature | Usage | Notes |
| --- | --- | --- |
| Frontmatter keys | `title`, `nav_order`, `layout`, `description` on all 52 pages; `parent` on 44; `has_children` on 8; `grand_parent` on 5; `permalink` on 1 | `layout`, `parent`, `grand_parent`, and `has_children` restate what the directory tree already encodes |
| Kramdown inline attributes | `{: .btn .btn-outline }` (7), `{: .btn .btn-purple }` (6), `{: .note }` (2) | Theme-coupled markup. Every `.btn` use and one `.note` use are in `docs/index.md` |
| Raw HTML | 5 `<div ... markdown="1">` wrappers and one `<style>` block, all in `docs/index.md` | `markdown="1"` is a kramdown extension with no CommonMark equivalent, and the pipeline drops raw HTML. The card grid and the `<style>` block become an `actions:` list when the page moves to `docs/overview.md` |
| Mermaid | none | Diagrams are checked-in SVG files |
| Fenced code languages | `yaml` (73), `bash` (65), `json` (21), `markdown` (13), `python` (10), `powershell` (1), `javascript` (1) | A fixed, small language set |
| Images | 16 SVG diagrams under `docs/assets/diagrams/`, each with descriptive alt text and an adjacent HTML-comment ASCII fallback | Governed by `.claude/rules/doc-diagram-style.md` |
| Internal links | Extensionless relative paths (`../consuming/publishing`, `oidc/`), 5 internal links written with an explicit `.md` suffix (all in `docs/deployment/oidc/index.md`), 5 absolute `https://github.com/lennylabs/podium/blob/main/...` links, and 1 link that leaves the docs tree (`docs/rfc/README.md` to `../../GOVERNANCE.md`) | The resolver rewrites the relative forms and leaves absolute URLs as written. The `docs/rfc/README.md` link is copied verbatim with the file |

Total prose is roughly 63,000 words. Nothing in the corpus depends on Liquid templating, Jekyll collections, includes, or data files.

### Coupling to the repository's test and coverage tooling

Two mechanisms read `docs/` directly and constrain any change:

- `tools/doccov` scans every markdown file under `docs/` plus `README.md`, classifies pages that contain a runnable command example, and requires each such page to map to a feature-named end-to-end test by `D-<slug>` or to a written waiver (`tools/doccov/manifest.yaml`).
- The end-to-end suite under `test/e2e/` carries feature-named files whose header comments name the documentation page they cover, and those tests execute the commands the pages document.

Both read markdown from `docs/`. Neither reads generated HTML. Keeping markdown as the source of content preserves both, and the generator must not require a markdown syntax that changes how `doccov` classifies a page. The move of `docs/index.md` requires one tooling edit: its entry in `tools/doccov/manifest.yaml` is retargeted to `docs/overview.md` in the same pull request, because `doccov check` fails both on a manifest entry naming a missing page and on a runnable page missing from the manifest.

### The gap

1. **No landing page.** The project's front door is a documentation page in a documentation sidebar. A visitor evaluating Podium reads the same layout as a reader looking up a frontmatter field.
2. **Presentation is delegated to an external theme.** Typography, color, spacing, code presentation, and navigation come from `just-the-docs`, so the site carries a stock theme's identity. The design handoff in `proposals/0007-design/` supplies an identity of the project's own, and the current toolchain has no place to put it.
3. **No path to interactive explanation.** Adding an animation or an interactive component to a Jekyll page means inline HTML and script tags inside a markdown file. That markdown is also read by `doccov`, rendered on GitHub, and edited by contributors, so inline script is the wrong carrier.
4. **Two toolchains.** The repository builds Go and TypeScript. Documentation adds Ruby and Bundler for local preview only.
5. **No link validation.** Nothing checks that internal links resolve. Two links in `README.md` are live 404s today: `https://lennylabs.github.io/podium/consuming/publishing/` and `https://lennylabs.github.io/podium/consuming/configure-your-harness/` both return 404 because the trailing-slash form does not match Jekyll's `<page>.html` output, while the extensionless forms return 200. A build-time link check catches this class of error.

## Decisions

These were settled during design and form the basis of the specification below.

1. **Markdown under `docs/` stays the source of content.** The generator reads it and never writes to it. `doccov`, the end-to-end suite, and GitHub's own rendering of `docs/` keep working unchanged.
2. **The generator is a project-owned TypeScript program, and its scope is fixed.** It covers the feature set listed in "Proposed solution" and nothing else. Versioned documentation, localization, a blog, a theme system, a plugin API, and a content management integration are out of scope, and the proposal records them so scope growth is a deliberate decision rather than an accretion.
3. **React renders at build time; the client bundle is small and optional.** Every page is fully rendered HTML with no client JavaScript required to read it. JavaScript is loaded for the behaviors the design specifies, which are search and its `⌘K` overlay, the theme toggle, the mobile navigation, the collapsible sidebar groups, the on-this-page heading highlight, the copy controls on the install field and every code block, the install-channel tabs, and any component islands a page declares. The tabs and the theme choice persist across pages.
4. **Existing URLs are preserved exactly.** The generator emits `<source path>.html` at the same paths Jekyll produced, so every published link and search-engine result keeps working. The landing page takes the site root, and the current `docs/index.md` content moves to a documentation overview page at `/overview.html`. The site root serves the landing page, and the build emits no redirect.
5. **Callouts use GitHub's alert syntax.** `> [!NOTE]`, `> [!TIP]`, `> [!IMPORTANT]`, `> [!WARNING]`, and `> [!CAUTION]` render natively on GitHub and parse cleanly, so a page reads correctly in both places. This replaces the 2 uses of the kramdown `{: .note }` attribute.
6. **Section call-to-action links move to frontmatter.** Every `{: .btn ... }` attribute in the corpus is in `docs/index.md`, at five positions: the hero row, the deployment-modes list, the hello-world example, one inside each card of the card grid, and the quick-links list. The hero row becomes the landing page hero. The remaining links become one `actions:` list in the frontmatter of `docs/overview.md`, which validates at build time and stays invisible in GitHub's rendering.
7. **Component markup uses directive syntax, reserved now and populated later.** A leaf directive (`::sync-playground{...}`) and a container directive (`::::tabs`) mark regions the generator turns into islands, and the directive name is the registry key. Each registry entry declares its props and its permitted children, so an unknown directive, an unknown attribute, a missing required prop, a malformed container, and an inline text directive all fail the build. Every island names a fallback that renders when the component is absent, when JavaScript is unavailable, or when the reader has requested reduced motion. The registry ships with the structural entries and no interactive component.
8. **Navigation is derived from the directory tree.** A directory is a section, its `index.md` is the section page, and `nav_order` in frontmatter orders siblings. The `layout`, `parent`, `grand_parent`, and `has_children` keys are removed by a one-time codemod, because the tree already carries that information and title-matched parent references break silently when a title changes.
9. **Syntax highlighting runs at build time.** Shiki produces highlighted markup during the build for the languages the corpus uses plus Go and TypeScript. No highlighter ships to the browser.
10. **Search is a prebuilt index served as a static file.** The generator writes a serialized MiniSearch index; the client fetches it on first interaction with the search field.
11. **Ruby is removed from the repository.** `docs/Gemfile`, `docs/Gemfile.lock`, `docs/_config.yml`, and the Jekyll entries in `docs/.gitignore` are deleted at cutover. Local preview becomes an npm script.

## Proposed solution

### Repository layout

The generator and the site application live in a new top-level `site/` directory as one npm package. `docs/` keeps only markdown and assets. The existing `web/` directory is the Go-embedded web interface and is unrelated. The root `.gitignore` excludes `build/` at any depth, so phase 1 adds a `!site/src/build/` negation below that line. Without it the build stage is untracked and a CI checkout has no generator.

```
site/
  package.json
  tsconfig.json
  vite.config.ts
  src/
    build/
      main.ts              # CLI entry: build, dev, check
      content/
        frontmatter.ts     # parse and validate frontmatter
        pipeline.ts        # unified/remark/rehype pipeline
        alerts.ts          # > [!NOTE] blockquotes to Callout nodes
        directives.ts      # block directives to island nodes; rejects text directives
        highlight.ts       # Shiki, build time
        links.ts           # internal link resolution and validation
        headings.ts        # slugs, anchors, on-page table of contents
      nav.ts               # directory tree to navigation model
      search.ts            # index construction
      render.ts            # React server rendering to HTML
      assets.ts            # copy docs/assets, hash static files
      check.ts             # validation gate
    components/
      layout/              # Shell, Sidebar, TableOfContents, Header, Footer
      content/             # Callout, CodeBlock, Figure, Tabs, ActionLinks
      islands/
        registry.ts        # directive name to island definition; structural entries only
        props.ts           # prop specs, coercion, container rules, and validation errors
    pages/
      Landing.tsx
      Doc.tsx
      NotFound.tsx
    content/landing.ts     # landing page copy as data
    client/entry.ts        # island mounting, search, navigation, theme, tabs, scroll spy
    styles/                # tokens.css and component styles
  test/
    fixtures/              # small markdown corpus
    *.test.ts
  dist/                    # build output, gitignored
```

### Content pipeline

The build runs in two stages. The first stage is pure Node with no React involved. It reads each markdown file and produces a page model:

```ts
type PageModel = {
  route: string;            // "/getting-started/quickstart.html"
  sourcePath: string;       // "docs/getting-started/quickstart.md"
  title: string;
  navTitle: string | null;
  description: string;
  navOrder: number;
  hidden: boolean;
  sectionRoute: string | null;
  headings: Array<{ depth: number; id: string; text: string }>;
  actions: Array<{ label: string; href: string; variant: "primary" | "outline" }>;
  body: HastRoot;           // hast, with element nodes for callouts and islands
  islands: Array<{ id: string; component: string; props: IslandProps }>;  // validated against the registry
  editUrl: string;
  updatedAt: string;        // last commit date for the source file
};
```

The markdown transform is a `unified` pipeline: `remark-parse`, `remark-gfm`, `remark-directive`, the project's alert and directive transforms, `remark-rehype`, `rehype-slug`, `rehype-autolink-headings`, then the link resolver and the Shiki highlighter over the resulting tree. The output is a hast tree, which is JSON-serializable, so the page model can be cached, inspected in tests, and reused by the search indexer without re-parsing.

`remark-rehype` carries no handler for directive nodes, and an unhandled directive emits nothing at all. The alert and directive transforms therefore set `data.hName` and `data.hProperties` on every node they claim. A directive that reaches `remark-rehype` unclaimed disappears from the output without an error, which is the failure the registry lookup under "Validation" prevents.

The second stage renders each page model with React. `hast-util-to-jsx-runtime` maps hast nodes to React elements with a component table, so `<pre>` becomes the project's `CodeBlock`, a callout node becomes `Callout`, and an island node becomes a hydration placeholder. Rendering uses `renderToStaticMarkup` for pages with no islands, whose output carries no hydration metadata and is never hydrated, and `renderToString` for pages that have them. Vite builds the client bundle with one chunk per island component, so a page loads only the components it declares.

Direct dependencies are held to a short list: `react`, `react-dom`, `unified`, `remark-parse`, `remark-gfm`, `remark-directive`, `remark-rehype`, `rehype-slug`, `rehype-autolink-headings`, `hast-util-to-jsx-runtime`, `shiki`, `minisearch`, `yaml`, and `vite`. Each is a well-maintained package with a narrow purpose.

### Frontmatter

The generator accepts and validates these keys. Any other key is a build error, so a typo fails the build rather than being ignored.

| Key | Required | Purpose |
| --- | --- | --- |
| `title` | yes | Page title, navigation label, and `<title>` element |
| `description` | yes | Meta description, search result summary, and section listing summary |
| `nav_order` | no | Order among siblings. Pages without it sort after ordered pages, alphabetically by title |
| `nav_title` | no | Navigation label when it should differ from the page title |
| `permalink` | no | Explicit route when a page's route must differ from its source path. The corpus's one use is `permalink: /` on `docs/index.md`, which the move to `docs/overview.md` drops |
| `actions` | no | Section call-to-action links, first entry rendered as primary |
| `hidden` | no | Excludes the page from navigation and search while still publishing it |

`layout`, `parent`, `grand_parent`, and `has_children` are removed by a codemod (`site/scripts/codemod-frontmatter.ts`), which runs once at cutover and is then deleted. Until the codemod runs, the generator accepts these four keys and ignores them, because Jekyll needs them to render the published site. After the codemod runs, the four keys fall under the undeclared-key rule and fail the build.

A markdown file with no frontmatter is not a page. `docs/rfc/README.md` is the corpus's only such file. The generator copies it to its source path unchanged, which reproduces the route Jekyll publishes for it today, and a copied file gets no navigation entry, no search entry, and no link rewriting, so its link to `../../GOVERNANCE.md` is left as written. `docs/rfc/` produces no navigation section.

### Navigation and URLs

Navigation is built from the directory tree. `docs/deployment/` is a section whose page is `docs/deployment/index.md`; `docs/deployment/oidc/` is a subsection. Sibling order comes from `nav_order`, and siblings sharing a value sort alphabetically by title, which is what the theme does with the two `nav_order: 7` pages under `docs/deployment/`. The current tree produces the same navigation the theme produces today.

Route mapping preserves the published URLs:

| Source | Route |
| --- | --- |
| `docs/getting-started/quickstart.md` | `/getting-started/quickstart.html` |
| `docs/deployment/index.md` | `/deployment/index.html`, also served at `/deployment/` |
| `docs/index.md` (moved to `docs/overview.md`) | `/overview.html`. The move drops the file's `permalink: /`, which the landing page occupies |
| new landing page | `/` (`/index.html`) |

The link resolver rewrites internal markdown links to routes. It accepts the extensionless relative form the corpus uses today, the explicit `.md` form, and directory links ending in `/`. An unresolvable link, a link to a missing anchor, or a link to a page excluded from the build fails `site check`.

Inbound links to `https://lennylabs.github.io/podium/` continue to resolve, and they land on the landing page instead of the current home page. The landing page links into the documentation from its hero and its footer, so no redirect is required. Every deeper route is byte-identical to the route Jekyll publishes today.

Each page's head carries what `jekyll-seo-tag` emits today: a `<title>`, a meta description, a canonical link, and the `og:title`, `og:description`, `og:url`, and `og:type` properties. The canonical and `og:url` values are built from the base path in open question 3.

### Callouts

A GitHub alert blockquote becomes a `Callout`:

```markdown
> [!NOTE]
> Podium is at 0.1.x, an early release. See [Implementation status](../about/status).
```

The transform reads the first paragraph of a blockquote, matches the `[!TYPE]` marker, strips it, and emits a callout node with the type. Unmarked blockquotes stay blockquotes. This renders correctly on GitHub, in any markdown editor, and in the generated site.

### Section call-to-action links

```yaml
---
title: Home
description: ...
actions:
  - label: Quickstart
    href: getting-started/quickstart
  - label: Concepts
    href: getting-started/concepts
---
```

The first entry renders as the primary action and the rest as outlined actions. `href` goes through the same link resolver as body links, so a broken action link fails the build. An `href` carrying a scheme, such as `https://github.com/lennylabs/podium`, is external and is emitted as written.

### Code blocks

Shiki highlights each fenced block at build time with a light theme and a dark theme, emitting CSS-variable-based markup so the theme switch is a CSS change with no re-highlighting. The `CodeBlock` component adds a language label, a copy button, and optional line highlighting through fence metadata (```` ```bash {2-3} ````). Blocks tagged `text` or left untagged render without highlighting.

The highlighter loads only the languages the corpus uses plus Go and TypeScript. An unknown language tag fails the build with the file and line, which prevents a silent fall back to plain text.

### Search

The generator walks each page model, extracts headings and prose text, and builds a MiniSearch index keyed by page and heading. The serialized index is written to `dist/search-index.json` and fetched on the reader's first interaction with the search field. At roughly 63,000 words the index is a few hundred kilobytes before compression, which is acceptable for a lazy fetch. If it grows past a threshold the index splits per top-level section and the client fetches the sections it needs; the threshold check is part of `site check`.

### The landing page

The landing page is a hand-authored React page. Its copy lives in `site/src/content/landing.ts` as data so it is reviewable without reading JSX, and the documentation style rules in `.claude/rules/doc-style.md` apply to that copy in full.

Its composition and its visual design come from the handoff described in the next section.

### Component islands and the follow-on work

An island is a region of a page rendered by a React component and hydrated in the browser. The mechanism is specified now so the follow-on work adds components without changing the pipeline.

#### Directive forms

Directives are block-level. A leaf directive names a component and its props:

```markdown
::sync-playground{fallback="../assets/diagrams/sync-watch.svg"}
```

A container directive wraps markdown content the component arranges. Nesting follows the fence convention of the directive syntax, where the outer container carries more colons than the inner one:

```markdown
::::tabs
:::tab{label="Claude Code"}
...markdown...
:::
:::tab{label="Cursor"}
...markdown...
:::
::::
```

The directive name is the registry key. `::sync-playground{...}` resolves to the `sync-playground` entry and `::::tabs` resolves to the `tabs` entry, so one lookup produces both the component and its props schema. A `component` attribute would add a second indirection and a second failure mode, so the mechanism does not use one.

Each tab is a container in its own right, which is what makes the grouping unambiguous. A leaf `::tab{...}` would parse as a sibling of the markdown that follows it, leaving the transform to gather a run of siblings and to guess where each tab ends.

Text directives (`:name[content]{...}`) are outside the mechanism. A component occupies a block, and the mechanism has no inline form. `remark-directive` parses text directives regardless, so the transform rejects every `textDirective` node with a build error that names the two block forms.

#### The registry

Each entry declares its props, its permitted children, and the source of its fallback:

```ts
// site/src/components/islands/registry.ts
type PropSpec =
  | { kind: "string"; required?: boolean; oneOf?: readonly string[]; default?: string }
  | { kind: "number"; required?: boolean; default?: number }
  | { kind: "boolean"; required?: boolean; default?: boolean }
  | { kind: "route"; required?: boolean }    // resolved by the link resolver
  | { kind: "asset"; required?: boolean };   // names a file under docs/assets/

type ChildrenSpec =
  | { kind: "none" }                                    // leaf directive
  | { kind: "markdown" }                                // container the component arranges
  | { kind: "directives"; name: string; min: number };  // container of child containers

type FallbackSpec =
  | { from: "prop"; name: string }   // the named prop resolves to the static fallback
  | { from: "children" };            // the container's own markdown is the fallback

type IslandProps = Record<string, string | number | boolean>;

type IslandDefinition<P extends IslandProps = IslandProps> = {
  props: { [K in keyof P]: PropSpec };
  children: ChildrenSpec;
  fallback: FallbackSpec;
  load: () => Promise<{ default: ComponentType<P> }>;
};
```

Entries are constructed through a `defineIsland<P>()` helper that holds `P` at the definition site, and the registry stores the results under one key per directive name.

`tabs` declares no props with `children: { kind: "directives", name: "tab", min: 2 }` and `fallback: { from: "children" }`. `tab` declares a required `label` string with `children: { kind: "markdown" }`. `diagram` declares a required `name` with `kind: "asset"` and `fallback: { from: "prop", name: "name" }`. The validator resolves the value as the stem of `docs/assets/diagrams/<name>.svg` through the resolver that checks body links, so the checked-in SVG becomes the fallback for an animated variant and a missing file fails the build. The specs are a hand-written descriptor read by one validator in `site/src/components/islands/props.ts`, so no schema library joins the dependency list in "Content pipeline". A container island's children never travel as props. The renderer emits the children's server-rendered HTML inside the island placeholder, and the client component hydrates in place over that markup, so `IslandProps` stays a record of scalars and the tab content is served to a reader with no JavaScript.

#### Validation

Directive attributes parse as strings. The validator coerces each value to its declared kind, applies declared defaults, and stores the coerced values in `PageModel.islands`. A build and `site check` both fail on:

- a directive name with no registry entry,
- an attribute the entry does not declare,
- a missing required prop,
- a value that fails coercion or falls outside `oneOf`,
- a `route` or `asset` prop that does not resolve, checked by the resolver that already checks body links,
- children that violate the entry's `ChildrenSpec`, which covers a `tab` outside a `tabs`, a `tabs` holding prose directly, and a `tabs` below its minimum count, and
- a text directive anywhere in the corpus.

Each error names the source file, the line, and the column, which the directive node's position carries.

The validator also checks the registry itself before it reads any markdown. An entry whose `FallbackSpec` names a prop it does not declare, or names a prop that is optional, fails at that point, which keeps the fallback rule below from depending on review alone.

The registry types the component as well as the markdown. `load` returns a component typed on the props the entry declares, so a component that reads an undeclared prop fails `tsc` instead of reading `undefined` in the browser.

#### Rules that make this safe for the rest of the repository

- **Every island names a fallback.** The entry's `FallbackSpec` records where it comes from: a named required prop holding a diagram path or a code block for a leaf island, and the container's own markdown content for a container island. The fallback renders in the generated HTML, so a reader without JavaScript, a crawler, and a reader who has requested reduced motion all see the content. The two island kinds mount differently, because React requires a hydrated tree to produce the output the server already wrote. A leaf island mounts with `createRoot`, which discards the fallback and renders over it, since a component whose output differs from the fallback cannot hydrate onto it. A container island mounts with `hydrateRoot` over the children React rendered into the placeholder, whose markup already matches. GitHub renders the markdown source, where a container directive still shows its children and a leaf directive line shows as literal text.
- **Runnable commands stay in markdown.** An island never removes the commands a page documents from the markdown source, because `tools/doccov` classifies pages by their fenced blocks and the end-to-end suite executes them. An interactive demonstration accompanies the commands.
- **`prefers-reduced-motion: reduce` suppresses hydration of animated components** and leaves the static fallback in place.
- **An unresolved directive fails the build.** `site check` runs the registry lookup and the prop validation over every directive in the corpus, so a typo in a directive name or an attribute stops the build with a location.
- **Animated diagram variants sit beside the static SVG.** `::diagram{name="sync-watch"}` renders `site/src/components/diagrams/sync-watch.tsx` when it exists and `docs/assets/diagrams/sync-watch.svg` when it does not. The `diagram` entry declares `name` as a required `asset` prop, and the static SVG stays checked in, keeps its alt text, and keeps its ASCII fallback, so `.claude/rules/doc-diagram-style.md` continues to apply.

The registry ships with the structural entries `tabs`, `tab`, and `diagram`, and with no interactive component. `remark-directive` is in the pipeline, the transforms and the prop validator exist, the client hydration path exists, and the tests cover them with fixture entries in a test registry. The follow-on work adds interactive entries without touching the pipeline.

### Accessibility and theming

The site ships a light theme and a dark theme with a toggle that persists in `localStorage` and defaults to the system preference. The toggle names the theme it switches to. Diagrams are white-background SVG files, so each one renders on a white card with padding in both themes rather than being inverted. Dark variants of the diagrams are separate work and are not required here.

Baseline requirements the build checks where it can and the review checks otherwise: a skip-to-content link, keyboard-operable navigation and search, text contrast at WCAG AA in both themes, alt text on every image, and heading levels that descend without gaps. The design settles two of these concretely. Every interactive element takes a 2px accent focus ring at a 2px offset, which holds on both themes. The terminal cursor blink is the only ambient animation, and `prefers-reduced-motion: reduce` freezes it, which is the signal that also suppresses hydration of an animated island. The handoff records its own measured ratios, and the accent never carries the active-navigation state alone, because the weight change and the rail carry it too.

### Build, preview, and CI

Commands:

| Command | Behavior |
| --- | --- |
| `npm run build` (in `site/`) | Full build to `site/dist/` |
| `npm run dev` | Watches `docs/` and `site/src/`, serves with hot reload |
| `npm run check` | Validation gate: frontmatter, links, anchors, directive names, directive props and containers, duplicate routes, orphan pages, missing alt text, and search index size. The link rule also reads `README.md` and resolves every absolute `https://lennylabs.github.io/podium/...` URL against the emitted route set, so a site-origin URL matching no route fails |
| `npm test` | Vitest unit and snapshot tests |

Makefile targets `docs-build`, `docs-dev`, and `docs-check` wrap these so the repository keeps one entry point.

`.github/workflows/docs.yml` changes its build job from `actions/jekyll-build-pages` to a Node build (`actions/setup-node`, `npm ci`, `npm run build` in `site/`) and uploads `site/dist/`. Its checkout step gains `fetch-depth: 0`, because `PageModel.updatedAt` reads the last commit date for each source file and a shallow clone carries no history to read. The trigger stays a `v*` tag push plus `workflow_dispatch`, and the deploy job is unchanged.

A new workflow, `.github/workflows/site.yml`, runs `npm run check` and `npm run build` on a pull request that touches `docs/`, `site/`, or `README.md`. It is a separate file because GitHub Actions filters paths at the workflow trigger, and `.github/workflows/test.yml` must keep running its Go and SDK jobs on every pull request. This catches broken links before a release rather than after, which is the failure mode described in "The gap".

### Tests

The generator is held to the same bar as the rest of the repository (`.claude/rules/test-coverage.md`: at least 85% line coverage on new code, tested at the highest level the behavior reaches). Vitest with V8 coverage reports it.

- **Unit**: frontmatter parsing and validation errors, navigation ordering from a fixture tree, link resolution across the three link forms, anchor validation, alert transform, action-link resolution, heading slug collisions, and search index construction.
- **Directives**: the transform and the prop validator, with a case per failure mode listed in "Validation": the unknown directive name, the undeclared attribute, the missing required prop, the value that fails coercion, the value outside `oneOf`, the unresolvable `asset` prop, a `tab` outside a `tabs`, a `tabs` holding prose directly, a `tabs` below its minimum count, and a text directive. Each case asserts the reported file, line, and column.
- **Integration**: a fixture corpus under `site/test/fixtures/` builds end to end and asserts route mapping, emitted files, and page content.
- **Regression on the `docs/` corpus**: a test builds the `docs/` tree and asserts that every route Jekyll published still exists in the output. The route list is a checked-in fixture, captured in phase 1 by enumerating the output of `bundle exec jekyll build` over the pre-codemod corpus and committed in that phase, so a later refactor that changes a URL fails the build.
- **Rendering**: snapshot tests for `Callout`, `CodeBlock`, `Tabs`, `ActionLinks`, and the documentation page template.
- **Islands**: a fixture component registered in a test registry hydrates in a jsdom environment, the fallback renders when hydration is skipped, and a nested `tabs` container groups its `tab` children in source order with each tab's markdown intact.

**Phase 3: validation gate.** `site check` with the full rule set, the checked-in route fixture, and the pull-request job that runs on documentation changes. Fix the two broken `README.md` links the check reports.

## Risks

| Risk | Mitigation |
| --- | --- |
| A project-owned generator is a maintenance obligation | The dependency list is short, the scope boundary is written down, and the test suite covers each transform. The generator is roughly 1,500 to 2,500 lines of TypeScript, most of it thin adapters over `unified` and React |
| Search quality regresses against the theme's search | MiniSearch indexes headings and prose with the same granularity `just-the-docs` uses. Phase 2 compares result quality on a set of representative queries before cutover |
| A URL changes silently and breaks inbound links | The checked-in route fixture is asserted by a test, so any route change is an explicit fixture edit |
| Dark theme degrades the white-background diagrams | Diagrams render on a white card in the dark theme. Dark diagram variants are separate work |
| The landing page drifts toward marketing copy | The copy lives in one data file that a reviewer can read in isolation, and the handoff draws it from the README and the documentation rather than inventing claims. Whether `.claude/rules/doc-style.md` governs that file is open question 7, and the answer changes shipped text |
| The design and the documentation drift apart once components are edited | The handoff is checked in with the proposal, and its README names the reference file as the source of truth for any unlisted value. Phase 2 reviews the built pages against the four mockups before cutover |
| Node becomes a build requirement for documentation | The repository already builds TypeScript for `sdks/podium-ts` with Node 20 or later. Ruby is removed at the same time, so the toolchain count goes down |

## Alternatives considered

**Keep Jekyll and restyle the theme.** `just-the-docs` supports color scheme overrides and custom includes. This addresses the visual concern and none of the others. It leaves Ruby in the toolchain, leaves no path to component islands other than inline script, and leaves link validation unsolved.

**Astro Starlight, Docusaurus, Nextra, or VitePress.** Each of these provides most of this proposal's feature set without a project-owned generator, and each has an established component story (MDX for Docusaurus and Nextra, islands for Starlight). Choosing one would trade the generator's maintenance cost for the framework's upgrade cost and its conventions about content location and frontmatter. The requester asked for a project-owned generator over `docs/` markdown, and the measured coupling supports that choice: the corpus carries theme-coupled markup only in the inline-attribute patterns and the card grid in `docs/index.md`, `doccov` and the end-to-end suite require markdown to stay where it is and stay plain, and the interactive work planned next wants a content model the project controls. The proposal proceeds with the custom generator, and this paragraph records what it costs.

**MDX for the documentation pages.** MDX would make components trivial to place. It also makes `docs/` files stop being plain markdown, which breaks GitHub rendering of the source tree, complicates `doccov` classification, and raises the barrier for a contributor editing a page. The directive syntax reaches the same outcome while keeping each file parseable as plain markdown, so GitHub still renders the page and `doccov` still classifies it by its fenced blocks.

## Open questions

1. **Directory name.** `site/` is proposed. `docs-site/` and `www/` are alternatives. `web/` is taken by the Go-embedded interface.
2. **Dark theme in the first release.** Settled by the design, which specifies both themes in full for both page types. Deferring it would ship half the handoff.
3. **Custom domain.** The site is at `lennylabs.github.io/podium`, which forces a `/podium` base path into every absolute reference. A custom domain would remove the base path handling. One configuration value selects between them, so this can be decided later.
4. **Landing page at the root versus a separate marketing route.** Settled by the design, which composes the landing page as the site's entry point. The current home content moves to `/overview.html`.
5. **Search index granularity.** Proposed as page plus heading. Section-level snippets would improve result previews at the cost of index size, which phase 2 can measure.

6. **Adversarial validation.** A lightweight review has run over this document: six lenses covering internal consistency, repository-fact accuracy, third-party library claims, plan feasibility, documentation style, and a holistic gap read, with each lens's findings verified by a skeptic instructed to default to refuting. It confirmed 41 findings of 62 raised, and this document incorporates all of them. That pass is lighter than the convergence loop the other proposals record, which repeats review and fix rounds until two consecutive rounds are clean and which is built for proposals that stage spec or product-code changes. Running the full loop before implementation remains available.

7. **Whether `.claude/rules/doc-style.md` governs the landing copy.** The handoff supplies copy drawn from the README and the documentation, and it records that the copy needs maintainer sign-off before any rewrite. Some of it is shaped as sentence fragments, which the rule excludes from documentation prose. Three readings are available: the rule covers the landing page and the copy is rewritten with sign-off, the rule covers documentation pages while the landing page follows the design as delivered, or the rule gains an explicit carve-out for landing copy. The risks table assumes the second reading for now. This decision belongs to the maintainer, and it is the one open question here that changes shipped text.

8. **Where the design handoff lives.** It sits in `proposals/0007-design/` because `tmp/` is gitignored and a reference under it would not survive. It is placed with the proposal rather than under a site directory because the directory name is open question 1. Once that name is settled, the handoff moves into the site package beside the components it describes.

9. **Font delivery.** Proposed as self-hosted Space Grotesk, JetBrains Mono, and Anton, which removes the Google Fonts request the handoff's reference file makes. Loading from Google Fonts is the alternative and needs no build step.
